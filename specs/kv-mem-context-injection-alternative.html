KV:Mem代替：選択的Context注入 実験設計

現行KV:Memの実装を分解し、永続KV snapshot networkを保持せず、SAAAとContextStillが選択した 小さいContext Packをrequestごとに注入する方式で置き換えられるかを評価するための設計です。 一般的なMemory DBの設計ではなく、KV:Mem serving pathの代替仮説、最小実装、比較実験、採否条件だけを扱います。

評価日
2026-09-16
暫定名称
Ctx:mem（Selective Context Injection Memory）
判定
試す価値あり。最初はsnapshotをOFFにした既存source-rebuild経路でA/Bする
成立条件
大規模source集合から、interactive requestの注入量を数百から少数千tokenへ縮められること

結論: 現行KV:Memの意味機能はすでにContext注入で実現されています。KV snapshotは 同じpromptのprefillを短縮する性能層です。したがって、source、View、token budget、forgetを残し、 snapshot save／restoreだけを無効化した構成が最小の代替候補です。ただし225K級の全文を毎回注入する構成は latency上成立しません。代替の本体は、SAAA／ContextStillによる小さいContext Capsuleの選択と、 不足時の追加取得です。

実装から分かった重要事項

Snapshot hitでもContext注入は行われる

prepareChatRequestはsnapshotをrestoreした後も、選択された全sourceを読み、system messageへ同じtext blockを組み立て、canonical token数を再計数します。snapshotはKnowledgeやMemoryを 選ぶ機構ではなく、注入済みpromptのprefill結果を復元するだけです。

現在のdisk lookupは完全request一致である

v1 Viewはmaterialization時に、v2 Personal State Viewはbind時に、View digestをrequest digestへ結合します。 snapshot storeはprincipal、runtime、release、compatibility key、結合済みView digestの完全一致で一件を検索します。 longest-prefix検索やparent session検索はありません。messages、tools、user turnのいずれかが変わる通常の次turnは、 LARMのdisk snapshot lookupでは別entryになります。

文書上の「保存prefixへ未見suffixを追加するsession continuation」はllama.cpp slot自体の能力としては成立しますが、 現行LARMのlookup keyは次turnの異なるrequestからそのprefix snapshotを発見しません。現在の自動testも 同じrequest bodyと同じViewを再作成するcaseをhit条件にしています。

通常会話ではwrite amplificationになり得る

snapshot eligibleなrequestは、exact hitしなければgeneration成功後にfull slotを保存します。 次turnでrequest digestが変わるとmissし、またfull slotを保存します。Contextが大きく毎turn変わるworkloadでは、 数GiBを書き続けながらhitしない可能性があります。保存価値を事前判定するhit予測、session parent index、 最小再利用回数は現在のsave gateにありません。

現時点のlive storeには利用実績がない

2026-09-16の点観測では、live daemonはhealthyでしたが、 /srv/ai/context-snapshotsと/srv/ai/context-sourcesはいずれもdirectory metadata相当の4 KiBで、committed fileはありませんでした。この観測は将来のworkload価値を否定しませんが、 現時点ではsnapshot網を維持すべき実利用hit率の証拠がないことを示します。

代替が成立する範囲

Snapshotは大きい同一promptでは圧倒的に速いため、Context注入が同じ225K全文を毎回prefillして競争する案は No-Goです。M3b実測では229,376-tokenのcold prefillが3,097.552秒、fresh CRC検証込みrestoreが p95約1.004秒でした。Context注入案は「同じ全文を別表現で保存する」のではなく、今回必要な部分を小さくすることで prefill自体を避けます。

検証する仮説

  1. 個人Memory、tool手順、過去の判断では、225Kの過去状態全体ではなく、queryに関連する数個の事実と現在taskを 正確に提示すれば回答品質を維持できる。
  2. SAAAとContextStillがsource-levelで検索できるため、LARMが大量のKV stateを保存しなくても、必要なturnで evidenceを再取得できる。
  3. 常時注入を小さいMemory Headerに限定し、詳細はmodelのtool callまたはSAAAのprefetchで追加すれば、 snapshot miss時の大規模prefillと数GiB writeを避けられる。
  4. source textを正本とするため、model／tokenizer／engine更新時のsnapshot全失効をMemory lossにせず、 同じContext Packを新runtimeへ再注入できる。
  5. current requestだけに必要なContextを注入する方が、大量のirrelevant contextをattention windowへ残すより、 distractor、stale memory、prompt injectionの影響を減らせる。

反証条件は明確です。必要なevidenceのretrieval missが多い、複数episodeを横断するtaskで品質が落ちる、 1–2K以下へ縮めると原文忠実性が失われる、または追加tool round tripがsnapshot hitより体感を悪化させる場合、 純粋なContext注入だけでは代替できません。

提案：Ctx:mem

L0 Memory Header

ほぼ全turnに必要な現在状態だけを、自由文会話要約ではなく短いtyped factsとしてrenderします。 利用者identity、現在goal、critical constraint、open commitment、直近の決定だけを入れます。 voiceでは128–256 tokenから開始し、512 tokenを越えたら削るか追加取得へ移します。

L1 Evidence Capsule

一つのCapsuleは一つのclaim、procedure、episode outcome、または原文excerptに限定します。 summaryだけで断定せず、authority、record ID、version、valid time、confidence、source digestを持たせます。 

<context-capsule
  id="memory:preference:answer-style@7"
  kind="preference"
  authority="saaa"
  confidence="asserted"
  valid-at="2026-09-16"
  sha256="...">
回答は日本語。結論を先に述べる。
</context-capsule>

tool schemaはCapsule本文にしません。実在するtoolの最新schemaをChat requestのtoolsへ渡し、 Capsuleには該当versionのprocedureと利用者固有設定だけを含めます。

L2 On-demand Context

最初のpackで不確かな場合、modelはmemory.search、knowledge.search、 source.getのいずれかを呼びます。SAAAは結果を検証し、該当箇所だけを次requestへ追加します。 これにより、低頻度の詳細情報のために全turnへ長いcontextを載せません。

二つの実験mode

Context注入の意味的価値と、runtime内の一時prompt reuseを分けて測定します。どちらもdisk slot snapshotは使いません。

Snapshotを使わない比較対象
mode request 目的
injection-cold cache_prompt: false、slot save／restoreなし Context Packそのもののtoken費用と品質を測る
injection-ram cache_prompt: true、process-local common prefixだけ再利用 永続cache網なしでsession中の体感を改善できるか測る

injection-ramも正しさをcacheへ依存させません。worker unload、restart、topic変更でcacheが消えれば source textから再prefillします。llama.cppのcache_promptは既定ONですが、比較では明示値を送り、 prompt prefixをcanonical orderにして同じsessionの再利用量を記録します。

既存実装を使う最小試験

最初のA/Bには新しいMemory backendも、新しいLARM APIも不要です。既存source-rebuildをそのまま使えます。

  1. LARM_CONTEXT_SNAPSHOT_ENABLED=falseでsnapshotだけを停止する。
  2. SAAAがqueryごとにContextStillとPersonal Stateから128–2,048 tokenのCapsuleを選ぶ。
  3. Capsuleを既存のimmutable context sourceとしてprovision／registerする。
  4. 既存POST /v1/context-measurementsとPOST /v2/context-viewsでexact token budgetを確定する。
  5. 既存Chat requestへContext Viewをbindし、source-rebuildでsystem contextへ注入する。
  6. cache_prompt: falseとtrueを別runにして、disk snapshotなしで比較する。
  7. 同じfixtureをsnapshot ONの現行pathでも実行し、品質、TTFT、I/O、hit率を比較する。

さらに単純なspikeでは、同じContext Packを通常Chat requestのsystem messageへ直接含められます。ただし、 製品候補はsource digest、canonical recount、subject fence、forgetを保持できる既存Managed Context source-rebuild経路を推奨します。

Snapshot store、CRC manifest、quota、GC、forget dependencyはA/B判定前に削除しません。global flagで隔離し、 Ctx:memが合格してから削除範囲を決めます。

fixture

  • 20M候補中の一つの個人事実を必要とするsingle-hop recall。
  • 2–5個のepisode／Findingを結ぶmulti-hop reasoning。
  • 古い嗜好と訂正後revisionが両方存在するstale-memory排除。
  • review済みprocedureと最新tool schemaを必要とするtool task。
  • 該当情報が存在しないnegative query。類似distractorを注入しないことを確認する。
  • 忘却開始後のsource、Capsule、View、遅延response再利用拒否。
  • 同一sessionでtopic維持、topic変更、元topic復帰を含む10-turn会話。
  • ContextStill停止、SAAA再起動、worker unload後のsource再構築。

保存する測定値

  • task success、grounded claim、tool success、citation correctness。
  • required evidence recall、irrelevant capsule precision、stale capsule件数。
  • pack tokens、actual prompt tokens、prefill tokens、reused tokens、completion tokens。
  • TTFT、prefill、decode、totalのp50／p95。
  • snapshot lookup hit／miss理由、save回数、restore／save bytes、NVMe read／write。
  • on-demand retrieval回数と追加round-trip latency。
  • worker startup、RAM／UMA headroom、foreground SAAA／音声経路への干渉。

Go／No-Go条件

Ctx:mem Go

  • I2またはI3のtask successがK0から2 percentage pointを超えて低下しない。
  • required evidence recallが98%以上で、forgotten／unauthorized／superseded source採用が0件。
  • tool schema違反、誤ったside effect、citationの存在しない断定がK0より増えない。
  • voice fixtureのMemory Headerはp95 512 token以下、通常interactive packはp95 2,048 token以下。
  • 通常会話のp95 TTFTがK0のhit／miss混合実測以下で、snapshot writeは0 bytes。
  • worker unload、model更新、snapshot root全削除後もsourceから同じ意味のContext Packを作れる。

純粋注入 No-Go、Hybrid継続

  • multi-hop taskが2,048 token以下では再現せず、on-demand retrievalでも回復しない。
  • exact-prefix snapshotの実workload hit率が高く、I3より明確にTTFTを改善し、write amplificationも小さい。
  • summary／Capsule化による情報損失が原文excerpt追加では解決しない。
  • tool round tripが多く、最終回答までのtotal latencyまたは利用者体験を悪化させる。

Hybrid判定の場合も、全MemoryをKV化しません。高頻度で安定したsession coreだけを将来のprefix cache対象にし、 long-tail KnowledgeはContext injection／retrievalのままにします。その場合はexact request keyではなく、 canonical stable prefixとparent sessionを識別する別設計が必要です。

主なriskと対策

Context注入固有の失敗
risk 対策
retrieval miss required/pinned memory、query expansion、on-demand search、存在しない場合の明示を使う
summary distortion atomic factと原文excerptを分け、evidence digestとsource.getを用意する
prompt injection ContextStill／Memory本文をdata blockとして扱い、tool schemaとsystem policyから分離する

推奨する次の一手

  1. 現行snapshotを削除せずkill switchでOFFにする。
  2. SAAA側で256、512、1,024、2,048 tokenの四段階Context Pack fixtureを作る。
  3. 同じquality workerでK0、I1、I2、I3を各fixture反復し、prompt progressとNVMe I/Oを採取する。
  4. 10-turn会話で現行snapshotの実hit率とsave bytesを測る。
  5. I2／I3がGoなら、公開名をKV:MemからCtx:mem／Managed Contextへ変更する設計を確定する。
  6. 純粋注入がNo-Goでも、retrieval＋小さいstable prefixだけをcacheするHybridへ範囲を縮める。

最初に実装すべき新技術はKV storeではなく、SAAA／ContextStillから短いCapsuleを作るselectorと評価fixtureです。 LARM側にはすでに必要なsource injection、token recount、identity、forget境界があります。
