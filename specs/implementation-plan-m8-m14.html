LARM Milestone 8–14 実装計画（履歴）

この文書は、Route、Allocation、LLM Gateway、単一file artifact lifecycleまでを実装した LARMを、local-node上で常用できるLocal AI Providerへ進める次期計画です。次の主目的は、 現行機能を実運用へ反映し、LLM、STT、TTSを同じAllocation固定の安定endpointから利用可能にすることです。

結論

次の着手対象は35Bではありません。まず現在のdaemonを常駐運用へ載せ、 /v1/chat/completionsに加えてSTTとTTSもAllocationで固定されたGatewayへ統一します。 その経路にRuntime単位の実行枠とbounded queueを加え、daemon再起動をclientが確実に検出できるようにします。 その後、checksum付きdirectory snapshotをartifact lifecycleへ追加し、PreferredなQwen TTSを最初の対象にします。

35Bはproduction Registryへ追加しません。特定taskの速度SLO、品質下限、memory実測、artifact metadataが揃ったときだけ、別のdecision recordを経てllm-speedへ追加します。 llm-defaultへ暗黙に混入させません。

次期サイクルの完了状態

  1. local-nodeでLARM daemonが常駐し、再現可能な検査とrollback手順を持つ。
  2. 利用側はLLM、STT、TTSの個別portを知らず、Allocation IDと安定endpointだけを使用する。
  3. Gatewayはrequest bodyからRuntime、upstream URL、pathを決定しない。
  4. Runtimeごとの同時実行数、待機数、待機時間が設定値でboundedになる。
  5. daemon再起動後、古いAllocationを復元せず、clientへinstance変更と再Allocationを明示する。
  6. 孤立したPreferred RuntimeをResidentへ影響させず回収できる。
  7. 宣言済みdirectory snapshotを検証・stagingでき、Preferred Runtimeだけを無人activationできる。
  8. Qwen 3.8 27Bが通常・リアルタイム要求のResident defaultであり続ける。

実装着手時に固定した設計判断

  • Active Allocationはdaemon再起動後に復元しません。利用中か不明なleaseを復活させるより、boot epochの変更を返して再Allocationを要求します。
  • Runtime定義へcapabilityと対応するprotocol識別子を追加します。protocolはenumであり、API requestから任意のupstream pathを受け取りません。
  • 同一protocolに複数Bindingがある場合、x-larm-capabilityで明示します。 省略時に選べるのは互換Bindingが一つだけの場合、または既存互換のllm.generalだけです。
  • Speech uploadは全量をdaemon memoryへ保持せず、byte上限付きstreamとしてupstreamへ転送します。
  • Queueは任意長にしません。Runtimeごとに実行slot、最大待機数、queue timeoutを宣言し、 上限時は429とRetry-Afterを返します。
  • Snapshot artifactはmanifestに全fileのrelative path、bytes、SHA-256が固定されたものだけを受け付けます。symlink、device、未列挙file、path traversalを拒否します。
  • Resident artifactの無人activation禁止は維持します。

依存関係と着手順

Milestone 12のdomain設計とMilestone 13のmanifest設計は先行して並行検討できますが、 production有効化は上記の順番でgateします。各Milestoneは小さな互換commitへ分割し、 直前のgateを満たすまでは次の機能をproductionで有効にしません。

Milestone 8: Automated baseline and commissioning

目的
現在の実装を再現可能なrelease候補にし、local-nodeでLARM自身を常駐運用へ載せる。
優先度
P0

実装項目

  1. CIへfrozen install、source-only、Spec HTML、TypeScript、全test、Bash syntax、Python syntax、systemd unit検証を追加する。
  2. /healthまたは専用version responseへsoftware version、config revision、boot epochをpayload本文やsecretなしで出す。
  3. Allocation作成、Resident 27B固定、Gateway stream、releaseを行う非破壊smoke scriptを deploy/local-nodeへ追加する。
  4. installerの再実行、credential保持、unit差分、polkit最小権限、Preferred boot disableをtestする。
  5. operator立会いでserviceをinstall、startし、既存Provider portを停止せずにsmokeを通す。
  6. 導入前unitへ戻すrollback手順と、daemonだけを無効化する手順を記録する。

完了条件

  • CIとbun run checkが同じ必須検査を実行し、mainで成功する。
  • larm-daemon.serviceが再起動後も起動し、/readyがfreshになる。
  • llm-defaultsmokeが必ずqwen-generalを返す。
  • 導入中にResident serviceをstopまたはrestartしない。
  • daemon停止時は既存direct Provider endpointへ戻せる。

Milestone 9: Protocol-aware Gateway foundation

目的
LLM専用proxyを、protocolごとの差だけをadapterへ閉じ込めた共通data planeへ発展させる。
優先度
P0

実装項目

  1. Coreへcapabilityとprotocolの対応schemaを追加し、Registry読込時にRoute候補との整合性を検証する。
  2. 最初のprotocol enumをopenai.chat-completions.v1、 openai.audio-transcriptions.v1、openai.audio-speech.v1とする。
  3. Allocationから互換Bindingを選ぶ純粋関数をCoreへ追加し、曖昧、未割当、protocol不一致を区別する。
  4. daemonのbody limit、deadline、cancel伝播、header allowlist、response stream、metricを共通proxy primitiveへ分離する。
  5. 既存chat completionsを共通primitiveへ移し、responseとerror contractを変更しない。
  6. upstream error本文はそのまま返せても、credential、内部URL、stack traceはlogへ残さない。

完了条件

  • 既存LLM Gatewayの全contract testが無変更で成功する。
  • request指定のmodel、URL、pathでBindingを変更できない。
  • protocol不一致と曖昧なBindingを推論開始前に拒否する。
  • upload、upstream接続、response streamの全区間へ同じdeadlineとcancelが伝播する。

Milestone 10: STT / TTS stable Gateway

目的
上位Ambient Agentから8081、8082、8084の個別portを隠し、音声経路もAllocationへ固定する。
優先度
P0

公開endpoint

追加するv1 data plane
Method Path Binding 主な制限
POST /v1/audio/transcriptions speech.stt multipart stream、upload bytes、deadline、cancel
POST /v1/audio/speech speech.ttsまたはspeech.tts.expressive JSON bytes、audio stream、credit header
GET /v1/audio/voices 選択済みTTS Binding Allocation必須、Runtime固有結果を明示

実装項目

  • STT uploadを全量bufferせず、転送中にbyte数を数えて上限超過時に両方向をcancelする。
  • TTSのaudio responseをstreamし、content type、request id、VOICEVOX creditを許可headerとして返す。
  • expressive TTSは明示routeで作成したBindingだけを使用し、通常TTSから暗黙に切り替えない。
  • Providerの429とRetry-Afterを保持し、LARM自身のcapacity拒否と区別可能にする。
  • 音声、文字起こし、合成textをlog、metric、operation journalへ保存しない。
  • LLM、STT、TTSを一つのvoice profile Allocationへ固定するE2E fixtureを追加する。

完了条件

  • voice profile一回のAllocationからSTT、LLM、TTSを順に呼び、各capabilityに固定されたBindingを使い続ける。
  • STTのchunked upload、上限超過、disconnect、timeoutをintegration testで検証する。
  • TTSの通常音声と表現音声を明示的に選び分け、暗黙fallbackを行わない。
  • 直接portを使わないAmbient Agent向け接続例とrollback例がある。

Milestone 11: Bounded execution and backpressure

目的
Allocationのresource予約と、実際の推論requestの同時実行制御を分離して両方をboundedにする。
優先度
P0

実装項目

  1. RuntimeのresourcesへmaxConcurrentRequests、maxQueuedRequests、 queueTimeoutMsを追加する。
  2. Gateway対応RuntimeはmaxConcurrentRequestsを必須とし、 maxQueuedRequestsの既定値は0として、明示設定がない待機を作らない。
  3. daemonへRuntime単位のFIFO execution gateを追加し、待機中のdisconnectとAllocation失効をcancelする。
  4. 実行開始直前にAllocation、boot epoch、observer freshness、固定Runtime状態を再検証する。
  5. queue timeoutと満杯を安定したerror code、429、Retry-Afterへ変換する。
  6. active、queued、rejected、queue durationをRuntime単位の低cardinality metricにする。
  7. local-nodeのslot値は推測で決めず、各Providerの負荷試験とmemory peakを記録して設定する。

完了条件

  • 同時要求、queue満杯、queue中cancel、TTL満了、shutdown drainの決定的testがある。
  • 設定した実行数と待機数を超えてPromise、body、audioを保持しない。
  • Resident 27Bの通常・リアルタイム経路がPreferred Runtimeの待機列に依存しない。
  • Provider固有429とLARM capacity 429をclientがerror codeで区別できる。

Milestone 12: Restart epoch, idempotency, and reconciliation

目的
daemon crashまたはrestartを曖昧な404ではなく、明示的で再試行可能なlifecycle eventにする。
優先度
P1

実装項目

  1. Milestone 8で公開したboot epochをAllocationとGateway response headerへ含め、data plane全体のinstance境界として使用する。
  2. Allocation IDへepochを含め、別epochのIDにはallocation_epoch_expiredを返す。
  3. Allocation作成にIdempotency-Keyを追加し、request hash、結果、TTLをbounded memoryへ保持する。
  4. 同じkeyと同じrequestは同じ結果を返し、異なるrequestは409で拒否する。
  5. 起動後のrecovery graceを経て、active Allocationを持たないHOTなPreferred Runtimeだけを回収する。
  6. Resident、配備中Runtime、health不明Runtimeはstartup reconciliationで停止しない。
  7. client向けにepoch変更時の再Allocation手順を示す。

完了条件

  • daemon kill、restart、重複POST、timeout後retryのintegration testがある。
  • 再起動前のactive Allocationを復元せず、別Runtimeへ暗黙移動しない。
  • 孤立Preferredを回収してもResident serviceへstop命令が発行されない。
  • idempotency cacheの件数、key長、TTLがboundedである。

Milestone 13: Directory snapshot artifact lifecycle

目的
複数fileのモデルをallowlistされた一つのimmutable snapshotとして検証・stagingする。
優先度
P1

Manifest contract

  • kindはfileまたはsnapshotのdiscriminated unionとする。
  • snapshotはrevision、合計bytes、最大file数、sorted file listを持つ。
  • 各fileは固定source、relative path、bytes、SHA-256を持つ。
  • canonicalなfile listからsnapshot digestを計算し、同じrevision名の内容差し替えを拒否する。

実装項目

  1. Coreで重複path、絶対path、親参照、case衝突、未bounded manifestを拒否する。
  2. Backendでregular file以外を拒否し、staging rootからの逸脱を実pathでも再検証する。
  3. file単位の一時download、size・hash検証、snapshot全体検証後のatomic renameを実装する。
  4. 中断時は不完全snapshotをactiveにせず、期限付きcleanup対象にする。
  5. active target切替とrollbackはsnapshot root単位で行い、journalへsnapshot digestを記録する。
  6. Qwen TTS設定はmanifestが管理するactive snapshot pathだけを読み、 revision切替がservice起動へ確実に反映されるcontract testを追加する。
  7. LARM serviceのReadWritePathsへQwen TTSのactive target directoryだけを追加し、model tree全体やResident artifactへの書込権限を与えない。
  8. 最初のproduction対象をPreferredなQwen TTSとし、Resident artifactはstaging-onlyにする。

完了条件

  • 一つのfileでもhash不一致ならsnapshot全体を拒否する。
  • 通信切断、disk不足、daemon restart、activation health失敗のfailure injection testがある。
  • 旧snapshotは新snapshotのhealth確認完了までrollback可能である。
  • APIから任意URL、path、file追加を行えない。
  • Resident activation禁止とsource-only policyを維持する。

Milestone 14: Canary migration and production gate

目的
一つの実clientを統一Gatewayへ移し、観測結果を基にdirect endpoint依存を段階的に外す。
優先度
P1

Rollout

  1. 実測するrequest形、同時実行数、latency、memory、安全reserveを受入資料へ固定する。
  2. text chatだけをcanary化し、direct LLM endpointへ戻せる状態でsoakする。
  3. STTを追加し、upload cancellation、429、privacy logを確認する。
  4. 通常TTSを追加し、VOICEVOX creditとaudio streamを確認する。
  5. expressive TTSは明示routeを使うtaskだけへ追加する。
  6. restart recoveryとPreferred idle回収を確認してから、統一Gatewayを既定接続先にする。

Production gate

  • 実際に使用したroute、Runtime、fallback、queue結果をpayloadなしで追跡できる。
  • 連続運転中にAllocation、request slot、queue、Preferred Runtimeのleakがない。
  • daemon停止またはrollback時もResident Providerは利用可能である。
  • 通常・リアルタイム・voice profileのLLM BindingがQwen 3.8 27Bである。
  • 35BがRegistry、default route、fallbackへ存在しない。
  • gateway overheadとProvider latencyの数値基準を実測から確定し、結果をSpec HTMLへ保存する。
