公式仕様と実行経路

Liquid AI株式会社の公式発表日は2026年6月5日。1.5B級の日本語音声・テキストモデルで、 独立したASRとTTSを必須とせず音声から音声へ回答できる。公式model cardは LM本体1.2B、FastConformer音声encoder 115M、context 32768 tokens、 bfloat16、LFM Open License v1.0を記載している。 「LFM2.5-1.2B-JP-202606」という別のテキストモデルのtool使用性能を、 このAudioモデルの性能として扱わない。

公式Python実装はLiquid4All/liquid-audio。今回使用した実行エンジンは community実装のaudio.cppであり、公式Python実装との同一出力をこのPCで照合したわけではない。 公式GGUFはbackbone、mmproj、vocoder、tokenizerの4ファイルを使用する。 通常のテキスト用llama-serverを起動しただけで音声出力まで使えるとはみなさない。

モデルのcontext仕様と実行エンジンの制約は別である。評価したaudio.cppの複数ターン会話は promptと出力を合わせ8192 stepsまでで、stepにはテキストtokenと80 ms単位の音声が含まれる。 公式の32768 tokensすべてを今回のAPI経路で自由に使えるという意味ではない。 長い会話、長大なSystem Context、割り込み、同時会話、長時間連続稼働は未検証。

System ContextとMCPの扱い

System Contextをsystem prompt、会話の前提、キャラクター設定、外部情報という意味で解釈すると、 公式PythonのChatStateではsystem turnに任意のテキストを追加できる。 音声対話には公式例のRespond with interleaved text and audio.を保ち、その後に追加指示を置く。 任意のテキストを入力できることと、すべての指示を確実に守ることは異なる。 ASR/TTSにはそれぞれ専用のタスク指定promptがあり、自由な会話指示として置き換えると同じ動作を期待できない。

今回のaudio.cpp S2S APIではrequest.textがsystem promptを置き換える。 同じ4.011秒の音声質問「案内係の名前と、今日の会議室を教えてください。」を使い、 前提だけを「こはる・さくら」から「あおい・かえで」へ変更し、2条件とも返却テキストに反映された。 標準S2S UIにはこの追加テキストの入力欄がないため、自由な前提注入にはAPIまたは専用UIが必要。 LARM固有のSystemContext連携を実装したという意味ではない。

MCPはモデル重みに直接追加する機能ではなく、利用アプリのhost/clientがMCP serverへ接続し、 tools・resources・promptsを取得する仕組みである。取得した情報のテキスト注入は構成可能だが、 モデルによるtool選択、構造化引数、実行、結果の再注入にはアプリ側の制御が必要。 音声モデルの公式資料に、当該JP checkpointの任意MCP serverへの即時接続や、 native function callingの信頼性保証は確認できなかった。

模擬試験では、systemにlookup_capital(country: string)というツールと JSON例を与え、日本の首都を尋ねる音声から要求JSONを作らせたが、普通の音声回答になった。 1問の失敗でモデルの全tool能力を否定せず、今回の音声対話モードでは採用根拠不足とする。 MCP操作が主目的なら、ASR → 既存の会話LLMとMCP host → TTSの分業を第一候補とし、 このモデルは日本語音声の入口・出口として別途評価する。 agentの実装やSAAA連携は今回の調査範囲に含めていない。

LIVE API追加試験と上位LLMへの入出力トレース

CPU専用モデルではない。公式liquid-audioにはAMD ROCm向けPyTorchの導入例があり、 評価エンジンにはCPU・CUDA・Metalの検証記載がある。このPCではCPUだけで動作するためGPUは必須ではない。 当該AMD GPU経路の対応と性能は未検証。CPU測定をモデルの標準・唯一の実行方式とは扱わない。

追加試験ではPOST /v1/audio/speech/liveに16 kHz mono s16le PCMを HTTP chunkedで100 msごとに送り、return_text=trueを指定した。 3.648秒の合成音声を3.670秒かけて送信し、入力終了後0.410秒で最初の返答音声を受信した。 回答テキストは「日本の首都は東京です。」、出力音声は1.68秒、HTTP 200。 speech.text.delta、speech.text.done、 speech.audio.delta、speech.audio.doneの4種、合計26イベントを保存した。 初回エントリ利用でありモデルロードは送信と重なり得る。1回の実測で、マイク・VADを含むブラウザ会話試験ではない。

LFMのこの実装は入力終了後に回答を生成する。入力音声を逐次送れても、 ユーザーの発話途中から回答するfull-duplex会話という意味ではない。 発話終了の判定、録音、再生、割り込み時の出力停止は利用アプリ側で構成する必要がある。 またLIVE endpointはhistory artifactsを受け取らず、要求ごとに初回会話となる。 履歴を維持するには/v1/tasks/streamと履歴artifactsを使うか、 LIVE endpointを拡張する。単一LIVE要求の成功を、永続的な多ターンセッションの実装済み証拠としない。

音声会話をLFMに任せ、その入出力を上位LLMへ渡して記憶・判断・MCP処理を担当させる構成は可能。 APIの前後に中継層を置き、入力音声、出力音声、回答テキスト、発話・会話ID、時刻を記録する。 回答テキストは生成イベントから取得できるが、S2Sはユーザー音声の文字起こしを自動では返さない。 入力をテキストLLMへ渡す場合は、同じ音声を別のASR要求にも送り、その認識結果を関連付ける。 音声対応LLMであれば入力音声を直接渡す構成も選べる。

上位LLMは非同期に会話を観測し、記憶や次のターンのSystem Contextを更新できる。 外部ツールの結果を発話へ反映するには、アプリがその結果を次の生成へ明示的に渡す必要がある。 発話済みの音声を上位LLMが後から修正することはできないため、発話前の承認が必要な用途では 出力を一時保留する制御が必要で、その分の待ち時間が増える。 上位LLMへの転送・セッション管理・MCP制御の中継層は今回未実装。

証跡は既存の外部保存先にあるlive-summary.json、live-events.json、 live-reply.wav、test-live-trace.py。追加試験serverも終了後に停止した。

VOICEVOXとのTTS速度比較

同じPCでLFM Q8_0 / audio.cpp CPU 8 threadsとVOICEVOX Core 0.17.0 CPUを比較した。 公平なthread数比較用にVOICEVOXの8 threads版をport 18097へ隔離起動し、 現行16 threads版・春日部つむぎも測定した。各方式に短文1回のwarmupを行ったあと、 短・中・長の同じ3文をそれぞれ3回測定し、順番を交替した。推論は方式ごとに逐次実行し、 競合負荷を意図的には発生させていない。起動・重みロード時間とLLMの文章生成時間は含まない。

短文は「はい、了解です。」8文字、中文は「今日の予定を確認して、次にやることを一緒に決めましょう。」28文字、 長文は既存latency corpusのlong-01「現在の状態を確認したところ、ネットワーク接続は正常ですが、…」81文字。 同じ入力でも声・話速が異なるため、生成音声の長さとRTFも記録した。 LFMはseed 42、最大1024 steps、temperature 0.8 / top-k 64の既定値を使用。 VOICEVOXはspeed 1.0。全文が揃ってからHTTP要求を送り、LFMの最初の再生可能WAV chunkと 全体完了を別に計測した。VOICEVOXの現行APIは全文合成後にWAVを返すため、この2時刻はほぼ同じになる。

System Contextを付けたS2S要求の形式。音声pathはserverと同じPCのファイルを指定する。

{
  "model": "lfm25-jp-s2s",
  "request": {
    "audio": "/srv/ai/evidence/lfm25-audio-jp-20261025/context-question.wav",
    "text": "Respond with interleaved text and audio. あなたは案内係です。名前はこはる、今日の会議室はさくらです。日本語で短く答えてください。",
    "options": {"seed": 42, "max_tokens": 384}
  }
}

POST先は/v1/tasks/run。ストリーミング時は/v1/tasks/streamへ送り、 最上位に"stream_format": "sse"を追加する。返却音声はbase64のWAV。 再現用資材と生成メディアはsource repository外に保管している。
