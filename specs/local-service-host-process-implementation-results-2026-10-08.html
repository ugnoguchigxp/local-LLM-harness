Local Serviceホストプロセス方式：環境基盤の実装と検証結果

2026年10月8日。今回の対象は、アプリを後から導入できるDocker不要の環境基盤である。docling-deskは将来の利用例であり、導入・依存取得・機能変更・起動の対象ではない。共通backend、設定と記録の移行、停止controller、環境準備手順を実装した。OS管理者による登録と専用UIDでの実機受入は未完了。設計と受入仕様を参照する。

作業範囲の訂正と撤去

環境の整備をAppの導入準備と取り違え、docling-desk向けのPython/Bun依存・モデル候補、専用配備scriptとAppの変更まで進めた。利用者の指示により、これらを撤去した。隣接docling-deskの変更5ファイルと追加試験を戻し、git worktreeがcleanであることを確認した。今回作成したdocling-native-20261008およびr2/r3/r4の環境、モデル、patch、専用unit候補を削除した。

App向けprepare・installer・launcher・renderer・backup・実機検証scriptは共通基盤の成果物から除いた。LibreOffice等のホスト導入コマンドと、抽出プレビューへの変更案も撤回した。ホストへの追加パッケージ導入、doclingの専用UID作成、サービス登録・起動、業務文書・DBの作成は行っていない。既存アプリのデータ、共有cache、既存Providerとモデルには変更を加えない。

設定と公開API local-services.v1の読取りを維持し、v2にsystemd-processを追加。member、観測unit、readiness、保存先UUIDと最低空き容量をstrict検証する。未知field、ゼロdigest、重複unit、同じportの重複登録を拒否する。ensure/renew/releaseとSDK bindingは維持する。
利用権と停止 Managerの2-container停止条件をopaque instanceTokenへ置換。停止時に期待instance、App boot、所有drainを照合する。全cgroupとlistenerの終了確認まで予算を保持し、自動SIGKILLしない。
記録移行 v1 journalをv2へ移行し元fileを.v1.bakへ保持。同期とatomic renameで確定する。破損・未知versionを上書きせず、新起動をjournal_recovery_requiredで拒否する。
backendとcontroller 共通Managerから既存containerと新processを振り分ける。root管理の固定manifest、unit、asset、実効保護、専用UIDと制限を検証する。consumerへ任意command/env/unit指定を許さない。
外付け保存先 mount UUID・read-write・realpath・容量を確認し、外付け不在では内蔵へのfallbackを拒否。登録後のAppはmount依存を持ち、停止確定後だけ起動世代のworkを回収する。
環境だけの準備 prepare-local-service-environment.pyのcheckは読取りのみ。installは共通directory、固定controller、未展開のunit templateと環境記録だけを配置する。App専用UID、依存、DB、manifest、unit、polkit許可を生成せず、daemonを有効化・再起動しない。

OS依存のI/Oはpackages/backendsと配備controller、設定・利用権・解決はpackages/coreに保持する。AIのProfile → route → runtime → backendとServiceResourceLedgerを継続する。新しいモデルschedulerやアプリごとの固定RAM partitionを追加していない。

検証と現在の限界

共通schema、process backend、単member lifecycle、停止期待値、停止未確認、instance置換、journal破損・v1移行を検証した。controllerの10 scenarioはUUID違い、read-only、容量不足、symlink、外部drain、instance置換、停止timeout、I/O障害を含む。環境準備の試験ではApp導入を有効にする設定の拒否、誤UUID・read-onlyの拒否、保存先確認に失敗した場合の書込みゼロを検証する。

実際のuser-systemdで親・子・孫および別sessionの3 processを試験した。通常TERM停止後は0。TERM無視時は停止要求のexit code 0でも3 processが残り、cgroup観測で未終了を検知できた。検証用fixtureだけを明示cleanupした。証跡は/srv/ai/local-services-prepared/cgroup-evidence-20261008.json。これはproduction専用UID・2 TBへの実保存・全B受入を認定する試験ではない。

環境checkでsystemd 259、cgroup v2のmemory/cpu/pids、正しいNextorage UUIDとread-write接続、最低空き容量を確認した。管理者認証を要求するsudoの状態により、/opt・/etc等への共通基盤登録はこのセッションでは未実施。source実装の完了とOSへの配置済み状態を区別する。現行LARMのLocal Servicesは既定無効のまま維持する。
