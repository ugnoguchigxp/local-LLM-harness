2026-10-18に利用者が調査・契約案を承認し、 読み取り専用APIをsourceへ実装した。この文書は監視APIの実装contract。 LARM稼働プロセスへの配備とEumenes backendへの接続は未実施であり、APIのsource完成とは分けて扱う。 停止・起動・再起動や本番設定変更は実施していない。

値・単位・時刻の読み方

generatedAtは応答組立時刻、snapshotIdは保存viewの世代、bootEpochはdaemon起動識別子。 各Observationはstatus、source、unit、kind、observedAt、interval、counterEpoch、maxAgeMs、lastAttemptを持つ。 ok/staleだけがvalueを持ち、それ以外ではvalueを省略する。実測0はok value=0。 observedAt・interval・lastAttemptはGETで書き換えない。時刻はUTCのISO 8601、ミリ秒3桁・Z付き。 counterは非負10進文字列で、epochが変われば差分を作らない。 statusの意味と各値の詳細定義は計測包絡と 取得元・単位一覧に従う。

イベント・保持・再起動

id=bootEpochとsequenceの組、occurredAt、recordedAt、kind、target、workId、reasonCode、outcome、sourceを返す。 workIdは監視用のopaque IDで、caller request ID、client名、会話内容を返さない。 Control operation、要求結果、モデルload、Observer状態遷移、kernel事実を区別する。 要求の結果集計にはrequest.terminal/request.rejectedを使い、control.terminal、枠解放、load完了を要求成功へ加算しない。

保持目標600000ms、上限100000件または64 MiB。容量破棄・記録欠落はcontinuity=gapとdroppedEventsTotalで通知する。 GETは履歴のackや消費を行わず、複数読者が独立にcursorを保存する。 初回cursorなしは保存範囲内の直近10分。ページ取得のwindow/highWaterSequenceは固定し、 hasMore=falseまで取得したnextCursorから次回の新しいwindowへ進む。

欠落と再取得の扱い
条件 応答・Eumenesの処理
保持期限・容量欠落 410 monitoring_cursor_expired。reasonCodeはretention_expiredまたはcapacity_evicted。履歴欠落を記録し、cursorなしで再取得する。
daemon再起動 409 monitoring_epoch_changed。previousBootHistory=false。旧daemonの履歴を復旧したように扱わず、cursorなしから始める。snapshotのbootEpoch変更も検査する。
センサー側の観測欠落 coverageのstatus、since、through、reasonCodeを検査する。イベントstoreに保存できた範囲と、sourceで観測できた範囲は別。回復時のsinceを確認し、不明な窓を正常0件としない。
取消と遅延結果 取消terminalを一度だけ保持し、遅延成功や遅延例外で成功/障害へ変更しない。Control操作もterminalを一度だけ投影する。共有loadとcaller取消は別対象。
OOMの二つの証拠 oom_counter_changedは検知区間と増分、oom_kill_observedは明示kernel記録。両者を足さない。counterだけでは発生の厳密時刻・被害process・LARM起因を断定しない。

再起動前履歴の永続化、過負荷でも完全な10分保持、新しい高権限collectorは実装していない。 kernel journalのbackfillはkernel事実の範囲だけで、旧daemonの要求履歴を補完しない。 event kindと取得理由の一覧はJSON Schemaおよび設計のイベント表を参照する。

未対応と別途合意が必要な事項

  • GPUと要求の正式なbinding、GPU別のactive/queued/最古待ち/速度/初回応答はunsupported runtime_device_mapping_absent。GPUが一台でも自動対応付けしない。
  • thermalThrottledはunsupported driver_metric_not_decoded。温度やクロックから推定しない。
  • 明示信号がないProviderのmodelLoadState、Provider内部queue、LARMを経由しない要求、remote nodeのhost計測は観測できない。
  • ROCm/HIP固有障害は正式な構造化記録が未整備のため初版で追加抽出しない。一般的なHTTP 500やtimeoutをGPU障害へ変換しない。
  • 本番sandboxのjournal権限が足りなければpermission_deniedを返す。root collector、debugfs、group/capability追加は行っていない。
  • 永続event journal、TTFT、既存admissionメモリ会計の変更、警報しきい値、平常比遅延や入れ替え頻度の判定は別途合意対象。

Eumenes側の接続作業

  1. LARMの新release配備とdaemon再起動を利用者の許可後に行う。 Eumenes backendの既存LARM_API_TOKEN、Control originとTLSを再利用する。
  2. Eumenes backendからSpatial表示中だけ60秒間隔でsnapshotとeventsを取得する。SDKならgetMonitoringSnapshotとgetMonitoringEventsを使う。重複pollを避け、eventはhasMore=falseまで取得してcursorを保存する。
  3. 既存監視snapshotへLARM Core/CPU/Memory/GPUを追加し、配列の識別子と各Observationのstatus/observedAt/intervalを維持する。
  4. 通信到達不能、401、旧daemonの404、503、部分センサー未取得、履歴gapを別状態として扱う。失敗時に直前snapshotの応答時刻だけを更新しない。
  5. event IDで重複排除し、409/410で欠落を記録して初回窓へ戻す。daemon再起動前履歴の非保持を表示上も隠さない。
  6. 表示色、アニメーション、4対象と既存9対象の集約をEumenesで決める。外部連携の実行履歴・代理アクセスは本APIへ追加しない。

LARM側はsource実装と検証を完了してから配備許可を求める。 Eumenes側の実装変更・接続試験はこのリポジトリでは実施していないため、「Spatialへの接続完了」とは報告しない。
