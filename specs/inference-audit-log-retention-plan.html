LLM推論内容監査ログ・7日保持 実装仕様

LARMを通るLLM推論について、clientが送信したrequest、Providerが適用したchat template後のprompt、 token IDとpiece、Provider responseを後からrequest単位で確認できるようにします。内容は高機密の監査 dataとして通常のjournaldから分離し、作成から168時間を超えたrecordを自動削除します。保持期間だけで disk使用量が無制限にならないよう、総bytesと空き容量にもhard limitを設けます。

promptには会話、source context、tool入出力、偶発的なsecretが含まれ得ます。この機能はdebug logでは なく、明示的に有効化する短期監査archiveです。Authorization header、API token、management token、 Provider短期tokenは保存しませんが、body内へ書かれたsecretは完全には自動判定できないため、payloadを 暗号化し、7日で必ず読取対象から外します。

決定

  1. 完全なLLM request bodyをLARM Gatewayで採取します。Provider portへの直接requestは監査不能なので、 production clientをGatewayへ移行後、Provider listenerをloopbackへ閉じます。
  2. raw requestだけでなく、選択されたRuntimeの/apply-templateと /tokenizeを使い、整形済みprompt、token ID、token pieceを作成します。
  3. request payloadとresponse payloadは暗号化し、通常event logにはrequest ID、model identity、bytes、 token数、outcome、digestだけを残します。
  4. hard TTLは作成時刻から168時間です。期限切れrecordは閲覧API相当のCLIから即時除外し、daemonの daemonの毎時timerとsystemd timerで物理削除します。
  5. 10 GiBの総容量上限と20 GiBのfilesystem最小空き容量を初期値にします。圧迫時は古い完了recordから 7日未満でも削除し、なお保存できない場合は監査必須modeで新規推論をfail closedします。

Record形式

requestごとに独立directoryを作り、active markerを置いてからpayloadを書きます。完了時に metadataをatomic renameし、active markerを外します。crashで残ったpartial recordも次回起動時に outcomeをinterruptedとして確定できる形にします。完了metadataのcommit後、marker削除前に crashしたrecordは正常な完了結果を維持し、残存markerだけを回収します。

raw requestは受信したUTF-8 bytesをそのまま保存します。JSONを再serializeした値だけを保存すると、field 順やescape差分が失われるためです。token materialize用にはparse済みJSONを同じProviderへ渡します。 responseはclientへ流したbytesと同じ順序でteeし、SSEが途中で切れた場合もpartialとoutcomeを残します。

機密性と権限

  • root directoryは0700、fileは0600、既存unitのUMask=0077を維持します。
  • payloadはAES-256-GCMで書込み単位に異なる96-bit nonceを使い暗号化します。AADへUTC record pathとpayload種別を含め、別record・別種別への暗号文差し替えを拒否します。keyは /etc/larm/inference-audit.keyへ置き、Git、release、logへ含めません。
  • Authorization、Cookie、API key、management token、短期Provider tokenは採取対象外です。
  • 閲覧はhost local CLIだけに限定し、network APIやWeb UIを追加しません。
  • CLIは既定でmetadataだけを表示し、show <request-id> <payload-kind>を 明示したときだけ復号します。
  • backup script、artifact snapshot、release packageから監査rootを明示的に除外します。
  • symlink、hard link、root置換、path traversal、non-regular fileをfail closedで拒否します。

prompt本文に含まれるsecretを完全に推測してredactすると調査再現性を損ねます。そのためheader secretを 構造的に除外し、bodyは完全保存・暗号化・短期TTLで扱います。将来redactionを追加する場合も、原文を 変更するのではなく、閲覧CLIの表示filterとして実装します。

Retentionと容量制御

  1. 各recordのexpiresAt = createdAt + 604800秒を作成時に固定します。
  2. CLIは現在時刻がexpiresAt以上のrecordを表示せず、pruneで物理削除します。
  3. daemonは起動時、各requestの保存前、稼働中は毎時、期限到達済みcompleted recordを削除します。
  4. larm-inference-audit-prune.timerを1時間間隔かつPersistent=trueで動かし、 daemon停止・host停止後のfallback cleanupを行います。
  5. daemon起動時にもexpired recordと1時間以上古いpartial recordをreconcileします。
  6. 総bytesまたは最小空き容量を超えた場合、active recordを除きcreatedAtの古い順に削除します。7日は 最大保持期間であり、disk safetyが必要なら早期削除を許可します。
  7. 新規request、最大response、prompt・token materialization、metadata overheadを保存前に予約し、 active reservationを容量削除の対象にしません。request、prompt、token、responseは各64 MiB以下、 production response初期値は16 MiBです。
  8. 削除はresolved root、record ID、regular directory、active marker不存在を再検証してから実行し、 broad globや未解決環境変数を削除targetに使いません。
  9. record削除後は空のhour、day、month、year directoryをrootまで安全に回収します。

実装結果

  1. core schemaとpolicy parserを追加し、record identity、expiresAt、size、outcomeをstrict validationしました。
  2. backend storeへsecure create、record path・payload種別を結ぶAES-GCM、展開上限付き復号、atomic metadata commit、完了commitを保つcrash recovery、TTL・capacity pruneを実装しました。
  3. Gatewayのbuffered LLM pathへcapture hookを追加しました。raw requestの永続化に成功してからupstreamを 呼び、response streamをclientとstoreへteeしました。 response captureだけが失敗してもclient streamを継続し、recordをtruncatedとして確定します。
  4. Runtime endpointの/apply-templateと/tokenizeをboundedに呼ぶmaterializerを追加し、 prompt、ID、piece、token countを同じrecordへ追加します。失敗時はraw requestを保持し materializationErrorを記録するようにしました。
  5. local CLIへlist、show、verify、pruneを追加しました。 showはrequest、prompt、tokens、responseを個別指定できるようにしました。
  6. systemd prune service・timer、installer、運用CLI contractを追加しました。daemonとpruneは 非secretの/etc/larm/inference-audit.envだけを共有します。prune serviceへAPI・management credentialを渡さず、network namespaceを持たせず、/var/lib/larm配下だけを書き換えます。
  7. repository desired stateはProviderをloopbackへ固定済みです。live hostのSAAA経路確認と 8080–8084の移行用listener閉鎖はproduction rolloutで実施します。
  8. 汎用defaultはoff、local-node production unitはfull-requiredにしました。 専用test rootで暗号化round trip、期限、容量、Gateway fail-closedを検証しました。

Failure policy

監査処理が失敗した場合の推論・保存動作
Failure 動作
request保存不能 full-requiredではupstreamを呼ばず503
template・tokenize失敗 raw bodyとmodel identityを残し、推論は継続。recordを再materialize対象にする
response保存上限 保存だけを打ち切り、client streamは継続。truncatedを記録
response write失敗 metadata eventを出し、client streamは継続。active recordはrecovery対象
key不正・root unsafe daemon startupをfail closed
prune失敗 新規full captureを停止し、metadata eventとmetricでoperator対応を要求

検証

Unit・property test

  • raw bodyのbyte一致、SHA-256一致、JSONのfield順・escape保持
  • Authorizationと全credential headerがpayload・metadata・journaldへ出ない
  • AES-GCM round trip、wrong key・改ざん・record間暗号文差し替えの検出
  • response teeがchunk順、backpressure、cancel、timeoutをclientとrecordで一致させる
  • 168時間の直前・ちょうど・直後、clock rollback、daemon restartで同じretention decision
  • 容量超過時のoldest-first、active保護、最小空き容量、早期削除event
  • symlink、hard link、root、path traversal、corrupt metadata、partial recoveryをfail closed
  • materializerがchat template、thinking設定、tool call、system message順序をrequestどおり扱う

production rollout acceptance

  1. 固有markerを含む約3,000 tokenのrequestをGatewayへ送り、raw request、rendered prompt、全token ID・pieceをCLIで照合します。
  2. 正常SSE、client cancel、30秒client timeoutを実行し、それぞれresponseとoutcomeを確認します。
  3. Provider logのprompt token数と監査recordのtoken数を同一request IDで照合します。
  4. fake clockと専用test rootで168時間を進め、expired recordがlist不能かつ物理削除されることを確認します。
  5. 容量上限と空き容量を小さくしたtest rootで古いrecordだけが安全に削除されることを確認します。
  6. daemon restart中のpartial recordがinterruptedへ収束し、Resident Provider PIDが変わらないことを確認します。
  7. SAAA hostから9810が成功し、8080–8084が到達不能であることを確認します。
  8. 7日soak後にexpired record 0、上限超過0、decrypt failure 0、capture gap 0を確認します。

Rollout

  1. 全testと専用test rootでcleanup dry-runを通します。
  2. host stateをbackupし、key、0700 root、prune timerを導入します。
  3. metadata modeでGateway経路とdisk accountingをcanaryします。
  4. full-requiredへ切り替え、local CLIでrequest・prompt・tokens・responseを確認します。
  5. SAAAをGatewayへ切り替え、同じrequest IDがclient、LARM event、監査recordで一致することを確認します。
  6. Provider portをloopback化し、LAN direct accessを閉じます。Resident unitは一件ずつ適用します。
  7. cancel再現、retention rehearsal、24時間canary、7日soakの順に完了判定します。

Rollback

  1. LARM_INFERENCE_AUDIT_MODE=offへ戻し、LARM daemonだけをrestartします。
  2. Gateway inferenceとResident PIDが正常であることを確認します。
  3. prune timerは停止せず、既存の暗号化recordが期限到達まで削除され続ける状態を維持します。
  4. 原因を修正後、metadata modeから再開します。

rollback時もProvider LAN portは原則として再公開しません。Gateway自体が利用不能で緊急に戻す場合だけ、 送信元を限定したattended network rollbackとして別に承認します。監査payloadの手動一括削除はrollbackへ 含めず、必要な場合はexact rootと件数・bytesをreviewした別操作にします。
