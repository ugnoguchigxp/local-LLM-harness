SAAAの最新mainを対象に、LARMのvoicevox-coreが提供する話者・スタイル・韻律制御を 製品音声設定へ実装してください。調査、実装、テスト、コードレビュー、ドキュメント更新まで行い、 改善点が残らない状態でcommit可能な差分にしてください。LARM側のsource、local-node配備、root service、モデルassetは変更しないでください。

  2. ファイル名は調査時点の入口として扱い、最新の構成を優先してください。少なくとも src-tauri/src/models/provider_settings.rs、 src-tauri/src/persistence/settings/provider_validation.rs、 src-tauri/src/voice/cloud_tts.rs、 src-tauri/src/providers/larm_voice/audio.rs、 src/lib/settingsTypes.ts、src/lib/providerSchemas.ts、 src/features/settings/ProviderCard.tsx、Harness音声設定、HTTP音声テストを確認してください。
  3. SAAAの既存の句単位合成、順序保証、再生、cancel、barge-in、遅延turn拒否、credential保管を維持し、 今回の設定追加を理由に別の音声pipelineを作らないでください。

LARM API contract

話者一覧は通常のTTSと同じbase URL・Bearer credentialを使って取得します。

GET /v1/audio/voices?model=voicevox-core
Authorization: Bearer <token>

rich catalogの各voiceにはid、display_name、 voice_presentation、default_style、styles、 capabilities、creditが含まれ、response全体に default_voiceがあります。既存互換の簡易voice一覧が返るProviderも壊さないでください。 JSON本文には上限を設け、redirectを追跡せず、credentialを別originへ転送しないでください。 

POST /v1/audio/speech
Authorization: Bearer <token>
Content-Type: application/json

{
  "model": "voicevox-core",
  "input": "本日の予定をご案内します。",
  "voice": "Kasukabe_Tsumugi",
  "style": "normal",
  "response_format": "wav",
  "speed": 1.1,
  "pitch_scale": 0.03,
  "intonation_scale": 1.15
}
VOICEVOX制御値
field 範囲 省略時
voice catalogに存在する具体的なvoice ID default_voice
style 選択voiceに属するstyle ID voiceのdefault_style
speed 0.5以上2.0以下 1.0
pitch_scale -0.15以上0.15以下 0.0
intonation_scale 0.0以上2.0以下 1.0

必須実装

  1. RustとTypeScriptのTTS設定contractへ、optionalなstyle、speed、pitch scale、intonation scaleを 型付きで追加してください。永続化JSONは既存設定をそのまま読める加算的変更とし、未設定値を保存時に 勝手に具体値へ書き換えないでください。finite number、上限・下限、文字列の空白・control文字をRustと TypeScriptの両境界で同じように検証してください。
  2. 通常のcloud-tts経路と、LARM音声Sessionから組み立てる一時TTS設定の両方に値を伝播し、 cloud_tts.rsのspeech requestでsnake_case wire fieldとして送信してください。未設定fieldは JSONから省略し、VOICEVOX以外のmodelへVOICEVOX専用fieldを暗黙に送らないでください。
  3. voicevox-coreではvoice catalogを取得し、設定画面で表示名付きの具体的なvoiceと、その voiceに属するstyleを選択できるようにしてください。catalog取得失敗時も保存済みIDを失わず、手入力または 再試行可能な状態を維持してください。catalogからvoiceが消えた場合は無言で別話者へ切り替えず、利用者に 不整合を示したうえでdefault_voiceへ戻す操作を提供してください。
  4. voice_presentationは表示補助だけに使ってください。「男性」「女性」から非決定的に話者を 選ばず、保存・送信する値は具体的なvoice IDにしてください。ピッチ変更を話者切替の代用にしないでください。
  5. speed、pitch、intonationはcatalogのcapability範囲をUIへ反映し、数値入力と操作結果を確認できる表示を 用意してください。catalog未取得時もLARMの固定範囲を越える値を保存できないようにしてください。 styleを変えたときにvoiceを変えず、voiceを変えたときは新voiceのdefault styleへ明示的に更新してください。
  6. 接続確認では保存済みのvoice・style・韻律値を使った短い合成を行ってください。400の invalid_voice_style、invalid_request、 unsupported_parameterを設定不整合として提示し、401、429、502、timeout、cancelと区別して ください。音声本文、Bearer、会話本文をlog、metric label、設定JSONへ記録しないでください。
  7. 日本語・英語の設定ラベル、説明、validation error、アクセシビリティを更新してください。既存のWAV／PCM、 24 kHz mono s16le、incremental decode、artifact cleanup、再生停止動作を回帰させないでください。

テスト要件

  • 旧設定JSONが変更なしで読み込め、既定のvoice-only requestが従来どおり生成されること。
  • 4つの新fieldが通常HTTP TTSとLARM Session TTSの両方で正確にwire requestへ入り、未設定時は省略されること。
  • speed 0.5／2.0、pitch -0.15／0.15、intonation 0.0／2.0を受理し、境界外、NaN、infinity、型違いを拒否すること。
  • catalogのdefault、voice/style従属、追加field、簡易互換response、malformed JSON、過大response、401、timeoutを fixtureで検証すること。
  • voice変更時のstyle reset、catalog消失時の保存値維持、feminine／masculine表示と具体的voice ID保存をUI testで 検証すること。
  • cancelとbarge-in後に前turnの音声が再生されず、設定追加後も句の順序とlate-output fenceが維持されること。
  • repositoryの標準checkをすべて通すこと。LARM実機が未配備でもunit／fixture実装を止めず、live試験だけを明確に 分離すること。

実機受入

LARMの対応releaseがlocal-nodeへ配備された後にだけ、operator明示のlive testを実行してください。catalogから 2話者以上と複数styleを選び、default、speed変更、pitch変更、intonation変更のWAV再生を確認します。 追加VVMが未stagingなら、catalogに存在しない男性系voiceを合格条件に含めません。実機試験で得た音声、token、 生responseはrepositoryへcommitせず、結果にはrevision、選択voice/style、成功可否、latencyだけを残してください。

完了報告

最終報告には、変更した設定contract、catalog取得とfallback、request mapping、UI挙動、migration、実行したtestと 結果、未実施のlive gate、LARM側へ必要な追加事項を含めてください。自動test成功とlocal-node実機受入を混同せず、 未配備または追加VVM未同意を「実装失敗」とも「本番完了」とも扱わないでください。

調査時点のSAAA差分

  • CloudTtsProviderSettingsはmodel、voice、response format、authenticationを保持しますが、 style、speed、pitch、intonationをまだ保持しません。
  • cloud_tts.rsはspeech requestへmodel、input、voice、response_formatだけを送信します。
  • Harness設定はttsVoiceだけを保持し、LARM音声Sessionの一時TTS設定もvoiceだけを引き継ぎます。
  • 既存HTTP音声pipelineにはbounded response、WAV／PCM検証、incremental decode、cancel、native playbackの test基盤があります。これを拡張し、別実装へ置換しません。
