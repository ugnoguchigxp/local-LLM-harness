ContextStill 動的LLM Provider適用 実装指示書

LARMの利用者workloadがない時間をContextStillの継続処理へ使うため、ContextStillにLARM Agent Connection方式の動的LLM Providerを追加する実装指示です。ContextStillの従来Provider経路と SAAAを含む既存利用者の経路は変更せず、設定で明示した場合だけ新経路を使用します。

固定判断: ContextStillが動作するときは、SAAA用Residentを使い回さず、 llm-agent-worker Routeで二つ目のQwen 3.8 27Bを起動します。二つ目はResidentへ 変更せず、ContextStillのConnectionが存在する間だけHOTにします。現在のjob完了後にLARMの別 workloadを検出したとき、またはContextStillの処理待ちがなくなったときはConnectionを解放します。

要求と非要求

必須要求

  • LARM Service Activity APIがactiveまたはdrainingの間、新しいLLM処理を開始しない。
  • Activity APIがidleで処理対象がある間、ContextStillは一件ずつ継続して処理する。
  • ContextStillへlarm-agent-connection Provider adapterを追加し、claimで得た baseURL、model、短期apiKeyをOpenAI互換clientへ適用する。
  • 従来Providerの設定schema、生成処理、保存済み設定、既定動作を変更しない。
  • SAAAのcoding-default Profile、Resident Route、Native WebSocket経路を変更しない。
  • 停止、失敗、cancel、process終了の全経路でAgent Connectionを解放する。

今回行わないこと

  • ContextStillからProvider port 8080または8083へ直接接続しない。
  • 二つ目のQwenを新しいResidentとして登録しない。
  • SAAA process、画面focus、session、heartbeat、callbackからactivityを推測しない。
  • 動的Provider失敗時に、同じjobを従来Providerへ暗黙に再送しない。
  • ContextStillのためにsaaa.llm-stream.v1を実装しない。背景処理は同じHTTP Chat Completions endpointへ要求した形式に応じてJSONまたはOpenAI互換SSEを使う。

現状と変更点

LARMには、Profile discovery、Allocation、semantic readiness、短期credential、renew、releaseを 一体化したAgent Provider Connection APIが 実装済みです。本指示に基づくLARM source変更により、現在の config/local-node/agent-connections.yamlにはSAAA向けcoding-defaultを維持した まま、ContextStill向けworker Profileも追加されています。

実装は二箇所に分けます。LARM側は明示選択専用Profileを一つ追加し、ContextStill側は既存Provider abstractionへ新adapterを追加します。従来adapterを改造して動的接続を混在させてはいけません。

LARM側の実装指示

Agent Profileを追加する

config/local-node/agent-connections.yamlのagentProfilesへ次を追加します。 既存defaultAgentProfile: coding-defaultとcoding-default定義は一文字も 変更しません。 

  contextstill-background:
    description: ContextStill background Qwen 3.8 27B provider
    providers:
      - name: llm
        capability: llm.coding
        route: llm-agent-worker
        publicModel: qwen-agent-worker
        readiness: llm-inference

streamingProtocolは指定しません。llm-agent-workerは explicitOnly: trueで、primaryはqwen-worker-agent、fallbackは qwen-generalです。ContextStillはConnection作成時にallowFallback: false を指定するため、SAAA用Residentへ暗黙に流れません。

Runtimeとllama-swap設定は維持する

  • qwen-worker-agentの64K context、推定28 GB、同時request数1を維持する。
  • qwen-worker-slotは一度に一memberだけHOTという既存制約を維持する。
  • qwen-agentの既存alias qwen-agent-workerをpublic modelに使う。
  • ContextStill用の新port、LAN listener、systemd Resident unitを追加しない。
  • worker artifactが未stageの場合、ContextStillからdownloadやactivationを開始しない。

64Kを超える入力が実際に必要だと測定された場合だけ、別の明示Profileを llm-long-contextへ追加します。初期実装から256K workerを選ぶと推定40 GBとなり、 background用途に不要なmemory帯域と起動costを使うため採用しません。

ContextStill側 Provider adapter実装

設定

現行設定をそのままparseできることを必須とし、動的Providerは新しいdiscriminated variantとして 追加します。名称は例示であり、ContextStillの既存命名規則に合わせて構いません。 

{
  "provider": {
    "kind": "larm-agent-connection",
    "controlBaseURL": "http://gnosis.local:9810",
    "agentProfile": "contextstill-background",
    "audience": "saaa-desktop",
    "ttlSeconds": 300,
    "requestTimeoutMs": 300000
  }
}
  • ContextStillがlocal-node上で動く場合はaudience: same-hostとloopbackの controlBaseURLを使う。SAAAと同じMacまたはLAN hostなら audience: saaa-desktopを使う。
  • controlBaseURLはmDNS/DNS名または現在到達できるDHCP addressを設定し、Provider claimのbaseURLは設定で上書きしない。
  • 長期LARM_API_TOKENはlocal-nodeの匿名Agent lifecycleでは省略する。
  • 短期Provider tokenをfile、DB、telemetry、error、通常logへ保存しない。

Connection確立手順

  1. GET /healthとGET /readyをbounded timeoutで確認する。 /readyが503なら背景処理を開始せずbackoffする。
  2. 起動時およびcatalog revision変更後にGET /v2/agent-profilesを取得し、contractが agent-connection.v2、Profileがexplicit-only、Provider protocolが openai.chat-completions.v1であることを検証する。
  3. 一意でretry中は不変のIdempotency-Keyを付け、次のbodyでConnectionを作る。 HTTP 201と202の両方を成功として扱う。 
POST /v1/agent-connections
Idempotency-Key: contextstill-<run-id>-<attempt-id>
Content-Type: application/json

{
  "agentProfile": "contextstill-background",
  "explicitAgentProfile": true,
  "audience": "saaa-desktop",
  "client": "contextstill",
  "ttlSeconds": 300,
  "allowFallback": false,
  "deploymentPolicy": "existing-only"
}
  1. 202または非readyならresponseのConnection IDを使い、pendingまたは probingの間だけbounded pollする。failed、released、 expiredは成功へ戻らない。
  2. ready後、POST /v1/agent-connections/:id/claimへ {"format":"openai-provider-v1"}を送り、llm Providerを一件取得する。 claimへIdempotency-Keyを付けない。
  3. claim全体をstrictに検証し、configuration.fields.baseURL、 configuration.fields.model、credential.tokenだけを新しいOpenAI互換client instanceへ渡す。値を環境変数やglobal singletonへ書き込まない。

推論、renew、解放

  • POST {baseURL}/chat/completionsを使用し、modelはclaim値と完全一致、 Authorization: Bearer {credential.token}を付ける。
  • ContextStillの既存adapterが要求する形式を維持する。stream: falseまたは省略時は JSON、stream: true時はOpenAI互換SSEを同じLARM HTTP Gatewayから受け取る。 SAAA専用Native WebSocketをContextStillから流用しない。
  • 一つのworkerへ同時に複数requestを送らず、ContextStill内部queueもconcurrency 1にする。
  • 継続処理中はTTL 300秒に対して180秒を目安にrenewする。renewごとに新しい Idempotency-Keyを使い、成功直後にclaimを取り直してOpenAI clientを交換する。 renew前のtokenは再利用しない。
  • queueが空、job境界で別workloadを検出、明示停止、未回復error、process shutdownのいずれかで 新規jobを停止し、ConnectionをDELETEする。実行中jobはactivity変化だけでは中断しない。
  • DELETEはhandlerのfinally相当から独立した短いtimeoutで実行する。処理用 AbortSignalをcleanupへ再利用しない。

LARM Service Activityによるjob gate

ContextStillはLARM Service Activity API・ContextStill連携 実装計画のGET /v1/activityをjob境界で使用します。activityはSAAAのapplication状態ではなく、 LARM Gatewayを通るHTTP LLM・ASR・TTS requestとNative LLM WebSocket active runの合計です。 Provider daemonが起動中、Agent Connectionが存在、WebSocketがidle openという理由だけではactiveにしません。

ContextStill runner状態遷移
状態 開始条件 許可する処理 終了条件
INHIBITED activityがactive、draining、またはAPI error queueへの蓄積だけ。LLM requestとConnection作成は禁止 freshなidle response
STARTING activityがidleかつqueue非空 Profile検証、Connection作成、ready待ち、claim claim成功、timeout、error
RUNNING claim成功 concurrency 1で一件を処理し、次job前にactivityを再確認 job境界でactive、queue空、停止、未回復error
STOPPING RUNNINGまたはSTARTINGの終了条件 dequeue停止、Connection DELETE cleanup完了またはcleanup timeout

activity responseはsnapshotであり予約ではありません。idle取得後に別workloadが開始するraceは許容し、 実行中ContextStill jobは完了させます。response bodyを閉じた後、次jobの前にactivityを再確認し、 activeならConnectionを解放して待機します。SAAAからの通知、heartbeat、callbackは使用しません。

従来方式の互換性

  • 既存設定にkindがない場合の解釈を変えず、従来adapterを選ぶ。
  • 従来ProviderのURL、model、API key、streaming、retry、timeout既定値を変更しない。
  • 保存済み設定のmigrationを必須にせず、新variantを選んだ利用者だけ新fieldを要求する。
  • larm-agent-connectionから従来Providerへのfallbackは、別の明示設定がある場合でもjob境界 でだけ許可する。request timeout後の同一jobを自動再送しない。
  • Provider種別を戻すだけで従来方式へrollbackできるよう、データ形式をProvider固有に変更しない。

Qwen 3.8二基構成の判断

local-nodeの静的memory admission
項目 予約量 扱い
物理統合memory 128 GB node定義
host reserve 16 GB LLMへ割り当てない
Resident floor 47 GB Qwen 40 GB、Qwen ASR 5 GB、Whisper 1 GB、VOICEVOX 1 GB
ContextStill worker 28 GB Qwen 3.8 27B、64K
admission後の余力 37 GB 112 GB usable − 47 GB − 28 GB

静的見積りでは二基を安全に収容でき、既存のOn-demand LLM Worker Pool契約でもResident 27Bと64K worker 27Bの同時taskを実機検証済みです。このため、ContextStillが処理中 の二基構成を採用します。ただし起動ごとにLARM admissionがlive telemetryを確認し、不足時は resource_exhaustedを返してfail closedにします。見積りを根拠に強制起動してはいけません。

二基目の目的は単一jobの速度向上ではなく、SAAA用Residentの即時性、execution slot、context cacheを 背景処理から分離することです。ContextStill内の並列度は1のままとし、二基へ同じjobを複製しません。

失敗処理

代表的な応答とContextStillの動作
条件 動作
HTTP 429 Retry-Afterを尊重して同じConnectionでjobを再予約する。並列度を増やさない
HTTP 503 jitter付きbounded backoff。次回のactivity確認まで新規jobを開始しない
Provider token 401 一回だけclaimを取り直す。再度401ならConnectionを解放して再作成する
Connection 410 daemon boot epoch変更として古い状態を破棄し、新しいConnectionを作成する
model mismatch 400 claim値を使っていない実装bugとしてretryせず停止する
resource exhausted 従来ProviderやResidentへ迂回せず、queueを保持して次のidle windowで再試行する
job境界でservice active 新規jobとnetwork retryを開始せず、Connectionを解放してINHIBITEDへ遷移する

再試行はjob ID、attempt、Connection ID、error codeだけを構造化記録します。prompt、completion、 Authorization、claim body、screen由来データを通常logへ含めません。

受入条件

ContextStill単体test

  1. 既存設定fixtureが変更なしで読み込まれ、従来Providerへのrequest snapshotが変化しない。
  2. activity API error、invalid response、active、drainingではConnection作成もLLM requestも発生しない。
  3. freshなidle確認後に一つだけConnectionを作り、201と202の両経路でclaimまで進む。
  4. claimのbaseURL、model、tokenがOpenAI clientへそのまま適用され、tokenはlogへ出ない。
  5. renew後にclaimを取り直し、旧clientと旧tokenを破棄する。
  6. job境界のactive、推論error、cancel、shutdownの全経路でDELETEを一回以上試行する。
  7. 実行中に別workloadが始まっても現在jobは一度だけ完了し、次jobの開始前に解放する。
  8. 429、503、401、410を上記policyどおり処理し、暗黙の従来Provider fallbackを行わない。

LARM repository test

  1. Profile catalog testでcontextstill-backgroundが selectionPolicy: explicit-only、Routeがllm-agent-worker、modelが qwen-agent-workerであることを固定する。
  2. Profile省略時の既定が引き続きcoding-defaultであることを固定する。
  3. explicitAgentProfile: falseでContextStill Profileが409、trueで受理されることを検証する。
  4. allowFallback: falseでResidentへfallbackしないことを検証する。
  5. Profile追加後も既存SAAA entryのshapeと意味が変わらず、catalog revisionだけが更新される。

local-node実機canary

  1. 開始前にqwen-generalがHOT、qwen-worker-agentがCOLDであることを確認する。
  2. ContextStill Profileをcreate、poll、claimし、Bindingが llm-agent-worker → qwen-worker-agent、fallback falseであることを確認する。
  3. claimされたHTTP ProviderでJSONとSSEの両completionを要求どおり完了する。
  4. 実行中にqwen-generalのPID、health、SAAA Native WebSocket readinessが維持され、二つの Qwen Runtimeが同時に存在することを確認する。
  5. ContextStill job中に別workloadを開始し、現在job完了後は次jobを開始せずConnectionを解放する。
  6. release後、既定idle TTL内にworkerがCOLDとなり、ResidentはHOTのままであることを確認する。
  7. 試験中の429、OOM、Provider crashが0で、systemとaccelerator memory headroomを記録する。

実装順序と完了定義

  1. ContextStillにactivity gateと従来経路の回帰testを先に追加する。
  2. LARM catalogへContextStill Profileを追加し、repository testと文書checkを通す。
  3. ContextStillへAgent Connection adapterとstrict claim validationを追加する。
  4. fake LARMでlifecycle、renew、cancel、cleanup、error policyを完走する。
  5. local-nodeへcatalogだけを反映し、SAAA既定Profileが不変であることをcanaryする。
  6. ContextStillを明示opt-inして二基構成canaryを行い、memory headroomを確認する。
  7. 十分なidle windowで継続運転し、別workload開始時のjob境界切替を複数回確認してから既定化を判断する。

完了は「ContextStillが動的Providerを一度呼べた」時点ではありません。従来方式の無変更、service active時の次job抑止、短期credential更新、全終了経路のrelease、workerのidle回収、Residentの即時性を 自動testと実機canaryの両方で確認した時点とします。
