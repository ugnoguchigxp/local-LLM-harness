ContextStill HTTP Provider・Queue回復 実装指示書

ContextStillの継続処理を、LARMの標準OpenAI互換HTTP APIへ接続するための実装指示です。 旧Agent Connection、claim、短期credential、専用transportを新経路の依存にしません。 ContextStillは通常のOpenAI互換clientとして:9810/v1へ接続し、LARM内部のmodel brokerがResidentまたはPreferred Runtimeの選択、起動、参照数、回収を担当します。

固定する接続契約

{
  "provider": {
    "kind": "openai-compatible",
    "baseURL": "http://gnosis.local:9810/v1",
    "apiKeyEnv": "LARM_API_TOKEN",
    "model": "qwen-agent-worker",
    "requestTimeoutMs": 300000,
    "stream": true
  }
}
  • 同一hostではhttp://127.0.0.1:9810/v1、LANでは管理済みDNS名を使う。
  • engine port 8080、8083や旧static port 44448へ直接接続しない。
  • API keyを設定file、DB、telemetry、error、通常logへ保存しない。
  • 接続先originを越えてAuthorizationを転送しない。redirectは追跡しない。
  • modelはGET /v1/modelsの公開IDと完全一致させ、engine固有model名へ変換しない。
  • HTTP keep-alive clientをprocess単位で再利用し、jobごとのTCP/TLS接続作成を避ける。

LARM側は公開modelからRouteを厳密に一つ決めます。Residentは即時利用し、Preferred workerは必要時だけ起動します。割当IDや内部portをContextStillへ公開しません。

低遅延のrequest flow

  1. process起動時にbounded timeoutでGET /health、GET /ready、 GET /v1/modelsを確認する。jobごとにcatalogを取得しない。
  2. job境界でGET /v1/activityを確認し、active、draining、errorなら開始しない。
  3. POST /v1/chat/completionsへstream: trueで送信し、最初の有意味な choices[].delta.contentまたはtool deltaから処理を開始する。
  4. SSEをUTF-8 byte streamとして増分parseし、CRLF、任意chunk境界、複数data行を処理する。 finish_reasonと[DONE]の両方を確認するまで成功にしない。
  5. 利用者cancel、timeout、process shutdownではHTTP bodyをabortし、LARM側の内部参照解放を待たず UIまたはrunnerを先に解放する。次jobは同じresponse streamを再利用しない。
  6. job結果を一度だけ永続化した後、次jobをdequeueする前にactivityを再確認する。

JSON応答は非stream処理と小さいsystem task用に残します。最速応答を必要とする通常推論ではSSEを 既定にし、全文完成を待ってからUIや後段処理へ渡しません。ContextStill内のLLM並列度は1です。

Activityによるjob境界制御

ContextStill runner状態遷移
状態 開始条件 許可する処理 終了条件
INHIBITED activityがactive、draining、またはAPI error queueへの蓄積だけ freshなidle response
READY activityがidle、model catalog確認済み 一件だけdequeueしてHTTP request開始 request開始、Provider error、queue空
RUNNING HTTP request開始 一件をstream処理して一度だけ保存 完了、cancel、途中切断
BOUNDARY_CHECK 現在jobの永続化完了 activityとProvider世代を再確認 READY、INHIBITED、RECOVERING
RECOVERING infra起因pauseと新しい正常Provider世代 段階的なpause解除 canary成功または再度infra error

activityは予約ではなくsnapshotです。idle確認直後にSAAA workloadが始まるraceは許容し、実行中jobは 一度だけ完了させます。ただし次jobはfreshな境界確認まで開始しません。process、画面focus、heartbeat、 callbackや旧transportの接続状態からactivityを推測しません。

失敗分類とretry

代表的な失敗と処理
条件 分類 動作
接続不能、HTTP 502／503、起動待ち provider_unavailable business attemptを増やさず、jitter付きbounded backoff
HTTP 429 provider_busy Retry-Afterを尊重し、並列度を増やさない
HTTP 401／403 configuration_error retryせず停止し、secretまたはaudience修正を要求
model mismatch 400／404 contract_error retryや別modelへのfallbackをせず停止
SSE途中切断、無効JSON、[DONE]欠落 incomplete_response 結果を保存せず、同一jobの重複副作用を防いで再予約
利用者cancel cancelled business failureにせず終了し、自動再送しない

Provider不通をjob自身の失敗回数へ加算しません。infra retry budgetだけを別に記録し、上限到達時は provider_unavailable_exhaustedとしてpauseします。prompt、completion、Authorizationを 通常logへ含めません。

Provider世代回復後のQueue自動再開

GET /healthのreleaseCommit、configRevision、 bootEpochを組にしてProvider世代として保存し、GET /v1/release-convergenceのdesired／observed release一致とstageを照合します。どちらかの endpointが未提供、schema不一致、releaseがcanary_verified未満なら回復判定をfail closedにします。

  1. pause originがinfraで、reasonがallowlist内のjobだけを候補にする。
  2. 手動pause、入力不正、認証不正、契約不一致、business failureのjobは解除しない。
  3. 最後に失敗した世代と異なる正常世代を検出し、JSONとSSEの固定canaryを一度通す。
  4. 最古の候補を一件だけ再開し、business attemptは増やさずrecovery attemptを記録する。
  5. 一件が保存まで完了し、次job境界を再確認できた後だけ、再開幅を1、2、4の上限付きで広げる。
  6. 再度infra失敗したら新規解除を止め、解除済み未実行jobを同じinfra reasonでpauseへ戻す。

世代値だけの変化は復旧成功ではありません。完了証跡にはjob IDのhash、完了状態、 persistenceCount: 1、次境界再確認、release identityを含め、本文やsecretを含めません。

移行とrollback

  • 既存Provider adapterと保存済み設定は読み込み可能なまま維持し、新variantを明示選択する。
  • 旧larm-agent-connection設定を通常OpenAI Providerへ自動変換しない。
  • 新経路から従来Provider、旧static port、旧transportへ暗黙fallbackしない。
  • Provider種別を明示的に戻せばrollbackできるよう、job result schemaをProvider非依存に保つ。
  • 新規機能、再接続改善、性能改善はHTTP経路だけへ追加する。

受入条件

ContextStill単体test

  1. 旧設定fixtureが変更なしで読み込め、新HTTP variantはbase URL、secret参照、modelをstrict検証する。
  2. 独自Profile、Connection、claim、旧transportを持たないHTTP fixtureでJSONとSSEを完了する。
  3. SSEの任意chunk境界、tool delta、finish、[DONE]、途中切断、cancelを検証する。
  4. Provider不通でbusiness attemptが増えず、infra起因だけが専用reasonでpauseされる。
  5. 同一世代や未検証世代でpause解除せず、新しいcanary済み世代で最初の一件だけ解除する。
  6. 手動・business起因pauseを解除せず、canary失敗時は段階展開を停止する。
  7. 一件のresultが一度だけ保存され、次job開始前にactivityを再確認する。

LARM repository・実機canary

  1. GET /v1/modelsにqwen-agent-workerが一意に掲載される。
  2. allocation headerなしでJSONとSSEが完了し、SSEはfinishと[DONE]を返す。
  3. 公開modelがPreferred Routeへ一致し、同時request数1と内部参照解放を確認する。
  4. :44448を監視せず、:9810のcatalog、JSON、SSEを監視する。
  5. 署名済みreleaseをroot activatorが切替え、identity一致とcanary完了を記録する。
  6. ContextStillのinfra起因paused jobを一件だけ再開し、保存一回と次境界確認を記録する。

実装順序と完了定義

  1. 共通OpenAI HTTP client、SSE parser、cancel、設定schemaを単体fixtureで完成させる。
  2. activity gateと失敗分類を接続し、business attemptとinfra retryを分離する。
  3. Provider世代監視と一件からの段階的Queue回復を実装する。
  4. LARMの署名済みreleaseをliveへ収束させ、JSON／SSE canaryを通す。
  5. ContextStill実jobを一件完了し、一度だけ保存、次境界確認、release identityを証跡化する。
  6. 24時間のHTTP経路soak後、利用が0の旧transport・claim consumer codeを削除する。

完了はsource test、push、shadow E2E、HTTP canaryだけではありません。承認済みcommitとlive identityが 一致し、JSON／SSE canary、ContextStill実job一件、保存一回、次境界確認まで揃った時点です。 それまでは実装を完了扱いせず、旧経路も削除しません。
