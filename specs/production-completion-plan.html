LARM Production Completion 実装計画

Local AI Providerコンセプトに対して残るrepository実装、 local-node実機への適用、commissioning、SLO校正、Ambient client canaryを、stable昇格まで 一つの順序付き工程として定義します。Milestone 15–21で完成したAllocation、Gateway、artifact lifecycle、release toolingを作り直さず、未収束の境界だけを閉じます。

監査時点のbaseline

Repository側の主要contractは実装済みで、bun run checkは266 test、729 assertion、失敗0で完了しました。一方、2026年8月29日のread-only確認では、 larm-daemon.service、port 9810、 /etc/larm/larm.envが存在せず、production Gatewayは未導入でした。 Qwen TTSはPreferred定義に反してactiveかつenabledでした。

計画時のlive Provider unitはport 8080から8084を全interfaceでlistenし、当時のhost準備 scriptもこれらをLAN CIDRへ許可していました。この状態は移行中のdirect Provider rollbackには使えますが、コンセプトの「通常の利用側は安定Gatewayを使い、個別Provider portを扱わない」という最終境界を network levelでは強制していません。

完了時の状態

  • Ambient clientはcapabilityとrouteをLARMへ渡し、個別Provider portやservice名を保持しない。
  • LLM、STT、TTS Providerはlocal-nodeのloopbackだけでlistenする。
  • LARMのproduction unitは0.0.0.0:9810でlistenし、認証済みConnection requestのoriginから SAAA向けGateway URLを生成する。LAN IPを固定または広告設定へ保存しない。API・management tokenを必須にし、port 9810はreview済み LAN CIDRだけを許可する。LAN境界外へ広げる場合はTLS終端を別decisionで必須とする。
  • Qwen 3.8 27B、Qwen ASR、VOICEVOXはResidentとしてboot後に利用可能である。
  • 27B workersとQwen TTSはCOLDを許容し、明示routeまたは許可済みfallbackでだけ起動する。
  • release後のidle TTLでPreferredを回収し、active AllocationがあるRuntimeは停止しない。
  • commit、config revision、boot epoch、runtime releaseを固定した証跡でacceptanceを再現できる。
  • SLO逸脱、fallback、epoch変化、operation leakのいずれかでcanaryがfail closedする。
  • stable昇格後もLARMだけをrollbackでき、Resident Providerを一括restartしない。

全工程の制約

  • モデルweight、binary、cache、log、prompt、transcript、音声、raw benchmarkをcommitしない。
  • live mutationはclean commitとreview済みplanからだけ実施する。
  • このdual-boot hostを配備automationからrebootしない。
  • Resident serviceを一括restartしない。変更したunitだけを一つずつattendedで適用する。
  • Qwen 3.8 27BのResident default、通常・リアルタイム共通方針を変更しない。
  • APIから任意URL、path、service、commandを受け取る経路を追加しない。
  • credential値を標準出力、Spec、Git、benchmark summaryへ保存しない。
  • firewall rule削除、service停止、traffic切替は対象とrollbackを表示してoperator確認後に行う。
  • 各Milestoneは前工程のexit criteriaを満たすまでproduction側へ進めない。

Milestone 22: Contract and network hardening

目的
stable Gatewayを通常clientの唯一のdata planeとし、運用詳細と個別portを通常経路から外す。
変更範囲
Daemon公開schema、systemd unit、host network tooling、静的検査
live mutation
なし。ここではdesired stateと検証toolだけをcommitする

実装項目

  1. 一般向け/runtimes、/runtimes/:id、/stateから deployment、service、model ID、個別endpointなどの運用詳細を除外します。運用上必要な情報はmanagement tokenで保護したinspection responseへ分離するか、local journalだけで観測します。
  2. これらのunversioned responseを狭める前に、repository内参照clientとshadow evidenceでconsumerを棚卸します。運用詳細への依存がある場合は、management token保護のinspection APIへ移行してから一般responseを縮小し、無告知のbreaking changeにしません。
  3. Allocationの公開responseは現在どおりendpointを除外し、Gateway requestは x-larm-allocation-idとcapabilityだけで成立させます。互換用resolve APIは直ちに削除せず、stable clientが利用していないことをcanary evidenceで確認してからdeprecationを判断します。
  4. llama-server、Qwen ASR、Qwen TTS、VOICEVOX、llama-swapのproduction unitを 127.0.0.1 bindへ変更します。IPv6を使う場合もloopbackだけを明示します。
  5. prepare-host.shから個別Provider portの恒久LAN allowを除きます。既存hostに残るruleは暗黙削除せず、現在値、削除候補、confirmation digestを出すnetwork convergence toolで扱います。
  6. preflightへ全Providerのlisten address、unit digest、enabled・active状態、UFW読取可否を追加します。 privilege不足は「安全」とみなさずunknownとして記録します。
  7. operations checkへ、production Provider unitのwildcard bind、Provider portのLAN allow、一般introspection schemaへのdeployment詳細再混入を拒否するtestを追加します。
  8. VOICEVOX COREだけでなく、運用者が取得する0.vvmのmodel release、配布元、SHA-256、利用規約同意を必要とする手順をsource-only metadataに固定します。未検証bundleはpreflightでunknownではなくfailとします。
  9. OpenAPI、参照client、API仕様、rollback手順を新しい公開境界に合わせます。

受入条件

  • bun run checkが成功する。
  • fixtureを使うnetwork plan testが、対象外ruleやfilesystem rootを変更しない。
  • 一般向けRuntime・state responseにservice、endpoint、model IDが含まれない。
  • 公開schemaに依存するconsumerの移行先があり、contract testが両境界を固定している。
  • 0.vvmのidentityとchecksumが固定され、preflightが実fileと一致を検証する。
  • GatewayのLLM、STT、TTS回帰testは固定Bindingを使用し続ける。
  • このMilestoneのcommitだけではlive Providerのbind addressを変更しない。

Milestone 23: Versioned production deployment

目的
LARM daemon、credential、unit、release pointerをlocal-nodeへ安全に導入する。
entry criteria
Milestone 22のclean commit、全check成功、rollback先とoperator backupの確保
変更対象
LARM daemonだけ。Resident Providerはこの工程でrestartしない

手順

  1. preflight-larm.shを再実行し、commit、candidate config revision、disk、unit、credential、port owner、Qwen TTS driftをrepository外JSONへ保存します。
  2. 既存unitとrelease pointerがある場合はoperator管理領域へ退避し、復元commandを記録します。
  3. install-services.shを実行してunit、polkit、directory、management credentialを配置します。再実行でcredentialを変更せず、Qwen TTSをdisableへ収束することを確認します。
  4. release-larm.sh planのcommit、target、dirty、cleanup候補をreviewし、必要な場合だけ表示された cleanup digestを指定してapplyします。
  5. release manifestのcommit、LARM version、Bun version、lockfile digest、dependency tree digest、config revisionと、 /healthのidentityが一致することを確認します。
  6. Qwen TTSがactiveなら、既存のdirect利用がないことをoperatorが確認した後だけstopします。disableだけを 完了扱いにせず、desired COLDまで確認します。

exit criteria

  • larm-daemon.serviceがloaded、enabled、activeである。
  • 0.0.0.0:9810のownerが導入したdaemonである。
  • credentialがregular file、mode 0640、期待owner・groupであり、値は表示されない。
  • /healthと/readyがrelease identityを返す。
  • Resident ProviderのPIDが変わらず、release有効化後のdaemon boot epochがsmoke中に固定される。
  • Qwen TTSはdisabledかつinactiveである。

rollback

新releaseがreadyにならなければrelease toolの自動回復を確認し、必要なら release-larm.sh rollbackでLARMだけを前世代へ戻します。初回導入で前世代がない場合も、Provider processとmodel dataは削除・restartせず、daemonを停止して作成したcurrent pointerを除去し、Ambient trafficをdirect経路のまま維持します。

Milestone 25: SLO contract and calibration

目的
観測だけのbenchmarkを、version管理されたfail-closed release gateへ変える。
entry criteria
Milestone 24の機能acceptance完了
原則
実測前にthresholdを仮定しない

repository実装

  1. SLO schemaにprompt class、token上限、concurrency、iteration下限、TTFB p95、total p95、startup、queue、minimum memory headroom、maximum error rate、fallback許可を定義します。
  2. local-node用thresholdをversion管理するmanifestを追加します。thresholdごとに測定commit、config revision、release、sample数、測定日時、rollback値を関連付けます。
  3. benchmark summaryからraw output pathなどhost固有・高cardinality情報を除いた匿名化結果を生成し、acceptance結果はSpec HTMLへ記録します。raw sampleはrepository外のoperator管理領域へmode 0600で 保持します。
  4. canary gateへSLO comparatorを追加し、identity不一致、sample不足、NaN、missing metric、fallback、epoch変化、latency・memory・error率逸脱をすべて失敗にします。
  5. fixtureで境界値、単位違い、古いconfig revision、部分summaryを拒否するtestを追加します。

校正手順

  1. 固定short prompt、同一token上限、concurrency 1でwarm-upと測定runを分離する。
  2. 通常LLM、リアルタイム相当、STT、通常TTSを別seriesとして測定する。
  3. memory headroom、queue、Provider 429、gateway overhead、fallback件数を同時に記録する。
  4. 複数runの分布からthresholdとrollback値をreviewし、測定evidenceと同じcommitで固定する。
  5. threshold commitに対してcanary gateを再実行し、自己矛盾がないことを確認する。

exit criteria

  • thresholdがすべて実測値とevidenceを持つ。
  • canary gateが正常fixtureを受理し、各逸脱fixtureを個別に拒否する。
  • production benchmarkが同じidentityと条件で再実行可能である。
  • SLOを満たすためにResident defaultを暗黙にoptional modelへ変更していない。

Milestone 26: Ambient shadow and canary

目的
上位clientをdirect ProviderからAllocation固定Gatewayへ段階移行する。
entry criteria
Milestone 25のSLO gate成功、direct rollback経路の確認
所有境界
Task判断とconversationはAmbient側、Runtime決定とBindingはLARM側
  1. 推論を行わないshadowで、既存経路とLARMのroute、Runtime、releaseを比較します。不一致は自動切替せず、 route catalogか上位intentのどちらを修正するか記録します。
  2. 参照clientを使う非音声canaryを少数taskへ限定し、期限付きAllocationと必ず実行されるreleaseを確認します。
  3. 非音声soak後にSTT・通常TTSを追加し、最後に明示的なexpressive TTSだけを追加します。
  4. 各段階でSLO、error budget、fallback、boot epoch、active Allocation、execution queue、artifact operation、memory headroomを評価します。
  5. error budget、identity、leak、fallback policy、latency、memoryのいずれかが不適合なら、対象trafficだけを direct Providerへ戻し、必要ならLARM releaseをrollbackします。

exit criteria

  • shadow差分が0、またはreview済みの説明を持つ。
  • 非音声と音声の両canaryがSLO gateを通過する。
  • soak終了時にAllocation、queue、artifact operationのleakが0である。
  • 通常LLMとリアルタイム相当のlive BindingがQwen 3.8 27Bである。
  • Ambient側から個別port、service名、artifact pathへの依存が除去されている。

Milestone 27: Gateway-only cutover and stable promotion

目的
移行用direct Provider経路を閉じ、コンセプトの最終network境界を適用する。
entry criteria
Milestone 26のAmbient canary成功と、Gateway経由rollback手順のreview
live risk
Provider unit restartとfirewall rule変更を伴うためattendedで一つずつ実施
  1. network convergence toolのplanで現在のlistener、UFW rule、変更対象、confirmation digestを確認します。
  2. Providerを一つずつrestartしてloopback bindを適用します。各restart後にLARM health、該当capability smoke、Resident default、memoryを確認してから次へ進みます。
  3. 個別Provider portのLAN allow ruleをreview済みdigest付きで削除し、review済みLAN CIDRからport 9810へのallow ruleだけを維持します。
  4. 別hostからProvider portへ接続できないこと、LARM Gatewayの未認証control requestが401になること、 API token付きrequestとclaimの短期tokenによるtaskが成功することを確認します。UFW状態を読めない場合は stableへ昇格しません。
  5. 最終canaryとSLO gateを実行し、stable release gateとcommissioning evidenceを更新します。

stable Definition of Done

  • repository、commissioning、SLO、Ambient canaryの全gateが成功している。
  • port 8080–8084はloopback以外でlistenせず、Provider用LAN allow ruleがない。
  • 通常clientが接続するdata planeはLARMだけであり、port 9810にはreview済みLAN CIDRのallow ruleと必須credentialがある。
  • Qwen TTSとoptional workersは不要時にCOLDへ戻る。
  • LARM rollbackがResident Providerをrestartせず、同じGateway contractを復元する。
  • 未解決の逸脱、暫定threshold、手動例外がない。

network rollback

loopback切替後の不具合では、まずLARM releaseをrollbackします。それでもGatewayが回復しない場合だけ、network planで保存したreview済み旧状態へ対象Provider一つを戻し、限定CIDRからの暫定direct経路を復元します。 wildcard公開や全port一括開放をrollback手順にしません。

停止条件

次のいずれかに該当した時点で後続工程を停止し、原因修正またはrollbackを行います。

  • Qwen 3.8 27B、Qwen ASR、VOICEVOXのResident healthが悪化した。
  • release identity、config revision、boot epochの対応が証明できない。
  • 管理credential、prompt、transcript、audio、raw logが出力またはGitへ混入した。
  • Allocation、queue、artifact operation、Preferred processのleakが残った。
  • SLO thresholdを満たすために未承認fallbackやRuntime変更が必要になった。
  • firewallまたはlisten状態を検証する権限がなく、Gateway-only境界を証明できない。
  • rollback先が存在しない、またはrollbackを実行してもreadyを復元できない。
