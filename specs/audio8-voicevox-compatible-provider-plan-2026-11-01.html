Audio8日本語TTS Provider：共通API・一時比較・VOICEVOXへの復帰

2026-11-01。状態は承認済み声による標準経路への配備・実API検証済み。利用者の要望は、常時warmのAudio8をVOICEVOXと同じ呼出し方式で利用し、VOICEVOXへすぐ戻せる構成、および失う機能の明示である。本書では独立したAudio8 Providerを追加し、既存VOICEVOXを復帰先として保持する方式を採る。比較用Providerの実装と一時起動での同文生成を完了した。声の比較後、承認された候補7と胸のEQ・1.43倍速をAudio8の既定voice presetに設定した。標準の日本語TTSをこの声へ切り替えた。以下の比較時点の記録と切替設定を区別する。

承認済み声を標準経路へ切り替える設定

利用者の切替指示により、tts-default と日本語 tts を持つ複合 Agent Profile は tts-audio8 を明示選択し、publicModel を audio8-tts-realistic-0.6b とする。汎用 tts-default route の候補も Audio8 にする。参照声は audio8-ja-butler-v1、テンポ1.43倍、胸のEQは160 Hz +4.5 dB、300 Hz +2.5 dB。音程は変更しない。

Audio8 は systemd user scope の audio8-tts.service、内部ポート8097、warm 最低数1とする。VOICEVOX は元のサービス・モデル・話者設定を保持し、warm 最低数0、idle TTL 0へ変更する。戻すための tts-voicevox Profile と route を保持する。標準選択と warm 設定を完全に戻す際は、保存した切替前の署名済みリリースを再提出する。新しい Connection と descriptor を取得し、VOICEVOX の数値話者IDや未対応の速度指定を送らない。

既存の SAAA checkout に未コミット変更があるため consumer 実装は変更しない。LARM の共通 API とカタログを更新する。consumer が古い model・voice を固定していた場合には再接続後も設定変更が必要となり、その動作は別途確認する。

利用者の追記：二重warmは比較中だけ

同日の実装開始指示で、両方を常時warmにする案は撤回された。今回の比較ではVOICEVOXを既存のまま使い、Audio8を必要な間だけ起動して終了時に停止する。常用する段階では選択した片方だけをwarmにする。以下の即時復帰手順で両方のConnectionを保持する記述は、比較・切替試験の間だけに限定する。非選択側を停止した常用運転での復帰には、保存済み設定での再起動とモデル読込時間を要し、常時二重warmの無待ち復帰とは区別する。

実装した比較用Audio8 runtimeはminInstances=0、idleTtlSeconds=0。現在のVOICEVOX標準経路は維持し、既定の変更やVOICEVOX停止は行っていない。常用選択のconsumer UIや切替制御は今回の比較Provider実装に含めていない。

採用する構成

Agent ProfileのProvider subsetを要求し、route、runtime、backendを解決する既存方式を使う。Audio8とVOICEVOXはそれぞれ別runtime・別systemd unitで管理する。公開protocolは両方 openai.audio-speech.v1、Provider名は tts、能力は speech.tts に揃える。モデルと話者の識別子は実際の選択を示す値を使用し、Audio8をvoicevox-coreや春日部つむぎとして扱わない。

提案する解決経路。Audio8の行は追加案で、VOICEVOXの行は現行構成。
要求Profile／Provider route runtime／backend publicModel
tts-audio8／tts tts-audio8（explicitOnly） audio8-tts-realistic／audio8-tts.service audio8-tts-realistic-0.6b
tts-default／tts tts-voicevox（explicitOnly） voicevox-tts／voicevox-tts.service voicevox-core

移行時は音声用Connectionだけを取得する。LLM・ASR・英語KittenTTSのProfileや既存Allocationを切り替える必要はない。現在のtts-defaultだけでなく、複合Agent Profileのttsもtts-voicevoxを直接参照しているため、routes.yamlのtts-defaultだけを書き換えても全consumerがAudio8へ移行するわけではない。consumerが共通のTTS呼出し処理へ、選んだProvider descriptorを渡す方式を基本とする。

Audio8は比較中だけ一時起動し、warm minInstances=0、idleTtlSeconds=0、preferred、managed、単一process、同時要求1、待ち行列0、メモリ見積もり8 GiB相当とする。常用時は選択した片方だけをwarmにし、非選択側は停止する。LLMや画像のswapGroupには入れず、音声要求にLLMの占有枠を使わない。profile retentionとConnection期限を考慮し、比較中だけ両方のConnectionを保持する。常用時は非選択のConnectionを解放し、そのruntimeを停止する。単にunitの起動状態だけを利用可能性としない。実装時はLARM既存の資源制限・quarantine・release管理に従う。

GET /v1/models 実際に利用できるmodelの一覧。 audio8-tts-realistic-0.6b。

consumerはclaimから得たbaseUrl、credential、modelを使用し、voice一覧からそのmodelの既定voiceを選ぶ。同じ関数で両Providerを呼べるが、model・voice・tokenまで同一値に固定する設計ではない。現行のscoped tokenはmodelに結び付いているため、Audio8のtokenにvoicevox-coreを渡すとmodel_mismatchになる。切替時はdescriptor一式を交換する。 

// 共通の呼出し。providerとcatalogは選択したエンジンのclaim・一覧から得る。
fetch(`${provider.baseUrl}/audio/speech`, {
  method: "POST",
  headers: {
    authorization: `Bearer ${provider.credential.token}`,
    "content-type": "application/json"
  },
  body: JSON.stringify({
    model: provider.model,
    input: "大丈夫。ゆっくり、一緒に進めましょう。",
    voice: catalog.default_voice,
    response_format: "pcm",
    speed: 1.0,
    stream: false,
    language: "ja"
  })
});

PCMのContent-Typeは audio/pcm;rate=24000;channels=1;format=s16le、X-Audio-Sample-Rateは24000、X-Audio-Sample-Formatはs16leとする。現行gatewayはPCM応答を24 kHzとして扱うため、Audio8の44.1 kHzデータをそのまま流すと再生速度と音程が壊れる。ヘッダだけを変更せず、実波形を高品質resamplerで24 kHzへ変換する。互換モードのWAVも24 kHzに揃える。元の44.1 kHz試聴音声との差は採用前にA/B試聴する。44.1 kHzネイティブ出力の公開は後続拡張として分ける。

Audio8のvoice一覧案は次の形。voice idは固定参照音声・正確なtranscript・checksumを含む外部assetに結び付け、変更時は版管理する。初版の固定話者はAudio8生成音声由来の参照codesを2種類用意した。以下は01の契約例で、実装は02も返す。安定した声として採用するかは再試聴で判断する。 

{
  "default_voice": "audio8-ja-01",
  "voices": [{
    "id": "audio8-ja-01", "name": "audio8-ja-01",
    "display_name": "Audio8 日本語 01", "language": "ja",
    "voice_presentation": "unspecified", "styles": [],
    "capabilities": {
      "speed": {"minimum": 1, "maximum": 1, "default": 1},
      "pitch_scale": {"minimum": 0, "maximum": 0, "default": 0},
      "intonation_scale": {"minimum": 1, "maximum": 1, "default": 1}
    }
  }]
}

上の固定範囲は、既定値を送るconsumerとの共通化に使う。調整できるという表示にはしない。対応範囲外の指定は400 unsupported_parameterで拒否し、黙って無視しない。styleは省略のみを基本とし、normalを受け付ける場合も自然な発話という既定の別名に限定する。gatewayは解決したruntimeのspeech制御契約を検証する実装へ変更した。Audio8のpitch_scale=0とintonation_scale=1は受理し、style指定は拒否する。

VOICEVOXへの即時復帰

  1. 移行前にVOICEVOXの有効なtts-only Connectionとclaimを確保し、healthと実際のWAV／PCM生成を確認する。モデルファイル・VVM・unit・routeをそのまま復帰用に保持する。
  2. Audio8用の別Connectionをproviders=["tts"]で作り、準備できたdescriptorと専用のvoice設定を別に保持する。両方のConnectionとtokenの有効期限をrenewする。
  3. 選択設定 japaneseTtsEngine=audio8|voicevox はconsumer側の提案名とし、既存LARM設定キーと偽らない。切替は新しい発話からactive descriptorを一括交換する。baseUrlだけを変え、古いmodel・voice・tokenを残す操作は禁止する。
  4. 戻す際はVOICEVOXのdescriptor、保存済みvoice・style・調整値に戻す。健康で空き枠があるwarm Providerなら再ダウンロードやモデル再ロードを待たず、次の発話をVOICEVOXへ送れる。実際の復帰所要時間は試験で確認する。
  5. 実行中のAudio8発話は完了させるか、明示取消して再生を止める。取消処理後もworkerがGPUを使用している間はその枠を解放しない。古い発話を自動再送せず、二重再生を防止する。

既存Connection・tokenは選択時のruntime世代に結び付いているため、routeの候補順を変えただけで既存発話が別エンジンへ移るとは考えない。将来、標準Profileの既定をAudio8へ変更する場合はrouteとpublicModelをセットで更新し、新規Connectionを取得する。切替直後も旧VOICEVOX Connectionを復帰用に残す。backendを隠して自動fallbackする機構は初版に入れず、エラー時の変更先を利用者が選べる形にする。

実装境界と運用要件

固定話者は参照音声と正確なtranscriptを選定し、固定したmodel／codec revisionで事前にreference_codesへ変換する案とする。外部manifestに参照音声・transcript・codesのchecksumとrevisionを記録し、Providerは起動時に検証済みcodesを読み込んで再利用する。毎要求で参照音声をencodeしない。参照なしで測った従来のメモリ・速度がそのまま成立するとは扱わず、参照codesを含む入力予算、生成速度、起動・常駐メモリを再測定して8 GiBの初期見積もりを確かめる。

提案するadapterはapps/audio8-ttsに置き、実行環境、モデル重み、参照声、checksum付きmanifestはrepository外に置く。固定revisionのAudio8、独立venvと依存lock、ROCmのfusion回避・MIOPEN_FIND_MODE=FASTを適用する。本体とcodec、参照声を起動時にロードする。health・claim・readinessによる試験音声の自動生成は行わず、warmはロード済みの意味とする。最初の合成で形状別の準備費用が残ることはhealth成功と区別する。

GPU workerは1つに直列化し、ASGI側でhealthと取消を処理できるようにする。生成は有限のmax_new_tokensとdeadlineで制限し、EOSに到達しない音声、NaN、空音声、過大出力を成功として返さない。初期案は150文字、最大650 frames、Provider deadline 90秒。実生成は30秒程度までの音声を上限とし、gatewayとconsumerのtimeoutをそれより長く整合させる。現在のgateway既定300秒に頼らず、consumer側のtimeoutも確認する。

client disconnect・deadline・releaseをworkerのstopping criteriaへ伝える。codec実行中など即時中断できないGPU処理では、処理の終了を待って枠を解放する。途中WAVや途中PCMを返さず、成功ヘッダを送る前に生成と24 kHzへの変換・検証を終える。同時要求は429＋Retry-After:1、準備中は503＋Retry-After:1、不正・未対応指定は400、発話不能な本文は422、本文64 KiB超は413、生成未完了・不正音声は502として分類する。合成を伴わないGETには推論枠を取得しない。

LARM側はapp-gateway-request.tsのmodel名によるvoicevox専用判定を、解決したruntimeの制御契約に基づく検証へ改める。runtime schemaへ任意のspeech制御契約を追加し、modelの文字列だけで許可しない。一般schemaの型・範囲検査は入口で行い、対応機能の検査はscoped token／Allocationからruntimeを確定してから行う。VOICEVOXの全範囲、Audio8の固定範囲、KittenTTSの話速だけという違いを宣言し、未知のruntimeは未宣言の調整を拒否する。これにより既存Providerへの誤った制御の透過を防ぐ。

voice一覧の汎用schemaは既に存在するため、VOICEVOXの数値ID形式を全Providerへ強制しない。PCMの24 kHz契約は維持する。実エンジンの監査はtokenに結び付くruntime/modelで記録し、新しい任意の応答headerに依存しない。X-VOICEVOX-Creditの透過はVOICEVOXで維持する。Audio8のクレジットを独自headerへ追加する場合はgatewayのresponse header allowlistとconsumerを合わせて変更する。

昇格条件と検証順序

  1. Providerを別portに起動して、WAV／PCMが実際に24 kHz・mono・s16leであること、再生速度・音程・clipが正しいことを検証する。44.1 kHz原音と24 kHz互換出力を同文で試聴する。portは既存・オンデマンド停止中を含む構成台帳と照合して決め、VOICEVOXの8084を再利用しない。
  2. 固定参照声を選定し、異なる日本語文章・複数seed・再起動後で声質の継続性と読みを確認する。VOICEVOX音声を無断で参照声に転用しない。現状の参照なし6サンプルだけで固定voice対応を完了扱いにしない。
  3. 同じcontract試験を両Providerへ実行し、形式、カタログ、既定値、未知voice、未対応調整、150文字境界、busy、起動中、EOSなし、取消中のslot保持、OOM後の回復、healthで合成しないことを確認する。VOICEVOXの数値voice/style指定と既存範囲の回帰試験を維持する。
  4. LARM経由のclaim、model拘束、音声転送、voices取得を試し、Audio8→VOICEVOX→Audio8で設定と再生が復元できることを確認する。古いtokenが新しいruntimeへすり替わらないことを確認する。
  5. 代表的な日本語文と数字・固有名詞を同文比較し、最初の再生開始時間、全文完成時間、読みの不一致、長時間warm後のメモリ、LLMとの同時GPU利用を測る。反復とrollbackの所要時間を保存する。

固定参照bankは /srv/ai/models/Edge0/audio8-ja-voices-v2 に準備し、sourceのvoice-manifest.jsonと全参照assetのchecksumを照合する。旧bankを保持し、差し替えで上書きしない。参照07を準備済み試聴directoryから取り込むため、常用時にQwenを起動する必要はない。FFmpegのatempo・equalizerを準備時に検査し、実APIでは処理失敗を502、期限切れ・cancelを既存のworker寿命管理で扱う。

実機検証ではvoiceとspeedを省略した通常のPOSTで出迎え文を生成し、承認された試聴版と7.22秒のPCMデータが完全一致した。最大sample差0、波形相関1.0。検証結果は /srv/ai/results/larm/tts/2026-11-01-audio8-default-butler-v1 に保存した。一時起動後Audio8は停止し、VOICEVOXは元の6話者のままhealthyだった。

この変更はAudio8 Providerの既定声の設定であり、tts-defaultのVOICEVOX経路と稼働中LARMのreleaseは保持している。Audio8のunitは未登録・未常駐で、次回この実装を起動すると新しい既定声を使う。参照bankのパスとproviderConfigRevisionもv2へ更新し、正式配備時の固定設定として扱う。
