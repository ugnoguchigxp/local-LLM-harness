SAAAの最新要求は、旧WebSocket前提のMVP 2.6 readiness資料ではなく、 spec/docs/larm-live-feature-verification.mdにある2026-09-16の実機検証を正本として読む。 この検証は稼働release be5e86272165f4e13e69f4da204b1425486c6070に対するもので、 現在のLARMソースより古い。したがって、旧releaseの失敗を現在のソース不具合と断定せず、 ソース対応済みと配備後未検証を分ける。

SAAAが期待する安定境界

  • 通常data planeはOpenAI互換HTTPの POST /v1/chat/completions、POST /v1/audio/transcriptions、 POST /v1/audio/speechで利用できること。
  • LLMはJSONとSSE、分割tool arguments、tool結果からの継続、finish reason、 [DONE]、途中切断の失敗判定を保証すること。
  • ASR、LLM、TTSは独立して選択・fallbackでき、一機能の停止で他機能を利用不能にしないこと。
  • model、voice、形式、対応parameter、ready／busy／unavailable、retry目安を機械判定できること。
  • 通常推論とPersonal State拡張を分離し、独自保証を要求したturnを保証なしの通常成功へ降格しないこと。
  • create、renew、release、cancelを冪等かつ期限付きにし、HTTP切断と遠隔計算停止を別状態として照会できること。

LARM側の回答と未完了境界は SAAA向けAPI契約回答にまとまっている。

共同受入で必要な証跡

  1. 配備release commitと検証対象source commitを一致させる。
  2. 公開modelごとに短文、SSE、tool往復、Structured Outputs、途中切断を確認する。
  3. ASR、voice discovery、WAV、PCM、TTS初回音声、cancelをcold／warmで確認する。
  4. Connectionのcreate、ready、claim、renew、releaseと、更新・解放後credentialの失効を確認する。
  5. Personal Stateは合成sourceでsubject分離、応答紛失、再起動、取消、遅延応答、全層forgetを確認する。
  6. 容量不足、起動待ち、429／409／503、retry budget、機能単位fallbackを共同fixtureで確認する。
  7. 秘密、本文、credential、allocation IDを証跡へ残さず、未確認項目を成功へ丸めない。

古い資料の扱い

SAAAのmvp-2.6-release-evidence.htmlと旧operations runbookは、WebSocket経路と旧canary commandを前提とする履歴資料である。G1／G2／G3という安全思想は参考になるが、現在の実行手順や現行API要求には使わない。 現行判断はHTTP API review、2026-09-16 live verification、Personal State製品接続記録を優先する。
