動的Provider再設計案：WSとHTTP SSEを一つの推論経路で提供する

2026-09-06。状態は設計提案。現行コードとliveを読み取り調査した。実装、配備、推論canary、consumer完了の検証は今回行っていない。既存の未commit文書は変更しない。

結論

Rustの全面撤去を先に行う根拠はない。LARM本体は既にBun／TypeScriptであり、調査した推論系はllama.cpp派生のC++ engineとTypeScriptのnative companionで構成される。ContextStillのRust実装にはProvider不通を通常の試行回数に加算する設計があるが、これは言語変更では解決しない。

推奨は、Bun／TypeScriptの単一Gatewayで接続・実行枠・中断を管理し、同じllama-serverのHTTP SSEを入力としてJSON、SSE、WSを提供する構成である。モデル・ROCm対応資産を維持し、独自native WS経路の必要性を再審査する。上流llama.cppへの置換も、現在の量子化・MTP・GPU対応を同条件で確認してから判断する。

この簡素化案は既存SAAAのnative WS契約と同一ではない。クライアントも変更する新しい契約として提案する。既存契約を維持する場合の案も後述する。回答が未確定なら、この文書によって現行契約が変更されたとは扱わない。

期待する利用体験

  1. 利用者は固定の9810へProfileを要求する。内部portやモデルprocessを探さない。
  2. Gatewayがモデルの準備と実行枠を管理し、準備中・混雑・認証不正を区別して返す。
  3. claimした同じProfile・model bindingで、JSON、HTTP SSE、WSのいずれかを選ぶ。
  4. 切断、中断、Provider再起動時に実行枠が解放され、再取得によって次の仕事を実行できる。
  5. Provider復旧後はinfra待機中の仕事を自動再開する。業務結果の保存を確認して初めて完了にする。

動的とは接続権限・実行枠・モデル割当を動的にすること。入口のportまで毎回変更する必要はない。旧static経路44448は使用も監視もしない。

推奨構成

最初の検証はresident Qwen 3.8 27B一つ、推論同時実行1、Gateway内待ち行列0で行う。これは検証条件であり、ContextStillをresidentへ無断で切り替える指示ではない。次に既存のcontextstill-backgroundのworker Profileで同じ三方式を検証する。モデルの品質・context長・利用優先度を暗黙に変更しない。

Gatewayへ無制限の仕事Queueを追加しない。永続jobと再試行はconsumerが所有し、Gatewayは即時実行枠だけを所有する。モデル起動はProfile単位でsingle-flightにし、Connection leaseと実推論枠を区別する。claimしただけで推論枠を占有しない。

Activityは表示と待機判断の補助にする。idleを見てからConnectionを作る間に競合するため、最終判断はGatewayのatomic admissionで行う。busyは故障ではなく、bounded Retry-Afterを返す。

通常の運用要素はGateway、engine、必要時のmodel manager、consumer。新たなRedis、Kubernetes、汎用workflow基盤は導入しない。既存coreのschema、Profile、認証、GPU資源制約は再利用を優先する。

WS・SSE共通の実行契約

各Runはrequest ID、principal、connection ID、release digest、profile revision、model binding、provider epoch、deadlineを固定する。transportは出力形式のみを担当し、終端判定とcleanupは共通Run管理が一度だけ行う。

共通動作と方式ごとの差
項目 HTTP JSON / SSE 新WS
入力 Chat Completions request。streamで形式を選択。 startに同じmessages、model、tools等を含める。1 socketにつきactive runは1件。
出力 共通の増分parserでupstreamを検証。SSEはchunkを逐次出力し、JSONは上限付きで集約。 accepted、delta、tool_call_delta、completed、failed、cancelledをversion管理されたJSONで返す。
成功 正常finishと終端を確認。SSEは正常完了時だけ[DONE]。途中EOFを成功にしない。 run ID付きのcompletedのみ成功。socket closeだけでは成功にしない。
中断 HTTP切断をAbortSignalへ伝える。 cancelまたはsocket切断を同じAbortSignalへ伝える。
遅いclient Web Streamsのbackpressureと総byte上限を適用。 sendの戻り値とdrainを扱う。send=-1はenqueue済みなので同じframeを再送しない。
再接続 初期版は同じ生成途中への復帰を保証しない。 初期版はresume非対応を明示。新しいclaimで新規Runを開始。自動再生成を途中応答へ継ぎ足さない。

parserはUTF-8とSSE recordの任意位置での分割、複数choice、tool argumentsの増分、reasoningとcontentの区別を保持する。対応していないfieldは黙って削除しない。profileで許可する機能を明示し、unsupportedを推論前に返す。toolはconsumerが実行し、結果を含む次の推論requestで継続する。

上流SSEのreaderを止めることはGPU推論のpauseを保証しない。buffer上限または送信停滞deadlineでupstreamをcancelする。cancel完了まで実行枠を再利用せず、停止を確認できないengineはquarantineして別Runを重ねない。nativeのKV状態保持・token単位pauseは広告しない。

headers送信前の異常は通常のHTTP error。SSE開始後はerror eventと異常終端として記録し、成功のfinishや[DONE]を合成しない。consumerは正常終端まで検査する。JSON集約も途中EOFなら502とする。

実行中の接続更新でRunのbindingを差し替えない。tokenはadmission時に検証し、lease expiry・明示失効・drainは既定deadlineに従ってRunへ伝播する。daemon restartで旧epochのclaimを失効し、clientが再取得する契約を共通SDKへまとめる。

HTTPとdesktop WSは短期Bearerを使用する。browser WSが必要ならOrigin検証付きの短期一回ticketを事前取得し、最初の認証frameまで推論を開始しない。長期secretをURLへ入れない。内部engineを直接公開しない。

既存SAAAと完全互換にする場合

現行PWS-DEC-08はSSE bridgeを禁止するため、推奨案を既存v1互換と呼ぶことはできない。完全互換が必要なら、既存native engine eventを共通Run管理の入力にする。WSは既存SAD1・ACK・再送契約を維持し、同じeventからHTTP JSONとSSEを生成する。

この案でもroot配備境界とQueue回復の修正は必要である。またworkerを含めたengine側でnative eventが必要となり、tool call、usage、finish、reasoningの意味変換を検証する必要がある。初期実装量は増える。native resumeを維持したまま、標準HTTP Providerだけに置換できるとは約束しない。

Rust撤去とnative要件撤去は別の判断である。既存consumerのDB・業務処理を書き直すと移行範囲が増えるため、まずProvider clientとinfra回復処理に変更を限定する。

Provider復旧とQueue再開

release identity、process boot epoch、Provider healthの回復世代を区別する。同一process内の一時障害からの復旧もあり得るため、commit変更だけを復旧条件にしない。 

healthy → unavailable → probing（1件のみ）→ healthy
                         └─ 失敗 → unavailable + backoff

job: pending → running → completed（結果保存済み）
               ├─ infra障害 → waiting_provider → pending
               └─ 業務上の失敗 → job用retry / failed
  • 接続不能、503、起動待ち、busyはjob failureへ加算しない。infra_attempts、next_probe_at、reasonを別管理する。指数backoffとjitter、上限時間を設ける。
  • 401、Profile不一致、release不一致はconfiguration blockedとして扱い、通常の短周期retryに混ぜない。設定変更と低頻度の再検証で回復を確認する。
  • Providerの軽量健康確認後、claimと実推論canaryを1件実行する。失敗したら追加jobを再開しない。回復probeは通常jobの選択とは独立に動かす。
  • 既存pausedはprovider_unavailable_exhausted等の明示的なinfra理由、手動停止なし、有効lockなし、という条件をconsumer所有のDB transactionで照合する。LARMがconsumer DBを直接更新しない。
  • canary成功後は対象jobを1件だけ許可し、その結果保存後に少量ずつ戻す。許可する件数と実行並列数は別で、engine capacityを超えない。
  • 手動paused、業務失敗、実行中jobは触らない。復旧を待つjob自身しかprobeを開始できない循環依存を作らない。
  • 再試行はat-least-onceを前提とし、job IDと処理versionをキーに結果保存を冪等化する。推論の再実行可能性と業務成果物の重複防止を分ける。

配備からconsumer完了まで

承認済みdesired releaseを保持する提案は維持する。ただし一つの巨大な状態列だけにせず、releaseの検証段階とProvider健康状態、consumer受入を別に永続化する。過去にcanary成功した記録を、現在も健康であることの代用にしない。

  1. 非特権builderが承認対象commitを検証・構築。独立した承認者がcommit、bundle digest、config digest、engine/model資産digest、単調増加する配備番号を署名する。builderに承認秘密鍵を渡さない。
  2. 事前導入された固定activatorが署名と対象host、digestを検証し、root所有の領域へ取り込む。symlink・hardlink・特殊file・path traversalを拒否し、取り込み後にdigestを再検証して変更競合を閉じる。
  3. activatorは固定のunitをrestartするだけとし、candidateのshell、test、hook、unit fileをrootで実行しない。実行runtimeも信頼済み固定pathから使用する。candidate本体はsystemdのUser指定で非特権実行する。
  4. 旧Runを期限付きでdrainしてatomic pointer切替。単一Gatewayのrestartには接続切断があり、atomic切替を無停止と呼ばない。clientの再取得を受入条件にする。
  5. 独立した非特権verifierがlive identity、Activity、Profile、claim、JSON、SSE、WSを検証する。検査結果は配備番号とdigestへ結びつけ、candidateからの自己申告だけを証拠にしない。
  6. canary成功後、consumerが指定された1件を処理・保存し、job ID、release digest、provider epoch、result IDを含むackを返す。gatewayのHTTP 200やQueue件数減少だけを完了条件にしない。

identity・contract不一致と新release起因のprotocol canary失敗は前世代へrollbackする。外部の一時的Provider不通やconsumer設定障害は原因を記録して未達を維持し、同じreleaseの再配備・rollbackを無限に繰り返さない。自動activationは配備番号ごとに1回、自動rollbackも1回まで。再承認または明示的な再試行操作を要求する状態を保存する。

root helperと信頼鍵の初回導入は管理者による基盤変更が必要である。アプリの配備承認を受け取る経路と、root権限そのものを自動付与する経路を混同しない。

実装順と受入

Controllerを全部完成させてから推論を試す順番にはしない。最初に1 model・1 Gateway・1 Runの縦断試作で三方式を実証し、権限境界とdesired releaseを整えてliveへ進める。各段階は未到達のまま次の段階の成功を名乗らない。
