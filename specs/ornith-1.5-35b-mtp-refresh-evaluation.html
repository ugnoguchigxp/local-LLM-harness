Ornith-1.5-35B-A3B MTP refresh再評価

Ryzen AI MAX+ 395 / Radeon 8060S / 128 GBのlocal-nodeで、Aug-24 MTP refreshを含む ROCmFP4 artifactをMTP OFF、MTP ONの順に測定しました。更新artifactの導入とMTP有効化は完了 しましたが、公開値105.6 tok/sは再現していません。speed routeは明示選択のままとし、Gemma 4や Resident Qwenを置き換えません。

測定条件

  • backendはVulkan0、Mesa RADV STRIX_HALO、context 131,072、slot 1です。
  • K/V cacheはともにq8_0、Flash Attention有効、batch 2048、ubatch 1024です。
  • 同じcoding promptをtemperature 0で256 output tokensずつ3回生成しました。
  • MTP ONはdraft-mtp、draft depth 4、p-min 0.6です。
  • serverは条件ごとに終了して新規起動し、warmup requestを集計から除外しました。
  • Resident providerはactiveのままです。停止による完全分離はsudo認証が必要なため未測定です。

Streaming first-character latency

同じ常駐service併存条件でOpenAI互換SSEを3回ずつ測定しました。HTTP request送信直前から、最初の SSE、最初のreasoning文字、最初の表示用content文字までをmonotonic clockで計測して います。warmupは集計外、temperature 0、上限512 output tokensです。

各値は3回の中央値

MTP OFF / reasoning auto 206 ms 206 ms 4,154 ms
MTP ON / reasoning auto 216 ms 216 ms 512 token内に未到達
MTP OFF / thinking off 209 ms 対象外 209 ms

MTPはthinking-offの最初の表示文字を約15 ms遅くする一方、同じrunの継続decodeを67.99から 72.13 tok/sへ改善しました。reasoning autoは通信上の最初の文字こそ約0.2秒ですが、表示本文を 数秒遅延させます。リアルタイム会話routeはrequestでenable_thinking: falseを固定し、 reasoning tokenを表示本文のTTFCとして数えません。

生成品質

MTP OFFはPython構文、必須tool call、strict JSON schemaの3試験に合格しました。MTP ONはtool callとstrict JSON schemaに合格しましたが、Python試験は説明を続けて512-token上限へ達し、閉じた code fenceを返さなかったため失敗しました。文字化けや反復崩壊は観測していませんが、Gemma 4 代替判定にはSAAA会話fixtureと長文coding品質の追加比較が必要です。

Gemma 4は最初の反応、memory、cold load、出力制御で優位です。Ornithは最初の文字まで約85 ms 遅い一方、長い回答のdecodeは約25%高速です。リアルタイム会話defaultはGemma 4を維持し、 Ornithは長文・coding・agent task用の明示candidateに留めます。Gemma 4のraw evidenceは /srv/ai/logs/gemma4-comparison/20260924T140000Zです。

運用判断

  • refresh artifactをornith15-35b-speedと64K Agent runtimeへ固定します。
  • MTPは要求どおりn4/p0.6で有効化しますが、明示routeに限定します。
  • 品質primaryの公式Q5_K_M、Resident Qwen、Gemma 4会話routeは変更しません。
  • 90 tok/s未満のため公開性能再現gateは不合格です。完全分離試験とengine更新後に再評価します。
