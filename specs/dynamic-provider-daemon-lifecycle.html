動的 Provider Daemon ライフサイクル仕様

LARMは全Agent Profileについて、Provider Daemonの選択、起動、readiness、割当、停止、revision更新を 所有する。利用者がsystemd unit、llama-swap本体、または個別Providerを手動再起動して設定を反映する運用を 正常系に含めない。

責務境界

常駐可能な層と動的管理対象
層 ライフサイクル 責務
LARM control plane 常駐またはblue-green更新 Catalog、Allocation、lease、revision、Gatewayを管理する
Provider supervisor 常駐可能 Provider processをrevision単位で生成、監視、停止する
Provider Daemon LARM管理 LLM、ASR、TTS、Embeddingなどの実推論を提供する

residentはLARMの制御外という意味ではなく、warm policyが最低一instanceの維持を要求するという意味に 限定する。Qwen 3.8 27Bはresident defaultとしてwarmに保てるが、drain、revision切替、障害復旧ではLARMが 明示的に停止・再生成できなければならない。

不変Provider revision

Allocationはruntime IDだけでなく、起動に必要な完全なProvider revisionを固定する。revisionは少なくとも次を digest対象にする。

  • artifactとmodel weightの識別子
  • 実行ファイルと引数
  • context window、batch、KV cache、reasoningなどのProvider設定
  • protocol、health probe、resource上限
  • 公開model aliasと内部binding

Backend APIはensure(runtime)とstop(runtimeId)ではなく、概念上 ensure(revision)からinstance identityを返し、stop(instanceId)する形へ移行する。 Gateway bindingとclaim credentialはinstance generationへ固定し、同じruntime IDの新旧revisionを混同しない。

状態機械

  1. Profileを解決し、必要な全Provider revisionを一つのAllocationへ固定する。
  2. 各revisionの既存instanceを再利用するか、Provider supervisorへ生成を要求する。
  3. 全Providerのprotocol固有semantic readinessが成功するまでclaimを許可しない。
  4. Connection、request、background operationの参照をinstanceごとに数える。
  5. 最後の参照解放後、warm policyのidle TTLまたは最低instance数に従って停止を予約する。
  6. 停止直前に参照数とgenerationを再確認し、使用中instanceを停止しない。
  7. 新revisionは新規Allocationだけへ割り当て、旧revisionは既存leaseを完了してから停止する。

Profileが複数Providerを持つ場合も同じtransactionで扱う。一つでも起動またはreadinessに失敗したらcredentialを 発行せず、このConnectionが新規生成した未共有instanceを回収する。

Backend別の実装方針

llama-swap

--watch-configの追加だけを最終解としない。署名済みreleaseから生成した不変のrevision entryを supervisorへ原子的に追加し、内部model IDへrevision digestを含める。新しいAllocationは新entryをloadし、旧entryは 参照がゼロになるまで残す。最後の参照解放後にunloadし、安全になってからentryを削除する。これにより llama-swapプロセス自体を再起動せず、225Kへの変更などを世代分離して反映できる。

systemd

固定された単一unitを直接参照する構成から、revision specを入力にするtemplate unitまたはtransient unitへ移行する。 ASR、TTSを含む各instanceに一意なinstance IDとloopback endpointを割り当て、LARMがstart、health、drain、stopを 実行する。固定公開portはLARM Gatewayだけが所有する。

設定とreleaseの反映

  • Provider設定はsource worktreeから直接読まず、検証済みrelease manifestから取得する。
  • release activationは新catalog generationを公開し、既存Allocationのbindingを書き換えない。
  • 設定変更のためにProvider supervisorを再起動しない。
  • 同一port競合を避けるため、Provider instanceは動的loopback portまたはrevision固有socketを使用する。
  • 起動失敗時は新generationだけを失敗させ、旧generationを継続する。
  • control plane更新はProvider processから独立し、再起動してもinstanceを再発見してleaseを復元する。

段階的移行

  1. 整合化: llama-swapとsystemdの設定参照を検証済みreleaseへ移し、source worktreeへの依存を除く。
  2. revision化: launch spec digest、instance ID、generationをBackend契約とAllocation bindingへ追加する。
  3. 無停止更新: llama-swapへrevision entryを原子的に追加し、新旧generationのdrainを実装する。
  4. 音声Provider: ASRとTTSをtemplate/transient systemd instanceへ移し、Profile leaseで起動・停止する。
  5. policy統一: resident_protectedを廃止し、warm policyと管理権限を分離する。
  6. 復旧: control plane再起動時のinstance再発見、孤児停止、binding generation照合を実装する。

受け入れ条件

  • 任意のAgent Profileをcold状態から要求し、全Providerが自動起動してclaim可能になる。
  • Connection release後、共有参照がなければpolicyどおり全Providerを自動停止する。
  • Provider設定を更新しても、supervisorと無関係なProviderを再起動しない。
  • 新旧revisionの同時leaseでbinding、credential、health、監査が混線しない。
  • 使用中revisionは停止せず、新規要求だけを新revisionへ送る。
  • ASR、TTS、LLM、Embeddingの全protocolでcold start、共有、release、idle stopをE2E検証する。
  • Qwen resident defaultはwarm policyで維持しつつ、LARMによるdrainとrevision切替が可能である。
  • 通常運用手順に手動systemctl restartを含めない。
