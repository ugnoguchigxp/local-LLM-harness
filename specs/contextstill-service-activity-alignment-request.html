ContextStill Service Activity契約整合 修正依頼書

ContextStillの動的LLM Provider実装を、SAAAおよびlocal-LLM-harness（LARM）で確定した service activity契約へ合わせるための修正依頼です。SAAAとLARMの契約は変更せず、ContextStill側の activity取得処理、test、関連文書を修正してください。

依頼日
2026-09-06
依頼先
ContextStill
対象実装
crates/context-stilld/src/domains/queue_lifecycle/dynamic_provider.rs
正本contract
larm-service-activity.v1
正本endpoint
GET /v1/activity

固定判断: /v2/agent-profiles/:profile/availabilityは使用せず、LARM全体の利用状況を /v1/activityで確認します。Profile discoveryとAgent Connection lifecycleは従来どおり 使用します。

必須変更

  1. activity取得先を GET /v2/agent-profiles/contextstill-background/availabilityから GET /v1/activityへ変更する。
  2. audienceとcurrentConnectionIdのqueryをactivity requestから削除する。 /v1/activityはqueryとrequest bodyを受け付けない。
  3. responseをstrictに検証し、未知field、契約version不一致、stateとcountの矛盾、期限切れ、許容範囲を 超える未来時刻をfail closedで待機扱いにする。
  4. freshなstate: idleかつactiveWorkloads === 0の場合だけ、新しいAgent Connectionまたは次jobへ進む。
  5. active、draining、非200、timeout、通信error、invalid responseでは Connection作成も新規job開始も行わない。
  6. Provider response bodyを閉じた後、次jobをdequeueする前にactivityを再確認する。実行中jobは activity変化だけで中断しない。

受信するresponse

{
  "contractVersion": "larm-service-activity.v1",
  "state": "idle",
  "activeWorkloads": 0,
  "observedAt": "2026-09-06T12:34:56.789Z",
  "validForMs": 1000,
  "retryAfterMs": 0,
  "reservationGuaranteed": false,
  "bootEpoch": "epoch-...",
  "configRevision": "..."
}
ContextStill側の判定
条件 動作
idleかつcount 0 Connection作成または次jobへ進む
active retryAfterMs以降に再確認する
draining 新規処理を開始せず待機する
errorまたはinvalid response fail closedで待機する

activityはsnapshotであり予約ではありません。idle確認後のConnection作成は、既存LARM admissionに よって改めて判定されます。Connectionが存在するだけではactiveにならないため、現在Connectionの allocationを除外するcurrentConnectionId処理は不要です。

変更しないこと

  • SAAAへの通知、callback、webhookを追加しない。
  • GET /v2/agent-profilesによるcontextstill-background discoveryは維持する。
  • POST /v1/agent-connections、poll、claim、renew、DELETEのlifecycleは維持する。
  • allowFallback: falseとdeploymentPolicy: existing-onlyを維持する。
  • 従来の静的Providerへ暗黙にfallbackしない。
  • 短期credentialとclaimされたendpointを永続化しない。

必須test

  • activity requestのpathが正確に/v1/activityで、queryとbodyがない。
  • idleかつcount 0の場合だけConnection createが一回呼ばれる。
  • active、draining、HTTP error、timeout、未知field、stale responseではcreateが呼ばれない。
  • Provider response body完了後、次jobの前に再確認する。
  • queueが空の間はactivityをpollしない。
  • 従来Providerのfixture、routing、request snapshotが変化しない。
  • sourceと文書から旧/availability依存が除去されている。

文書更新

ContextStill側の spec/docs/local-llm-harness-background-availability-change-request.htmlと spec/docs/larm-dynamic-provider-contextstill-implementation-plan.htmlを本契約へ更新してください。 完了報告では、LARMにProfile単位のavailability APIが必要という記述を残さず、live配備待ちの対象を contextstill-background ProfileとGET /v1/activityに統一してください。

完了条件

ContextStillのtestと文書checkが成功し、旧availability endpointへの依存がなく、freshなidle responseだけでProvider取得へ進むことをfake LARMで確認できた時点でsource修正完了です。恒久的な Queue自動消化の有効化は、LARMのlive配備と別途行うJSON応答品質canaryの合格後に実施してください。
