状態の読み方

「実装済み」はsource commitに変更が存在すること、「検証済み」は記載したcommandがそのcommitで 成功したことを表します。「完了」は対象commitがmergeされ、CI artifactと必要な外部受入が revisionへ紐付いた場合にだけ使用します。

目標と非目標

目標

  • High以上の依存脆弱性をCIで拒否し、例外を期限付きで管理する。
  • critical pathのcoverage低下を、基準revisionとの比較で拒否する。
  • 公開contractを保ったまま、状態所有と副作用の境界に沿って巨大moduleを分割する。
  • 全Spec HTMLの正本性、状態、種類、後継、観測revisionをcatalogから追跡できるようにする。
  • APIの利用者、authority、stability、互換性、deprecation状態を直交したmetadataで管理する。
  • 互換routeは、既知consumer移行、全attempt観測、live canary、rollback準備の後だけ削除する。

非目標

  • Provider選択、モデル、priority、lifecycle policyを同じ変更で変更しない。
  • 行数だけを目的に抽象化層を増やさない。
  • 静的source scanまたは成功requestのcounterだけで、consumer不在を証明しない。
  • 履歴文書を削除・移動して既存の相対linkを壊さない。
  • unit coverageをsemantic canary、concurrency test、fault injectionの代替にしない。

実施原則

  • Agent Profileと要求Provider subsetをintentの起点とし、profile、route、runtime、backendの順に追跡する。
  • 構造変更、contract変更、Provider変更、互換route削除を同じreleaseへ混在させない。
  • 各変更は単独でreview、検証、rollbackできるcommitまたはPRにする。
  • 測定値には対象commit、時刻、環境、command、artifactを付ける。
  • 完了条件を満たせない項目は、理由にかかわらず進行中またはblockedとして残す。

各operationは次の条件を全て満たした場合だけ削除できます。

  • OpenAPI、client、文書に後継とsunset日が公開され、最低30日経過している。
  • 既知consumerごとのcanonical contract testとowner sign-offがある。
  • 全production instanceを含む30日連続かつ一つ以上の完全なrelease cycleで、全outcomeのattemptが0である。
  • scrape欠損、instance欠落、counter resetがあった期間は観測期間へ算入しない。
  • live canaryが成功し、route復帰用feature flagまたは直前release artifactが検証済みである。
  • 構造分割、Provider、model、priority、lifecycle policy変更を同じreleaseに含めない。

削除後一releaseは互換routeを設定だけで復帰できる状態を維持します。復帰判断者、15分以内の目標復旧時間、OpenAPI・client・monitoringの復帰手順をrunbookへ記載します。

PRとreleaseの分割

  1. PR-A: revision固定、依存audit、文書catalog。挙動変更なし
  2. PR-B: coverage baselineと比較checker。threshold変更以外のproduction変更なし
  3. PR-C: app composition分割。公開contract snapshot不変
  4. PR-D群: domain componentを状態owner単位で分割。一PR一責務
  5. PR-E: API metadata直交化と全attempt metric。route削除なし
  6. PR-F: repository consumer移行とcontract test
  7. Release-G: external canaryと30日観測。構造変更なし
  8. Release-H: 条件を満たしたoperationだけ削除。復帰手段を一release維持

後続PRは先行PRのmerge済みcommitをbaseにします。巨大な未commit差分を一つのPRとして完了扱いしません。

Rolloutとrollback

  1. repository gateを通過したimmutable release artifactを作成する。
  2. 単一canary nodeでhealth、profile、Allocation、JSON、SSE、audio、release convergenceを検証する。
  3. 観測window中にerror rate、latency、memory、compatibility attempts、operation terminal整合性を比較する。
  4. 問題がなければ段階的に展開し、各段階のrelease revisionとconfig revisionを記録する。

失敗 停止条件 復帰

Coverage baseline低下、inventory欠落 production変更を戻す。baselineは下げない

Stateful domain race、journal、terminal state不整合 component抽出をfacadeへ戻し、保存形式は維持する
API removal 互換attempt、consumer障害、canary error feature flagまたは直前artifactでrouteを15分以内に復帰する
