試用結果

promptは「雨の未来的な東京の夜景」を表す同一英文、seedは12345とした。 これは単発のmanual smoke testであり、3回以上のwarm runを行う正式benchmarkではない。 既存のLLM、ASR、TTS serviceを停止せずに実行したため、絶対性能値は専有実行より低くなり得る。

採用可能なsampleは /srv/ai/data/generated/images/qwen-image-2.1-smoke/qwen-image-2.1-512-seed12345-steps40-vae-cpu-fp32.pngに保存した。modeはRGBA、sizeは512 × 512、file sizeは548,455 bytes。metadata JSONも同じbase nameで保存した。生成結果には日本の夜の街路、傘を差す歩行者、濡れた路面の反射が明瞭に現れ、 promptへの基本的な追従を確認できる。

同じ512角sampleをlossy WebPへ変換した結果、RGB quality 40は29,732 bytes、alphaを保持した RGBA quality 25は29,488 bytesだった。この実測に基づき既定出力をWebPとし、encoder qualityを 段階調整して30,000 bytes以下を目標にする。画像内容によって達成できない場合があるため30KBは hard limitではなくtargetであり、APIは実際のbytesを返す。

model loadはrunにより約11.4〜20.9秒、GPU移動後のmodel allocationは約32.4GBだった。 512角40 stepsのlatentは全stepでfiniteだった一方、同一latentのGPU VAE decodeだけが壊れ、CPU decodeでは正常画像になった。この結果からmodel weightやschedulerではなく、gfx1151上の MIOpen VAE convolution経路を主要因と判断する。

APIでの画像返却

既定はbase64ではなく、LARMが管理するgenerated artifactの認証付きURLとする。生成にはqueue待ちと 1分以上の推論があり得るため、POST /v1/images/generationsはjobを作成して 202 Acceptedを返し、clientは状態取得後に画像binaryを別requestで受け取る。 filesystem pathは公開しない。 

{
  "provider": "qwen-image-2.1",
  "prompt": "A futuristic Japanese city at night",
  "width": 512,
  "height": 512,
  "seed": 12345,
  "steps": 40,
  "output": {
    "format": "webp",
    "delivery": "url"
  }
}

直接Provider指定の代わりにqualityを指定できるようにし、初期contractでは providerとqualityのexactly oneを要求する。曖昧な優先順位を作らない。

content endpointは認証を要求し、Content-Type: image/webp、 Content-Length、ETagを付けてbinaryを返す。既定はlossy WebP、30,000 bytes以下を目標に qualityを調整する。PNGは明示指定時だけ使用する。opaque artifact IDから専用root内のfileを 解決し、requestから出力pathを受け取らない。

inline base64互換

output.delivery: "b64_json"は単一requestで完結したいclient向けに許可できるが、 n = 1と小さい最大bytesへ制限する。base64はbinaryより約33%大きく、daemon・proxy・ clientで追加copyが発生し、JSON logへの混入riskもあるため既定にはしない。

job状態はqueued、running、succeeded、failed、 cancelledに限定する。Idempotency-Key、取消、retention TTL、queue position、 stage別時間を保持し、必要ならSSE progress endpointを追加する。model配布物を管理する既存の LocalArtifactStoreと生成outputのretentionは責務が異なるため、generated artifact用storeを 分離する。

実装済みartifact操作と容量制御

生成画像artifact API
Method Path Purpose
GET /v1/image-artifacts 一覧とpool使用量・上限
GET /v1/image-artifacts/:id metadata取得
GET /v1/image-artifacts/:id/content WebPまたはPNG binary取得
DELETE /v1/image-artifacts/:id 画像とmetadataを一括削除

保存rootは既定で/srv/ai/data/generated/images、hard limitは20,000,000,000 bytes、 low watermarkは18,000,000,000 bytesとする。起動時と5分ごと、および将来の生成書込み予約時に poolを検査し、hard limitを超える場合は作成日時が古いartifact directoryからlow watermarkまで 削除する。画像だけを消してmetadataを残すことはせず、symlinkやroot外pathは拒否する。

Provider実装前の次の確認

  1. GPU denoise + CPU FP32 VAEをbaselineとして512角を3回以上warm計測する。
  2. 1024角はCPU decodeで再計測し、GPU VAEの1,403秒結果を性能値として採用しない。
  3. MIOpen更新、VAE tiling、別backendでgfx1151 GPU decodeの正当性と速度を比較する。
  4. Qwen Research Licenseのnon-commercial制限をProvider metadataとroute admissionへ反映する。
  5. 生成output storeと非同期job contractをmock backendで先にtestする。
