実装目標

この計画の完了時に、LARMは次の状態を満たします。

  1. 通常・リアルタイム要求はResidentのQwen 3.8 27Bへ決定的に割り当てる。
  2. 特殊Runtimeは宣言済みrouteが明示された場合だけ選択する。
  3. 選択したRuntimeを期限付きallocationへ固定し、処理途中で暗黙に変更しない。
  4. memoryと同時実行制約を満たす場合だけPreferred Runtimeを起動する。
  5. LLM利用側へ個別portを見せず、allocationを検証する安定した推論endpointを提供する。
  6. 宣言済みでchecksum付きの単一file artifactに限り、APIから検証、staging、activation、rollbackできる。
  7. 35Bを将来登録する場合も速度特化routeからだけ利用でき、通常経路へ混入しない。

守るべき不変条件

  • Qwen 3.8 27B ResidentをLARMの判断で停止しない。
  • リアルタイム要求だけを理由に35Bやoptional workerへ切り替えない。
  • 通常の推論要求からmodel downloadやactivationを暗黙に開始しない。
  • APIから任意URL、任意path、任意commandを受け取らない。
  • Coreからsystemd、llama-swap、filesystem操作を直接呼ばない。
  • weight、binary、cache、operation logをrepositoryへ保存しない。

確定するRoute policy

公開APIはRuntime idを直接選ばせず、version管理されたroute idを受け取ります。 これによりmodelやquantizationを変更しても利用側のcontractを維持できます。

gnosisで最初に定義するroute
Route 既定候補 Fallback 選択条件
llm-default qwen-general 呼出側が許可した場合だけqwen-worker-quality 通常、リアルタイム、reasoning、codingの既定経路
llm-long-context qwen-worker-quality 呼出側が許可した場合だけqwen-general 長いcontextが明示された場合だけ
llm-speed qwen-worker-fast 呼出側が許可した場合だけqwen-general 速度特化routeが明示された場合だけ
stt-default qwen-asr なし speech.sttの既定経路
tts-default voicevox-tts なし 低遅延のspeech.tts経路
tts-expressive qwen-tts なし speech.tts.expressiveが明示された場合だけ

35Bは評価と登録が完了するまで候補に含めません。登録後もllm-speedだけの候補とし、 llm-defaultのprimaryまたはfallbackには追加しません。 fallbackはrequestのallowFallbackが真の場合だけ許可し、結果へ理由を含めます。

現行Route定義の要約

routes:
  llm-default:
    capabilities: [llm.general, llm.reasoning, llm.coding]
    candidates:
      - runtime: qwen-general
        purpose: primary
      - runtime: qwen-worker-quality
        purpose: fallback
  llm-speed:
    capabilities: [llm.general, llm.coding]
    explicitOnly: true
    candidates:
      - runtime: qwen-worker-fast
        purpose: primary

field名とvalidation ruleはschemaで固定済みです。候補順は設定順を使用し、Runtime idの偶然の辞書順では決めません。

実装API contract

新しいcontractは/v1配下へ追加し、既存のprepare、resolve、 releaseは移行期間中にdefault routeへ変換するcompatibility adapterとして残します。

Milestone 1: 明示Routeと決定的Selector

目的
capabilityだけの暗黙順位を廃止し、version管理されたroute policyで候補を絞る。
主な対象
packages/core、config/gnosis

実装項目

  • routes.yamlとRouteDefinition schemaを追加する。
  • routeのcapability、候補順、primaryとfallback、explicitOnlyを検証する。
  • 未知Runtime、capability不一致、Residentを特殊routeだけに置く誤設定を起動時に拒否する。
  • selectorをPlannerから純粋関数として分離し、同じ入力には常に同じ結果を返す。
  • 選択結果へroute、candidate rank、fallback有無、理由を含める。
  • 既存prepareは各capabilityに対応するdefault routeへ変換する。
  • shadow modeで現行selectorとの差分をlogへ出し、まだlifecycle操作には使用しない。

完了条件

  • 通常・リアルタイム要求は、HOTなoptional Runtimeが存在してもqwen-generalを選ぶ。
  • llm-speedを明示しない限りqwen-worker-fastをprimary選択しない。
  • 35Bを仮fixtureへ追加してもllm-defaultから選択されないtestがある。
  • fallback不許可時はprimary unavailableを明示errorとして返す。

Milestone 2: Lease-bound allocation

目的
選択Runtimeをleaseへ固定し、prepareとresolveの間の選択driftをなくす。
主な対象
packages/core、apps/daemon

実装項目

  • LeaseをAllocationへ発展させ、capabilityごとのBindingを保持する。
  • selector結果をtrial allocationとして検証し、成功時だけ原子的に登録する。
  • 必要Runtimeをensureし、observerがreadyを確認するまでoperationをrunningに保つ。
  • startup deadline、allocation TTL、operation TTL、renew、cancelを実装する。
  • ensure失敗またはtimeout時はallocationをfailedにし、不要なPreferred Runtimeをcleanupする。
  • resolveはallocation idとcapabilityを受け、Bindingに固定されたRuntimeだけを返す。
  • releaseをidempotentにし、他allocationを再確認してからidle timerを開始する。
  • daemon再起動時はmemory上のallocationを失効させ、利用側に再取得を要求する。

完了条件

  • allocation作成後に別RuntimeがHOTになってもresolve結果が変わらない。
  • 同一Runtimeを共有する複数allocationの一つをreleaseしてもRuntimeを停止しない。
  • deadline超過、ensure失敗、cancel、二重releaseのtestがある。
  • Residentをstopするtransitionをproperty testで生成しても実行されない。

Milestone 3: Resource admission

目的
gnosisのmemoryとRuntime slotを超える起動を開始前に拒否または待機させる。
主な対象
packages/core、Runtime registry、observer

判定原則

usable = memoryTotalGB - reservedMemoryGB
committed = unique(HOT, BUSY, STARTING runtimes) + in-flight reservations
incremental = candidateがまだcommittedでない場合のestimatedMemoryGB
admit when committed + incremental <= usable
  • 一つのRuntimeが複数capabilityを提供してもmemoryを重複計上しない。
  • Residentのmemoryと安全reserveを先に確保する。
  • 推定値がないRuntime、staleなsnapshot、計算不能なNodeはfail closedとする。
  • Preferredを起動するためにResidentをevictしない。
  • 同時作成されるallocationはin-flight reservationで競合を防ぐ。
  • 最初は明示的なresource_exhaustedを返し、queueは上限とcancelを設計してから追加する。

完了条件

  • 境界値、複数capability、同時allocation、STARTING中のreservationをtestする。
  • admission結果にrequired、available、rejection reasonを含める。
  • 実機のpeak memory計測でestimatedMemoryGBを更新し、根拠を記録する。
  • voice profileとoptional LLMを同時に使用する実機smoke testを通す。

Milestone 4: Stable inference Gateway

目的
利用側から個別portを隠し、allocationのBindingを強制するOpenAI互換経路を提供する。
主な対象
apps/daemonと小さなprotocol adapter

実装項目

  • 最初の対象を/v1/chat/completionsのstreamingとnon-streamingに限定する。
  • request headerでallocation idを受け、期限、client、capability、Bindingを検証する。
  • upstream URLはRegistryとBindingからだけ構築し、request bodyから受け取らない。
  • 許可header、body size、connect timeout、first-byte timeout、total timeoutを制限する。
  • client disconnectをupstreamへ伝播し、streamとslotを確実に解放する。
  • 最初のbyteを返した後は別Runtimeへretryしない。
  • 最初のbyteより前の失敗でもBindingを暗黙変更せず、再allocationが必要なerrorを返す。
  • STTとTTSは各protocol contractを定義するまで既存direct endpointを維持する。

完了条件

  • OpenAI互換clientからstreaming responseを最後まで受け取れる。
  • 期限切れ、未知allocation、capability不一致をGatewayが拒否する。
  • disconnect、slow upstream、partial stream、BUSYのintegration testがある。
  • Gateway経由のRuntimeはallocationに記録されたRuntimeと常に一致する。

Milestone 5: Observabilityとproduction hardening

目的
選択、起動、推論、回収の結果を検証できる状態でproduction利用を開始する。
主な対象
全component、gnosis運用手順

実装項目

  • request id、allocation id、route、runtime、selection reasonを構造化logへ含める。
  • allocation結果、fallback、admission拒否、startup時間、TTFB、推論時間、releaseをmetric化する。
  • prompt、response、audio本文、認証情報を既定logへ保存しない。
  • healthをdaemon、observer freshness、Backend、Gatewayへ分ける。
  • control APIはloopback既定を維持し、LAN公開時は認証とUFW制限を必須にする。
  • graceful shutdown時に新規allocationを止め、in-flight requestへ上限付きdrainを行う。
  • route変更をconfig reloadではなく、検証済みrestartで最初に運用する。

production gate

  • default route、speed route、fallback、resource rejectionのE2E testをgnosisで通す。
  • 連続運転中にallocation leak、Preferredのstop漏れ、Resident停止がない。
  • 主要errorにoperator向けの原因と復旧手順がある。
  • 上位Ambient Agentを一clientだけGatewayへ移行し、direct endpointへ戻せる。

Milestone 6: Artifact deployment lifecycle

目的
宣言済みmodelをAPIから安全にstaging、activation、rollbackできるようにする。
主な対象
packages/core、新しいdeployment Backend、deploy/gnosis

実装順序

  1. models.yamlをschema validationし、Runtimeからartifact idを参照できるようにする。
  2. 単一file GGUFを対象に、固定source、revision、bytes、SHA-256を検証してstagingする。
  3. 一時pathへdownloadし、検証成功後だけ同一filesystem上でatomic renameする。
  4. activate前に対象Runtimeをdrainし、検証済みrevisionを指すlinkまたは設定を原子的に切り替える。
  5. Runtime起動とhealth確認が失敗した場合は直前revisionへrollbackする。
  6. operation journalをrepository外へ保存し、daemon再起動後に中断状態を検出する。
  7. directory形式modelと複数file artifactは、snapshot全体のhash manifestを定義してから追加する。
  8. 最後に権限付きallocation requestのdeploymentPolicy: allow-listedを実装し、 stageからallocationまでを一つのcomposite operationとして追跡する。

Security boundary

  • APIが受け取るのはartifact id、runtime id、宣言済みactionだけとする。
  • source URL、checksum、配置path、service名はrepositoryのmanifestから取得する。
  • 配備APIはloopbackまたはUnix socketに限定し、通常の推論credentialと分離する。
  • root権限が必要な操作は固定引数のallowlisted helperへ隔離する。
  • 同じartifactまたはRuntimeに対するoperationは排他lockで直列化する。
  • disk空き容量、download上限、operation deadline、staging cleanupを必須にする。

完了条件

  • checksum不一致、容量不足、中断download、activation失敗のtestがある。
  • 失敗時に現在稼働中の検証済みrevisionを破壊しない。
  • 通常のallocationはexisting-onlyのままでdownloadを開始しない。
  • allowlisted composite operationでstage、activate、start、allocateの進捗を取得できる。
  • artifact dataとoperation journalがsource-only検査の対象外pathにだけ作成される。

Milestone 7: Optional 35B onboarding

目的
35Bが特定taskの速度SLOを満たす場合だけ、明示的な速度routeへ追加する。
依存
Milestone 1から6のproduction gate

評価と導入

  1. 対象task、prompt長、output長、同時実行数、要求latencyを先に固定する。
  2. Qwen 3.8 27B primaryと同じ条件でstartup、prompt processing、TTFB、token生成、memoryを測定する。
  3. 速度SLO、品質下限、memory安全域を満たすrevisionとquantizationだけをmanifestへ追加する。
  4. Preferred Runtimeとして登録し、Resident保護下でadmissionできることを検証する。
  5. llm-speedの明示候補へ追加し、default routeには追加しない。
  6. 実運用metricから効果が確認できなければrouteから外し、artifactはinactiveに戻す。

完了条件

  • 通常、リアルタイム、defaultのcoding profileから35Bが選ばれないcontract testがある。
  • llm-speedだけが35Bを選択でき、実際に使用したRuntimeをresponseとmetricで確認できる。
  • 35B起動失敗時もQwen 3.8 27B Residentが継続利用できる。
  • 将来のmain昇格は別decisionとしてroute設定、benchmark、rollback planをreviewする。

Rolloutとrollback

  1. Route selectorはshadow結果だけを記録し、現行選択との差分を確認する。
  2. /v1/allocationsをopt-in clientへ限定し、既存APIを維持する。
  3. Gatewayは一つのAmbient Agent clientから開始し、direct endpointへ戻せるようにする。
  4. artifact APIはstaging-onlyから開始し、activationは明示的なoperator操作に限定する。
  5. composite deploymentを有効化する前に、単独のstage、activate、rollbackを実機で検証する。
  6. 35Bはroute設定一つで無効化できるようにし、Resident構成を変更しない。

larm-daemon.serviceとcredential生成を含むinstall手順は実装・静的検証済みです。 この作業では既存systemd構成を変更しておらず、operatorがinstall手順を実行するまでport 9810の常駐serviceは有効になりません。35B登録、実artifact activation、速度workerの実機benchmarkは、model metadataと運用影響を伴う別のattended production gateです。

各Milestone共通のDefinition of Done

  • 要求とerror caseをtestで先に固定し、対象testと既存testをすべて通す。
  • bun run checkとbun run docs:checkが診断なしで成功する。
  • CoreとBackendのarchitecture boundaryを維持する。
  • 公開contractまたは運用手順を変更した場合はSpec HTMLを同じ変更で更新する。
  • source-only検査に違反するartifactをrepositoryへ追加しない。
  • Resident保護、timeout、cleanup、observabilityを受入条件へ含める。
  • gnosisへ反映する変更はrollback手順と実機verification結果を持つ。
