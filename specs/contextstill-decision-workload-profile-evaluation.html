ContextStill探索用Decision Model・Workload Profile・ML Compute MCP 検討検証

ContextStill／DeepStillの探索workloadだけへSmall Decision Modelを適用し、通常のSAAA、 NightWorker、常駐Qwenへ影響するglobal modeを作らない案を、現在のLARM実装、local-node実機、 model公式情報、MCP 2026-07-28の仕様に照らして検証した結果です。結論は 条件付きで採用です。新しいprofile切替headerや新しいlease系は追加せず、既存の Agent Profile、Agent Connection、Allocation TTL、renew、release、priorityを再利用します。

検証evidence

sourceとhost

  • local-nodeがpinするllama.cppは cb300598d5f90189cb69d2702f4930aaf99d32a2、build 10655で、sourceに QWEN35、QWEN35MOE、Gemma 3のLLM_TYPE_270Mが存在した。
  • hostは121 GiB system memoryのうち観測時52 GiB availableだった。APUの管理toolが示す2 GiB dedicated VRAMだけをadmission値に使わず、LARMのsystem／accelerator telemetryと実測RSSを使う必要がある。
  • small model weightは/srv/ai/modelsに未配置である。source-only方針に従い、この検討では weightをdownloadしていない。

構造化出力のlive確認

稼働中のresident Qwen 3.8 27Bへ、Decisionのenumとconfidenceを含むJSON Schemaをloopbackで渡した。 thinkingを既定のままmax_tokens: 48にするとreasoningだけでlength終了し、contentは空だった。 enable_thinking: false、max_tokens: 128では1.3秒、22 completion tokenで次を返した。 

{"action":"fetch","confidence":0.91,"reasonCode":"high_value_source"}

これはbackendがJSON Schema constrained outputを処理できることと、Decision workloadでは non-thinkingを明示しなければ64 token上限が安全でないことを示します。llama.cppは JSON SchemaからGBNFへの変換 を提供しますが、対応するJSON Schemaは部分集合で、特に実数のminimum／maximumはgrammarだけでは保証されません。 生成後validationは必須です。

LARM Gatewayへの無資格live requestは401で拒否され、認証境界がfail closedであることを確認した。 task環境からsecretは取得せず、Gatewayがbodyを透過し外側のChat Completionを検証する性質はsourceと既存testで確認する。

model公式情報

  • GoogleのFunctionGemma model card は270M、32K context、text function calling向けである一方、specific taskで高精度にするにはfine-tuneを推奨している。 公開例でもbase 58%からfine-tune後85%への差が示されるため、zero-shot production controllerとは見なさない。
  • Qwen公式Qwen 3.5 2B model card は2B、native 262,144 context、non-thinking既定、OpenAI-compatible servingとtool useを案内する。 本用途ではvision encoder不要、4K〜8K context、短いoutputに制限し、実測memoryを優先する。

Workload Profile契約

原案の一つのYAMLにはruntime設定、provider選択、consumerのsemantic policyが混在しています。 strict ownershipを保つため三つへ分割します。

LARM Agent Profile

agentProfiles:
  contextstill-explore:
    description: Explicit ContextStill and DeepStill exploration decision providers
    schedulingPriority: 1000
    providers:
      - name: decision-fast
        capability: llm.decision.fast
        route: llm-decision-fast
        publicModel: decision-fast
        readiness: llm-inference
      - name: decision-default
        capability: llm.decision.default
        route: llm-decision-default
        publicModel: decision-default
        readiness: llm-inference
      - name: llm-general
        capability: llm.general
        route: llm-contextstill-general
        publicModel: qwen-contextstill-general
        readiness: llm-inference

profileはdefaultにせず明示選択だけを許可します。caller supplied headerをそのまま信頼せず、選択済みprofile revision、principal、audience、Allocationへ結び付いた短期Provider tokenを使います。

Runtime／route設定

  • FunctionGemmaはCPU専用systemd runtime、resident、4K context、admission envelopeは初期1 GiBとし、 live RSS測定後に補正する。
  • Qwen 3.5 2Bはtext-only Q4候補、4Kから開始し最大8K、preferred、llama-swapでTTL後unload可能にする。 admission envelopeは「2 GB見込み」をそのまま信じず、初期4 GiBの保守値からlive peakで確定する。
  • decision routeは各tierを一意に識別する。availability fallbackで別tierへ透過的に置換すると評価log上の escalationが消えるため、初期評価ではallowFallback: falseにする。
  • profile全体の準備に失敗した場合、ContextStillは既存のresident general providerへfail openする。 探索自体をsmall model availabilityへ依存させない。

ContextStill Decision Policy

profile: contextstill-explore
schemaVersion: contextstill-explore-decision.v1
maxInputTokens: 4096
maxOutputTokens: 64
thinking: false
temperature: 0
actions: [skip, fetch, extract, expand, requery, escalate]
terminationOwner: deterministic-code
fast:
  mode: shadow
  acceptedActions: [fetch, extract, expand, requery, escalate]
default:
  mode: shadow
  skipRequiresCalibratedGate: true
general:
  mode: teacher
validationFailure: escalate

stop_branchはmodelの最終actionから外し、modelは停止の根拠となるscoreだけを返します。 branch停止は連続低gain数、残budget、未探索候補数などを用いるcodeの状態遷移にします。

Decision schemaとrisk gate

{
  "schemaVersion": "contextstill-explore-decision.v1",
  "action": "fetch",
  "confidence": 0.91,
  "novelty": 0.81,
  "relevance": 0.92,
  "expectedKnowledgeGain": 0.77,
  "reasonCode": "high_value_source"
}
  1. JSON Schema constrained decodingでsyntaxとenumを狭める。
  2. Zodで未知field、required field、有限数、0〜1範囲、versionを検証する。
  3. NaN、Infinity、重複key、trailing data、length終了、空contentを拒否する。
  4. modelの自己申告confidenceを直接thresholdにせず、held-out dataでaction別に校正する。
  5. skipは非対称risk actionとして扱う。FunctionGemmaにはproduction初期のskip権限を与えず、 2Bもcalibrated false-skip上限を満たす場合だけ許す。
  6. native FunctionGemma tool-callとresponse_formatを同一datasetで比較する。tool schemaはpromptへ 注入されるため、FunctionGemmaではemit_explore_decision一個のrequired toolの方が安定する可能性がある。 Decision Clientが両方を同じcanonical objectへnormalizeし、勝者を実測で決める。

teacherである27Bとの一致率は補助指標です。teacherも誤るため、最終labelはfetch／extract後に得た新規fact、 knowledge graph更新、引用採用、人手auditから作ります。shadow期間はsmall modelがskipしても実際にはfetchし、 counterfactual outcomeを失わないようにします。

UMA schedulingの不足と最小拡張

現行Execution Gateはruntimeごとのqueueなので、resident 27Bと別runtimeの2Bは同時decodeできます。 「residentは並列、decodeは直列」を保証するには、runtime processのswap groupとは別の execution domainが必要です。swap groupはmemory上の同時常駐を排除する概念であり、ここでは使いません。 

resources:
  executionDomain: local-node-uma-llm
  maxConcurrentRequests: 1
  maxQueuedRequests: 16
  queueTimeoutMs: 120000

Gatewayはruntime IDの代わりにexecutionDomain ?? runtime.idをqueue keyとして使い、同じdomainの policy整合をregistry load時に検証します。FunctionGemma CPU laneはdomainへ入れません。これは LARMのdeterministic schedulerの小さな一般化であり、model判断によるscheduler置換ではありません。

shared domainはnon-preemptiveなので、長い27B requestの途中へ2Bを割り込ませられません。Decision Clientは bounded timeoutを持ち、待ち時間超過時は探索を止めずdeterministic safe actionまたは後続general呼出しへ移ります。 実測で同時decodeの干渉が小さい場合は、domain capacityを2へ上げる選択肢を残します。

評価設計とpromotion gate

record

各candidateについて最低限次を相関可能にします。

traceId, candidateIdHash, observedAt
workloadProfile, profileRevision, decisionSchemaVersion
inputFeatureDigest, sourceType, language, topicBucket
modelRole, runtime, runtimeRelease, configRevision

raw candidate本文やContextStill knowledge本文は既存の暗号化7日auditへ限定し、長期学習datasetはredaction、provenance、 retention、opt-outを持つ別artifactにします。trace IDなど高cardinality値をPrometheus labelへ入れません。

quality gate

  1. topic、source type、language、新旧knowledge、duplicate難度で分割したshadow datasetを使う。
  2. 少なくともvaluable candidate 600件を含め、skipの片側95%信頼上限を評価する。
  3. valuable-source recall 99.5%以上、false-skip率の95%上限0.5%以下を満たさなければskip権限を与えない。
  4. schema-valid率99.9%以上、length終了、空content、unknown enumを個別に測る。
  5. calibration curveとselective risk curveをaction別に作る。sampleが少ない段階は複雑なcalibratorよりbinomial lower boundを使い、 十分なdataが得られた後にisotonic regressionを比較する。
  6. 同じinputでFunctionGemma native tool-callとJSON Schema contentを比較する。

performance／resource gate

  • cold start、warm p50／p95、queue、prefill、decode、end-to-endを分離する。
  • system RSS、UMA available、backend別memory、GPU busy、27B throughput低下を同時に採取する。
  • 4Kと8K、CPU／Vulkan、Q4候補を同じprompt setと固定seedで比較する。
  • fast p95は500 ms以下かつ27B p95の20%以下を暫定目標とし、qualityを満たさない高速化は採用しない。
  • 2B warm化中でもresident 27B、ASR、TTSの既存SLOを悪化させない。

cascade KPI

fastからdefaultへのescalation率をef、defaultからgeneralを ed、tierごとの平均costをcf、 cd、cgとすると、candidate当たり期待costは次です。 

E[cost] = c_fast + e_fast × c_default + e_fast × e_default × c_general
27B call reduction = 1 - e_fast × e_default

shadow期間は比較のため27Bを必ず呼ぶのでcost削減は発生しません。quality gate通過後のlimited activationで、 27B call 50%以上削減、total GPU busy time 30%以上削減を暫定Go条件にします。hard candidateのtail latencyは cascade分だけ増えるため、平均だけでなくp95／p99を必ず比較します。

ML Compute MCPの適合性

相性は良いですが、「MCP Resource」ではなくMCP Toolとして設計するのが正確です。 Resourcesはdatasetやevaluation reportの参照、Toolsはranking、clustering、calibrationなどの計算実行に使います。 MCP 2026-07-28はstatelessなHTTP core、 requestごとのversion／identity、header routingを導入し、tool入出力にはJSON Schemaを使えます。長時間のbatchには Tasks extensionを利用できますが、client対応が必要なので 同期bounded callも維持します。

LARMとの境界

現行LARMのprotocol enumとGatewayはLLM、speech、embeddingだけなので、MCP transportを直接LARM runtimeへ加えるのは Phase 1の最小変更ではありません。最初はCPU中心のevaluation MCPを独立serviceとして作り、GPUを使う段階で ml.compute capabilityとtyped compute protocolをLARMへ追加します。MCP自体をschedulerやlease authorityにはしません。

実装順序

  1. Phase 0: contract／dataset — Decision v1 schema、Zod validator、deterministic executor、 teacher／actual outcome record、replay scorerをContextStill側へ追加する。現行27Bだけでdata contractを固める。
  2. Phase 1: runtime spike — review済みmodel artifact、license acceptance、checksum、release catalogを作り、 FunctionGemma CPUとQwen 3.5 2B Q4をproduction trafficから隔離したrouteで起動する。4K／8K、tool-call／JSON Schemaを比較する。
  3. Phase 2: shadow profile — contextstill-explore Agent Profile、TTL 300秒、renew、releaseを接続し、 small modelの結果を実行せず全candidateへteacherとactual outcomeを付ける。
  4. Phase 3: limited activation — fastはfetch系の低risk actionだけ、defaultは校正済みgateだけを受理する。 skipとbranch stopはpromotion条件を満たすまで従来code／generalへ送る。
  5. Phase 4: resource／MCP — 実測干渉があればexecution domainを追加し、offline評価用のbounded ML MCPを公開する。 GPU MLはLARM compute capabilityができるまで導入しない。
  6. Phase 5: distillation候補 — 十分なprovenance付きdatasetと固定holdoutができた後だけFunctionGemma fine-tuneを比較する。 fine-tune前後を同じpromotion gateで評価する。

受入条件

  1. SAAA、NightWorker、通常ContextStillを動かしたまま、explore profileだけを同時に作成／renew／releaseできる。
  2. 探索終了またはheartbeat断後にAllocationがexpiryし、2Bがidle TTL後unload可能になる。
  3. small modelがunknown field、invalid number、empty content、length終了を返すと必ず次tierへescalateする。
  4. model出力だけでshell、URL、SQL、filesystem操作、探索budget増加、branch継続を実行できない。
  5. false skipのpromotion gateを満たすまでFunctionGemmaのskipとstopをproductionで受理しない。
  6. selected model、runtime release、schema／policy revision、latency、escalation、teacher、actual outcomeを相関できる。
  7. resident Qwen 27Bをdefaultのまま維持し、optional speed modelを暗黙選択しない。
  8. ML MCPはstrict input／output schema、auth、quota、timeout、size limit、fixed algorithm enumを持つ。
  9. bun run checkとbun run docs:checkが通り、live canaryは認証済み経路で別途実施する。

実装前に残る実測項目

  • 採用するFunctionGemma／Qwen 3.5 2B GGUFの配布元、license、sha256、量子化方式
  • FunctionGemma固有chat templateとllama.cpp tool-call parserの互換性
  • Qwen 3.5 2B Q4のVulkan／CPU別peak RSS、UMA headroom、4K／8K throughput
  • 27Bと2B同時decode時の双方のp95悪化率と、execution domain導入の要否
  • ContextStill実dataでのvaluable candidate定義、human audit sample、retention policy
  • MCP host側の2026-07-28とTasks extension対応。未対応hostには同期toolだけを公開する。

これらはmodel weightなしでは確定できません。したがって今回の「採用」はarchitectureと検証計画に対するもので、 100 tok/s、2 GB footprint、270Mのproduction精度を確認済みとするものではありません。
