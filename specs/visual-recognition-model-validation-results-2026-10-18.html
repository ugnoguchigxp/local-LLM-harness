画像認識モデルの取得・環境構築とCPU単体実証

2026年10月18日。段階的実証計画に基づき、 Florence-2 Base、表検出、表構造認識、Granite Doclingの固定snapshotを取得し、 repository外の環境で既存OCR・物体認識と比較するCPU単体実証を実施した。 本書は小規模な探索評価で得た証拠を記録する。実際の利用資料による精度と本番接続の受入は別段階である。

解消した互換性の問題

MicrosoftのFlorence-2原本をTransformers 5.17.0のnative processorで読む最初の試行は、 tokenizerのimage_tokenがないため失敗した。 現行Transformersの公式例が用いる変換済みcheckpointと、今回指定された原本の設定は同一ではない。 今回は原本を維持し、取得済みの公式custom codeをTransformers 4.49.0の専用環境で使って動作させた。 重み・公式sourceへのpatchや、別モデルへの暗黙差替えは行っていない。

表モデルはcheckpointにbackboneを含むため、別の事前学習backboneを取得しない設定を読込時に明示した。 最初のAPI引数の不一致も証拠へ残し、configを通す形へ修正した。 新環境で表示されるBatchNormのnum_batches_trackedに関する余剰bufferと、 Docling読込時のpad token設定の警告はログに保持し、読込成功を精度の保証とはみなしていない。

入力資料と測定範囲

11資料を用意した。合成資料は日本語文字、白紙、日英の単純表、結合セル表、二つの数式、 日英の本文・表・数式混在文書の9点。写真は既存受入用busと、公式使用例にあるcarの2点である。 写真は広く使われる例であり、未知資料への汎化を実証したものではない。 生成条件、font、出典、入力のSHA-256、期待文字・セル・式をfixture manifestに記録した。

新モデルはCPU FP32、intra-op 4、interop 1で測定した。 時間は画像読込・前処理・推論・出力後処理を含む単体呼出しの観測値であり、LAN・Gateway・leaseは含まない。 warm反復の代表taskとモデルloadは分けて記録する。 process再起動の測定ではOS page cacheを除去しておらず、完全なcacheなし起動時間ではない。 GPU性能、会話等との併用性能、P99や実運用の応答保証は未評価である。

task別に確認できた内容と失敗例

既存OCR・物体認識
日本語文字、日英表の文字、bus・person・carの検出と、白紙での空結果を確認した。 日本語の合成文字画像は空白一文字の脱落があり、未正規化のCERは1/23。 空白を含めた比較と、表のセル内容の比較を区別する。
Florence-2 Base
carとbusの全体説明、領域説明、物体検出と、carのphrase groundingが動作した。 一方、白紙をノートPC、日本語文字画像をスーツ姿の人物として説明した。 詳細説明には画像内で確認できない空の状態の追加もあり、説明を検証済みの事実として扱えない。 写真の説明・領域候補として次段階へ進めるが、白紙や文書を含めた無条件の説明には使わない。
Table TransformerとOCR
単純な日英3×3表では行列を復元し、OCRの文字を18/18セルへ期待どおり割り当てた。 CSVとExcelへ出力し、Excel再読込でも文字列を保持した。 結合セル表は4行3列を検出したものの結合領域を見落とした。 白紙でも表検出・構造認識が誤った領域を出したため、対象領域や入力品質の確認が必要である。 セル割当は実証用の小さいadapterであり、複雑な表を扱う正式な後処理の完成とはしない。
Granite Docling
日英の単純表と混在文書からDocTagsを生成した。 三平方の式は転記できたが、解の公式では小文字xを大文字Xへ変えた。 白紙への数式変換では架空のmatrixを生成し、192 token上限に達した。 日本語の単純表を単独入力した場合は文字を保持したが、ページ全体では表見出し「金額」を 「令和 1 2 3 4 5」へ変える誤りが出た。cropと全体変換の品質を分けて評価する必要がある。
D1
既存の固定重みと公式実装をCPUで単体loadし、384px以内の画像に対して人・表・式の3問を評価した。 7画像の結果をyes確率0.5以上で照合した範囲では、対象の有無は期待どおりだった。 この小規模な資料で確率の校正や未知資料への精度を実証したことにはならない。 CPU FP32では約18.1GiBのprocess peak RSSと約2.9秒の3質問処理が観測され、軽量処理すべての必須前段にはしない。 初回load時間はassetsの検証と5回のwarmupも含むため、他モデルのload時間とは分けて扱う。

再実行と証拠の保存先

実装はbenchmarks/visionのsetup.sh、provision.py、fixtures.py、evaluate.py、run_suite.py、analyze.py。 setupは専用環境だけを作り、provisionだけが明示的にモデルを取得する。 run_suiteは対象を順番に実行し、evaluateは同じ証拠directory内の同時推論をlockで抑止する。 run IDの重複と作成済み評価資料の上書きは拒否する。

/srv/ai/apps/vision-recognition-eval/.venv/bin/python benchmarks/vision/provision.py --root /srv/ai/models/visual-recognition --evidence /srv/ai/evidence/visual-recognition-NEW-RUN
/srv/ai/apps/vision-recognition-eval/.venv/bin/python benchmarks/vision/fixtures.py --output /srv/ai/evidence/visual-recognition-NEW-RUN/fixtures --font /srv/ai/local-services-prepared/excalidraw-fonts/NotoSansJP.ttf --bus /srv/ai/local-services-prepared/vision-ocr-acceptance/fixtures/bus.jpg
python3 benchmarks/vision/run_suite.py --evidence /srv/ai/evidence/visual-recognition-NEW-RUN --stages baseline florence table docling d1 --run-id main
/srv/ai/apps/vision-recognition-eval/.venv/bin/python benchmarks/vision/analyze.py --evidence /srv/ai/evidence/visual-recognition-NEW-RUN --baseline baseline-main.json --florence florence-main.json --table table-main.json

今回の証拠は/srv/ai/evidence/visual-recognition-20261018/。 models.json、environment.json、fixtures/manifest.json、task別JSONとlog、CSV・Excel、 DocTagsからの変換結果、summary.jsonを保存する。 最初のbaseline-mainは失敗したFlorence native初期化と短時間重なったため、基準性能には単独の再測定を使う。 失敗試行のJSON・logも保持する。

採用した基準runと二つの再起動runにより、各対象の3回のprocess起動と単体推論を確認した。 task別の代表warm処理は各20回測定した。run-index.jsonに成功・失敗と各JSONのdigestを保存し、 source/とsource-manifest.jsonに再実行用sourceとdigestを保存した。 setupの再実行でも依存の変更はなく、実環境のfreezeはlockfileと一致した。 評価用の文字誤り率・セル割当等の5試験、source-only検査、文書検査も成功した。
