Music Generation Provider Phase 1

LARM は音楽生成を LLM、ASR、TTS、Embedding とは独立した capability として扱う。最初の provider は ACE-Step 1.5 の公式非同期 HTTP API を adapter 経由で利用し、上流固有の task ID、ファイルパス、パラメータ名を公開 API から隔離する。

決定

  • POST /v1/music/generations はジョブを登録し、HTTP 202 とジョブ表現を返す。
  • GET /v1/music/generations/:id は状態と、完了時のみ成果物 URL を返す。
  • GET /v1/music/generations/:id/events は実測できる phase だけを SSE で通知する。推測した進捗率は返さない。
  • DELETE /v1/music/generations/:id は待機中または実行中のジョブをキャンセルし、キャンセル後の成果物を公開しない。
  • 既定 concurrency は 1 とし、GPU を使う生成を直列化する。
  • 出力形式の既定は opus とし、Ogg Opus・64 kbps固定・48 kHzで保存する。
  • SAAA は完了済み楽曲をお気に入りへ指定し、daemon 再起動後も一覧からリプレイできる。

ファイル受け渡し

ジョブ結果にはホスト内部の audioPath を含めない。代わりに認証対象の audioUrl と metadataUrl を返す。クライアントは通常の bearer token を付けて音声をストリームダウンロードする。この方式は JSON への base64 埋め込みを避け、180 秒音源でもメモリと応答サイズを増幅せず、LAN 越しのクライアントにもローカルパスを漏らさない。

Music API が返す成果物の取得方法
用途 URL Content-Type
音声 /v1/music/generations/:id/audio audio/wav、audio/flac、または audio/mpeg、audio/ogg
再現用情報 /v1/music/generations/:id/metadata application/json

音声取得はHTTP Rangeに対応する。期限付き URL は提供しない。LARM の bearer 認証を必須にできるため、URL 自体を資格情報にしない。将来ブラウザへの大規模配信が必要になった場合は、同じ audioUrl 契約の裏側を object storage または Range 対応配信へ差し替えられる。

成果物と再現性

音声と metadata は LARM_MUSIC_ARTIFACT_ROOT/YYYY/MM/<job-id>/ の output.<format> と metadata.json に保存する。metadata には prompt、lyrics、seed、model、生成オプション、生成時間、音声時間、RTF、上流 task ID を含める。絶対ファイルパスはダウンロードする metadata に含めない。

完成した楽曲は形式やお気に入り登録の有無を問わず、既定で期限なしに保存する。 Opus変換に使う中間WAVは変換直後に削除し、完成したOpusとmetadataだけを残す。 全形式の合計50 GiBは通常20 GiBとお気に入り30 GiBに分ける。容量上限でも保存済みの曲を 自動削除せず、新規保存または枠を移すお気に入り変更を拒否する。生成ジョブは music_storage_fullで失敗し、お気に入り変更はHTTP 507を返す。 不要な曲は利用者が明示的に削除する。

通常曲に期限を設けたい運用では、保持秒数を正の値で指定できる。その場合に限りWAVの短期保持上限も適用する。 お気に入りは保持期限の対象外。掃除はdaemon起動時、生成完了後、既定5分間隔で行う。 実行中ジョブを保護し、完成していない成果物と失敗・キャンセルの履歴は既定24時間で回収する。 手動削除は成果物ディレクトリを先に退避してから履歴を消し、途中でdaemonが停止した場合も起動時に削除を完了する。 削除済み楽曲のURLは以後404を返す。

楽曲ライブラリ API

GET /v1/music/tracks
完成した全楽曲を生成日時の新しい順に返す。応答はtracks、検索結果全体のtotal、続きがある場合のnextCursor。
GET /v1/music/tracks?q=ピアノ&favorite=true&limit=50
qは曲名・prompt・歌詞・タグの部分一致検索。Unicode NFKC正規化と英字の大小文字無視を行い、空白で区切った語をすべて含む曲を返す。favoriteは省略・true・false、limitは1〜100（既定50）。nextCursorをcursorに指定して続きを取得する。
GET /v1/music/tracks/:id
曲名、タグ、生成条件、お気に入り状態、音声・metadataの取得URLを返す。生成要求のtitle（200文字以内）とtags（各64文字以内・32件以内）は任意。既存曲などtitleがない場合はpromptの先頭200文字を曲名にする。
GET /v1/music/tracks/:id/audio
保存済み音声を返す。HTTP Rangeに対応し、途中シークに利用できる。モデル起動は不要。
GET /v1/music/tracks/:id/metadata
再現用metadataを返す。daemon再起動後も保存済み曲を復元する。
DELETE /v1/music/tracks/:id
音声、metadata、ジョブ履歴、お気に入り登録をまとめて削除し、204を返す。生成中は409、存在しない曲は404。

自動タグと並び順

生成要求のtitleとpromptに明記された表現から、日本語・英語の辞書でタグを自動生成する。 テンポ（アップテンポ、ゆったり）、雰囲気（明るい、落ち着いた、暗い、切ない、力強い、幻想的）、 ジャンル（ポップ、ロック、ジャズ、クラシック、アンビエント、ローファイ、電子音楽）、 楽器（ピアノ、ギター、ストリングス、シンセサイザー）を対象にする。 instrumentalがtrueならインストゥルメンタルも付ける。例：fast-pacedとアップテンポは同じタグ、 bright・happy・upliftingと明るいは同じタグにする。upbeatは明るいに対応する。 英語のno・not・withoutや日本語の「なし」「ない」など、近接した単純な否定表現は除外する。 辞書による説明文の分類であり、音声の分析や自由な文脈判断は行わない。複雑な否定や辞書外の表現は扱えない。

明示されたtagsを先に保持し、Unicode正規化後の重複を除いて自動タグを追加する。上限は合計32件。 新規曲では生成要求・metadata・履歴に保存する。既存曲では読み出し時に説明からタグを補うため、再生成は不要。 歌詞は雰囲気の自動判定に使わない。

GET /v1/music/tags
保存済み完成曲で使われているタグと曲数を返す。応答はtags配列のtagとcount、タグ総数のtotal、続きがある場合のnextCursor。既定50件、limitは1〜100。曲数の多い順で、同数の場合は正規化したタグ名順。
GET /v1/music/tracks?tags=アップテンポ,明るい
カンマ区切りのすべてのタグを持つ曲に絞る。タグはUnicode正規化・大小文字無視の完全一致。qやfavoriteとも併用できる。
GET /v1/music/tracks?sort=createdAt&order=asc
生成依頼日時の古い順。order=descは新しい順。sortの既定はcreatedAt、orderの既定はdesc。
GET /v1/music/tracks?q=明るい&sort=relevance
検索語の一致度が高い順。各語について曲名は完全一致12点・部分一致6点、タグは完全一致10点・部分一致5点、promptの部分一致3点、歌詞の部分一致1点を合計する。各欄内の繰り返しでは加点しない。同点は生成日時の新しい順。qがない場合も同点として新しい順になる。

ページの続きを取得する場合はq、tags、favorite、sort、orderを維持してnextCursorをcursorに渡す。 条件を変更したcursorは400となる。limitだけは変更可能。以前の新しい順のcursorも対応する。 楽曲・お気に入り・タグの一覧はすべて既定50件（limitは1〜100）とし、totalと任意のnextCursorを返す。nextCursorがなければ最終ページ。各APIが返したcursorは同じAPIで使用する。お気に入り一覧は登録日時の新しい順を維持し、qとtagsで絞り込める。お気に入りの同時刻はjobIdの降順で決める。タグ一覧は曲数が更新されるため、生成・削除後は先頭から再取得する。

PUT /v1/music/generations/:id/favorite
完了済み楽曲を冪等にお気に入りへ登録し、再生用 URL を返す。
GET /v1/music/favorites
お気に入りを登録日時の新しい順に返す。任意のqとtagsでライブラリと同じ検索・絞り込みができる。応答はfavorites、検索結果全体のtotal、任意のnextCursor。limitとcursorで既定50件ずつ継続取得する。保存済み metadata から起動時に復元する。

お気に入り1件と、音声・metadataの取得URLを返す。
GET /v1/music/favorites/:id/audio
音声ファイルを返す。HTTP Rangeに対応し、SAAAからのストリーム再生と途中シークに利用できる。
GET /v1/music/favorites/:id/metadata
再現用metadataをJSONファイルとして返す。
DELETE /v1/music/generations/:id/favorite
お気に入りを解除し、通常の20 GiB枠へ戻す。既定では楽曲の保存期限は変わらない。

ACE-Step adapter

adapter は /release_task、/query_result、/v1/audio を使用する。上流が返した音声 URL は設定済み ACE-Step origin と一致する場合だけ取得し、SSRF を防止する。出力は最大バイト数で制限する。品質指定は inference steps（fast: 4、balanced: 8、high: 12）へ変換する。 補助LMをロードしない構成に合わせ、thinkingはfalseとし、既定品質の要求が未起動LMへ依存しないようにする。

ACE-Step の出力専用 root はOpus出力で必須。音声の取得・変換を終えた場合も、失敗・キャンセルした場合も、一時ファイルを削除する。 削除対象は realpath が設定 root 内にある通常ファイルだけとし、root 外パス、root 自体、 シンボリックリンクは拒否する。worker停止後とdaemon起動時の孤児worker回復後にも、同root直下の一時音声を掃除する。 掃除に失敗したOpusジョブは完了扱いにしない。

reference audio は共通 schema に予約するが、この adapter ではまだ受け付けない。外部 URL の直接取得は SSRF と再現性の問題があるため、今後は LARM 管理下への upload を先に行い artifact ID で参照する。

2026年10月10日：高速な試作品の検討

画像Turboと同様に、楽曲も短い試作品から方向を決める運用は可能。生成内容の編成を簡単にするだけで、同じ音声長・同じ生成stepsの計算が大幅に減るとはみなさない。主な比較軸は音声長、denoising steps、モデル、推論backendと起動・保存処理である。短いcaptionの効果と、実際に生成する音声量の削減は分ける。

現在のunitはacestep-v15-turboを選び、補助LMを初期化しない。adapterもthinking: falseとし、quality: fastを4 steps、balancedを8 stepsへ変換する。公開APIのdurationSecondsは省略時180秒なので、高速試作の候補は15〜30秒、fast、1曲ずつ。編成や歌詞を簡単にする指定は確認しやすさには役立つが、instrumental指定単独の速度改善は未測定である。

公式の推論資料はTurboを標準8 steps、baseを推奨32〜64 stepsとし、profile用コードはduration・steps・batch・thinkingを比較軸にする。少ないstepsでまとまるかはモデルの蒸留方式に依存し、モデルのサイズや量子化だけでこのPCの速度順を判断しない。stepsを半分にしても、モデル起動、音声decodeと保存を含む全体時間が半分になるとは保証しない。

次の測定候補は15秒と30秒、それぞれfast 4 stepsとbalanced 8 steps。同じprompt・seedで複数回比較し、起動を含む時間と生成部分を分けて、音質・曲のまとまりも確認する。今回は設定と公式資料の確認のみで、新たな生成benchや既定値の変更は行っていない。2026年9月24日の30秒・8 stepsの実測は内部30.52秒、API end-to-end36.18秒だが、現在のcold-on-demand処理の新しい測定値ではない。

短い試作品から同じ旋律を保って長尺へ仕上げることは、promptによる独立再生成とは別の要件。現在のadapterはreference audioを受け付けないため、参照音源のupload・artifact IDと、モデル側の参照・編集機能の検証が必要である。

確認した公式資料はhttps://github.com/ace-step/ACE-Step-1.5/blob/main/docs/en/INFERENCE.mdとhttps://github.com/ace-step/ACE-Step-1.5/blob/main/profile_inference.py。このPCの過去実測はACE-Step 1.5 ROCm試行に記録する。

APIから取得する使い方

SAAA-w-musicのservices[].descriptionに、生成APIの入力と結果の取得方法を含める。 Profile発見とConnection作成・取得・claimで同じ説明を返し、Connection応答のservices[].urlから生成を要求できる。 説明はdurationSecondsの範囲1〜600秒と省略時180秒、qualityのfast（4ステップ）、balanced（8ステップ・既定）、high（12ステップ）を広告する。 起動時間が加わることと、highで音質向上を保証しないことも明記する。

試作例は30秒・fast・instrumentalのJSONとする。歌なしはinstrumental: trueで、その場合lyricsを指定しない。 出力形式はopus・mp3・wav・flac（既定opus、64 kbps固定・48 kHz）、seedは任意、参照音源の編集は未対応と説明する。 HTTP 202で受け取ったjobIdを使いGET /v1/music/generations/{jobId}で確認し、 completed時のresult.audioUrlをControlのURLに解決して音声を取得する。 

{
  "prompt": "軽快なピアノのBGM",
  "durationSeconds": 30,
  "quality": "fast",
  "instrumental": true
}

Opus出力と中間形式の選択（2026-10-11）

ACE-Stepは48 kHzの波形tensorを生成し、ファイル形式への保存は生成後の処理である。 モデル自体にMP3やOpusを生成させる必要はない。配備済みのAudioSaverと公式実装を確認し、 中間形式にはwav32（32 bit浮動小数点PCM WAV）を選択した。 WAVとFLACはsoundfile経路を利用し、wav32はsoundfileへ浮動小数点波形を直接書き込む。 FLACの圧縮や整数PCMへの丸めを挟まず、生成波形をOpus変換へ渡せる。 保存経路と以下の小規模測定に基づく判断であり、モデル生成速度の改善を意味しない。

中間形式の比較
形式 保存処理 採用判断
wav32 soundfileで32 bit浮動小数点PCMを直接保存 採用。量子化と非可逆な再圧縮を避ける
wav soundfile経路。通常は整数PCM 明示的な最終出力として対応を維持
flac soundfile経路。整数PCMの可逆圧縮 中間容量は減るが、圧縮・展開が増える
mp3、opus FFmpeg等で非可逆エンコード Opus変換の前段には使わない

配備ソースrevisionはca1e85fe9430179831e6bc6be790c332190a3866。 CPU上で30秒・48 kHz・2チャンネルの合成正弦波をAudioSaverで保存し、初回を除く3回の中央値を測定した。 wav32は8.00 ms（11,520,088 bytes）、wavは13.20 ms（5,760,044 bytes）、flacは31.93 ms（1,891,687 bytes）だった。 この配備環境ではwavとflacはAudioSaverのsoundfile fallback経路で保存された。 ffprobeでwav32がfloat32、wavとflacが16 bit整数PCMであることを確認した。 この条件ではwav32が最短で、浮動小数点の精度も維持する。 値は保存処理だけの小規模測定であり、楽曲生成時間の比較ではない。FLACの容量は実楽曲の複雑さにより変わる。 比較で作成したすべての中間ファイルは測定終了時に削除した。

LARMはOpus要求に対して上流へaudio_format: wav32を送る。 取得したWAVをFFmpegの標準入力へ渡し、libopusで64,000 bit/s、CBR、48,000 Hzへ変換する。 Oggコンテナを標準出力から受け取り、最終成果物をoutput.opus、Content-Typeをaudio/oggとする。 変換のCPU処理はモデルの生成品質指定とは独立し、生成品質を変更してもビットレートは64 kbpsのままである。 音声tensorのチャンネル数を維持し、不要なダウンサンプリングは行わない。

変換中はLARM側に中間ファイルを作らず、取得・変換のバイト上限、120秒の変換上限、キャンセルを適用する。 ACE-Stepが作る一時WAVは変換の成功・失敗時にfinallyで削除する。 生成途中の中断でパスを取得できなかった音声も、on-demand workerが停止してから出力専用root内で掃除する。 保存・お気に入り・再起動後の復元・Range配信・容量管理では最終Opusだけを音声成果物として扱う。 実HTTP配信では、Bunがsliceしたfile streamを元ファイル全体として送信する最適化を避けるため、 Range応答のstreamをTransformStream経由で転送する。HTTP 206のbodyとContent-Lengthが指定範囲と一致することを実サーバーで検証する。 明示的に指定したWAV、FLAC、MP3は最終成果物なので、既存の保持規則に従う。

環境要件はFFmpegのlibopusエンコーダーである。 Debian系ではffmpegパッケージを導入し、ffmpeg -hide_banner -encodersで libopusを確認する。検証にはffprobeも使用する。 このホストは両プログラムとlibopusを導入済みで、追加のPython音声エンコード依存は不要だった。 Opus要求を上流へ送信する前にもエンコーダーの存在を検査する。

参照した公式実装はhttps://github.com/ace-step/ACE-Step-1.5/blob/main/acestep/audio_utils.py、 https://github.com/ace-step/ACE-Step-1.5/blob/main/acestep/inference.py。 FFmpeg設定はhttps://ffmpeg.org/ffmpeg-codecs.htmlのlibopusと https://ffmpeg.org/ffmpeg-formats.htmlのOggを確認する。 確認日は2026-10-11。実際の配備ソースでもwav32の直接保存経路と48 kHzの設定を確認した。

設定

LARM_MUSIC_PROVIDER_ENDPOINT
ACE-Step API の base URL。未設定なら Music API は 503 を返す。
LARM_MUSIC_PROVIDER_API_KEY
任意の ACE-Step bearer token。
LARM_MUSIC_ARTIFACT_ROOT
成果物 root。既定は /var/lib/larm/music。
LARM_MUSIC_POLL_INTERVAL_MS
上流ジョブ確認間隔。既定は 1000 ms。
LARM_MUSIC_MAX_AUDIO_BYTES
単一出力の上限。既定は 512 MiB。
LARM_MUSIC_ARTIFACT_RETENTION_SECONDS
通常曲の保持期限。既定は0（期限なし）。正の値を指定した場合のみ期限で削除する。
LARM_MUSIC_WAV_RETENTION_SECONDS
通常曲の保持期限が正の場合に適用するWAVの上限。既定は3600秒。期限なし設定では完成したWAVも保存する。
LARM_MUSIC_ARTIFACT_MAX_BYTES
成果物 root 全体の容量上限。既定は 50 GiB。
LARM_MUSIC_FAVORITE_MAX_BYTES
全体上限のうちお気に入り専用枠。既定は 30 GiB。通常枠は全体上限との差分になる。
LARM_MUSIC_PRUNE_INTERVAL_SECONDS
定期掃除の間隔。既定は 300 秒。
LARM_MUSIC_UPSTREAM_OUTPUT_ROOT
ACE-Step 出力専用 root。Opus出力では必須。通常ファイルだけを削除し、変換成功・失敗・キャンセル時に中間音声を保持しない。

残課題

  • ACE-Step runtime の systemd 配備、ROCm 実機 commissioning、モデル revision の固定。
  • ジョブ journal と daemon 再起動後の状態復旧。ファイル retention は実装済み。
  • reference audio の認証付き upload と artifact ID 化。
  • 実音声ヘッダーからの duration 検証、benchmark command。
  • 既存 allocation と unified-memory admission への music runtime 統合。
