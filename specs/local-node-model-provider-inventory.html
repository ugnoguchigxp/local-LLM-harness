この文書は、local-nodeに存在するモデルweightと、LARMからProviderとして要求できる状態を一枚で 見渡すためのpoint-in-time棚卸である。weight本体はsource-only repositoryへcommitせず、 /srv/ai/modelsに置く。固定revision、byte数、digestの正本は、登録済みartifactについては deploy/local-node/models.yamlとする。

棚卸時点では、LLM 10構成と音声・Embedding 5構成がProvider準備済みである。これとは別に、7モデル群が ダウンロード済み・未Provider化、2つの大規模LLM weightが評価stagingにある。

状態の定義

Provider準備済み
必要artifactが存在し、Runtime、model releaseまたは外部runtime bundle、routeがRepositoryに定義されている。 Agent Profileがある場合は公開model名も併記する。現在processがHOTであることや、直近canaryの合格を 意味しない。
ダウンロード済み・未Provider化
完全なweightまたはsnapshotは存在するが、Runtime、release、routeのいずれかがなく、通常requestからは 選択できない。
評価staging
.larm-staging内に比較試験用資産があるが、production catalogや公開routeへ採用していない。
補助artifact
MTP draft、speech tokenizer、templateなど、単独Providerにはならない資産。

「Provider準備済み」と「既定」は異なる。例えばQwen 3.8 ROCmFP4はRuntimeとreleaseを維持しているが、 SAAAや通常LLMの既定profileからは外れている。また、llama-swap配下のモデルは要求時だけ起動し、解放後に COLDへ戻り得る。

棚卸時のservice状態

2026-09-16の確認時点では、larm-daemon、llama-swap-worker、 llama-server、qwen-asr、whisper-asr、voicevox-ttsがactiveだった。 qwen-ttsとlarm-embeddingはinactiveだったが、unitとProvider定義は存在する。 これは瞬間的なHOT／COLD観測であり、上表の準備判定を変更しない。

更新時の確認順

  1. /srv/ai/modelsで完全なweight、snapshot、symlink先を確認する。
  2. deploy/local-node/models.yamlでrevision、byte数、digest、roleを確認する。
  3. config/local-node/runtimes.yamlとdeploy/local-node/releases.yamlを照合する。
  4. config/local-node/routes.yamlとconfig/local-node/agent-connections.yamlで 利用者から選択可能か確認する。
  5. Provider化した候補はsemantic canaryを通し、この一覧の状態と棚卸日を更新する。

weightが存在するだけでProvider準備済みへ昇格させない。逆に、systemd unitが一時的にinactiveでも、 artifactと構成が固定されてon-demand起動できるものはProvider準備済みとして扱う。
