SAAA非同期Connection・5分idle release・ContextStill復帰 実装計画

本計画は、SAAAが要求するLLM、backchannel LLM、ASR、TTS、embeddingの複合Agent Connectionを短時間のHTTP requestで受け付け、別のstatus readで準備状況をpollできるようにする。 Connectionがreadyになった後、LLM、ASR、TTSの利用が5分間なければSAAAのAllocation全体を自動解放し、 通常時のContextStill利用へ自動的に戻す。

/readyはLARM daemonがcontrol APIを受け付けられることだけを表す。個別のAgent Connectionは、Profile内の全required Providerがsemantic readinessを満たすまで readyではない。daemon readinessとConnection readinessを一つのbooleanへ統合しない。

目的と非目的

目的

  • Connection作成HTTPをProvider配備・容量待ち・semantic probeから切り離す。
  • 全required Providerが利用可能になった場合だけConnectionをreadyにする。
  • 同じSAAA sessionから重複Allocationを作らない。
  • LLM、ASR、TTSが5分間使われなければ、SAAA bundleを安全に自動解放する。
  • SAAA解放後、待機中のContextStill要求を直ちに再評価して通常利用へ戻す。
  • 待機理由、Provider別進捗、idle deadline、terminal reasonをpoll responseとeventで観測可能にする。

非目的

  • 実行中のLLM stream、音声request、embedding requestをidle timerで中断しない。
  • LARMがconsumerのprincipalを代行してContextStill Connectionを勝手に作成しない。
  • Provider processのwarm TTLとAgent Connectionのidle releaseを同じtimerにしない。
  • モデルweight、backend binary、固定portをこの変更で追加しない。

不変条件

  1. SAAA ProfileのLLM、backchannel、ASR、TTS、embeddingはすべてrequiredとし、一つでも未準備なら Connection全体をreadyにしない。
  2. claimはConnectionがreadyで、全Providerのsemantic probeが成功した場合だけ credentialを返す。
  3. 作成requestの切断やclient側timeoutは、受付済みConnectionの所有権を曖昧にしない。同じ idempotency keyの再送は同じConnectionを返す。
  4. auto release前にConnection generation、active request数、最終activity、terminal状態を同じ critical sectionで再検証する。
  5. auto release後は既発行credentialを失効させ、新しいrequestをProviderへ転送しない。
  6. ContextStillへの復帰はSAAAの全Provider解放後に行い、部分的なbundle切替を行わない。
  7. status、health、claim、renewの読み取りや管理操作だけではidle deadlineを延長しない。

非同期API契約

Agent Connection lifecycle API
操作 応答 責務
POST /v1/agent-connections 201または202 admissionを開始してConnection IDを返す。既に全Providerがreadyなら201、それ以外は 202、Location、Retry-Afterを返す。
GET /v1/agent-connections/:id 200 状態、phase、Provider別readiness、blocker、idle deadline、terminal reasonを返す。
POST /v1/agent-connections/:id/claim 200または409 readyの場合だけ全Providerの短期credentialを返す。
DELETE /v1/agent-connections/:id 204 明示release。auto releaseと同じ一回限りのterminal処理を使う。

POSTの既定は待機なしとする。互換用Prefer: wait=Nは最大3秒に制限し、3秒を超える 値には実際に適用した値をPreference-Applied: wait=3で返す。Providerの5分ready deadlineは background lifecycleの期限であり、元のPOSTを5分保持する期限ではない。deadline到達時はstatus resourceを failed、connection_ready_timeoutへ遷移させる。

重複Connection防止

SAAAは音声sessionの開始からrelease完了まで同じ永続idempotency keyを使用する。poll timeout、UI再描画、 IPC retryではkeyを変更しない。releaseが確認できた後だけ次のkeyへrotateする。

LARM側にも防御を追加し、同一principal、profile、audience、client session keyの非terminal Connectionが 既にある場合は新しいAllocationを作らず既存resourceを返す。request bodyが異なる同一keyは従来どおり conflictとする。異なるSAAA processを意図的に並行利用する場合は別のclient session keyを要求し、暗黙共有しない。

5分idle release policy

idleRelease:
  enabled: true
  idleSeconds: 300
  activityProtocols:
    - openai.chat-completions.v1
    - openai.audio-transcriptions.v1
    - openai.audio-speech.v1

このpolicyはSAAA Profileへ設定し、他のAgent Profileへ暗黙適用しない。Chat protocolには通常LLMと backchannel classifierの両方を含む。Provider名の文字列比較ではなく、compile済みprotocolで判定する。

idle deadlineへの影響
操作 5分を再開するか 実行中の解放を防ぐか
LLM／backchannel request する する
ASR request する する
TTS request／stream する する
embedding request しない する
semantic probe／health／status poll しない しない
claim／renew しない しない
  1. Connectionがreadyになった時刻を最初のidle基準時刻とする。
  2. 対象protocolのrequest受付時にtimerを停止し、active request refを取得する。
  3. response bodyまたはstreamが閉じたterminal境界で最終activity時刻を更新し、そこから300秒後を新しい deadlineとする。upstream error、client cancelも認証・admission済みrequestなら利用として数える。
  4. deadline到達時に対象protocolのactive requestが0で、全Providerを含むactive request refも0なら、 Connectionをreleasedへ遷移させる。
  5. embeddingだけが実行中なら途中解放せず、終了後に再検査する。対象protocolの最終activityから既に300秒を 超えていればembedding終了直後に解放する。

auto release理由はforeground_idle_timeout、eventは agent_connection_idle_releasedとする。旧credentialによるrequestはProviderへ転送せず、 409 connection_idle_releasedを返す。認証情報そのものはeventへ記録しない。

ContextStillを通常状態にする

ContextStill consumerは一つのdesired Connectionを所有し、SAAAのforeground preemptionを受けた場合は foreground_preemptedをterminal成功と誤認せず、同じ再取得idempotency keyで一件だけ Connection作成を再送する。LARMはこれを202 waiting-capacityとして保持できる。

  1. 通常時はContextStillがreadyでbackground処理を行う。
  2. SAAA要求が来たらContextStillの新規requestを停止し、active requestのterminal処理後にcredentialを失効する。
  3. SAAAの全required Providerがreadyになった後だけSAAAへclaimを許可する。
  4. SAAAでLLM、ASR、TTSの無利用が5分続いたらbundle全体をauto releaseする。
  5. release完了時にwaiting queueを直ちに再評価し、ContextStillを優先度1000で再admitする。
  6. ContextStillがreadyになったらconsumerが再claimし、background処理を再開する。

LARMはprincipalを代行してContextStill Connectionを新規作成しない。自動復帰のdesired stateと再取得責務は ContextStill consumerに置き、LARMは一意なwaiting request、昇格、credential generationを管理する。 SAAA release後のProvider warm holdはprocess停止を遅らせてもよいが、ContextStillのadmission再評価を遅らせては ならない。

競合と障害時の扱い

  • timerと新規requestが競合した場合、request ref取得とrelease判定を直列化する。requestが先ならtimerを取消し、 releaseが先ならrequestをterminal errorで拒否する。
  • streamはheader返却時ではなくbody close時までactiveとする。
  • daemon drainは新規requestを拒否し、active request終了後にConnectionを解放する。
  • daemon再起動時は従来どおり旧boot epochのConnectionを復元せず、clientが新規作成する。
  • release処理は冪等とし、明示DELETE、TTL、idle timerが競合してもAllocationを一度だけ解放する。
  • ready前のConnectionにはidle timerを開始せず、ready deadlineだけを適用する。
  • 時刻逆行の影響を避けるため、timer計算にはmonotonic clock、公開時刻にはwall clockを使う。

実装順序

WP1: API schemaと設定契約

  • packages/core/src/agent-connection.tsへphase、Provider別readiness、blocker、 readyDeadline、lastForegroundActivityAt、idleReleaseAtを追加する。
  • agent-connections.yamlのSAAA ProfileへidleReleaseを追加する。
  • packages/core/src/api-contract.tsとOpenAPI fixtureを更新する。
  • 旧clientが未知fieldを拒否する場合に備え、契約versionと移行順序を固定する。

WP2: Connection作成のbounded wait化

  • apps/daemon/src/app.tsでPreferの実待機を最大3秒へ制限し、必ず LocationとRetry-Afterを返す。
  • apps/daemon/src/agent-connection-controller.tsでready deadline処理をPOST lifecycleから完全に 分離する。
  • Allocationのwaiting、ensure、semantic probeを公開phaseとProvider別進捗へ射影する。
  • 同一SAAA client sessionの非terminal Connectionをsingle-flight化する。

WP3: Connection activity tracker

  • Agent Connection ControllerへConnection ID、generation、protocol、active request IDs、最終activity、timer generationを保持するtrackerを追加する。
  • apps/daemon/src/app.tsのGateway request ref取得・onFinish境界からtrackerを更新する。
  • JSON、SSE、audio stream、client cancel、upstream errorの全terminal pathで一度だけreleaseする。
  • 既存Provider Instance Managerのrequest refは維持し、Connection idle判定とは別層にする。

WP4: 5分auto release

  • Connection単位のgeneration付きtimerを追加し、古いcallbackを無効化する。
  • release直前にterminal状態、deadline、全active request、Allocation bindingを再検証する。
  • foreground_idle_timeoutをrecord、Allocation release reason、監査eventへ一貫して保存する。
  • terminal recordを履歴保持期間中poll可能にし、idle release理由をclientが識別できるようにする。

WP5: ContextStill自動復帰

  • SAAA release完了後にwaiting Allocation promotionを同じqueueへ投入する。
  • provider switch holdがContextStill admissionを抑止しないことを明示testする。
  • ContextStill consumerへsingle-flight再取得、bounded backoff、poll、再claimを実装し、preemption中の background jobを新Provider ready後だけ再開する。

WP6: SAAA consumer移行

  • ../SAAA/crates/larm-session/src/lib.rsでPOSTを短時間受付、GET polling、claimの三段階として 固定し、Prefer: wait=300を使用しない。
  • ../SAAA/src-tauri/src/providers/larm_voice/mod.rsでsessionごとの永続idempotency keyと Connection IDを一つだけ所有する。
  • connection_idle_released受信後は旧credentialを再利用せず、次の実ユーザー操作で新しい Connectionを作成する。
  • UIへ準備待ち、Provider別進捗、再接続中、terminal reasonを表示する。

試験計画

必須の自動試験
分類 確認内容
API contract cold ProviderでもPOSTが3秒以内に202を返し、GETでpendingからreadyへ遷移する。
Atomic readiness 5 Provider中1つでもprobe失敗ならclaim不可で、全成功後だけ一括claimできる。
Deduplication 同じsessionから同時POST、retry、再起動replayを行ってもactive Allocationは一件だけになる。
Idle clock fake clockで299秒はready、300秒でauto releaseとなる。
Activity reset LLM JSON、SSE、ASR、TTSの終了ごとにdeadlineが300秒延長される。
Non-activity poll、health、claim、renew、embeddingだけではdeadlineが延長されない。
In-flight safety 長時間streamとembedding実行中はtimerが発火しても解放せず、終了後に正しく再判定する。
Race deadlineと同時のrequest、DELETE、TTL、drainで二重releaseや転送後失効を起こさない。
ContextStill復帰 SAAA preemption、SAAA利用、5分idle release、ContextStill再昇格・再claimを一続きで確認する。

production E2Eでは実時間5分を一度だけ測定する。通常test suiteではfake monotonic clockを使い、5分sleepを 入れない。live証跡にはrelease commit、config revision、Connection IDの短縮表示、状態遷移時刻、release reasonだけを残し、credential、会話本文、音声を保存しない。

配備順序とrollback

  1. 追加fieldを読めるLARM clientとSAAAを先に配備する。auto releaseはまだ無効にする。
  2. LARMの非同期status強化とsingle-flightを配備し、重複Allocationがないことをcanary確認する。
  3. ContextStillのsingle-flight再取得とpollingを有効にする。
  4. SAAA Profile一つだけでidleRelease.enabled: true、300秒を有効にする。
  5. 24時間soak後、全SAAA variantへ同じpolicyを展開する。

rollbackは設定のidleRelease.enabledをfalseへ戻す。非同期POST、status polling、deduplicationは 安全性改善として維持する。rollback時も既にauto releaseされたConnectionを復活させず、新規Connectionを作成する。

完了条件

  1. Provider cold startまたは容量待ちでもConnection作成POSTが3秒を超えて保持されない。
  2. poll responseだけでwaiting理由と各Providerの準備状態を説明できる。
  3. SAAAの同一sessionが複数の5-Provider Allocationを作らない。
  4. 全required Providerがsemantic readyになる前にclaim credentialを発行しない。
  5. LLM、ASR、TTSの最終request終了後300秒でSAAA bundle全体が解放される。
  6. 実行中request、embedding、streamをauto releaseが中断しない。
  7. SAAA解放後、ContextStillが手動操作なしで再admit・再claimされる。
  8. 旧SAAA credentialは解放直後から使用できず、明確なterminal reasonを返す。
  9. bun run checkとproduction profile E2E、実機5分canaryが成功する。
