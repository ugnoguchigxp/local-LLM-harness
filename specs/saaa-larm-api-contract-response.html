SAAA向けLARM LLM・ASR・TTS API契約 回答

確認日：2026-09-16。対象はlocal-LLM-harnessの現在のrepository実装であり、live hostの 配備release、実モデル応答、GPU／CPU容量、LAN経路は今回確認していない。本書の 「実装済み」はsourceと自動testで確認できた範囲を指し、live commissioning完了を意味しない。

結論

通常のBearer認証、base URL、request bodyのmodelだけでLLM、ASR、TTSを呼ぶ data planeはrepositoryへ実装済みである。Profile、claim、Allocation headerは通常推論には 必須ではない。Chat CompletionsのJSONとSSE、ASRのmultipart＋JSON、TTSの音声bodyを同じ Gatewayで扱う。

ただし、交換可能なProvider契約として完成しているとはまだ扱わない。モデル別のtools、 Structured Outputs、reasoning_effort、token上限、ASR形式、TTS voice／音声形式を 機械可読に広告する契約がなく、未対応parameterをLARMが一貫して事前拒否していない。 また、通常data plane用の機能別状態取得とTTS voice discoveryは不足している。

1. 通常推論data plane

基準base URLはLARMが返す値をそのまま使う。Agent Connectionが返す値は末尾 /v1であるため、例えばhttps://larm.example/v1へ /chat/completionsを連結する。clientが常に/v1を追加してはいけない。 operatorがorigin形式を設定する場合はfull path /v1/chat/completionsを使用する。どちらの設定形式を採るかはSAAA内で一つに正規化し、 proxy prefixを削除しない。

通常推論で確認した公開面
機能 request response 現在の制約
LLM POST /v1/chat/completions、JSONのmodelとmessages stream false／省略はJSON、trueはSSE model別parameter能力は未広告
ASR POST /v1/audio/transcriptions、multipartのmodelと非空file JSONのtext。language等は任意 通常Gatewayの保証対象はJSON。Realtime入力ではない
TTS POST /v1/audio/speech、model、input、任意のvoiceとresponse_format 要求形式に合う音声body model別voice／形式広告とlive conformanceが不足

global API tokenを使う通常経路ではAuthorization: Bearer <token>を送る。 requestにx-larm-allocation-idがなく、公開model catalogが設定されていれば、LARMの Model Brokerが内部Allocationを作成し、準備完了を待ち、request終了時に参照を解放する。 allowFallback: falseで取得するため、通常経路は別の公開modelへ暗黙に置換しない。

認証と広告の区別

固定base URLとglobal API tokenをoperatorがSAAAへ設定する場合、Profile／claimは不要である。 LARMから短期のscoped credentialとbase URLを動的に取得したい場合だけAgent Connectionの create、claim、renewが必要になる。後者は標準推論APIではなくbootstrap／割り当てAPIである。

2. LLM JSON、SSE、モデル差

「Gatewayを通すとtool／reasoning SSEが欠落するためJSONへ固定する」というrepository上の 制約は解消済みである。GatewayはSSEをbufferせず転送し、UTF-8とCRLFの分割、comment、複数event、 role-only chunk、content、reasoning content、function call、分割されたtool callを検査する。 finish_reasonはstop、length、tool_calls、content_filter、function_callを区別し、 全choiceのfinishと[DONE]がないEOFを正常終了にしない。

LARMはtool argumentsを実行用に組み立てないが、index／ID／function fragmentを欠落させず clientへ渡す。SAAAがcall indexまたはIDごとにargumentsを組み立て、finish後に一度だけtoolを 実行する。stream開始後に形式違反または途中切断が分かった場合、既に返したHTTP statusは変更せず、 response streamをerror終端する。SAAAは単なるEOFを成功とせず、finishとDONEの両方を確認する。

モデル差に関する現在の保証
機能 Gateway実装 公開契約の状態
SSE 転送・正規化・終端検証あり 全公開chat modelで使う設計。live実モデル試験は未実施
function tools request透過、JSON／SSE response検証あり model別の対応可否は未広告。live tool round tripが必要

空本文のlive観測とrelease canary

稼働release be5e862…では短い英語指示に対し、本文を生成せず終了する事例が二種類 観測された。finish_reason=lengthかつ256 token消費の事例は、1024 tokenでの再試行に 成功したため上限不足と整合する。一方、finish_reason=stop、生成3 token、本文空の事例は token上限では説明できず、別のmodel／template挙動として扱う。

release後のHTTP Provider live smokeは、Structured OutputsとSSEに加えて、再現入力 Reply with just OK.を非stream JSONで送る。HTTP正常終了だけでは合格にせず、 finish_reason=stopと可視本文OKを要求し、stop＋空本文を明示的に失敗させる。

現在のrequest schemaは未知fieldを許容する。したがって、LARMが未対応parameterを常に 400 unsupported_parameterとして返す保証はまだない。upstreamが無視するか、upstream固有の errorを返す場合がある。これは交換可能なProvider契約にする前の修正対象である。

3. ASR・TTSのモデル固有契約

ASR

公開model qwen3-asr-1.7bのadapterはWAVを含むfile uploadを受ける。公開の最小保証は WAV入力と{"text":"..."}である。検出できた場合だけlanguageを追加し、空または nullのlanguageはGatewayが除去する。verbose_jsonではtask、duration、textと任意の languageを返す。話者分離、speaker ID、segment単位の保証はない。

adapterはplain textも生成できるが、現在の通常Gatewayは成功ASR responseをJSONとして検査するため、 response_format=textは公開保証に含めない。未対応形式をrequest前に拒否せず、後段で format mismatchになる点は修正対象である。

TTS

repositoryから確認できたTTS能力
model voice 形式 逐次返却
voicevox-core 既定Kasukabe_Tsumugi。Shikoku_Metan、Zundamon、Kasukabe_Tsumugi、Amehare_Hau WAV、PCM。PCMはmono、s16leで実sample rateをheaderとmedia typeに返す 非対応。engineが全文を合成してからbodyを返す
qwen3-tts-expressive Aiden、Ono_Annaほか設定済み9 voice 公開Gatewayとして保証する形式を未固定 upstream設定にstream生成項目はあるがlive conformance未確認

稼働release be5e862…ではQwen TTSの公開model qwen3-tts-expressiveをupstreamが400 invalid_modelで拒否した。 原因はupstream設定のmodel keyが0.6B-CustomVoiceのまま公開名と不一致だったためである。 現在のsourceではdefault model keyもqwen3-tts-expressiveへ統一し、readiness probeと 通常speech requestが同じ公開名をupstreamまで使用する。

Gateway自体はupstreamの音声bodyを全量bufferせず転送するため、upstreamが早期に音声chunkを返せば clientは全文生成前に再生できる。ただしVOICEVOXでは最初のbyteが全文合成後である。24 kHz、mono、 16-bit little-endian PCMのうち、現行VOICEVOX adapterはmonoとs16leを検査するがsample rateを 24 kHzへ固定検証していない。24 kHzを共通保証にするにはadapterのfail-closed検査とlive fixtureが必要である。

GET /v1/audio/voices?model=...は通常Bearerだけでmodelを解決し、GET bodyなしで内部Allocationを取得・解放する。 model queryは必須かつ一つに限定し、上流のvoice一覧へ透過する。SAAAの固定voiceを外す際は このendpointをmodel別voice discoveryの正本として使用できる。

4. 通常推論とLARM personal-state拡張の境界

portableな契約とLARM拡張
利用形態 必要な入力 保証
通常Chat Completions Bearer、model、messagesと通常parameter 応答生成。LARM context／attempt receipt／削除保証は含まない
context view使用 明示Allocation、x-larm-context-view-id、対応するcontext APIとrelease binding 固定viewを対象runtimeへmaterializeし、requestへ結び付ける
generation attempt使用 明示Allocationまたはclaimed Provider、x-larm-attempt-id、personal-state権限 forwarded／terminal／cancel／stop stateを別APIのreceiptとして確認する

この確認で、通常経路にx-larm-attempt-idだけを付けた場合にheaderが無視され得る問題を 修正した。現在は明示Allocationまたはclaimed Providerがなければ 400 allocation_requiredで拒否し、独自保証がないのに通常成功へ見える状態を防ぐ。

contextをSAAAが通常のmessagesへ展開すれば、会話生成に必要なtext文脈はcloudへ持ち運べる。 一方、source digest、data epoch、固定view identity、snapshot／slotの再利用、attempt receipt、backend停止確認、 forget operation、削除完了証跡はmessagesだけでは維持できない。これらを要求したturnは、cloud切替後に 同等成功として扱わず、保証低下を利用者または上位state machineへ返す。

5. 稼働状態、error、cancel、lease、fallback

通常推論で観測できる主な分類
状態 現行の観測方法 retry
未対応model 404 model_not_found 設定変更まで不可
準備中 通常callは内部で待機。local-nodeの接続・Model Broker待機は300秒で、deadline後は 503 model_loading_timeout Retry-After: 1付き。client側総予算内だけ再試行
容量不足／queue満杯 429 allocation_capacity、resource_exhausted、 queue_fullまたはqueue_timeout Retry-Afterを尊重し、表示・tool・再生開始前だけ再試行候補
upstream障害 502 upstream_unavailableまたはprotocol／response不正 副作用開始前に限って別Provider候補
timeout 504 gateway_timeoutまたはupstream_transport_timeout 結果が表示・実行されていないことを確認できる場合だけ候補
draining／quarantine 503、codeで原因を区別 release収束またはoperator復旧後

Retry-AfterはModel Brokerの一部の429／503、execution queueの429、upstreamが返した headerで保持される。ただし全503に付く保証はない。通常client向けには available、preparing、capacity、failed、unsupportedをrequest前に取得するmodel別endpointがなく、 /v1/modelsは静的なID一覧、/v1/activityはdaemon全体のidle／active／drainingである。 Agent ConnectionのProvider healthはより詳細だが、通常data planeとは別のbootstrap契約である。

HTTP requestのabortは待機queue、upstream fetch、response readerへ伝播し、LARMの実行枠と内部参照を 解放する。これでclient待機は止まるが、各engineが計算を直ちに停止したことまでは共通保証しない。 personal-state attempt cancelはbackend stop stateをreceiptに残せるため、通常abortより強いLARM拡張である。

通常三APIの内部leaseはLARM所有で、SAAAによるrenew／releaseは不要である。明示Allocationではrenewと release APIを使う。releaseは記録が保持される間は再実行しても200を返すが、boot変更または履歴削除後の 永続的な冪等性は保証しない。

通常Model Brokerは公開modelを別modelへfallbackしない。responseのmodelは要求した公開modelへ 正規化され、x-request-idとx-larm-boot-epochを返す。内部route／runtimeは監査eventへ残るが、 cloudへの切替理由を表す公開fieldはないため、SAAAがProvider試行履歴、切替理由、実際に採用したmodelを turn単位で記録する。

LARM側の必要な変更と依存関係

  1. 公開model manifestへprotocolとmodel別能力を追加する。LLMはSSE、tools、JSON Schema、 reasoning effortの対応値、token parameter名と上限、ASRは入力／応答形式と言語／話者metadata、 TTSは既定voice、voice一覧、音声形式、sample仕様、native streamingを表す。
  2. manifestをGET /v1/modelsのnamespaced extensionまたはversion付きLARM endpointで公開し、 同じmanifestからrequestを事前検証する。未対応fieldは 400 unsupported_parameter、値違反は400 invalid_valueとしてparam名を返す。
  3. GET /v1/audio/voices?model=...を通常Bearerで利用可能にする。これは実装済みで、 bodyなしrequestからmodel別Bindingを自動取得して上流voice catalogを返す。
  4. model別statusをavailable、preparing、capacity、failed、unsupportedで返し、snapshot時刻、 有効期限、retry可能性、Retry-Afterを定義する。LLM、ASR、TTSを別々に評価し、一機能の障害で catalog全体を使用不能にしない。
  5. OpenAPIへASR multipart、OpenAI形式error、SSE終端条件、音声media type／header、capability／status schemaを追加する。現在の/openapi.jsonはASR request bodyとmodel差を十分に表さない。
  6. live conformanceへtool arguments分割、reasoning delta、Structured Outputs、途中EOF、WAV ASR、 24 kHz mono s16le PCM、TTS first playable byte、cancel後のengine停止状態を追加する。

共同受入の順序

  1. 固定release identityのLARMで三APIの通常Bearer conformanceを実行する。
  2. LLM JSON、SSE、tool round trip、Structured Outputs、途中切断をmodelごとに確認する。
  3. ASR WAVとTTS WAV／PCM、voice discovery、first playable byte、cancelを確認する。
  4. 「ASRだけcloud」「TTSだけ別Provider」を独立した選択stateで確認する。
  5. ローカルLLMの429／503時だけ、総timeoutと試行予算内でcloudへ切り替える。
  6. 表示、tool実行、音声再生のいずれか開始後は自動再生成せず、重複副作用がないことを確認する。
  7. personal-state保証を要求したturnでは、cloud切替が同等成功に見えないことを確認する。
