採用する方針

  • 既存のLocal Service名称、LocalServiceManager、利用権APIとClientLocalServicesを維持する。別のApp Runtime Managerや汎用container管理frameworkは追加しない。
  • Linux標準backendとしてsystemd-processを追加する。Docker daemon、image、仮想OS、アプリごとの固定RAM領域は標準方式の前提にしない。
  • ホストprocessもサービス専用cgroupで所有・資源・終了を観測する。環境変数の分離だけで子孫processの停止を保証しない。
  • 登録済みで信頼するアプリを対象とする。host filesystem保護とprivate状態は誤書込み防止のために使い、未知コードに対する強いsecurity boundaryとは扱わない。
  • 既存systemd-container-groupは互換性と明示選択のために保持する。今後の標準サービスにコンテナを要求せず、VMや新コンテナbackendを追加実装しない。
  • メモリー効率はhost全体の実測で判断する。共有ファイル、共有推論process、論理予算、使用上限、物理断片化を区別する。

責務と実行経路

Consumerのensure → 既存認可 → LocalServiceManagerの利用権・起動集約 → 資源受付 → 登録済みbackend → systemd unit起動 → 所有instance観測とApp readiness → ready leaseのendpoint、という経路を維持する。 停止は全利用者と活動の確認 → drain → 再確認 → 所有process群のTERM → 完全終了の観測 → 資源解放とする。

定義・観測契約の最小変更

  1. local-services.v1を引き続き読めるようにし、process定義はv2のbackend別strict schemaで追加する。backendを省略して旧設定の意味を変えない。新規設定の生成時はsystemd-processを選ぶ。
  2. process側のdeploymentは承認済みunit、release、manifestDigest、固定endpointを持つ。実行ファイル・argv・cwd・許可envは管理者が準備したunitとreleaseの内容に固定し、consumerのensure bodyへ載せない。
  3. HTTP readinessのpath、期待statusと必要capabilityを承認済み定義へ移す。doclingのsource_management要件を維持し、他Appにdocling固有capabilityを要求しない。汎用のJSON式評価frameworkは不要。
  4. 観測にbackend種別、opaqueなinstanceToken、明示的な停止確認、observedAtと資源観測を持たせる。未知観測、読込み失敗、unit inactiveだけを完全停止の証拠にしない。
  5. process側のinstanceTokenはhost boot、unitのInvocationID、member構成、releaseから作る。MainPIDとControlGroupは診断・所有照合に使う。PID再利用と、同じunit名での別起動を区別する。
  6. stop操作へ期待instanceTokenを渡し、制御直前に同じinstanceであることをbackend側でも確認する。unitを操作する前後に変わったinstanceを勝手に停止・adoptしない。
  7. journalをv2へ移行し、v1のcontainerIdsは既存container adapterの識別へ正規化する。移行は元fileを保存してatomicに行い、revision不一致・未知所有は資源を保持してfailedへする。daemon再起動時の旧lease失効は維持する。

初期の公開lease、HTTP endpoint、ensure/renew/releaseと利用者認可は維持する。 lifecycleはon-demand・単一instanceから開始し、always-on/manual、dynamic port、MCP stdioは独立の追加契約とする。 複数unitのサービスは承認済みmember一覧で必要数を定義する。固定targetを入口にしても、targetのactiveだけを稼働や終了の根拠にせず、全memberのinstanceとcgroupを確認する。

一つのメモリープールを有効に使う手順

phase 1では既存のstartupReservationBytesと静的admissionを維持し、backend変更と容量policy変更を同時に行わない。 doclingの9 GiBも実測前に引き下げない。OSのMemoryMaxは異常増加の上限、LARMの予算は同時実行を承認する見込み容量、観測値は現在の使用量として扱う。 MemoryHighは必要な実測が揃ってから調整する。低く設定しすぎるとreclaimによりforegroundとAppの遅延を増やすため、単なる節約設定にはしない。

通常停止・異常停止・再起動

  1. 有効lease、queued/running job、active request、processor処理のいずれかがあれば通常停止しない。lease失効だけでjobが終わったとみなさない。
  2. idle期間を満たしたらdrainで受付を閉じ、同じApp boot IDとtokenのゼロ活動を再確認する。drain中の新規ensureは既存の停止取消・再起動競合制御を維持する。
  3. 期待instanceを照合した固定停止controllerから全memberへTERMを送る。systemdはKillMode=control-group、SendSIGKILL=noを明示し、通常停止の無断強制終了を避ける。
  4. unit状態と全所有cgroupの空、所有listener/socketの終了を確認した後だけstoppedを返し、予算と一時物を解放する。観測失敗や期限超過はfailedとし、endpointを引き上げて予算を保持する。
  5. 強制終了は管理者の別手順とする。通常APIから利用できるforceを追加しない。固定停止unitは入口unitがfailed/inactiveでも実行できるようにし、勝手に置き換わったinstanceをkillしない。
  6. App unitは初期Restart=noとし、次のensureでLARMが起動を決める。daemon再起動ではjournal、unit InvocationID、App boot IDとreleaseを照合し、未知の既存processを採用しない。job POSTを自動再送しない。

すべての信頼済みAppがTERMで必ず終了するとは保証できない。「無断でjobを中断しない」と「停止期限以内に必ず全processが消える」は同時には約束しない。 RAM効率のために、停止未確認の予算を解放してはならない。 prepare/buildの子processも専用unitで扱い、失敗時にcompilerやinstallerがホストへ残らないようにする。

doclingをホストprocessへ移す具体案

隣接docling-deskはcleanなcheckoutの94f4351142afad6326058c373443bf1c2c8ffccdを読取り確認した。 Bun Knowledge APIとPython processorは既に分かれ、workerはLARM activity/drain連携を持ち、model/state/cacheは環境変数で指定できる。 本体の変更・pull・install・起動はしていない。SAAAの実装は今回使用しない。

  1. Knowledge APIはそのlockと指定Bun版を使う。LARM本体と異なるruntime版を無理に統一せず、共有runtime catalogで版別に用意する。
  2. Python processorを将来導入する場合は実際の解析・描画・OCR経路から必要依存を確認し、版を固定する。Dockerfileの依存一覧をホストへの導入指示へ流用しない。LibreOffice等を環境基盤の前提にはしない。App機能を勝手に変更せず、推論時のapt/pipや利用者HOMEへのinstallを避ける。
  3. モデルは既存download/verify工程でrepository外のsnapshotへ用意し、DOCLING_MODELS_DIRへread-onlyで渡す。DOCLING_STATE_DIR、DOCLING_DATA_DIR、DOCLING_CACHE_DIR、DOCLING_ENV_FILEを明示してsource checkoutの既定保存先を使わせない。
  4. APIとprocessorを二つのforeground unitにし、一つの論理docling serviceとして制御する。processor ready → API readyの順に確認し、停止はApp groupのdrain後にAPI・processor全体を終了する。unit間のstop伝播と順序を明示して実機検証する。
  5. 両HTTP入口を127.0.0.1へbindし、固定portの競合を確認する。Composeのprocessor DNS名はloopback endpointへ置き換える。loopbackはnetwork isolationではないので、private APIのtoken認証と外向き連携の承認条件は維持する。
  6. 同じartifact rootを両processが使い、API DBはAPI専用とする。既存volume内にdataがある場合は停止中にbackupし、コピー・所有権・DB整合を検証してから切り替える。旧volumeを稼働中に二方式から同時更新しない。
  7. 初期はHTTP API、CPU資料変換、offlineモデル、lease、drain、再起動、data保持を将来のApp受入条件とする。実際に選定した処理のTMP、子process回収と書込み境界を確認する。今回はAppの機能・変換方式を変更しない。

各段階の実装ではbun run checkを通し、配備のunit・controller・installerも検証する。 実機受入はhost idle、cold起動、steady ready、最大fixture job、停止後、既存AIとのmixed workloadで比較する。 メモリーはhost availableと非reclaimable使用量、必要なGPU観測、資源圧迫、swap、起動時間、foregroundの応答遅延を記録する。 待機時の予算解放とphysical RAM減少を別の成果として示し、コンテナ比較環境がなければ測定済みの比較結果とは呼ばない。

既存成果の保持とrollback

まず現行container設定の読取りとsourceを保持してprocess backendを追加する。 doclingの標準設定を切り替えるのはnative受入後とし、利用中のleaseがあれば停止・切替を拒否する。 切替では新revisionとgenerationを使い、古いendpoint利用権を継続扱いしない。 新processを確実に停止してdata互換を確認してから前releaseへ戻す。同じport・dataに旧方式と新方式を並行起動しない。 旧コンテナが未配備なら、container rollbackを即実行可能とは扱わず、sourceだけの保持と区別する。

今回は方針・計画をSpec HTMLで保存し、コンセプト案内と旧計画へ後継を明記する。 ChatGPT Pageの製品コンセプト正本は今回編集していないため、Pageへの同期は未実施。 新しい標準方針、過去の個別配備案、source実装、未完了の実機受入を別々に記録し、判断の継承を保つ。
