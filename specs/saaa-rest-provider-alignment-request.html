Gnosis側はsystemd常駐化、credential、polkit、UFW /32 rule、create・poll・claim、semantic health、SSE、DELETE、短期token失効までacceptance済みです。秘密を含まない結果はCommissioning Evidenceを参照してください。

依頼内容

SAAAがprofileとaudienceをREST APIへ要求し、claim responseからOpenAI-compatible接続設定を動的に 構成して推論し、終了時にConnectionを解放するadapterを実装してください。

SAAAからgnosisへの接続はTCP 9810のREST APIだけを使用します。SSH、SFTP、SCP、SSH tunnel、port forwardingは使用しません。

実装するREST lifecycle

  1. 一意なIdempotency-Keyを付けて POST /v1/agent-connectionsを呼びます。 
    {
  "agentProfile": "deep-reasoning-35b",
  "audience": "saaa-desktop",
  "client": "saaa-desktop",
  "ttlSeconds": 300,
  "allowFallback": false,
  "deploymentPolicy": "existing-only"
}
  2. responseがpendingまたはprobingなら、 GET /v1/agent-connections/:idをbounded pollしてreadyを待ちます。
  3. ready後、POST /v1/agent-connections/:id/claimへ {"format":"openai-provider-v1"}を送ります。claimには Idempotency-Keyを付けません。
  4. claim responseのaudience、model、expiryを検証し、OpenAI clientへ次をそのまま設定します。
    • baseURL = provider.configuration.fields.baseURL
    • model = provider.configuration.fields.model
    • apiKey = provider.credential.token
  5. claimされたsemantic health URLを短期tokenで確認します。
  6. stream:trueで推論し、非空completionとSSE [DONE]を確認します。
  7. 成功、失敗、cancelの全経路で長期API tokenを使い DELETE /v1/agent-connections/:idを呼び、204を成功とします。

SAAA側の要件

  • Providerのbase URL、model、短期tokenを固定設定またはdiskへ保存しない。
  • allowFallback:falseとexisting-onlyを明示する。
  • pollとtask executionにtimeout・cancelを実装し、releaseは独立したbounded処理にする。
  • 401、409、410、429、503を明示的な失敗として扱い、SSHや別Providerへ迂回しない。
  • daemonのboot epoch変更またはConnection expiry後は、新しいConnectionを作成する。
  • renewを利用する場合は旧短期tokenが失効するため、renew後に再claimしてOpenAI clientを更新する。
  • token、Authorization header、claim response全体、prompt、completion本文をlogしない。

SAAA側から回答してほしいこと

  1. firewall許可済み送信元192.168.0.76がSAAA Macの現行IPv4であることの確認。
  2. control URLとAPI tokenを設定するSAAA側の設定名・secret保存先。
  3. adapterの実装ownerとreview commit。
  4. Gnosis側の準備完了後にLAN canaryを実行できる時間帯。
  5. REST-only、dynamic claim、SSH不使用へのacknowledgement。

LAN canary

  1. SAAA Macから未認証control requestが401になることを確認します。
  2. 認証付きでcreate、poll、claim、semantic health、SSE inference、DELETE releaseを実行します。
  3. claim responseだけからOpenAI clientが構成されていることを確認します。
  4. release後にConnectionとworkerが残っていないことをGnosis側と照合します。

証跡にはtimestamp、release commit、config revision、HTTP status、SSE完了、release結果だけを含め、 token、Authorization header、prompt、completion本文を含めないでください。

完了条件

  • SAAAがRESTだけでAgent Connection lifecycleを完了できる。
  • claim responseからProvider設定を動的に構成できる。
  • deep-reasoning-35bのSSE inferenceがfallbackなしで完了する。
  • 成功・失敗時ともDELETE releaseを実行し、resource leakがない。
  • SSH、direct Provider、Cloud fallbackを使用しない。
