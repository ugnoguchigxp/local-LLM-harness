local-node側はsystemd常駐化、credential、polkit、UFW /32 rule、create・poll・claim、semantic health、Native WebSocket、DELETE、短期token失効までacceptance済みです。秘密を含まない結果はCommissioning Evidenceを参照してください。

依頼内容

SAAAがprofileとaudienceをREST APIへ要求し、claim responseからOpenAI-compatible接続設定を動的に 構成して推論し、終了時にConnectionを解放するadapterを実装してください。

SAAAからlocal-nodeへの接続はTCP 9810のREST APIだけを使用します。SSH、SFTP、SCP、SSH tunnel、port forwardingは使用しません。

実装するREST lifecycle

  1. GET /v2/agent-profilesのdefaultAgentProfileが coding-default、該当ProfileのselectionPolicyがdefault、 streamingProtocolがsaaa.llm-stream.v1であり、 supportedCapabilitiesがgeneral・reasoning・codingを含むことを確認します。
  2. 旧adapterがGET /v1/agent-profilesと静的 deep-reasoning-35bを使用する場合、v1のstrict shapeを受理し、返されたProvider modelがcoding-defaultであることを確認します。Profile IDとProvider modelを 同一と仮定してはいけません。
  3. 一意なIdempotency-Keyを付けて POST /v1/agent-connectionsを呼びます。 
    {
  "audience": "saaa-desktop",
  "client": "saaa-desktop",
  "ttlSeconds": 300,
  "allowFallback": false,
  "deploymentPolicy": "existing-only"
}
  4. responseがpendingまたはprobingなら、 GET /v1/agent-connections/:idをbounded pollしてreadyを待ちます。
  5. ready後、POST /v1/agent-connections/:id/claimへ {"format":"openai-provider-v1"}を送ります。claimには Idempotency-Keyを付けません。
  6. claim responseのaudience、model、expiryを検証し、OpenAI clientへ次をそのまま設定します。
    • baseURL = provider.configuration.fields.baseURL
    • model = provider.configuration.fields.model
    • apiKey = provider.credential.token
  7. claimされたsemantic health URLを短期tokenで確認します。
  8. claimのstreaming.urlへ短期Provider tokenで接続し、非空completionとterminal integrityを確認します。
  9. 成功、失敗、cancelの全経路で長期credentialなしにDELETE /v1/agent-connections/:idを呼び、204を成功とします。

SAAA側の要件

  • Providerのbase URL、model、短期tokenを固定設定またはdiskへ保存しない。
  • v2 ClientはselectionPolicy: compatibilityまたはdeprecated: trueのProfileを 自動選択しない。
  • allowFallback:falseとexisting-onlyを明示する。
  • pollとtask executionにtimeout・cancelを実装し、releaseは独立したbounded処理にする。
  • 401、409、410、429、503を明示的な失敗として扱い、SSHや別Providerへ迂回しない。
  • daemonのboot epoch変更またはConnection expiry後は、新しいConnectionを作成する。
  • renewを利用する場合は旧短期tokenが失効するため、renew後に再claimしてOpenAI clientを更新する。
  • token、Authorization header、claim response全体、prompt、completion本文をlogしない。

SAAA側から回答してほしいこと

  1. firewall許可済み送信元192.168.0.76がSAAA Macの現行IPv4であることの確認。
  2. control URL、profile、audienceを設定するSAAA側の設定名。
  3. adapterの実装ownerとreview commit。
  4. local-node側の準備完了後にLAN canaryを実行できる時間帯。
  5. REST-only、dynamic claim、SSH不使用へのacknowledgement。

LAN canary

  1. SAAA Macから匿名Agent Profile/Connection requestが成功し、匿名の通常control requestは401に なることを確認します。
  2. v2 Profile APIからQwen 3.8 27Bが唯一の既定Profileとして選択されることを確認します。旧35B 名が存在する場合もdeprecated compatibility aliasであり、canonical profile、Provider model、 allocation bindingがQwenを示すことを確認します。
  3. 長期credentialなしでcreate、poll、claimを行い、短期tokenでsemantic health、Native WebSocket inferenceを実行して、匿名DELETE releaseまで完了します。
  4. claim responseだけからOpenAI clientが構成されていることを確認します。
  5. release後にConnectionが残らず、Resident Qwen 3.8 27Bが稼働を継続していることをlocal-node側と 照合します。

証跡にはtimestamp、release commit、config revision、HTTP status、WebSocket完了、release結果だけを含め、token、Authorization header、prompt、completion本文を含めないでください。

完了条件

  • SAAAがRESTだけでAgent Connection lifecycleを完了できる。
  • claim responseからProvider設定を動的に構成できる。
  • coding-defaultのNative WebSocket inferenceがfallbackなしでQwen 3.8 27Bにより完了する。
  • 成功・失敗時ともDELETE releaseを実行し、resource leakがない。
  • SSH、direct Provider、Cloud fallbackを使用しない。
