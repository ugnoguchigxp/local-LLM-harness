評価

目的、非目的、共有資源と個別状態の区別が明確で、LARMの軽量なオンデマンド制御に適している。 Linuxではsystemdによるホストプロセス管理とcgroupを標準候補にできる。 既存LocalServiceManagerの利用権、起動集約、readiness、活動確認、受付停止、停止競合保護、世代管理、再起動照合を再利用し、 Local Serviceという既存名称を維持する案を推奨する。別のApp Runtime Managerを並設する必然性は現時点ではない。

添付をそのまま使うと、既に実装済みの仕組みを再調査・再実装したり、六言語と三OSの汎用frameworkへ初期範囲が広がる恐れがある。 最初に既存実装との適合表を作り、単一Linuxホストの承認済み一サービスにホストプロセスbackendを追加する範囲へ絞るとよい。 先日のコンテナ案はdoclingの分離配備に対する個別案として扱い、今回の標準方式と同一視しない。

先日の実装と今回の位置付け

  • 先日のプロンプト評価は、systemd・コンテナ・VMを条件に応じて比較した記録である。今回の添付とは評価対象が異なる。
  • docling分離配備計画は、APIとCPU processorをrootlessコンテナで管理する個別設計。
  • 実装結果には、LARM側のsource実装と実機受入の未完了が記録されている。
  • 今回の確認でもdockerとpodmanはPATHに見つからず、docling起動unitはLoadState=not-found、ActiveState=inactiveだった。コンテナの運用開始やメモリー改善の実測を確認したものではない。

過去の成果を捨てる必要はない。サービス制御の共通部分を維持し、実行backendの選択を追加する。 今回の評価は新標準の採用決定ではなく提案であり、過去の計画を無断で決定済みの新方針へ書き換えない。

メモリー共有について修正すべき前提

Linux nativeコンテナはVMのようにguest OSと固定の仮想RAMを必ず持つ方式ではない。 memory.maxやDockerのmemory limitは使用上限であり、その量のRAMを事前に占有する指定ではない。 同じimage layerはストレージ上で共有できるため、「コンテナごとにOS・runtime・全ファイルが必ず複製される」とは評価できない。 コンテナを避ける理由は、今回不要な配備・image・daemon管理を減らすことと、共有資産の運用を単純化することに置くと正確である。

分断・重複の種類と対策
種類 評価と対策
物理RAMの固定分割 cgroupの使用上限は物理RAMの区画を固定確保する機能ではない。コンテナを廃止すれば物理断片化が解消するといった保証もない。allocator・driverの断片化は別の実測課題。
予算による容量の使い残し 現状の9 GiBはLARMの論理的な受付予算。実使用量が少なくても静的admissionでは9 GiBを差し引く。起動peak、平常使用量、ジョブ追加分、OS上限を分ける候補があるが、未観測分を消して危険なovercommitへ変えない。
モデルの重複ロード 同じweightファイルを共有しても、別processで展開したtensor・GPU allocation・KV cacheまで一つになるとは限らない。重量級の推論は共有Providerへの呼出しに集約する。App内に埋め込まれたモデルは利用経路を確認して移行可否を判断する。
runtimeと依存の重複 共有runtime実行ファイルとpackage取得cacheはSSD効率を改善する。各processのheap、module state、JIT等まで共有できるという意味ではない。lockfile・ABI・toolchainが異なる依存まで無理に共通化しない。
共有ページの二重会計 共有ページは複数cgroupから使えても、課金先は単純な等分とは限らない。RSSの総和を物理使用量と扱わず、host MemAvailable、cgroupの使用量と内訳、必要ならPSSを目的ごとに使い分ける。
CPU/GPUのUMA 登録上このnodeは128 GBでOS等の安全床が16 GB。CPU RAMとGPU表示容量を独立poolとして足さない。driverによる確保・予約・計測の関係は実機確認が必要で、cgroupだけで全GPU割当を把握・制限できるとはしない。

最優先は「重いモデルを共有Providerで一度だけロード」「起動中・ジョブ中の将来増加を含めた一つの資源会計」 「必要なときだけ起動して完全終了を確認」である。LocalProcessへ移せば必ず何GiB節約できるという実測根拠はまだない。

停止の保証を曖昧にしない

既存実装はジョブ保護を優先し、通常停止でTERMだけを送り、終了未確認なら資源予算を保持する。 「必ず全子プロセスを消す」「自動強制終了しない」「猶予以内に必ずstoppedになる」は同時には保証できない。 初期は既存のdrainと利用権保護を維持し、失敗時はfailedとしてendpointを引き上げ、予算を保持する。 許可された強制終了は別の管理操作とし、通常停止との境界を設計する。

systemdのKillMode=control-groupはunitに残る子孫を対象にするが、標準では期限超過後にSIGKILLへ進む。 既存のTERM限定を継承するprocess backendではSendSIGKILLの設定を明示する必要がある。 cgroupが空であること、所有するlistener/socketが消えたこと、leaseとendpointが無効になったことを停止完了の受入条件にする。 persistent data・承認済みbuild・共有cache・保持期限内のlogsは「停止時の痕跡除去」の対象から除く。

最小の実装順序と受入条件

  1. 既存container backendの動作を維持しつつ、containerIdsをbackend別のinstance観測へ一般化し、2個固定条件をcontainer adapterへ移す。journalは版を上げ、旧記録の移行・未知所有の隔離を検証する。
  2. 一つの承認済みHTTPサービスにSystemdProcessBackendを追加する。固定portと完成済みentrypointで、利用者二人の起動集約、private HOME/TMP、子プロセス終了、idle競合、daemon再起動を確認する。App側の活動契約がないサービスへ既存docling契約を擬装しない。
  3. 必要な言語だけprepare処理と共有取得cacheを整える。実行時build/pullを避け、異なる依存lockの共存、再起動でbuildを繰り返さないこと、cacheを変更して他Appを壊さないことを確認する。
  4. AIを使用するAppを既存Profile解決とallocationへ接続する。必要なProviderをjob中に保護し、最後の利用者が解放した後に各policyで停止する。同じ解決先を使う二Appがモデルを二重起動しないことを確認する。
  5. cold/startup/ready/job peak/停止後の回収、startup時間、ホスト空き容量、GPU観測、foreground遅延を測定する。必要なら起動予算と平常予算を分け、追加jobもadmissionしてから既存のmedia相互拒否を段階的に見直す。測定前に静的予算を単なる現在値へ置き換えない。

dynamic port、Windows/macOS、全言語adapter、Container/VMの新実装は初期の必須成果物にしない。既存doclingのホストprocess移行も、外部アプリの構造と失われる隔離を確認してから別の受入にする。

プロンプトへ追記するとよい条件

  • LocalServiceManager等の既存成果とdoclingの個別コンテナ配備案を調べ、再利用・変更・追加を分ける。別managerを新設するなら必要性を示す。
  • コンテナの使用上限、LARMの受付予算、実使用量、ファイル共有、ロード済みモデル共有、物理断片化を区別する。UMAではCPU/GPU容量を二重計上しない。
  • AI依存の選択はAgent Profile → route → runtime → backendを守る。Appごとのモデル内蔵を共有Provider化できるかは実装確認で判断する。
  • 初期対象はLinux一ホスト、一サービス、固定port、承認済み完成成果物。一般APIからcommand・env・cwd・imageを指定させない。
  • lease/heartbeatだけでなくjob・WebView・stdio接続の寿命、停止中ensure、起動失敗と再試行、再起動journal照合を受入条件に入れる。
  • 上限は物理予約にしないが、安全な同時起動の予算は維持する。共有cacheの管理者、排他、版、読書き権限とGCを決める。
  • 通常停止のジョブ保護と強制cleanupを分ける。「痕跡を残さない」は一時物・実行process・所有socketに適用し、永続dataを消さない。
  • RAM節約はprocess方式へ移すだけでは確定しない。起動peakと混合負荷を測定して判定し、事実・提案・未検証を区別する。
