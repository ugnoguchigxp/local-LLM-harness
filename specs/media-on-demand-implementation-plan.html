画像・楽曲生成のオンデマンド実装計画

2026-10-06の利用者合意に基づく計画。公開APIは常時稼働し、受理した要求に必要なモデルを起動・ロードして生成し、成果物をLARM側へ保存した後にモデルプロセスを停止する。APIは停止後も結果と成果物を配信する。本書は提案であり実装・配備完了を表さない。

境界と完了条件

常時稼働するAPIとはlarm-daemonのControlと成果物配信を指す。画像・楽曲の内部HTTP workerはモデルと一緒に停止してよい。モデルを内部APIと別プロセスに分離することは初期実装の必須条件にしない。外部クライアントは内部workerへ直接接続しない。

処理順は、認証・入力検証、profile/service/modelからのruntime解決、実行枠予約、資源確認、worker起動、モデル準備完了、上流への生成POSTを1回、成果物取得と永続化、worker停止確認、結果公開とする。画像の応答と楽曲completedは保存・停止確認の後に確定する。生成POSTの自動再送は行わない。

起動準備待ちはGET等の照会で行う。停止中のworkerがhealthに応答しないことは正常であり、公開APIのreadinessと区別する。モデル稼働状態と生成可否は別に表示する。

画像応答のartifactsにはid、contentUrl、mimeTypeを含む既存のartifactオブジェクトを格納する。contentUrlはControl URLに対する相対URLで、モデル停止後も取得可能。内部workerの応答契約と公開応答契約は分け、workerに互換フィールドを強制しない。

実行管理の変更

初期実装では画像と楽曲を合わせて実行中1件に制限する。画像は混雑時409を返し、モデルを起動しない。楽曲の受理済みjobは上限付きキューで待機し、他の画像・楽曲処理が終わってから実行する。キュー上限と待機期限を設定として検証し、上限到達は503、期限超過はjobの明示エラーにする。先行する楽曲待機要求を画像が無期限に追い越さないよう予約順を管理する。

packages/coreはprofile/service/model解決、policy、要求検証を担当する。packages/backendsのMediaVariantManagerは共有実行枠とOS操作adapterを持ち、idle、starting、ready、generating、persisting、stopping、faultedの状態を追う。daemonはAPIと生成・保存の順序を担当する。画像・楽曲以外のProviderは明示された資源・priority policyに従い、モデル名だけで停止対象にしない。

releaseはPromiseを返し、呼び出し元が停止完了をawaitする。停止中は予約を保持し、新しいworkerを起動しない。起動失敗・起動中abort・closeの全経路で起動途中のunitも停止する。closeは非同期drainへ変更し、新規受理停止、進行中処理の期限付き待機、期限超過時abort、worker停止を順に行う。

画像providerおよび楽曲OnDemandMusicProviderだけに所有権を閉じ込めず、保存処理まで含む要求またはjobの実行範囲で予約を所有する。楽曲の現在のwrapperはファイル保存より先にreleaseするため、managerの保存完了後へ移す。画像はworker保存後にControl側でmetadata、実ファイル、サイズ等を検証し、原子的な保存完了を確認する。

起動・ロード・停止

画像workerに明示的な準備処理を設け、モデルload完了を示すreadyを照会可能にする。現在のhealthのloaded: falseを生成readyと扱わない。ready確認後に生成POSTを送る。ACE-Stepは配備済みバージョンのロード契約を調査し、必要な初期化と生成モデル準備の確認をadapterへ実装する。単なるHTTP 200だけで判定しない。

runtime-variant.shのsystemctl操作には期限を設ける。起動は資源確認からモデルreadyまでを期限内に収め、失敗時はunitを停止する。停止はinactiveかつプロセス消滅を確認する。SIGINTの猶予後はsystemdがunit配下のプロセスを確実に終了する設定を確認する。停止済みへのstopは成功として扱う。

unitは自動起動を無効にし、モデルworkerのRestart=on-failureはnoへ変更する。再起動をLARMの要求管理の外で行わない。daemon再起動時は管理対象の画像・楽曲unitと回収途中jobを照合し、所有者のないworkerを停止する。API readynessを上流常時起動に依存させない。

起動・生成・停止の期限を別々に設定し、全体の上限も定義する。画像同期APIのcold-start時間に対してControl、HTTP接続、クライアントのtimeoutを照合する。同期で収まらない場合の画像job APIは別の契約変更として扱い、この実装へ暗黙に混ぜない。

失敗と成果物保護

起動失敗、ready期限超過、上流接続失敗、生成失敗、成果物保存失敗、停止失敗を区別する。ユーザー向けには識別可能なcodeを返し、内部ログではrequest/job ID、runtime、phase、unit状態を関連付ける。tokenやprompt全文を不要に記録しない。

成果物保存後に停止が失敗しても成果物は削除しない。画像は停止失敗の503応答にartifact参照を含め、楽曲はfailed jobに保存済みresultと停止エラーを残す。この場合にも認証付きで成果物を取得できるよう、配信判定を単なるcompleted依存から保存済み成果物の検証へ変更する。グループはfaultedとして隔離し、停止の再試行は許可しても生成POSTは再送しない。

画像の接続切断と楽曲DELETEはモデル処理のキャンセルを要求する。上流にキャンセル契約がなければworker停止で終了を保証し、終了確認まで枠を解放しない。キャンセル後に処理が遅れてcompletedへ変わらないよう状態遷移を制御する。

楽曲jobの要求と状態を実行前に永続化する。daemon再起動で中断されたjobは明示的にfailedへ回収し、自動で生成を再実行しない。保存済み成果物は回収して配信する。キューと実行中状態が再起動で消える現在の問題を、モデル後始末と同時に解消する。

実装順序

  1. 公開release、OpenAPI、daemon環境設定、unit、上流endpointと起動権限を読み取りで照合する。2026-10-01の404と接続失敗の原因を現在の状態と区別して記録する。秘密情報は表示しない。
  2. coreのmedia policyと公開schemaを変更し、選択規則、互換画像応答、エラー契約、TTL 0を定義する。設定の読み込みとcatalogの一致を検証する。
  3. backendsの実行管理を非同期停止、共有排他、期限、abort、faulted、drainへ変更する。unitと起動スクリプトの再起動・停止設定を合わせる。
  4. 画像ロードreadyと画像要求の保存・停止処理を実装する。楽曲jobの所有範囲、永続化、停止後の結果確定、回収処理を実装する。
  5. OpenAPI、client schema、利用例、運用文書を更新し、自動検証を完了する。
  6. 既存作業ツリーの変更を保護してreleaseを作り、既存のrelease検証・切替手順で配備する。配備直後のカタログとOpenAPIを再照合する。
  7. SAAAとの各1回の実生成検証を行う。SAAA作業ツリーがdirtyのため、その扱いを解決するまではpullや実装を現行とみなした参照を行わない。

検証と受け入れ条件

  • 入力・認証・model不一致はモデル起動前に拒否する。ロードready前の生成POSTは0回、正常処理の上流生成POSTは1回である。
  • 保存完了より前にstopしない。stop確認より前に同期成功またはcompletedを公開しない。成功後にAPIは稼働し、成果物を取得でき、画像・楽曲workerはinactiveである。
  • 画像・楽曲の同時要求、キュー上限・期限、公平性を検証し、稼働中workerを次の要求で停止しない。
  • 起動・生成・保存・停止それぞれの失敗、起動中と生成中のabort、重複release、shutdown、daemon再起動でworkerと予約が残らない。停止失敗では隔離し、保存済み成果物を保持する。
  • 制御・契約テストでは実モデルを使わず、生成回数と順序を観測する。変更に対応したbackend、daemon、core、client、起動スクリプトのテストを追加する。bun run checkとbun run docs:check:fixを通す。
  • 実機は画像・楽曲各1回だけ。事前起動なしでPOSTし、cold-startを含む成功、Control経由の成果物取得、モデル停止、API稼働を確認する。失敗した際は無条件の再送をしない。

現行契約との差分と確認済み事実はオンデマンド接続調査を参照する。上流ACE-Stepのready契約、cold-start実測とクライアントtimeout、配備環境の停止権限は実装開始時に確定する項目である。
