Agent Provider Connection API 実装仕様

必要なAgent種別をAPIで要求し、LARMがRuntimeをAllocationした後、そのAgentが動的に設定できる LLM・STT・TTS Provider接続情報を返すv1 contractを定義します。接続情報は Allocation固定のLARM Gatewayを指し、llama-swapの内部portや個別Runtime endpointは通常の Agentへ公開しません。

このcontractはdaemon、OpenAPI、TypeScript clientへ実装済みです。公開API全体の正本はAPI契約、検証結果は実装証跡を参照してください。

目的と責務境界

  • 上位Orchestratorは自然言語要求を登録済みagentProfileへ変換し、LARMへ要求する。
  • LARMはProfileを既存RouteとAllocationへ変換し、固定Bindingが実推論可能になった後に Provider descriptorを返す。
  • AgentはdescriptorをSDKまたは一時process設定へ適用し、LARM Gatewayを通じて推論する。
  • Agent processの起動、sandbox、task分配、設定fileの永続化、自然言語からProfileを選ぶ推論は LARMの責務外とする。

Connectionは既存Allocationのfacadeであり、新しいRuntime leaseを追加しません。一つの Connectionは一つのAllocationだけを所有し、既存Allocationの再利用や複数Connection間での共有は 行いません。同じResident Runtimeへ複数AllocationがBindingされることは既存capacity contractの 範囲で許可します。

固定した設計判断

  • requestは自由記述のmodel名、URL、host、port、Runtime IDではなく、version管理された agentProfileとaudienceだけを選ぶ。
  • descriptorはadvertised LARM Gatewayだけを返し、backend endpointを返さない。
  • ProviderごとにAllocation、capability、audienceへ限定した短期credentialを発行する。 LARM_API_TOKENとLARM_MANAGEMENT_TOKENは複製しない。
  • Connection作成principal用のaggregate healthと、Agent用tokenで呼べるProvider単位healthを 分離する。
  • LLM Readyは固定Binding上のmax_tokens: 1の実推論で判定する。TCP、HTTP alive、Runtimeの自己申告healthだけではReadyにしない。
  • Connection control stateはmemoryだけに保持し、daemon restart後はboot epochにより全Connectionと credentialを失効する。
  • Qwen 3.8 27BはResident defaultのままとする。追加27Bと35Bは明示ProfileからだけAllocationする。

処理構成

設定fileとstrict schema

config/local-node/agent-connections.yamlを単一の正本として追加します。top-level versionは整数1、未知fieldは全階層で起動時またはcatalog reload時に拒否します。 identifierは1から128文字の[A-Za-z0-9][A-Za-z0-9._-]*、descriptionは1から256文字、 Provider数はProfileごとに1から8です。 

version: 1
defaultAgentProfile: coding-default

audiences:
  same-host:
    network: loopback
    baseUrl: http://127.0.0.1:9810/v1
  saaa-desktop:
    network: host-private
    baseUrl: request-origin

agentProfiles:
  coding-default:
    description: Resident 27B coding agent
    providers:
      - name: llm
        capability: llm.coding
        route: llm-default
        publicModel: coding-default
        readiness: llm-inference

Cross-validation

  1. defaultAgentProfileは登録済みProfileを一つだけ指し、その全Providerは explicitOnly: falseのRouteを使う。その他のProfileを将来追加する場合は explicitOnly: trueのRouteだけを使う。
  2. 全ProfileでProvider nameとcapabilityをそれぞれ重複させない。
  3. routeは既存Route IDであり、そのRouteのcapabilitiesにProvider capabilityが含まれる。
  4. Routeの全candidate Runtimeが同一protocolを持ち、Provider capabilityを宣言する。fallbackを含む 一候補でも不一致ならcatalog全体を拒否する。
  5. publicModelはidentifierと同じ文字・長さ制約を持つ。同一Profile内で重複させず、 対象Runtimeがその値をOpenAI互換requestのmodelとして受け付けることをcommissioningで 検証する。
  6. Protocolとreadinessは次の対応だけを許す。未知値や組合せ不一致はfail closedにする。
  7. streamingProtocolを広告する場合は、Routeの全primary Runtimeが同じprotocolを 実装していなければcatalog全体を拒否する。

openai.audio-transcriptions.v1 stt-transcription POST /v1/audio/transcriptions

openai.chat-completions.v1はstream: falseまたは省略時のJSONと、 stream: true時のOpenAI互換SSEを同じGateway pathで提供します。 claimは二次transport descriptorを返さず、ProviderのbaseUrl、 protocol、model、短期credentialだけを返します。

Providerはresponseでname昇順に並べます。Profileのcanonical JSONからSHA-256を算出した profileRevisionと、Audienceのcanonical JSONから算出した audienceRevisionをConnectionへ固定します。このfileは既存catalog revisionとrelease identityの入力にも含めます。

この文書のcanonical JSONは、schema既定値を展開し、object propertyをschema記載順、record keyとProvider arrayをidentifier昇順へ並べ、JavaScript JSON.stringify相当のUTF-8・空白なしでserializeした値です。 YAMLの記載順やcommentはrevisionへ影響させません。

Allocation作成時には固定Bindingのcapability、route、Runtime、node、内部endpoint、protocol、active release、runtime contract revision、catalog revisionをcanonical JSONにし、SHA-256 lowercase hexの bindingRevisionを内部生成します。値はresponseへ返さず、Gateway revalidationとsemantic cache失効に使用します。releaseがない場合は空string、runtime contract revisionは active release digest、releaseがないRuntimeはcanonical Runtime定義のSHA-256とします。 各revisionは64文字のlowercase hexです。

Audience validation

baseUrlはabsolute HTTP(S) URLで、userinfo、query、fragmentを禁止し、pathを末尾slashなしの /v1に固定します。parserから得たscheme、hostname、明示または既定portをdescriptorへ返し、 string分割でhostやportを生成しません。

networkごとの起動時条件
値 条件
loopback hostnameは127.0.0.1、::1、localhostのいずれか
host-private hostnameはloopback以外。HTTPまたはHTTPS、operator管理のhost identity、許可CIDR、API・management 認証をcommissioningで確認
tls HTTPS必須。TLS証明書、Gateway認証、Gateway-only network境界をcommissioningで確認

request bodyからURLを上書きできません。request-originは受理したConnection作成requestの 実際のscheme、authority、portだけからcanonicalな/v1 URLを生成し、 X-Forwarded-*は参照しません。host-private Audienceをloopbackまたはwildcard originから作成する要求と未登録Audienceは409 connection_audience_unavailableです。 Connection作成時に解決した値をTTL終了まで固定します。catalogはdaemon起動中に差し替えず、 設定変更時のdaemon restartで全Connectionをboot epochごと失効させるため、active ConnectionのAudienceが途中で変わることはありません。

repository設定はsame-hostとsaaa-desktopを登録します。後者は request-originを使用します。SAAAはmDNS/DNS名または現在のDHCP addressへ直接control requestを送り、claimはその到達先をcanonicalな/v1 URLとして返します。production LARMは0.0.0.0:9810でlistenし、 server設定としてAPI・management tokenを維持し、review済みLAN CIDRだけを許可します。SAAAの 長期control tokenは任意で、短期Provider tokenはConnection TTL内だけ保持します。LAN境界外へ公開する場合は tls AudienceとTLS終端を別途commissioningします。

host-private claimはrequest originと同じhost・portのHTTP baseUrlを返します。LAN境界外ではtls Audienceを選び、同じ OpenAI互換endpointをHTTPSで提供します。

Allocationと全Providerの初回semantic probeが同期完了した場合はHTTP 即時readyの場合はHTTP 201、起動、配備、probeを待つ場合はHTTP 202と Location: /v1/agent-connections/:id、 Retry-After: 1を返します。事前validationまたはadmission失敗ではConnectionを作らず、既存 Allocation errorをそのまま返します。作成後の非同期失敗は状態responseへ保存します。

Status response invariants

  • GET /v1/agent-connections/:idはrecord保持中の全statusでHTTP 200を返し、作成responseと同じ base fieldを持つ。GETはsemantic probeを実行しない。
  • Provider readinessはpending、probing、 ready、failed、released、expiredのいずれか。 claimableはConnectionがreadyで、fresh成功cacheがある場合だけtrue。
  • errorはfailed時だけ必須の{ "code": string, "message": string }、 releasedAtはreleased時だけ必須のRFC 3339 timestamp。それ以外ではfield自体を省略する。
  • 全responseにx-larm-boot-epochとx-larm-config-revisionを付ける。

状態機械と原子性

Connection IDはaconn_<bootEpoch>_<UUIDv4>で生成し、最大192文字です。 current boot epochをIDから判定できるため、旧epochと未知のcurrent IDを410と404へ分離できます。

Connection lifecycle status
Status 条件 遷移先
pending 所有Allocationがpending probing、failed、released、expired
probing Allocationはreadyだが、全Providerの初回semantic成功が未完了 ready、failed、released、expired
ready 全Providerが少なくとも一度semantic probeに成功 failed、released、expired
failed Allocation失敗、初回probe deadline、または固定contract不一致 terminal
released 明示DELETEによりcredentialを失効しAllocationをrelease terminal
expired ConnectionまたはAllocation TTL満了 terminal

readyは初回検証済みというlifecycle状態であり、後続の10秒cacheが期限切れになっただけでは probingへ戻しません。現在の利用可否はhealthのreadyと acceptingRequestsで表します。Allocationがterminalになった場合は同じ原因へ収束します。

  1. Profile、Audience、auth、idempotency、admissionをAllocation作成前に検証する。
  2. Connection IDを予約して一つのAllocationを作り、相互IDを同じcontroller transactionへ登録する。
  3. Allocation ready後、Providerをname昇順に検証する。freshなBinding共有cacheまたはlive probeの全成功で readyへ遷移する。
  4. 初回probeはAllocation期限とLARM_CONNECTION_READY_TIMEOUT_SECONDSの早い方まで再試行する。 retry間隔は既存LARM_STARTUP_POLL_INTERVAL_MSと失敗cache TTLの大きい方とする。ただし固定probeへのHTTP 400、404、405、422は provider_contract_mismatchとして再試行せず、Connectionを直ちにfailedにして 所有Allocationをreleaseする。deadline時もConnectionをfailedにして所有Allocationをreleaseする。
  5. 登録後に予期しないfacade処理失敗が起きた場合もfinally相当の処理でAllocationをreleaseし、 activeな孤立Allocationを残さない。

DELETEはpending operationのcancelとAllocation releaseを行い、record保持中の再DELETEは204で idempotentに成功します。renewはpending、probing、readyだけで許可し、 { "ttlSeconds": 1..86400 }のstrict bodyで既存Allocationと同様に現在時刻から期限を再計算します。renewには作成時と同じschemaの Idempotency-Keyを必須とし、retryでgenerationを二重更新しません。renew成功時はcredential generationを1増やし、全旧tokenを即時失効させます。 

POST /v1/agent-connections/aconn_epoch_uuid/renew
Authorization: Bearer <LARM_API_TOKEN>
Idempotency-Key: renew-agent-task-0182
Content-Type: application/json

{ "ttlSeconds": 900 }

renewはHTTP 200でsecretを含まない最新Status responseを返します。DELETEはbodyなしのHTTP 204です。 failedへの遷移時に所有Allocationがactiveならreleaseし、transientなsemantic probe失敗だけではlifecycleを failedへ変更しません。

Scoped credentialのwire format

署名keyはAPI token、management tokenと分離したLARM_CONNECTION_SIGNING_KEYで指定します。 値は43文字のpaddingなしbase64urlで、decode後ちょうど32 bytesとします。API tokenまたは署名keyが未設定なら 既存daemonは起動したままConnection endpointを503で無効化し、署名keyが設定済みで不正長または不正文字なら daemon起動を拒否します。daemon稼働中のkey rotationは行わず、変更はrestartとして扱います。 

larm_conn_v1.<base64url(payload UTF-8 JSON)>.<base64url(HMAC-SHA-256)>

JSON propertyは次の順序でserializeし、空白を含めません。時刻はUnix secondsの整数で、millisecond時刻をfloorして生成します。signatureはprefixとpayload segmentを.で連結したASCII bytesに対し、decode済み32 bytes keyで計算したHMAC-SHA-256です。 

{"v":1,"epoch":"epoch-example","connection":"aconn_epoch_uuid","allocation":"alloc_epoch_uuid","provider":"llm","capability":"llm.coding","audience":"same-host","generation":1,"iat":1787982300,"exp":1787983200}
  1. token長を4096 bytes以下、segment数を3、prefixを固定値として検証する。
  2. base64urlとpayload schemaをstrictに検証し、未知claim、重複JSON key、非整数時刻を拒否する。
  3. signatureをconstant-time比較し、iat <= now < expを確認する。
  4. memory上のConnection、Allocation、boot epoch、Provider、capability、Audience、現generation、期限と payloadを毎requestで再照合する。署名だけでauthorizationを完結させない。
  5. release、expiry、renew、failed、daemon restartのいずれかで旧tokenを拒否する。

一つのProvider tokenは自身のProvider healthと対応Gateway pathだけを呼べます。aggregate health、別Provider、 Allocation、renew、release、inspection、artifact、release、catalog、metrics、OpenAPIには使えません。 errorとaccess logにtoken、signature、API token fingerprint、probe生成内容を含めません。

Gateway authorizationとmodel固定

既存Gatewayのx-larm-allocation-id認証に加え、Agent tokenをBearerとして受け付けます。Agent token経路ではallocation headerを要求せず、指定されていてもtoken claimと完全一致しなければ拒否します。 tokenのProvider protocolから許可methodとpathを決め、bodyやmultipartのmodelをroute選択には 使用しません。

  • LLM・TTS JSONではmodelがstringかつdescriptorのmodelと完全一致しなければ 400 model_mismatchとし、upstreamへ送らない。
  • STT multipartではmodel fieldを一つだけ要求し、同じ完全一致を検証する。重複fieldも拒否する。
  • 一致したmodel値はそのままupstreamへ渡す。operatorはpublicModelを各Runtimeが受理する値に設定し、 release commissioningで実証する。
  • tokenからConnectionの固定Bindingを取得し、既存Gateway revalidation、body上限、execution gate、timeout、 client cancellationを同じように適用する。別Runtimeへのfallbackやswapをrequest時に行わない。

既存Allocation header経路の互換性は変更しません。Agent tokenと既存API tokenを同じ意味として扱わず、 token prefixを認証middlewareで明示的に分岐します。

Semantic readiness contract

Aggregate healthは全required Provider、Provider healthはpathで指定した一つだけを検証します。どちらも connection、allocation、epoch、catalog、release、Binding freshnessを先に検証し、probeはadvertised URLへのHTTP self-callではなく、同じGateway dispatchと固定Bindingを内部から使用します。これによりprotocol、 tokenizer、scheduler、model forward pass、response serializationまでを通しつつ、Audience DNSやTLSの外部到達性は commissioning testへ分離します。

LLM probe

Requestはcode定数とし、次のJSONからfieldを追加・変更しません。

{
  "model": "<provider.publicModel>",
  "messages": [{ "role": "user", "content": "0" }],
  "temperature": 0,
  "max_tokens": 1,
  "stream": false
}

2xx responseから次のprojectionを型と上限付きで検証します。top-level object、 choices 1から16件、少なくとも一件のinteger index、 message.role === "assistant"、message.contentがstringまたはnull、 usage.completion_tokens === 1をすべて要求します。reasoning modelでcontentが空またはnullでも、 completion tokenが1なら成功です。未知の標準OpenAI fieldはprojection外として無視しますが、message.contentは16,384文字以下、response bodyは 65,536 bytes以下に制限します。必須fieldの欠落、誤型、zero token、2 token以上、malformed JSON、上限超過は 失敗です。生成文字列の内容、品質、指示追従は評価しません。

STT・TTS probe

  • STTはcodeで生成する16 kHz、mono、16-bit PCM、250 ms無音のWAV 8,044 bytesを model=<publicModel>でtranscription endpointへ送り、2xx JSON objectの textが0から4096文字のstringであることを検証する。response body上限は65,536 bytes。transcript内容は評価しない。
  • TTSは{ "model": "<publicModel>", "input": "a", "response_format": "wav" } を送り、2xx、audio/wav、RIFF/WAVE header、非空data chunkを検証する。response body上限は1,048,576 bytes。音質は評価しない。

負荷制御と判定

  • live probeは通常request用queueへ入れず、execution slotを即時取得できる場合だけ実行する。同じcache keyの 同時probeはsingle-flightで一つに集約する。
  • 成功cacheは10,000 ms、失敗cacheは1,000 ms。cache keyはboot epoch、Runtime、release、runtime contract revision、protocol、public model、bindingRevisionの組とする。同じ固定Bindingを使う Connection間でcacheとsingle-flightを共有し、credential renewだけでは失効させない。
  • RuntimeがBUSYでfreshな成功cacheがある場合はready: true、 acceptingRequests: false。成功cacheがないBUSYは 503 provider_probe_busyとする。
  • Health endpointはCOLD Runtimeを起動せず、別workerへのswap、fallback、release activationを行わない。 それらはConnection作成時のAllocation lifecycleだけが行う。
  • probeごとのdeadlineは既定15秒で、timeout時に古い成功結果を延命しない。aggregate probeはProviderをname昇順に 実行し、各Providerへ個別deadlineを適用する。
  • 全Connection health responseにCache-Control: no-storeを付ける。成功はHTTP 200、一つでも未Readyなら HTTP 503とRetry-After: 1を返す。 
{
  "id": "aconn_epoch_uuid",
  "status": "ready",
  "ready": true,
  "acceptingRequests": true,
  "checkedAt": "2026-08-29T06:00:00.000Z",
  "providers": [
    {
      "name": "llm",
      "capability": "llm.coding",
      "ready": true,
      "acceptingRequests": true,
      "probe": {
        "kind": "semantic-inference",
        "protocol": "openai.chat-completions.v1",
        "release": "qwen-worker-fast-current",
        "latencyMs": 412,
        "validated": true,
        "cached": false,
        "observedAt": "2026-08-29T06:00:00.000Z"
      }
    }
  ]
}

失敗時はProviderごとにready: false、acceptingRequests: false、boundedな reason codeを返します。値はconnection_not_ready、 allocation_inactive、stale_state、binding_changed、 provider_busy、probe_timeout、upstream_status、 provider_contract_mismatch、 invalid_responseだけです。prompt、生成token、audio payload、backend endpoint、例外stackは responseへ含めません。Agent tokenでProvider healthを呼んだ場合、responseにはそのProvider一件だけを含めます。 

{
  "id": "aconn_epoch_uuid",
  "status": "ready",
  "ready": false,
  "acceptingRequests": false,
  "checkedAt": "2026-08-29T06:00:00.000Z",
  "providers": [
    {
      "name": "llm",
      "capability": "llm.coding",
      "ready": false,
      "acceptingRequests": false,
      "reason": "probe_timeout"
    }
  ]
}

AggregateのreadyとacceptingRequestsはProvider値のlogical ANDです。healthの503は 上記health schemaを返し、expired、epoch不一致、auth失敗などhealthを評価できない4xxは通常のerror schemaを 返します。

Route、memory、telemetry、Runtime capacity、deployment、swap conflict、draining、catalog reloadの失敗は既存Allocation errorを保持します。healthの503 responseを除く全errorは既存の { "error": { "code": "...", "message": "..." } } strict schemaを使い、messageはsecret、 endpoint、prompt、生成内容を含まないbounded textとします。

Observabilityと情報境界

  • eventは作成、初回probe、ready、claim、renew、release、expiry、failureを記録する。Connection ID、 Allocation ID、Provider name、結果codeは許可し、token、signature、API token fingerprintは記録しない。
  • metric labelはallowlist済みProfile、Audience、protocol、probe kind、outcomeだけとし、Connection ID、 client、model生成内容をlabelにしない。
  • Profile一覧、状態、health、OpenAPIにRuntime ID、node、backend endpoint、内部port、artifact pathを含めない。 management inspectionは既存認証境界を維持する。
  • credentialを含むclaimだけでなく、全Connection endpointへ Referrer-Policy: no-referrerを付け、claimとhealthにはCache-Control: no-storeを付ける。

Acceptance matrix

以下はrepository testと2026-08-29のlocal-node live E2Eで完了しました。実行条件と結果は実装・E2E記録に保存します。

Schema・catalog

  • 全request、response、configでunknown field、範囲外値、重複Providerを拒否する。
  • 未知Route、capability不一致、candidate protocol不一致、readiness不一致でcatalog loadを拒否する。
  • Audience URLのuserinfo、query、fragment、path、scheme、network制約をtable-driven testする。
  • agent config変更がcatalog、profile、audience revisionへ反映される。

Lifecycle・resource

  • 一つのConnectionが一つのAllocationだけを所有し、失敗、DELETE、expiryで孤立Allocationを残さない。
  • 全状態遷移と不正遷移、初回probe deadline、renew generation、二重DELETEをfake clockで検証する。
  • createとrenewの同じIdempotency-Key retryでAllocationまたはgenerationを二重更新せず、異なるbodyは409にする。
  • daemon restart後に旧Connection IDを410、旧tokenを401にする。

Credential・Gateway

  • token tamper、誤key、誤epoch、誤Provider、誤capability、誤Audience、旧generation、期限切れを拒否する。
  • Agent tokenで別Provider、別Connection、control API、aggregate healthへ到達できない。
  • claim response内のtoken出現はProviderごとに一回で、状態、error、event、log、OpenAPI exampleに実secretがない。
  • 同じgenerationでclaimを再実行すると同一tokenを返し、renew後は異なるtokenを返す。
  • model不一致をupstream call前に400とし、一致時はtoken固定Bindingだけへ送る。
  • 既存Allocation header経路のGateway contract testが変更なく成功する。

Semantic readiness

  • ListenerとRuntime /healthだけが200でmodel未ロードのfixtureを503にする。
  • LLM probeのrequestが固定prompt、非stream、temperature: 0、max_tokens: 1と一致する。
  • completion tokenがちょうど1のresponseだけを成功にし、malformed 2xx、zero token、timeoutを拒否する。
  • healthからcold start、swap、fallbackを呼ばず、BUSY時に通常queueへprobeを追加しない。
  • binding、runtime contract、release、boot epochの変更でcacheが即時失効し、同じBindingの同時requestが 一つのlive probeへsingle-flightされる。
  • multi-providerの一件失敗でaggregateを503にし、Provider token responseには一件だけを返す。
  • Claimは全Providerにfreshな成功がない限りcredentialを一つも返さない。

実機flow

  • 省略されたagentProfileはcoding-defaultへ解決し、Resident Qwen 3.8 27Bを使用してswapを発生させない。
  • workerと35BのRuntime・Routeは比較用途に残り、明示選択policyとHTTP contractを満たすものだけを Agent Profile一覧へ広告する。
  • host、port、baseUrl、model、apiKeyだけで標準OpenAI-compatible clientがstreamを完了する。
  • Agent終了後のDELETEでPreferred Runtimeが既存idle policyにより回収される。

API schema、認証主体、token wire format、権限matrix、状態遷移、失敗時cleanup、probe request、response判定、 timeout、cache、single-flight、Audience validation、catalog revision、永続化境界、error code、実装配置、受入testを 固定し、実装と実機E2Eを完了しました。SAAA向けにもclaim schemaは変更せず、受理したrequest originからadvertised URLをConnection作成時に解決します。IP addressは設定・claim contractへ 固定しません。今後のwire field変更はv1互換性を審査し、必要なら新しい contract versionとして扱います。
