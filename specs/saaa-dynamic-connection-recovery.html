原因と境界

当時観測された4ミリ秒の失敗は、SAAA processにLARM_API_TOKENが存在せず、HTTP request前のClient preflightで停止したものです。LARM daemon、LAN descriptor、推論modelの失敗では ありません。token値をsource、文書、chat、通常logへ埋め込む修正は行いません。

当時のClientは未認証livenessとcredential不在を分離して報告し、Agent Connection APIを api_token_missingでfail fastさせていました。2026-09-01以降のClientはtoken省略時に Authorization headerなしでAgent Connection requestを送り、local-nodeの匿名lifecycleを使用します。

追加調査では、旧releaseが固定したLAN addressと現在のDHCP addressが不一致となり、claim後の data plane接続が到達不能になることも確認しました。また30秒で停止したResident要求はslot内で 約31 token/s、940 tokenまで生成しており、推論停止ではなく、無制限reasoningと非stream応答が Client timeoutを超えたものです。固定addressを廃止し、低遅延要求はbounded generationまたは streamingを使用します。

Network address policy

local-nodeのinterface addressはDHCPで管理し、LARM repositoryから固定addressを配備しません。 初期Control API discoveryにはmDNS/DNS名またはoperatorが発見した現在のaddressを使用します。 旧/etc/netplan/99-larm-static-ip.yamlが残るhostでは、 deploy/local-node/scripts/restore-dhcp.shがattended netplan tryを行い、 dynamic address、DHCP default route、gateway到達性を確認してからoverlayを除去します。検証失敗時は overlayとnetwork stateを復元します。
