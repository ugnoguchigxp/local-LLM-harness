docling-deskの環境分離とオンデマンドホスティング実装計画

2026年10月6日の利用者合意に基づく提案。docling-deskは利用頻度が低くても、第三者パッケージを試すための環境分離の初期事例としてLinuxネイティブコンテナで実行する。既存のKnowledge APIとCPU processorを再利用し、LARMから一つの論理サービスとして起動・接続・停止できるようにする。本書の作成は実装、イメージのビルド、インストール、配備、データ移行の実施を意味しない。

製品方針はLARMコンセプト正本への案内、調査依頼の評価と分離方式の比較はLocal Service Runtime調査プロンプト評価を参照する。今回のdoclingはコンテナを必須とするが、他の全サービスへコンテナを強制しない。

実装sourceと配備受入の進捗は実装と配備受入状況に記録する。実装時はprobeを固定契約とし、consumer許可を別Secret設定へ分けた。強制停止APIは実装せず、未観測groupは資源予約を保持して隔離する。 leaseと状態管理はcoreへ置き、daemonからhost backendとjournalを注入する。group停止にはcontainerごとの60秒のTERM猶予を使い、LARM制御期限を180秒とした。以下のmanifestは初期提案で、実装のstrict schemaと配備設定はconfig/local-node/local-services.yamlを参照する。

採用する構成と非目標

SAAA等のconsumerがdocling-deskの利用権を要求し、LARMが資源枠を確保して承認済みsystemd unitを起動する。unitは専用ユーザーのrootless Dockerで、固定されたCompose構成のAPIとprocessorを起動する。processorを先に準備し、APIの利用契約のreadiness成立後に接続先を返す。LARMはDocker socketを保持せず、Appもsocketへアクセスしない。

最小Service manifest案

以下は実装予定schemaの例であり、現行LARMの読込可能configではない。単位はbytesとsecondsを明示する。image digest、Compose project、mount、envとSecretは管理者が所有する固定配備定義へ置き、consumer requestで上書きできない。revisionは配備定義、image digest、probeとresource policyのdigestから算出する。 

schemaVersion: larm.local-services.v1
services:
  docling-desk:
    node: local-node
    backend: systemd-container-group
    deployment:
      unit: larm-local-service-docling-desk.service
      release: docling-knowledge-cpu-v1
      endpoint: http://127.0.0.1:18766
    readiness:
      path: /health/ready
      expectedStatus: 200
      expectedJson:
        status: ready
        capabilities.source_management: true
      timeoutSeconds: 180
    activity:
      path: /internal/larm/activity
      secretRef: docling-lifecycle-token
      pollSeconds: 5
      staleAfterSeconds: 15
    lifecycle:
      minInstances: 0
      idleSeconds: 120
      leaseSeconds: 300
      gracefulStopSeconds: 60
      restartPolicy: on-next-ensure
    resources:
      startupReservationBytes: 9663676416
      cpuMaxCores: 5
      maxInstances: 1
      gpuAccess: false
    permissions:
      consumerScope: docling-desk.use
      managementScope: local-services.manage

180秒のreadiness、120秒のidle、300秒のlease、60秒の停止猶予と9 GiBの予約は検証開始値であり実測保証ではない。API memory limit 512 MiB、processor 8 GiB、API CPU 1、processor CPU 4、抽出concurrency 1を初期候補とする。これらの制限が実際に適用されることと、対応fixtureが完了することを確認して採用する。processorの1件制約は既存実装と合わせ、上限変更は別受入を要する。

vuln-workbench等の第二サービスはmanifest形状の一般化検証に限定し、この計画で配備しない。通常processのbackendを後から追加できるdiscriminated schemaとするが、未実装backendをreadyと広告しない。

配備と境界分離

  • rootless DockerはLARM daemonと別の専用ユーザーで実行し、systemdのcgroup v2 delegationとUID mappingをpreflightする。daemonにはDocker socket、docker group、汎用sudo、任意systemctlの権限を渡さず、登録済みunitに限定する。
  • Composeとhelperは管理者所有でconsumerやcontainerから書換不可。project名、service名、releaseとimage digestを固定し、起動時build、pull、package installを行わない。submoduleと依存lockを固定したimageを別のbuild工程で作る。
  • 両containerを非root、cap_drop ALL、no-new-privileges、default seccomp、read-only root filesystem、init付きとする。必要な/tmp、LibreOffice profileとPython cacheの書込先は上限付きtmpfsまたは専用cache volumeへ限定し、互換性はfixtureで確認する。tmpfsとshared memoryもメモリ予算に含める。
  • GPU device、host network、host PID/IPC、privileged、host root、SSH鍵、ユーザーhome、.codex、LARM管理token、APIのactor署名鍵をprocessorへ渡さない。APIのSQLite volumeはprocessorへ渡さず、artifact volumeのみ共有する。
  • runtime networkは原則外部egressを許可しないprivate network。APIとprocessor間の必要通信とhost側入口の動作をrootlessで検証する。外部OCR、translation、answer、embeddingは初期off。環境全体の.envを取り込まずallowlistした設定のみ渡す。
  • Secretは管理者設定のfile referenceで渡す。API clientとactor署名鍵、processor token、lifecycle tokenを分離する。現行のenv-only tokenにfile対応が必要ならdocling側で追加する。Secretをimage、manifest本文、API応答、監査logへ保存しない。
  • 標準Composeのrestart:unless-stoppedをrestart:noへ置き換える。起動helperはforegroundのApp processをunit内に直接含むと仮定せず、Docker側のcontainer ID、所有label、exit codeとOOMKilledを別途観測する。
  • unitのactiveだけでgroup readyとしない。管理helperが固定projectのAPIとprocessorの状態をqueryできる限定経路を用意し、LARMはその状態とHTTP probeを照合する。daemonから汎用inspectやdocker execを呼べる経路は作らない。

初期はhost port 18766をAPI用loopbackとして事前検査する。衝突は起動前に拒否し、consumerにはportを恒久IDとして扱わせない。Macから利用する段階では管理者が認証付きTLS reverse proxyのFQDNと固定経路を設定し、LARMのresolveがその到達可能な入口を返す。127.0.0.1をMac向け接続先として返さない。private activity/drain経路は外部proxyから拒否する。

Knowledge APIはactor client tokenと短期actor JWTを要求し、browserからの直接呼出を想定していない。service leaseはAppデータへの認可を代替しない。SAAAのserver adapterはAppの利用者権限を検証して問い合わせ、viewerの配信入口とsession期限は既存viewer契約に合わせて受入する。一般的なHTTP reverse proxyだけでbrowser認証が成立したとは扱わない。

Control APIとconsumer契約

新規API案
操作 要求と結果 認可と副作用
GET /v1/local-services 許可されたServiceの能力、revision、稼働状態 consumer scope。起動、予約、credential発行なし
GET /v1/local-services/:id stopped / starting / ready / draining / stopping / failed、healthとactivity freshness consumer scope。pid、unit、Secretと内部processor endpointは非公開
POST /v1/local-services/:id/leases ensureに相当。Idempotency-Key、希望TTLと任意catalog revision。201 readyまたは202 startingの同じleaseを返す consumer scope。固定serviceのみ。command、image、env、path、任意endpoint指定は400
GET /v1/local-service-leases/:id 利用権の状態と有効期限。readyなら承認済み公開endpoint、revision、instance generation、boot epochを解決 同一principalのみ。準備中は接続可能としない。resolveは新しい起動をしない
POST /v1/local-service-leases/:id/renew 同じgenerationとboot epochの期限を延長 同一principalのみ。古いinstanceは409 stale_binding。失効後は新規ensure
DELETE /v1/local-service-leases/:id 自身の利用権を冪等解放。204 他consumer、jobと共有参照は維持。即座に全体停止しない
POST /v1/management/local-services/:id/stop 通常はdrainとidle確認、busyなら409。forceは明示理由と監査を要求 management scope。一般LLMへforce権限を渡さない。forceはjob中断とデータ保全の結果を返す

初期登録は管理者がconfigへ承認済みmanifestを追加し、起動時に検証する方式とする。公開register APIは不要。consumer identityとscopeは認証設定に結び付け、request本文のclient名を認可主体にしない。401、403、404、409、429、503とRetry-Afterを型付きで返す。HTTP切断でleaseや起動を自動取消せず、明示releaseまたはTTLで回収する。

同じprincipal・key・bodyの再送は同一leaseとoperationへ戻し、keyのbody不一致は409。異なるconsumerのensureも同じservice revisionの一つの起動へ合流する。待機leaseの全解放でstartupを取消す場合は、既存jobや他参照がないことと、自分が作成したcontainerだけを停止することを確認する。

活動通知と競合しない停止

docling側へ認証付きのprivate契約を追加する。GET /internal/larm/activityは契約version、app boot ID、単調sequence、observedAt、queuedJobs、runningJobs、activeRequests、processor activeJobs、drain状態とdrain tokenを返す。job一覧、文書IDと内容はLARMへ返さない。APIは自身のcounterとjob DBを照合し、processorの活動を集約する。processor到達不能、counter不一致と期限切れはidleではなくunknownとする。

POST /internal/larm/drainは新規の資料登録、抽出開始、検索、viewer処理等の業務受付と外部からの新規job受理を停止する。既に受理した処理とqueueはclaimを継続して完了へ進め、queueが残る間は停止可としない。単調sequenceとapp boot IDを含むtokenを返し、LARMは同じtokenでdrainedを確認する。activityとdrainのcheckはreadiness照会と区別する。POST /internal/larm/resumeは同じ世代のdrainを解除する。

  1. 有効lease、依存参照、queued/running job、active requestのいずれかがある間はbusyとしてidle時計を進めない。busyは稼働状態と独立したactivityとして表示する。
  2. 全参照ゼロかつ新鮮なidleが120秒続いたら、service lockの下でdrainを開始する。App側が受付を閉じたことを確認してから最後のactivityを取得する。
  3. 同じapp boot IDとdrain tokenで、queue・job・request・processor活動のゼロを確認し、leaseとgenerationを再確認する。ここが停止判断の確定点となる。
  4. 確定前の新しいensureはdrainを解除して利用再開する。確定後のensureはstoppingを追跡し、旧世代の完全停止後に新generationを起動する。同時に二つのSQLite writerを起動しない。
  5. APIを先に正常停止し、processorの終了を確認してから停止する。両containerのexitと子process消滅を確認し、resource予約を解放する。volumeは残す。

activity不明、通信断、processorの応答不明の際は通常停止を保留し、drainを解除できれば解除する。5分継続時を通知開始値とし、管理者の照合を要求する。通知期限を自動killの期限に読み替えない。60秒の正常停止猶予を超えた場合もstop_timeoutと予約を残し、通常idle回収で無条件SIGKILLへ進まない。明示forceだけが中断とchild tree強制回収を行う。

WebViewを表示しているconsumerはleaseをrenewする。consumerが落ちてもApp内のjobがあればactivityで保護する。Appから生成APIへの要求が中断された場合、LARMは業務POSTを再送しない。job再開・失敗・重複防止はdoclingが決定する。

ユニファイドメモリの資源管理

config/local-node/nodes.yamlはRyzen AI MAX+ 395、128 GB、reservedMemoryGB 16を宣言する。これは登録値であり今回の空き容量の実測ではない。system RAMとGPU使用分は同じ物理poolを競合するため、総容量へRAM＋VRAMを加算しない。containerのmemory limitは上限であり同量の常時占有を意味しない。GPU device非公開でも、CPUのDocling処理がLLMの余裕を減らすことをadmissionに反映する。

初期はCPU専用groupに9 GiBのstartup/peak予算を静的予約し、稼働中も同じ予約を維持する保守的な方式を使う。containerごとのmemory limitを予約と別に強制し、tmpfs、shared memoryと子processを含む実測peakが予算内に収まるか検証する。Docker/rootlessの常駐費用はnodeのsystem overheadとして一度だけ計上する。

admissionは二段階とする。静的gateは既存AI runtimeの重複しない予約、起動中Service予約とnode保護枠を同じ会計で集計する。live gateは新鮮なMemAvailableとUMA上のGPU観測を確認し、既にlive使用量へ反映された稼働予約をもう一度丸ごと減算せず、まだ観測されていない起動予約・予算残額を照合する。CPUとGPU双方の観測を突き合わせる方法をpure関数へ切り出し、二重計上・過小計上・競合をfixtureで検証する。CPU-only ServiceにはGPU freeだけを起動条件にしない。

Serviceの枠確保とAI Allocationのadmissionを共通node lockで直列化し、どちらか一方だけに予約を見せる実装を禁止する。稼働ServiceをAI側が未管理メモリとして無視しない。通常は重要なforeground Providerをdoclingのためにpreemptしない。枠不足またはstale telemetryは起動を503で拒否し、予約漏れを残さない。disk空き不足は別理由で拒否する。

OOMKilled、memory.events、memory peak、CPU負荷、起動時間、抽出時間、AIのTTFTと音声遅延を測定する。上限到達を自動で制限解除する理由にせず、対応入力の制限または管理者による予算変更で解決する。container停止後はprocess由来メモリと予約の回収を確認し、reclaim可能なpage cacheの残留を孤児processと誤認しない。

永続化と復旧

rootless専用ユーザーの管理領域にcontainer state、imageとcacheを置き、API DBとartifactの固定volume名をreleaseから独立させる。readiness失敗と起動取消時は今回起動したgroupだけを回収し、以前のvolumeへ変更を加えない。通常運用にdown -vやvolume pruneを使わない。

LARMはservice ID、配備revision、container ID、generation、App boot ID、drain状態と予約の小さなjournalを永続化する。再起動時は通常APIを開く前に所有labelと実際のcontainerを照合し、観測済みgroupの資源枠を再登録する。古いleaseはboot epochで失効させるが、それを理由に稼働jobを停止しない。consumerは再ensureし、jobはAppのIDで照合する。

unit activeでも片方がexitした場合はfailed/degradedとして新規leaseをreadyにしない。正常稼働中のjobがある側を即座に全停止しない。未知revision、duplicate writer、label不一致と所有者不明containerはquarantineして自動adoptやkillをせず報告する。LARM停止中も既存containerは自律的に処理を継続できるが、新しいensureとidle回収は利用不可とする。

crashしたinstanceは同じleaseへ別generationとして黙って差し替えない。新規ensureで再起動を試み、backoffと試行上限を持つ。writer leaseの解放と既存の最大30秒程度の復旧待ちをreadiness期限に含める。Appの原本DB・索引・jobの整合性はApp自身が検証する。

更新はdrain後に旧groupを停止し、DBとartifactを同じ時点でbackupして新image digestへ切り替える。schema migration前に互換性を確認し、非互換migration後は旧imageへの切替だけをrollback成功とせず対応backupへ戻す。環境分離と永続データ削除権限を混同しない。

検証項目とリリース判定

  • core：manifestの余分なfield、重複ID、未知node、無許可unit、revision改変、lease主体と期限、idempotency不一致、同時予約、UMA二重計上を検証する。
  • backend：status:readyとsource_management:trueのprobe、processor不健康、container片側exit、OOM、unit状態の不一致、cancelと停止失敗を検証する。
  • daemon：二consumer ensure、片側release、長いjob、queue残存、WebView renew、通信断、drain直前直後のensure、再起動と旧credential失効を検証する。
  • 実機：read-only/non-root、capability、memory/CPU/pids制限、GPU非公開、egress遮断、Secret非漏えい、host port衝突とprivate processor非公開を確認する。
  • App：PDF、画像PDFのOCR、PPTX、XLSX、DOCX、Markdownの合成fixtureで登録・抽出・FTS・viewerを検証する。資料内容、ページ数、indexとjobの成功判定はdocling側が行う。
  • 永続化：stop/startとimage再生成後の原本・DB・索引保持、backup/restore、crash中jobのApp側の正しい最終状態、孤児processの消滅を確認する。
  • 性能：container engineのみ、group idle、startup、抽出peak、停止後を分け、解決されたforeground Profileとの混合で測る。静的memory上限の候補値をそのまま性能保証にしない。
  • LARM回帰：bun run typecheck、関連test、bun run checkを実装後に実行し、既存LLM / ASR / TTS / Embeddingと画像・音楽の契約を維持する。live検証はconsumerが要求したProfile→route→runtime→backendを追跡し、たまたま動いているモデルで代用しない。

性能閾値、最大入力サイズ・ページ数、rootlessのkernel/cgroup条件、TLS名、image digest、backup先はPhase 0から3の配備値で確定する。未確定値が残る状態で本番受入を完了としない。feature gateはdefault offとし、独立fixtureと混合負荷の受入後にdoclingだけを有効化する。既存未コミット変更と本計画の変更を混在させて配備しない。
