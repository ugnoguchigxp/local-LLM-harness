実装状況

2026-09-06時点で、M1、M2、M3、M5のrepository実装を完了した。公開model catalog、 GET /v1/models、通常Bearerとrequestのmodelだけで呼べる POST /v1/chat/completions JSON／SSE、内部Allocationを所有する ModelBroker、Preferred cold startのsingle-flight、request終了時の解放、準備中cancelを LLM・ASR・TTSへ追加した。既存の明示Allocation／claim経路はHTTP管理APIとして残しているが、 claimから独自transport広告は削除した。

  • model alias解決はpackages/core/src/openai-model-catalog.ts、調停は apps/daemon/src/model-broker.tsへ分離した。
  • chat bodyは一度だけ上限付きで読み、検証済みbytesをGatewayへ渡す。SSE response bodyは bufferせず逐次検査・転送し、途中EOF、model drift、finish欠落、[DONE]欠落を 成功として記録しない。
  • ASR multipart/JSON、TTS request/audio media type、OpenAI error、標準clientの増分SSE iterator、 句単位TTS開始例を追加した。model一覧、標準JSON、同時SSE、unknown model、cold start中のclient切断、内部Allocation残留0をcontract testで確認した。
  • benchmark:http-providerは同一fixture・token数でHTTP JSONとSSEを比較し、TTSは first playable audioを別計測する。smoke:http-provider-liveはBearer＋modelだけで JSON、SSE、ASR、TTSを検査してsecret-free evidenceを返す。
  • 非特権builder、署名済みdesired intent、root activator、atomic rollback、機械可読status、 canary→consumerの順序gate、9810 JSON/SSE定期監視をrepositoryへ実装した。rootは候補コードや testを実行しない。builderは全gate後にdev dependencyを除去し、production dependencyだけを release bundleへ含める。
  • Queue回復の純粋状態機械と段階再開計画、旧transport source／test／unit definitionの撤去を 実装した。live release、30 sampleのSLO校正、SAAA／ContextStill切替、 実Queue統合、24時間soak、旧installed unit削除は未確認である。このhostにはSAAAとContextStillの source treeがないためM4と実Queue変更は外部作業である。

この段階の正確な表現は「標準HTTP data planeと安全なrelease収束経路をrepositoryへ実装済み」である。 live稼働、性能改善、移行完了とは扱わない。

推奨

LLMの公開推論APIはOpenAI互換Chat CompletionsのJSONとHTTP SSEへ統一し、新規の独自transportは作らない。ASR・TTSもOpenAI互換のHTTP endpointを基準にする。OpenAIサービスへの送信へ切り替える意味ではなく、ローカルengineを一般的なclientで利用できるAPIにする方針である。

OpenAI互換は業界の全機能共通規格ではない。対応endpoint、SDK version、model alias、受理field、応答形式、error、cancel動作を明記した互換範囲を固定する。必要のないResponses API、Realtime APIの全面再実装を今回の完了条件へ追加しない。

以前検討した独自transport案は廃止し、専用仕様書と実行sourceをrepositoryから削除する。 公開contractはOpenAI互換HTTP APIだけを正本とする。

公開API

共通化するのはHTTP APIと認証。音声の応答までSSEへ統一しない
用途 API 初期対応
LLM POST /v1/chat/completions stream=falseはJSON、stream=trueはChat Completions形式のSSE。tool calling、必要なstructured outputを同条件で検証する。
ASR POST /v1/audio/transcriptions multipartの録音または発話区間を受け、JSONのtextを返す。対応する場合だけ文字起こし結果のstreamingを広告する。
TTS POST /v1/audio/speech input、model、voice、response_format等を受け、音声bodyを返す。低遅延用途ではPCM/WAVを候補にし、engineが対応する場合は逐次返却する。

新規の独自binary frame、ACK、resume、Provider専用client実装を要求しない。標準SDKでbase URL、credential、modelと通常の音声設定を指定して動作することを受入基準にする。modelやvoiceの能力差は残るため、URL変更だけで全機能が完全に同じになるとは約束しない。

ASRで結果をSSE配信しても、マイク音声を連続送信するRealtime ASRにはならない。まず発話区間をVADまたはpush-to-talkで確定して送る構成を採る。連続字幕や同時双方向音声が必須になった場合は、標準的なRealtime/WebRTC等を別途評価し、独自transportを再発明しない。

速度の判断

双方向transportは通信方式であり、推論速度を自動的に上げない。SSEも生成途中から返せる。今回、同model・同prompt・同GPU条件での旧transport対SSEの速度差は測定していないため、同速・低速とは断定しない。独自経路の維持コストに見合う速度改善の証拠は確認できていない。 

発話終了 → VAD確定 → ASR確定 → LLMの最初の発話可能な句
         → TTSの最初の音声 → clientで再生開始

測るのは接続速度だけでなく、この全体のp50/p95である。LLMのTTFTは最初のcontentを基準にし、role-only chunk、heartbeat、reasoning tokenを返答開始に数えない。音声はHTTP headers到着でなく実際の再生開始を測る。

  • model常駐と適切なprewarmを使い、毎回のモデルロードとConnection再作成を避ける。LLM・ASR・TTSの同時常駐は実メモリとGPU競合を計測してから決める。
  • HTTP接続を再利用し、proxy、Gateway、SDKの全層で全文bufferingを避ける。SSEの正常終端と途中EOFを区別する。
  • LLMの全文を待たず、発話可能な句単位でTTSへ渡す。句長は速度だけでなく読み・韻律・文脈を評価して決め、tokenごとのTTS requestにはしない。
  • TTS生成と音声再生を重ねる。先読みQueueは上限を持ち、発話順序を保つ。割り込み時は再生停止・後続破棄・LLM/TTS requestのabortを行う。
  • 通信の中断とengineの計算停止を区別する。engineが即時停止できない場合は計算終了まで枠を保持し、その制約を明示する。

現行音声実装で分かったこと

gnosisのsource HEAD 1b5e427d5d655e7fb8d2abf10ff46a113f6ae2e0で確認した。Qwen ASRのapps/qwen-asr/api.pyは既に/v1/audio/transcriptionsを持ち、uploadを保存した後にmodel.transcribeを実行する。promptは非対応、temperatureは0だけを受理する。全OpenAI機能互換とは言えない。

apps/voicevox-tts/voicevox_api.pyも/v1/audio/speechを持つ。synthesizer.synthesisでwav_bytes全体を生成してからResponseを返すため、現在の実装は生成途中の音声配信ではない。stream=trueも拒否する。生成後のWAVを小分けで送っても、初回音声の生成待ちは減らない。

したがって音声はAPIを一から作り直すより、既存adapterの互換範囲、音声format、buffering、errorを整理する。VOICEVOXで低遅延が不足する場合は句単位合成を測定し、それでも不足するときに初めて逐次生成engineを比較する。Qwen TTSを含む全音声engineの速度・対応機能の網羅調査は今回していない。

残す責務と減らす責務

Gatewayは固定9810でHTTP推論を受け、model aliasを内部engineへ解決する。短期credential、Profile、実行枠、モデル準備、idle unload、推論cancelの共通管理を維持する。動的ProviderとHTTP APIは両立する。

Agent Connectionの作成・更新が必要なら、起動・更新時に行う薄いbootstrapへ閉じ込める。LLM tokenごとの制御や独自stream decoderをclientへ持たせない。将来、通常のOpenAI-compatible Provider設定だけで使える統合を検討する際も、認証範囲やlease規則を黙って緩めない。

非特権builderとroot activatorの分離、承認済みdesired release、live identity、Provider回復とjob retryの分離、consumer結果保存による完了確認は引き続き必要である。HTTPへ替えてもrelease不一致やpaused固定は自然には解消しない。

Rust consumer、GPU engine、model資産、業務DBを一括で書き換えない。LLMのnative専用companionとengine改変は、HTTP受入後に依存がないものだけを廃止する。専用transportを使わなくなったことだけを理由に、ROCm/MTP対応まで削除しない。

目標構成

Model Broker

ModelBroker.acquire(model, principal, signal)をdaemonの共通入口にする。OS非依存のalias、 route、scope判定はpackages/core、systemd／llama-swapによる起動と停止は packages/backends、requestとleaseの調停はdaemonに置く。

  1. Bearerを検証し、principalに許可されたmodelか判定する。
  2. 公開aliasを完全に一つのrouteへ解決し、request中はbindingとrelease identityを固定する。
  3. ResidentがHOTなら直ちにbindingを返す。既定のcoding-defaultは常にこの経路を使う。
  4. Preferredがcoldなら同一modelの起動をsingle-flight化し、service-owned leaseを一つだけ作る。 model load中にExecution Gateの推論枠を占有しない。
  5. ready後に既存Execution Gateへ進み、maxConcurrentRequestsとbounded queueを適用する。 初期値は推論同時実行1、Gateway queue 0を維持する。
  6. active requestをreference countし、最終request完了後にidle TTLを開始する。処理中、SSE送信中、 cancel確認中はleaseを解放しない。

model起動がclient deadline内に終わらない場合は、OpenAI形式のerror bodyとHTTP 503、bounded Retry-Afterを返す。Gateway内に永続job queueを作らない。job、再試行、成果保存はconsumerが 所有する。

一要求の状態機械

received
  → authenticated
  → contract_validated
  → model_resolving
  → provider_ready
  → execution_admitted
  → upstream_started
  → first_meaningful_output
  → terminal_verified
  → slot_released

client abort / deadline / release drain
  → upstream_cancel_requested
  → engine_stopped_or_quarantined
  → slot_released

HTTP connection closeだけを成功にしない。JSONは有効なcompletionとfinish、SSEは意味あるdelta、全choiceの finish、正常な[DONE]を成功条件にする。upstreamが停止確認を返さない場合はruntimeをquarantineし、 同じ実行枠へ別requestを重ねない。

互換profileと認証

互換性は「OpenAI互換」という名前だけで判断せず、larm.openai-http.v1として次のsubsetを contract fixtureとOpenAPIへ固定する。基準は公式のChat Completions作成、Chat Completions streaming events、audio transcriptions、audio speechとする。

段階導入とrollback

  1. 測定: 現行releaseでHTTP SSEと旧transportの公平なbaselineを取り、機能差、TTFT、total、 tokens/s、cancel、memory、GPU競合を保存する。
  2. shadow: allocation header不要のHTTP modeをfeature flagで有効化し、loopbackとconsumer hostから標準SDK contractを実行する。旧client trafficはまだ変えない。
  3. SAAA canary: 一つの設定または一つの利用者だけをHTTP SSEへ切り替え、tool continuation、 interrupt、長文、途中切断、再試行を検証する。
  4. ContextStill canary: Queueをfail closedのままHTTP Providerを検査し、対象job一件だけを 再開する。業務成果の永続化と次job境界の再評価まで確認する。
  5. default切替: SAAAとContextStillの既定transportをHTTPにし、独自transport sourceを含まないreleaseへatomicに 切り替える。旧companion unitはrollback window中もdaemonから到達不能であり、新規通信を受けない。
  6. soak: 24時間以上、HTTP成功率、TTFT、tokens/s、cancel、slot leak、release identity、 consumer完了を監視する。旧transportのactive connectionと新規attemptは0であることを記録する。
  7. 撤去: source、schema、upgrade、unit definition、専用scriptとtestはHTTP-only releaseで削除する。旧installed unitはroot installerが停止・disable・削除する。

rollback単位はreleaseとconsumer設定を揃える。HTTP releaseでidentity、contract、SSE terminal、性能gate、 consumer成果保存のいずれかが失敗した場合、Queueを止め、consumerを直前の確認済み経路へ戻し、LARMを previous releaseへatomicに戻す。旧transport sourceを削除した後はそれへ戻さず、確認済みHTTP previous releaseへ戻す。

削除対象はlarm-native-qwen-provider.serviceである。Resident QwenのHTTP engine、MTP、ROCmFP4 assetはHTTP性能gateを満たす限り維持する。外部model weightsやengine binaryを repository削除と同時に消去しない。

実装時に次のscriptを追加または置換する。名称は計画上の固定名とする。

command 役割

最終受入条件

  • 標準OpenAI clientがbase URL、Bearer、modelだけでLLM JSONとHTTP SSEを利用できる。
  • SSEは最初のmeaningful deltaを逐次受信し、stable identity、tool delta、finish、[DONE]を contract fixtureと実modelの両方で満たす。
  • ASRとTTSが対応field、media type、sample rate、voice、error、abortの受入を満たす。
  • Qwen 3.8 27BがResident既定であり、warm requestにmodel startupが発生しない。
  • HTTP SSEの校正済みTTFT、tokens/s、cancel、mixed workload SLOをlive releaseが満たす。
  • desired commit、live release、catalog revision、boot epoch、実runtime releaseが一貫する。
  • SAAAのtool継続とinterruptがHTTP SSEで成功する。
  • ContextStillのLLM必須job一件が完了し、業務成果が一度だけ保存される。
  • provider_unavailable_exhausted等のinfra起因jobがProvider世代回復後に一件から段階再開し、 Provider障害をjob failure回数へ加算しない。
  • clientから旧:44448やnative companionへの接続が0件である。
  • 24時間soakとrollback windowを完了し、独自transportの広告、service、source、test依存を撤去する。

以上のいずれかが未達なら「HTTP実装済み」または「shadow成功」とは記録できても、移行完了とは扱わない。 とくにlive identityとconsumer成果保存は省略しない。
