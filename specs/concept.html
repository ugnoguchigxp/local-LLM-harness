Local AI Provider コンセプト

LARMは、Linux上の複数のローカルAI Runtimeを一つのProviderとして扱う、 source-onlyのcontrol planeです。利用側はport、service名、quantization、起動方式ではなく、 必要なcapabilityと明示的な実行意図を要求します。

North Star

常用するローカル対話経路を常に利用可能に保ち、追加Runtimeは明示された必要性に応じてだけ起動し、 利用側へ安定したProvider contractを提供する。

中核価値はモデルそのものではなく、Runtimeの状態を観測し、要求に適したRuntimeを安全かつ決定的に割り当て、 利用終了後に資源を回収することです。

上位システムとの責務境界

Ambient Agent側はTask Route、会話、音声フロー、Situation、UI、永続設定を所有します。 LARMは、上位システムが示したcapabilityと実行意図を、ローカルRuntimeの具体的な割当に変換します。

運用原則

  1. Local-first: 基本処理はCloudなしで成立させます。
  2. Resident-first: 常用経路は追加モデルの状態に依存させません。
  3. Explicit selection: 特殊Runtimeは明示されたrouteまたはperformance intentでだけ選択します。
  4. Lease-bound allocation: 一度選択したRuntimeはleaseへ固定し、処理途中で暗黙に変更しません。
  5. Observable fallback: fallbackは理由と実際に使ったRuntimeを利用側へ返します。
  6. Bounded lifecycle: lease、operation、queue、startup待機、idle保持には上限を持たせます。
  7. Adapter-first: OSやRuntime固有処理はBackendへ閉じ込めます。
  8. Source-only: weight、外部binary、build結果、cache、log、生成mediaをGitへ保存しません。

目標とするRequest lifecycle

  1. 利用側がcapabilityと必要な実行意図を指定します。
  2. LARMがroute候補、health、空きslot、資源制約を評価します。
  3. 必要なPreferred Runtimeを起動し、期限内にreadyになるか観測します。
  4. 選択結果をleaseのallocationとして固定します。
  5. 利用側は固定されたendpoint、または将来の安定Gatewayを通じて推論します。
  6. release後、他のleaseとidle policyを確認してPreferred Runtimeを回収します。

「動的にモデルを変える」とは、最初の段階では宣言済み・配備済みRuntimeの起動、割当、fallback、解放を意味します。 新しいweightのdownload、checksum検証、staging、activation、rollbackは別の管理lifecycleとして扱います。

API境界

Runtime allocation API
capabilityとperformance intentを受け、配備済みRuntimeをprepare、resolve、releaseします。 現行APIを拡張する最初の実装対象です。
Inference data plane
現在はresolveされたendpointを利用側が直接呼びます。将来はallocationを検証する安定したOpenAI互換Gatewayへ統合します。
Artifact deployment API
将来、宣言済みmodelとversionだけをchecksum検証、staging、activation、rollbackします。 任意URL、任意path、任意commandは受け付けません。

LARMが所有するもの

  • Runtime registryとmodel artifact manifest
  • health observationとRuntime state
  • Resident / Preferred / Elastic policy
  • resource admission、allocation、lease、operation
  • capabilityと明示的な実行意図からRuntimeへの解決
  • systemdとllama-swapへのlifecycle委譲
  • OpenAI互換の安定Gateway
  • 使用Runtime、fallback理由、startup・推論latencyの観測
  • 将来の宣言済みartifactに対する検証・staging・rollback

LARMが所有しないもの

  • Ambient AgentのSituation判断、Conversation、Presentation、UI
  • TaskごとのLocal / Cloud選択やProvider設定の永続化
  • CodexなどAgent Providerのthreadとsandbox
  • tool use、memory retrieval、Knowledge管理、Coding Agent
  • モデル推論engineの再実装
  • APIから渡された任意command、任意URL、任意pathの無検証実行
  • Resident 27Bの暗黙停止または特殊モデルへの暗黙昇格

機能追加の判断基準

新機能は、次の質問に一つ以上明確に答える場合だけLARMへ追加します。

  • ローカルRuntimeの発見、状態観測、割当、起動、停止を安全にするか。
  • 利用側からport、service名、model配置などの運用詳細を隠せるか。
  • Resident経路を保護しながら、必要な追加capacityを利用可能にするか。
  • 実際に使ったRuntimeとfallback理由を検証可能にするか。

Taskの意味理解、UI表示、会話管理、Cloud選択、Agent実行そのものが中心なら、LARMではなく上位Runtimeの責務です。
