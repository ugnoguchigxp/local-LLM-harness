1. 判定

最適解は、先にLARMのrealtime topologyを SAAA WSS → LARM RunActor → native Provider streamへ固定し、その境界へACK、resume、 tool、cancel、backpressure、TLSを配置する構造である。HTTP controlと非streaming requestは同じdaemonに 残せるため、Mac側のallocation lifecycleを変える必要はない。

今回提供されたprotocol詳細により、以前の不確定事項だったbinary header、field、limit、error、close mappingはすべて確定した。LARM独自の軽量protocolを考案する必要はなく、むしろ独自差分を入れないことが 最短の相互接続経路である。

4. 1対1性能に対する強み

  • 一つのsocketへ一つのactive runだけを置くため、stream registry、runごとのfairness、同一socket内の head-of-line schedulingをhot pathから除ける。
  • connectionをuser turnより前にprewarmし、handshake、auth、allocation bindingをprompt確定後に 繰り返さない。
  • deltaは16 byte fixed headerで、JSON field名、run ID、nested envelope、per-message compressionを token pathへ持ち込まない。
  • terminal全文を再送せず、Macのcanonical accumulatorを正本にするため、長文完了時の重複copyを避ける。
  • ACK/resumeは処理を増やすが、切断後の重複発声を防ぎつつ再生成を避ける構造上必要な処理であり、 16 eventまたは100 msの累積ACKでcontrol trafficをboundedにする。
  • UIの遅延をACK条件へ含めないMac設計と、run単位backpressureを行うLARM設計が一致し、遅いpaintが Provider generation全体を止めない。

6. 詳細protocolの評価

protocol自体は、性能だけを理由にintegrityを捨てず、必要な仕事をboundedにしている点で技術的に 適合している。特に次の判断は維持すべきである。

  • seqを全Provider eventへ一列に振るため、text、tool、terminal間の順序を別channelへ分散させない。
  • contentSha256をACKとterminalへ持たせるため、replay cursorだけが一致して本文が異なる failureを検出できる。
  • unacknowledged上限とresume retentionが固定され、切断時もmemory使用量とrun寿命が有限である。
  • run errorとconnection framing errorを分離し、一件の入力不良でprewarmed connection poolを壊さない。
  • tool argumentsを完成後に一度だけ送るため、Macへfragment assembly stateを増やさない。

注意点は、LARMが最大8を機械的に広告しないことである。connection prewarm数はHTTP同時接続数ではなく、 resident modelが安全に同時生成できるrun数で決める。現行Qwen local-nodeは1を広告するのが正しい。

7. 優先順位

  1. native Provider streamの実証。これが失敗したら他のWS実装を先行しない。
  2. Mac正本由来のschema、golden binary/hash fixture、PWS-C01〜PWS-C19 runner。
  3. 一connection、一runのvertical sliceとmetadata-only path。
  4. seq/hash/limit、ACK/pause、disconnect/resume。
  5. tool continuation、pool、WSS、drain。
  6. 全conformance後にSSE routeとfixtureを削除。

この順序なら、最も不確実なProvider境界を最初に解消し、その後は確定済みcontractへ機械的に 実装を積み上げられる。Mac側には暫定fallbackや互換分岐を追加しない。

8. Release判定

次の三条件が揃った時点で「Mac無修正対応可能」から「実装完了」へ判定を上げる。

  1. native Qwen pathでSSE dependencyが0になっている。
  2. MacとLARMが同じschema / golden fixtureを使い、PWS-C01〜PWS-C19が全件成功している。
  3. 非loopback WSS、allocation lease、cancel、resume、30分network flapを実機で通している。

したがって回答は「可能」である。ただし変更範囲はdaemonのWebSocket endpointだけではなく、 core contract、native Provider backend、runtime configuration、TLS、tests、deploymentまで含む。 ここをLARM側の一つのvertical sliceとして完了すれば、Mac側修正は不要である。
