Qwen-Image 2.1 Turboのオンデマンド採用とサービス案内

2026年10月10日、利用者の採用指示に基づき、普段の画像生成にはTurbo AD-Q4_Kを選ぶ。7候補の実機評価で512角・768角の速度と画質を確認した。写真・イラストを直接生成でき、下書き風の指示は高速化の必須条件ではない。

実装と配備の区別

ソースの画像service広告、公開入力schema、native engine接続、systemd起動設定、確保応答の説明と完全URLを変更した。隔離APIで実生成と停止後の画像読出しを確認し、利用者指定の認証情報で管理者所有の本番unitを更新した。release 08fecdae29a7029ee5ef711182b27a97256b30a3は署名付き配備とcontract_verifiedを通過した。本番の確保・claim、実生成、停止後の画像取得まで確認済み。

通常版のモデルとPython Providerは保持する。公開画像APIは今回Turboへ切り替え、通常版の選択と参照画像による仕上げは別途実装する。公開modelの旧値をTurboへ黙って読み替えない。

起動と停止

利用者はSAAA-w-Imageのserviceを選ぶ。Agent Connectionの作成だけでは画像モデルを起動しない。POST /v1/images/generationsでimage variantを確保し、larm-image-qwen21.serviceを起動する。画像とmetadataを保存してControlが読めることを検証し、worker停止の完了後にHTTP 200を返す。idle TTLと常駐数は0。並行する画像・楽曲生成は既存の重量級排他で拒否する。

Providerの8091とnative engineの8092はloopback専用。native engineは同じsystemd cgroup内の子プロセスで、終了時に停止する。既存のlistenerを奪わず、初期化失敗時も子プロセスを片付ける。healthのreadyはengineが要求を受け取れることを表し、モデル転送・初回処理の時間は生成要求に含まれ得る。

native HIP buildとモデルはrepository外に置く。engineは/srv/ai/apps/qwen-image-turbo-benchmark/stable-diffusion.cpp/build-hip/bin/sd-server。DiTはAtomicChat AD-Q4_K、encoderはQwen3-VL-8B Q8_0、VAEはComfy-Org BF16を使い、GPU VAE、Flash Attention、Euler、CFG 1、CPU RNG、8ステップと公式sample sigmaを固定する。AtomicChat revisionはbb25d06bc74119c12207243d68917951e6d9c232。

重量だけの約12 GiBを必要メモリとはみなさない。workspaceと背景負荷を考慮して既存の予約34 GiBと安全余白16 GiBを維持し、生成中もMemAvailableの16 GiB floorを監視する。

写真風画像の連続測定で、停止直後のengineポートにTIME_WAIT接続が残ると、次の起動前のbind検査が失敗することを確認した。 engineのLinux listenerはSO_REUSEPORTを使うため、SO_REUSEADDRだけの検査では不足した。 bindが失敗した場合、対象ポートのTCP状態がすべてTIME_WAITの場合にだけ起動を許可する。 検査socketにSO_REUSEPORTを使って稼働中listenerを共有することは避ける。 同じsocket optionの実TCP接続を閉じて直ちに再起動する回帰試験と、占有listenerを奪わない試験を通過した。

発見・確保応答と入力

既存のGET /v3/agent-profiles?profile=SAAA-w-ImageはProfile全体のdescriptionとserviceの相対endpoint・model・startupPolicyを持っていた。今回serviceのdescriptionに用途、入力、時間の目安、画像取得方法を追加する。Connection作成・取得・claim応答のservices[].urlは選択したaudienceのoriginから構成し、利用者側で内部Providerポートを使う必要はない。管理権限やcredentialを追加するフィールドではない。 

{
  "services": [{
    "name": "image",
    "capability": "media.image.generate",
    "protocol": "larm.image-generation.v1",
    "endpoint": "/v1/images/generations",
    "url": "http://127.0.0.1:9810/v1/images/generations",
    "model": "qwen-image-2.1-turbo",
    "description": "Qwen-Image 2.1 Turbo AD-Q4_Kによる画像生成。入力、所要時間と画像取得方法を案内する。",
    "startupPolicy": { "minWarmInstances": 0, "idleTtlSeconds": 0 }
  }]
}

上のURLはloopback networkであるsame-host audienceの例。host-privateのrequest-origin audienceでは、確保要求の到達先originを使う。service descriptionはcatalogの設定文をそのまま返す。画像serviceは会話Providerのclaim対象ではなく、認証は従来のControl APIの規則に従う。

検証記録

本番反映後、same-host audienceとembeddingだけのProvider subsetでSAAA-w-Imageを確保し、確保・取得・claimに画像serviceのdescriptionと完全URLが返ることを確認した。Connection作成では画像unitは起動しない。LAN経由のsaaa-desktop audienceではhttp://192.168.0.130:9810/v1/images/generationsを広告した。検証用ConnectionはすべてDELETEで解放した。

本番の生成APIで日本語promptから512角PNGを生成し、systemd起動・生成・保存・停止・HTTP downloadまで15.76秒で完了した。実際のengineは8ステップで、weight revisionも広告したTurboと一致する。応答後はMainPID 0、unit inactive、8091と8092の両portが閉じた。停止後のGETは200で、downloadのSHA256がmetadataと一致した。写真風の緑の椅子・赤いソファ・木のテーブルと照明を目視確認した。

本番証跡は/srv/ai/data/benchmarks/qwen-image-turbo-live-20261010/verification.json、lan-verification.jsonとlive-image.png。保存証跡にProvider tokenや管理者認証情報は含めない。全体checkは715件のapp/package試験、tooling 24件、deployment 56件とshell/Python検査を通過し、Turbo Provider固有の6件も成功した。

実際のnative engine、Turbo weights、Python Provider、Controlの画像routeとartifact managerを隔離して接続し、512角の人物写真を生成した。HTTP 200まで15.46秒、Provider生成・保存は15.223秒。image variantのstartとstop各1回、返却前の停止、停止後も23652 bytesのWebPを取得できることを確認した。engineの起動は試験前に行っており、この15.46秒はsystemd cold startの計測ではない。

証跡は/srv/ai/data/benchmarks/qwen-image-turbo-integration-20261010/api-result.jsonとworker log、生成artifactに保存する。入力モデル・steps拒否、確保応答のdescriptionとURL、終了待ち、upstreamエラーを自動試験で確認する。Python Providerはサイズ不一致、job失敗、メモリfloor、listener競合、保存metadataを試験する。
