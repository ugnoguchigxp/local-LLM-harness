SAAA実装依頼：LLM・ASR・TTSをOpenAI互換HTTP APIへ統一する

作成日：2026-09-06
対象：SAAAのProvider設定、推論client、音声入出力、接続確認、関連テスト・仕様書

依頼の目的

SAAA側を先行して整備し、専用transportを必須とせず、一般的なOpenAI互換HTTP Providerで会話と音声機能が動作する状態にしてください。

LLMはChat CompletionsのJSON／SSE、ASRは音声アップロードと文字起こしJSON、TTSはHTTPの音声応答を基本契約にします。旧専用transportや新しいAgent Session protocolを追加する方針にはしません。OpenAIのクラウドサービスへ切り替える依頼ではなく、ローカルを含むProviderの接続契約を一般化する依頼です。

目的は、利用できるProviderを増やし、接続・復旧の複雑さを減らしながら、短い待ち時間で会話できることです。通信方式の名称だけで高速と判断せず、実際の応答・音声再生までの時間を測定してください。

今回の範囲と作業上の注意

SAAAのHTTP client、設定・保存・検証、Provider解決、会話stream、tool継続、ASR、TTS、cancel、接続表示、テスト、仕様書を対象とします。Rust／Tauriを維持して構いません。言語の置換は目的に含めません。

LARMの本番配備、root activator、推論engineの改造、モデル交換、ContextStill Queueの変更は対象外です。会話履歴・memory・toolの業務仕様を変えず、transport変更による影響を既存の境界で吸収してください。設定の形式変更が必要な場合は、既存データを保持した移行と後方読み取りを用意してください。

調査時点のSAAAには、Provider設定・認証・runtime・UIと、新規agent_session関連に未commit変更があります。作業開始時に最新の差分を確認し、既存変更を削除・上書きせずに整合させてください。以下のファイル情報は調査の入口であり、最新構成を優先してください。

  • src-tauri/src/providers/stream/：通常のProvider実行、LARM・dynamic LAN経路。
  • src-tauri/src/providers/openai_compatible.rs：URLとcredentialの解決。
  • src-tauri/src/providers/dynamic_lan/validate.rs、service_harness.rs：旧transportの広告・形式に依存する検証。
  • src-tauri/src/providers/agent_session.rs、agent_session/sse.rs：追加中の独自Session／event stream。Chat Completions SSEと同一ではありません。
  • src-tauri/src/voice/cloud_asr.rs、network_asr.rs：既存のHTTP ASR。
  • src-tauri/src/voice/cloud_tts.rs：既存のHTTP TTS。調査時のartifact経路は音声を集約してファイル化しています。
  • Provider設定のRust model、保存・validation、src/lib/のschema、設定画面、日英翻訳、IPC契約。

1. LARMを通常のOpenAI互換HTTP Providerとして接続する

LARM固有のbootstrapを挟まず、利用者が設定するbase URL、model、認証だけで三APIを利用します。

ProviderとLARM内部の責務
層 入力 責務
SAAA base URL、公開model、認証。TTSはvoice等も設定 LARMのActivity、Profile、Agent Connection、独自Sessionを要求せず、HTTP APIを直接利用
LARM 標準HTTP requestのBearer tokenとmodel 公開modelから内部Routeを選び、Runtime起動、参照数、回収を管理

SAAAはLARMのProfile、Agent Connection、claim、allocation、lease、短期credentialを実装しません。 これらは旧経路のrollback期間だけ残し、新HTTP経路の接続条件や正常性指標にしないでください。

HTTP Providerの利用可否を、旧transportのstreamingProtocol、streaming.url、SAD1、native upstream、ACK／resumeの有無で判定しないでください。HTTP能力を持つ設定は旧transport広告がなくても受理します。ただし、認証、固定model、URL検証を緩めて受理してはいけません。

旧static経路:44448への自動fallbackやport監視を追加しないでください。401や契約不一致を理由に認証なし・別Providerへ自動的に切り替えないでください。接続先のoriginを越えてcredentialを転送しないでください。

2. LLMをChat Completions JSON／SSEへ移行する

POST /v1/chat/completionsを利用し、通常会話はstream: trueとします。JSONを使う既存の非stream処理も、同じmodel・認証・error処理で維持してください。

base URLから操作URLを組み立てる規則を一か所にまとめ、/v1/v1等の重複を防いでください。既存設定のendpoint形式を明示的に移行し、proxy配下のprefixを勝手に消さないでください。

SSE実装の受入条件は次のとおりです。

  • HTTP chunk境界とSSE event境界を同一視せず、UTF-8途中分割、複数eventの同時受信、改行形式、commentを処理する。
  • choices[].delta.contentを逐次表示する。roleだけのchunk、空delta、usage-only chunkを誤って不正扱いしない。互換性のために未知の追加fieldだけで拒否せず、必要fieldと意味を検証する。
  • 正常なfinishと[DONE]を確認し、途中EOFや不正JSONを成功にしない。stop、tool_calls、lengthを区別し、長さ上限到達を自然終了と同じ表示・扱いにしない。
  • tool callのargumentsをcall index／IDごとに組み立て、完了するまでtoolを実行しない。既存のtool許可、回数制限、memory／recall規則を維持し、結果を次のChat Completionsへ渡して会話を続ける。
  • reasoningが返るProviderでは表示・音声用contentと混ぜない。reasoning_effort、token上限、structured output等は既存利用を棚卸しし、Providerが対応する範囲で送る。非対応機能を黙って無視して成功扱いにしない。
  • 途中応答へ再生成を継ぎ足さず、独自ACK・resume・Session作成を成功条件にしない。SSEであることを理由にLast-Event-IDによる再開を仮定しない。

現行のAgent Session SSEは別APIです。そのevent形式をChat Completions対応の代用にせず、通常のOpenAI互換Providerが独自Session endpointを持たなくても動作することをテストしてください。

3. ASRを一般的なHTTP音声アップロードへ揃える

POST /v1/audio/transcriptionsへmultipartでfile、modelを送り、基本応答はJSONのtextとします。language等は必要かつ対応する場合に指定してください。

既存のHTTP処理を活用し、通常ProviderとLARM由来のProviderで同じ処理を使ってください。現行cloud_asr.rsのverbose_json固定は見直し、textだけのJSONでも利用可能にします。language、segments、no_speech_probがないことだけで失敗にしないでください。

録音・VAD・push-to-talkの既存機能を維持し、発話区間を確定してアップロードします。sample rate、channel、WAV encoding、音量、無音、長い発話、cancelを検証してください。無音や空文字は会話入力を生成せず、Providerの接続障害と区別します。

連続音声のRealtime ASRを新規実装する依頼ではありません。旧transportに依存するライブ字幕等がある場合は利用箇所を示し、HTTPで代替できる範囲と失う体験を報告してください。ASR結果をSSEで返すことを、音声の連続入力対応と呼ばないでください。

4. TTSをHTTP音声応答へ揃える

POST /v1/audio/speechへmodel、input、voice、対応するresponse_format等を送り、音声bodyを再生してください。SSEや独自binary frameを必須にしません。標準的な音声responseを受けるために、独自のstream: trueを必須送信しないでください。

初期対象はWAVとPCMとし、実装したformatだけを設定で選べるようにしてください。PCMはsample rate、channel、sample formatを明確にし、byte列だけから推測しないでください。Providerの返す音声仕様との不一致は検知してください。

対話再生は、逐次音声を返すProviderなら全bodyの受信・ファイル保存を待たずに開始します。既存のartifact保存機能は維持して構いませんが、会話再生の必須前処理にはしないでください。buffered responseのProviderも利用できるようにし、受信の分割だけでengineの生成待ちが短くなるとは扱わないでください。

LLMの全文を待たず、発話可能な句単位で合成・再生を進めてください。tokenごとのTTS requestや無制限の先読みQueueは避け、順序を保ちます。tool argumentsやreasoningを読み上げないこと、句の切れ目で日本語の読み・韻律が崩れないことを確認してください。

利用者の割り込みでは、再生を停止し、未再生の句を破棄し、関連LLM／TTS requestをcancelします。前turnの遅延応答が新turnの表示・再生へ混ざらないようにしてください。

5. 設定、接続確認、障害からの復旧

  • 通常のHTTP Provider設定では旧transport URL、独自protocol、allocation IDを入力させない。base URL、model、認証と必要な音声設定を基本にする。ローカルProviderも設定できる名称・説明にする。
  • 既存credential保管を維持し、tokenを設定JSON、log、画面へ露出しない。ユーザーが選ぶ認証なしの設定は維持するが、認証失敗後の暗黙の認証解除は行わない。
  • /models一覧取得と推論可能性を分ける。modelを明示できるProviderに一覧endpointがないことだけで利用不能にせず、短い実処理で接続を検証する。ASRは固定音声、TTSは短い固定文を用い、通常の接続確認で不要なマイク収録を要求しない。
  • 接続不能、起動待ち、混雑、認証不正、model不一致、protocol不一致、途中切断を区別して表示する。旧transport未接続の表示をHTTP Providerへ流用しない。
  • 429／503はRetry-After等を使った上限付きbackoffとcancel可能な待機にする。401／403や設定不正を短周期で再試行しない。
  • LARMのrelease identityまたはboot epoch変更後は、次requestを通常HTTPで新規開始する。応答開始前の再試行と、途中応答・tool実行後の再試行を区別する。外部副作用を持つtoolをtransport retryで二重実行しない。
  • HTTP切断とengine計算停止の保証を分ける。client側の待機・再生停止は確認し、Provider側の停止保証が未検証ならその状態を報告する。

6. 実装順と旧経路の扱い

  1. 最新の差分と旧transport依存箇所、既存HTTP処理を棚卸しし、現状の機能・失敗・性能のbaselineを保存する。
  2. 通常ProviderのChat Completions SSEとtool継続を実装し、fixtureで会話を完走させる。
  3. LARMもbase URL、Bearer token、公開modelだけで同じclientへ設定し、独自discoveryなしで動作させる。
  4. ASR、TTS、設定UI、接続確認、cancelを共通HTTP契約へ揃える。
  5. 対象clientの会話・音声・設定移行を検証し、HTTPを通常経路にする。
  6. 移行対象で使われなくなった旧transportの設定・表示・実行依存を外す。旧経路は切替検証中の明示的な退避用途に限り、新規機能を追加しない。

他の連携が旧transportを使っている場合は、依存があるまま無差別に削除しないでください。廃止対象と残存依存を報告し、今回のHTTP経路へ旧transportを暗黙fallbackさせないでください。関係のないAgent Session機能の削除も、この依頼だけを根拠に行わないでください。

7. 検証

LARM本番が未配備でも先行できるよう、実socketを使うローカルfixture serverでHTTP応答と遅延・切断を再現してください。通常Provider fixtureは独自Session・Activity・Profile・claim・旧transportを実装せず、その状態で三APIを利用できることを確認します。

必須ケースは、正常な会話、tool往復、UTF-8／SSE分割、usage-only chunk、途中EOF、429／503、401、model不一致、応答前後のcancel、遅い音声配信、buffered音声、ASRのtext-only JSON、無音、Provider再起動後の次request、前turn応答の混入防止、旧設定の読み込みです。

検証コマンドと合格条件
コマンド 用途と合格条件
cargo test --manifest-path src-tauri/Cargo.toml providers:: Providerの既存テストと追加HTTP契約テストが成功。対象moduleの実際のtest件数を確認し、0件実行を合格にしない
cargo test --manifest-path src-tauri/Cargo.toml voice:: ASR・TTS・cancelの既存および追加テストが成功
bun run test:frontend 設定・翻訳・stream表示の回帰がない
bun run check 型、整形、clippy、IPC、品質契約、既存全体テストが成功
bun run build frontendと関連生成物のbuildが成功
bun run spec:check 仕様書の検査が成功
bun run larm:preflight、bun run larm:canary、bun run larm:report HTTP用判定へ更新後、接続先・期待release・各実処理・cleanupの結果を記録。旧transport合格条件をそのまま使わない

上記コマンドは調査時点のpackage scriptsとmodule構成に基づきます。変更後の構成に合わせて必要なtargetを追加し、実行した正確なコマンドを記録してください。既存checkの失敗は変更由来と既存要因を区別し、skipで成功に見せないでください。

性能は同model・同prompt・同音声・同GPU条件で比較し、cold／warm、単独／競合を分けてください。LLMの最初のcontent、ASR確定、TTSの最初の再生可能音声、実際の再生開始、発話終了から再生開始のp50／p95を記録します。role-only chunk、heartbeat、reasoning tokenを返答開始に数えないでください。

まずbaselineと必要な対話品質から許容遅延を設定し、その値に対して判定してください。未測定の速度目標を捏造せず、比較できない条件は未測定とします。fixtureで通信の逐次処理を確認しても、実engineの速度を証明したことにはしません。

失敗時は層と再現条件を記録し、修正後に該当ケースを再実行してください。一時的な実Provider障害の確認再試行は回数を決めて行い、合格するまで無制限に繰り返さないでください。外部要因が残る場合は未達項目と必要な変更を記録します。

8. 責任分担と完了条件

担当範囲と段階別の完了条件
区分 担当と完了条件
SAAA先行整備 SAAA担当。通常ProviderとLARMを同じHTTP clientで利用し、fixtureによる会話・tool・ASR・TTS・割り込み、設定移行、既存checkを通過。新経路は旧transport・Session・claim不要。到達状態は「SAAA HTTP対応完了／LARM live統合待ち」と明記
LARM提供側 LARM担当。承認済みreleaseの配備、公開model catalog、HTTP認証・三API、engineの能力・cancel・資源管理を提供。SAAA担当が独断でroot配備・engine変更をしない
実機統合 LARM準備後に実施。SAAAからHTTPで会話とtoolを完了し、ASR→LLM→TTSを再生まで確認。中断とProvider復旧後の次turn成功、内部参照のcleanup、期待releaseを確認して「SAAA–LARM実機統合完了」とする
システム全体 別工程。ContextStillの実job結果保存、Queue回復、release収束の検証も必要。SAAA単体の合格で全体の本番稼働完了と報告しない

HTTP対応で失う既存のライブ字幕・resume等が見つかった場合は、該当する利用場面と代替案を具体的に報告してください。認証の緩和、外部送信先やモデルの無断変更、履歴の破棄で移行を成立させないでください。

納品には、変更概要、対応APIと非対応機能、設定移行、検証コマンドと結果、性能比較、既存transportからの移行状況、LARM側への必要事項、未達条件を含めてください。LARM未配備を理由にSAAA単体で進められる実装・fixture検証を止めず、外部依存を切り分けて完了させてください。
