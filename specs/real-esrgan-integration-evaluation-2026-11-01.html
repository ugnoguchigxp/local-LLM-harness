Real-ESRGANの画像拡大・補修機能の導入検討

2026年11月1日。結論は条件付きで導入可能。LARMに静止画の超解像Providerを追加し、 既存の画像生成結果と取込画像を入力にできる構成を推奨する。 第一候補はReal-ESRGAN-ncnn-vulkan。実機のRadeon 8060SをVulkanから認識できたが、 Real-ESRGANの推論・速度・peakメモリー・画質は未測定であり、配備済みという意味ではない。

LARM調査対象revisionは20ba531eb7ef6ffb62298a23e719291692e4eaf3。 調査は公開資料・ソース・release情報とローカル設定の読み取り、GPU列挙、文書作成に限定した。 パッケージ導入、モデル・実行物の取得、既存サービスの変更、推論は実施していない。 SAAA実装は参照していない。

機能ごとの導入判断
機能 判断 条件・限界

イラスト・アニメ画像 realesrgan-x4plus-animeを追加候補とする。 汎用モデルと分けて選択する。画像内容から自動でモデルを切り替えない。

動画の高解像度化 後続。初期対象から外す。 フレーム処理に加え、音声・時刻・再エンコード・長時間ジョブ管理とちらつき評価が必要。

512角を2048角へ、1024角を4096角へ拡大する用途が最初の評価に適する。 4倍は各辺の倍率で、画素数は16倍になる。高解像度で直接生成する処理との速度差や画質差は、 この実機では未比較。常に高速・高品質になるとは決めない。

実行方式の選定

Vulkan版を先行し、追加機能が必要な場合にPython版を検討する
方式 適合性 確認事項
Real-ESRGAN-ncnn-vulkan Linux・AMD GPU向けの第一候補。CUDA・PyTorchを必要とせず、CLIを子プロセスとして管理できる。 古い配布物と現行RADVの実行互換性、モデルごとの倍率、タイル境界、黒画像の発生を実機確認する。
Real-ESRGAN Python・PyTorch GFPGAN、denoise strength、任意の最終倍率、16-bit等が必要な場合の候補。 gfx1151対応PyTorch・ROCmとBasicSR等の組合せを専用環境で固定する。既存Providerの仮想環境へ追加しない。

Python版の任意倍率はモデル本来の倍率で推論した後のリサイズを含む。 ncnn CLIのヘルプには2・3・4倍があるが、すべてのモデルが各倍率へ対応するという意味ではない。 初期契約は汎用x4plusと任意追加のanimeモデルの4倍に限定する。 2倍出力が必要なら、native 2倍モデルを使う方式と4倍推論後に縮小する方式を別々に評価する。 Python版の.pthとncnn版の.param・.binは実行資産として区別する。

実機のvulkaninfo --summaryは正常終了。GPU0はRadeon 8060S Graphics、RADV STRIX_HALO、 device API 1.4.335、Mesa 26.0.8-1ubuntu0.3。GPU1はCPUのllvmpipeだった。 実行時はハードウェアGPUを明示し、ログでも選択を確認する。GPU列挙成功だけでは推論成功を保証しない。

上流APIで確認した最新releaseはPython版v0.3.0（2022-09-20）、ncnn版v0.2.0（2022-04-24）。 調査時のmasterはそれぞれa4abfb2979a7bbff3f69f58f58ae324608821e27、 37026f49824c5cf84062e7c6a5dd71445dcf610fだった。 更新間隔が長いため、READMEの最小依存バージョンを現行環境の動作保証とは扱わない。 配布バイナリが動かなければ、固定revisionと依存関係でのビルドを評価する。

LARMへの接続案

既存のPOST /v1/images/generationsはpromptを受ける画像生成APIで、現在のschemaはQwen・FLUXのみを許可する。 Real-ESRGANをこのmodel列挙へ加えるだけでは、入力画像を受け取れず、 Daemonの生成モデル・steps・寸法の検証にも一致しない。画像拡大の専用操作を設ける。

API案はPOST /v1/images/upscales、capability案はmedia.image.upscale、 runtime variant案はimage-upscale。これらは提案名であり、現在の公開APIには存在しない。 Agent ProfileのProvider subsetからroute、runtime、backendを明示解決し、 独立したControlのメディア操作でも明示したvariant設定から同じ実行対象へ到達させる。 実行中の画像モデルやsystemd unitの状態を要求モデルの代用にしない。 

{
  "source": { "type": "image-artifact", "id": "image_0123456789abcdef0123456789abcdef" },
  "model": "realesrgan-x4plus",
  "scale": 4,
  "format": "png"
}
  1. Controlの既存認証で入力artifactを解決する。外部の写真は既存の画像取込APIで先に登録できる。 入力は検証済み画像の専用コピーを確保し、読込中の削除・retentionとの競合を防ぐ。
  2. 明示modelに対応するmanifest・資産の存在と入力・出力上限を、GPU起動前に検証する。 未配備モデルは別モデルへ自動代替しない。
  3. 既存のaccelerator-media-heavy排他groupと共通起動gateを通し、要求時にだけworkerを起動する。 画像生成・音楽・3Dと競合する場合は既存の競合契約へ合わせる。
  4. 専用の内部workerがncnn CLIを引数配列で起動する。モデル・GPU・tile・作業領域は管理側で制限する。 公開ネットワークで上流CLIを直接操作できる構成にはしない。
  5. 出力をdecodeし、要求寸法・形式・alpha・hashを検証して新しいartifactとして原子的に公開する。 元画像を上書きしない。出力をControlから取得でき、workerと子プロセスが終了した後に成功を返す。

初期試行は同時実行1件、4倍、出力各辺4096以下・16メガピクセル以下を提案する。 1280角の4倍は5120角になるので、この初期上限では起動前に明示エラーにする。 暗黙に縮小して成功にしない。上限拡張は実測後に判断する。 RGBのPNG出力を先行し、WebP・RGBAは透過境界と再エンコードの受入後に有効にする。

image artifactの寸法schemaは各辺16384まで許容するが、既存の画像取込normalizerは各辺2000・ 4メガピクセルまでで、入力16 MiB・保存20 MiBの制限もある。 拡大結果を取込APIへ送り直す設計は採らず、処理結果専用の検証・公開経路を追加する。 取込の防御的な上限を一律に緩和しない。既存copyForMeshにも4096辺・20 MiBの制限があり、 画像の保存成功だけで3D入力としての利用まで保証しない。

メモリーは現行の実測空き判定を継承する。 UMAのsystem・GPU空きを加算せず、ホスト安全余裕を一度だけ適用する。 モデルファイル容量や旧画像生成の固定予約値を起動判定へ流用しない。 tile処理でも出力全体・decode・encode用のメモリーが必要であり、tileだけでpeakが一定になるとは考えない。 待機・モデルロード・処理・停止は要求の総期限と取消に従う。

実行物・専用環境はrepository外の/srv/ai/apps/real-esrgan-runtime、 モデルは/srv/ai/models/Real-ESRGAN等へ分離する案とする。 manifestへ配布元・revision・各ファイルのSHA-256を記録し、要求中の追加downloadは行わない。 ソースのLICENSEはPython版がBSD-3-Clause、ncnn版がMIT。 配布物・モデル資産・依存物の付属条件と著作権表示も実際の採用品ごとに記録する。

導入前の試験と採用条件

  1. repository外で固定したLinux実行物とモデルを準備し、RADVを使う単体CLI試験を行う。 写真、圧縮画像、生成画像、イラスト、細線・文字を含む画像について通常のLanczos拡大と比較する。
  2. 512角→2048角、1024角→4096角で、起動・ロード・処理・保存の時間とOS・GPUのpeakを測る。 tile設定を変えて境界・速度・メモリーの差を調べる。既存会話Providerが稼働する条件でも評価する。
  3. 黒画像、継ぎ目、輪郭の過強調、文字変形、色変化を目視確認する。 upstreamはncnn版とPyTorch版の差やタイル不整合の可能性を説明しており、同一出力を前提にしない。 終了codeだけで成功とせず、出力decode・寸法・hashを機械検証する。
  4. CLI試験後にLARMへ統合し、初回起動、競合、取消、期限超過、メモリー不足、資産不足、保存失敗、 worker停止失敗を試験する。失敗時に半端なartifactを公開せず、子プロセス・作業ファイルを回収する。
  5. PNG取得とhashの一致、原画像保持、処理中の削除・pruneとの整合、来歴、停止後の画像取得を受け入れる。 WebP・RGBA、顔補修、動画はそれぞれ追加の受入を行う。

単体CLIで動作・画質・負荷の受入を満たせば、静止画4倍拡大から導入を進める。 現時点の未解決事項は、古いncnn実行物と現行GPUの互換性、実測性能、実際の画質、 適切なtile設定と出力上限である。技術的な接続案と導入完了を区別する。
