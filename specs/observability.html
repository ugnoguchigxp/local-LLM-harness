LARM 性能計測・トレーシング基盤

2026-10-16。既存のモデル解決、優先度、Provider lifecycle、キャンセル、TTSの直列実行を変更せず、管理処理とupstream応答を分解する。実モデルの高速化、Rust移行、起動・配置の変更は対象外。本書と性能診断仕様を併せて参照する。

既存実装の調査と優先順位

既存経路、不足点と今回の対応

Model Broker app-model-broker-gateway → ModelBroker.acquire → control.allocate → ready polling。同一モデルの処理中leaseは共有、最後の参照でclose。prepare開始・完了eventは存在するがモデル解決、割当、ready待ちが分離されない。 優先度1。model_resolution、allocation_acquire、broker_acquire、runtime_readiness。共有処理自体は先行リクエストに属し、後続は自身のbroker_acquireで共有ready Promise待ちを計測。

ASR allocation/claimed Provider経路と、service-harness-gatewayの固定ASR経路がある。multipart uploadはstream、最終JSONは既存検証器で検証。 優先度2。両経路の実行待ち、upload完了待ち、headers/body/全体を計測。入力長・RTFは診断fixtureで取得。通常APIはエンジン推論開始やVAD時刻を提供しない。
TTS Gatewayのruntime実行制御と、Eumenesの会話内の直列生成が別々に存在する。音声の順序保証はconsumerにある。 優先度2。各HTTPチャンクのLARM待ち、最初のWAV音声、全体、文字数、音声長、RTF、キャンセルを取得。Eumenesのpendingキュー・再生時間はLARMから観測できない。
リソース・既存診断 LinuxNodeTelemetryはprocfs/sysfsのRAM・AMD VRAM/GTT。Observerの既存tickと/metricsを使用。performance-larm.tsはJSON/SSE、LLM/ASR/TTS単独・mixed、p50/p95/max、JSON外部保存、ASR shadow比較を実装済み。 優先度2。任意CPU/GPU busy、daemon RSS/heap・CPU・event loop、GC対応時のpauseを追加。診断にdirect比較、trace参照、区間別集計、engine統計を追加。

調査範囲はapps、packages、deploy/local-node、benchmarks、既存specs。SAAA実装には依存せず、変更していない。Eumenesはローカルのclean checkout c651e23dbbe7850f7ae5664f240db313829113b2をread-only調査した。最新remoteとの同一性は検証していない。

区間の意味と確認方法

新規計測の経過時間はperformance.now()を使う。spanのUTC時刻は受付時のDate.nowに単調時計の差を足す。プロセス間でUTC時刻を引いて遅延を算出しない。既存queueとGatewayの既定duration時計も単調時計へ変更し、TTL・期限判定のwall clockは維持する。

spanとlarm_request_stage_secondsのstage。単位はhistogramが秒、trace属性とServer-Timingがms
stage 開始・終了と制限
dispatch 共通middleware受付からGateway handler開始まで。認証・readinessポリシー・ルートdispatchを含む。ネットワークで受信する前やHTTPサーバー内の待ちは含まない。
ingress Gateway入口の検証・body準備。multipartの音声本文はログにもtraceにも保存しない。
model_resolution Broker catalogからモデル・protocolを解決する同期区間。
broker_acquire Broker.acquireの入口からlease取得。共有prepare・先行close待ちを含む。
allocation_acquire / allocation_admission control.allocate全体と、その内部のplanAllocationRequestAdmission判定。後者は前者の内数。
runtime_readiness Brokerの割当応答からready binding確認。capacity待ち、起動、poll intervalの待ちを含み、純粋なモデルload時間ではない。
allocation_lookup / provider_admission 既存allocationのbinding選択・resolveと、foreground/background Provider要求の受付。新規モデル起動と区別する。
execution_wait ExecutionGate.acquire呼出しからslot取得、または失敗まで。LARMの待ちであり、upstream内部キューを含まない。slot取得後のconcurrencyは既存execution_activeと比較する。
binding_revalidation / request_preparation / forward_preparation slot取得後のbinding再確認、body・chat-input・context・監査準備、onForwardedの実行。これらをエンジン推論時間に混ぜない。
upstream_headers fetch呼出しからresponse headers受信。接続、upload、upstream内部キュー、推論の一部を含む。fetchは接続完了・送信完了の独立時刻を公開しないため個別値を作らない。
upload_completion response headers取得後、stream uploadが正常完了したことを確認する待ち。送信全体の所要時間ではない。
upstream_body headers/upload確認後からbody EOFまで。SSEではdecode、受信、正規化、consumer backpressureを含む。engineのdecode_msとは別物。
first_body / first_token 共通受付から最初の非空body chunk／最初のmeaningful SSE deltaまで。JSONのTTFTは未取得。SSEのrole、usage、finishだけではTTFTを確定しない。
relay_sum / relay_max streamのreader.read解決から検証・監査capture・downstream enqueueまでの所要時間の合計／最大。1チャンク1ログを出さず最後に集約。ソケット送信・再生完了を意味しない。
first_playable_audio fetch開始からWAV data headerと最初の音声byteを観測するまで。実際のengine内部推論開始からの時間ではない。最大64KiBのheaderだけを検査し、非WAVでは未取得。
total 共通受付からGateway terminalまで。stream EOF、cancel、timeout、異常終了を含む。buffered応答では検証完了時まで。実際のネットワーク配信・ブラウザ再生完了はEumenes側で別計測する。

入れ子や累積時間を含むため全stageを合算しない。larm.upstream client spanはfetchからbody完了まで。early failureでは進行中区間をterminal時点で閉じる。非同期監査finalizeやterminal callbackによるslot保持は既存仕様を維持する。確定処理とslot保持はrequest_cleanup operation、監査finalizeはaudit_finalizeで確認する。

Trace属性はlarm.duration_ms.*、runtime/protocol、初期allocation/binding状態、到着時のqueue深度・active数、内部Request ID。既存のallocation・lifecycle eventをRequest ID、runtime、routeと照合する。状態は観測の分類であり、物理的cold/warmと断定しない。 

larm_request_stage_seconds{stage="execution_wait",runtime="...",protocol="...",outcome="..."}
larm_execution_active{runtime="..."}
larm_execution_queued{runtime="..."}
larm_observed_request_total{protocol="openai.audio-speech.v1",outcome="client_cancelled"}

実際のhistogram系列は上記nameに_bucket、_sum、_countが付く。低遅延区間を観測できるようbucket下限を0.1msとした。Prometheusではhistogram_quantile(0.95, sum by (le, stage, runtime) (rate(larm_request_stage_seconds_bucket[5m])))で確認する。IDはmetric labelにしない。Server-Timingはheaders確定時点の完了区間のみで、stream完了後のtotalやrelayはtraceと/metricsで確認する。

推論・音声統計と未取得の扱い

inferenceStatisticsは既にparseされたJSON/SSEから数値のみ抽出する。検証前のlegacy allocation JSON応答は最大64KiBの任意tapから完了時に統計を読む。超過時はtapを破棄し、応答はそのまま配信する。usage.prompt_tokens、usage.completion_tokens、usage.prompt_tokens_details.cached_tokens、timings.cache_n、prompt_ms、predicted_ms、predicted_per_secondを対象とする。cache_nは再利用prompt token数、prompt_msとpredicted_msはエンジン報告値。cache hit率やtoken速度を文字数から推定しない。traceのlarm.engine.*とlarm_engine_reported_* gaugeに記録し、診断ではp50/p95/maxを集計する。gaugeは最後に得た値であり、リクエストごとの履歴ではない。

診断JSON schema 4では、JSONのfirstTokenMsとusageなしのcompletionTokens、outputTokensPerSecondをnullとする。deltaEventsは引き続き別に記録する。outputTokensPerSecondは報告されたcompletion token数÷クライアント側total時間であり、エンジンのdecode_tokens_per_secondと区別する。

TTSはlarm.input_characters、WAVが完結した場合のlarm.audio_seconds、fetch開始からterminalまで÷音声長のlarm.upstream_rtfを記録する。対応gaugeはlarm_request_input_characters、larm_request_audio_seconds、larm_request_upstream_rtf。headerが大きいWAV、未完結WAV、未知の長さ、PCM・MP3等では長さを推定しない。キャンセル音声のduration/RTFは確定しない。

ASR診断ではfixtureのWAV headerまたは明示した音声長とclient totalからRTFを計算する。通常ASR最終JSONからengine内部の開始時刻や推論時間は得られない。verbose JSONにdurationが報告される場合だけaudio_input_secondsとupstream RTFも記録する。音声の長さと処理時間は別の値として扱う。

トレースIDの伝播とEumenes変更案

OpenTelemetryの公式API、W3C propagator、BasicTracerProvider、ParentBasedSamplerとTraceIdRatioBasedSampler、BatchSpanProcessor、OTLP HTTP exporterを使用する。グローバルproviderや自動HTTP monkey patchは登録せず、middlewareのAsyncLocalStorageと明示Request参照を併用する。stream pullが別の非同期contextで実行されても同じ観測を保持する。

計測対象は/v1/に限定せず、/v2/context-viewsなどのversion付きAPIにも同じ伝播を適用する。/health、/ready、/metricsの監視入口はtraceを生成しない。

  1. Eumenesからのtraceparent/tracestateを標準propagatorで検証・抽出する。不正なparentは新しいtraceにする。新規server span、管理区間のchild span、upstream client spanを作る。
  2. upstreamにはclient spanのtraceparent/tracestateと既存x-request-idを送る。credentialやbaggageは無条件に転送しない。engineが未対応でもLARM側のclient spanは記録する。
  3. 応答にはserver spanのtraceparentとx-larm-trace-id、既存のx-request-idを返す。traceは会話全体、spanは個別処理、Request IDは既存HTTP・監査の識別子として区別する。安全な形式の呼出元x-request-idはcaller_request_id属性へ記録し、内部IDを置き換えない。
  4. Eumenesは会話turnのtraceを親とし、LLM、感情推定、TTSチャンクに別client spanを作る。再試行も別span・Request IDとする。trace IDをruntimeやProfile選択には使わない。

Eumenesのapi/application/app.tsとapi/infrastructure/logger.tsにはhttpRequestId、requestId、runId等が存在する。api/domains/larm/service/index.tsのinferはProvider bearerを付けてrequestを行い、api/domains/inference/service/index.tsは個別推論・チャンクのreceiptを扱う。現状これらにW3C伝播がないため、次を別リポジトリ変更案とする。今回はEumenesを書き換えていない。

  • 入口でHTTP traceparentまたはWebSocket message metadataのtraceparent/tracestateを検証し、log contextへtraceId/spanIdを追加する。会話のrunId/utteranceIdを維持する。
  • inferのrequest headersへ、そのcallのclient spanをinjectする。onExchange/receiptへLARMのx-request-idとx-larm-trace-idを保存する。現在Date.nowで差を取るinferの経過時間をperformance.nowへ移す。
  • voice-dialogue/service/index.tsのpending.push、pending.shift、speak/executeRequest完了でTTS enqueue、start、completeを記録し、pending深度・chunk index・attempt・キャンセル理由を残す。既存while loopの直列awaitと先読み音声数の上限を維持する。
  • 同ファイルには回答確定後にspeech.appendする分岐がある。answer確定→enqueue、LLM first delta→answer確定、TTS完了→playback開始を別々に測る。仕様上の待機を不要なブロックと決め付けない。
  • ブラウザのaudio ready/play/end、VAD endを同じtrace/turn/chunkに関連付ける。異なる時計の時刻差は計算せず、各プロセスで単調時計によるdurationを記録する。message metadata例は{traceparent, tracestate, requestId, runId, chunkIndex}。音声frameごとにspanを作らない。

設定、負荷、障害分離

LARM_OBSERVABILITY_ENABLED=true
LARM_TRACE_SAMPLE_RATIO=0.01
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://127.0.0.1:4318/v1/traces

既定は無効。新規metrics、trace、process samplerは上記スイッチで有効化する。既存/metricsと制御eventは従来通り。endpoint省略時は新規metricsとID伝播だけで、traceは送信しない。ratioは0〜1で新規rootに適用し、受信parentのsampled判断を継承する。Eumenes側の親が全件sampledならLARMでも全件採取となるため、LARMのratioをtrace全体の採取率の上限とは扱わない。ratio=0もID伝播と全リクエストの集約metricsは残る。trace内容を確認するにはcollectorを設定し、テスト時はratio=1またはsampled親を使う。

batch queueは最大2048span、batchは256span、送信周期1秒、送信timeout2秒。要求処理はexportやflushをawaitしない。満杯時は詳細spanが失われ得るため、欠測を処理時間0と解釈しない。metric sink、spanの書込み、export障害は推論の応答から隔離する。shutdown時だけbest effortでflushする。収集器への認証・接続経路は運用側で設定する。

token/frameごとのspan・同期console出力は追加しない。prompt、認識文字列、TTS本文、音声payload、credential、任意のrequest headersは保存しない。数値統計、固定stage、runtime/protocol、IDをallowlistとして記録する。Request ID、trace ID、span IDはPrometheus labelから除外する。既存のinference-audit保持ポリシーは独立し、計測の設定で変更しない。

有効時は1秒周期でdaemon CPU（1.0=1コア）、RSS、heap、timer遅延を計測する。event_loop_delayは周期超過時間で、1秒内の短いpauseを全て捉えるものではない。PerformanceObserverがgcをサポートするときだけprocess_gc_pause_secondsを記録し、未対応時の0msを捏造しない。既存Observer tickで/proc/statの差分CPU利用率と/sys/class/drm/card*/device/gpu_busy_percentの最大値を任意取得する。Linux非対応・欠測時は値を出さない。CPUはホスト全体、GPU busyは観測可能なカードの最大値、daemonのCPU/RSSはモデルprocessの値ではない。

診断の実行と比較条件

LARM_PERF_SCENARIOS=llm,llm-sse,asr,tts,mixed,mixed-sse \
LARM_PERF_ITERATIONS=20 LARM_PERF_WARMUPS=2 \
LARM_PERF_AUDIO_FILE=/absolute/fixture.wav \
LARM_PERF_OUTPUT=/outside-repository/diagnostic.json bun run perf:diagnostic

schema 4は各sampleのrequestId/traceId、headers時点のinternalStagesMs、engineReported、既存p50/p95/maxとraw iterationをJSON保存する。resource monitorはCPU/GPU busy最大値、daemon RSS最大値も保存し、取得できなければnullとする。TTFT、engine decode速度、client totalを別々に比較する。最低20件の例でもp95は安定性の保証ではなく、十分な反復と条件固定が必要。 

LARM_PERF_COMPARE_DIRECT=true \
LARM_PERF_DIRECT_LLM_URL=http://127.0.0.1:PORT/v1/chat/completions \
LARM_PERF_DIRECT_LLM_RUNTIME=RESOLVED_RUNTIME \
LARM_PERF_SCENARIOS=llm,llm-sse \
LARM_PERF_OUTPUT=/outside-repository/direct.json bun run perf:diagnostic

directは明示指定のHTTP loopback URLとruntime IDが必要。ASR/TTSもDIRECT_ASR_URL/RUNTIME、DIRECT_TTS_URL/RUNTIMEで同様に指定する。public allocationには内部endpointを要求せず、指定runtimeと実際の割当bindingが一致しなければ失敗させる。Profile→route→runtime→backendを確認してURLを設定する。稼働中の別モデルを流用しない。

direct時も割当leaseを保持して実行条件を維持するが、HTTPはExecutionGateを経由しない。管理者が隔離した比較環境で、同じモデルrelease、入力、sampling、token上限、slot数、context長、KV設定、同時workload、他consumerの有無を揃える。スクリプトは各系列でGatewayとdirectを順に測定し、warmupを同数実施する。差分はengine/cache/熱状態の変動も含むため純粋なGateway CPU時間と呼ばない。ASR shadowとの混在比較は拒否する。

KV比較は、対応エンジンと隔離環境でLARM_PERF_CACHE_PROMPT=trueとfalseを別々の出力先で実行する。cache_promptを同一payloadへ付加するだけで、共有slot消去・モデル再起動・設定変更は行わない。cached_tokensの実報告がなければ、比較モードは要求値に過ぎず、cache利用有無が実証されたとは扱わない。

bun run perf:overheadはモデル不要の模擬upstreamとcollectorをlocalhostに起動し、無効／metrics（sampling 0）／全件trace送信（sampling 1）を比較する。反復はLARM_OVERHEAD_ITERATIONS、round数はLARM_OVERHEAD_ROUNDS、任意外部JSON保存先はLARM_OVERHEAD_OUTPUT。既存source-only保存制約と排他的出力を使用する。

追加の計測基盤：応答後処理・制御キュー・起動・収集器

2026-10-16の拡張。HTTP応答時間だけでなく、次の要求を待たせ得る管理処理と、計測系自身の詰まりも追跡する。処理順、割当、優先度、キャンセル、TTS直列制御を変更しない。デプロイ・モデル再起動・実モデルの選択は実施していない。

独立したoperation spanとoperation_stage_seconds
operation 計測区間・意味
request_cleanup response terminalから後処理完了まで。terminal_callbackはsnapshot等の確定処理、finish_callbackはlease解放等のonFinish。slot_holdはslot取得からrelease関数完了、post_response_slot_holdはresponse terminalからrelease関数完了。既存のRequestTrackerとslotの解放順序を維持し、応答から後処理をawaitする待ちは追加しない。
control_task ControlPlaneの既存applyChainに投入してから開始するまでのqueue_waitと、開始後のrun。キュー深度control_tasks_queued、実行中control_tasks_activeも公開する。task_kindはtraceに固定名で記録。単一制御キューの先頭処理によって後続が待つ現象を見られる。
runtime_startup 割当runtimeの起動・検証処理全体。health_probeは実際のObserver.tick呼出し時間の合計、poll_waitは既存sleepの実時間の合計、health_probe_countは確認回数。pollごとのspan・ログは作らない。

runtime_mutation 既存MutationCoordinatorのreserveからreleaseまで。kindはtrace、kind別runtime_mutation_activeはgauge。排他方針や拒否・drain動作は維持する。

request_cleanupはrequest spanのchildだが、親の応答spanより後に終わる。totalは引き続きGateway terminalまで。後処理のエラーはcleanupのoutcomeへ記録し、成功した推論のoutcomeを上書きしない。後処理が遅い場合は次のexecution_waitとpost_response_slot_holdを照合する。

既存request stageにはpersonal_state_preparation、context_preparation、chat_input、audit_begin、audit_finalize、broker_closing_wait、broker_ready_waitを追加した。最後の2区間は共有leaseのclose待ちとready Promise待ちで、broker_acquireの内数。downstream_pull_gapは最後のenqueueから次のReadableStream.pull開始までの合計であり、ソケット送信や再生の遅延を断定する値ではない。

共通ActivityObservationはstage、measure、operation、run、finishを提供する。currentObservationの固定名operationを作り、runで非同期contextへ引き継ぐことで、新しい処理も同じtraceへ追加できる。Request IDは入口で発行し、runtime・allocation・routeの確定後に属性を追加する。要求受付前に決まらないruntime属性は空欄にし、別プロセスの稼働モデルから補完しない。

保持する非同期operation観測は最大1024件。15分を超えた観測はobservation_expiredとして閉じ、保持領域を解放する。これは計測上の打切りであり、アプリケーションのキャンセル・timeoutを実行しない。shutdownもobserver_shutdownとして観測のみ終了する。HTTP要求そのものの既存timeout・drain方針は変更しない。

perf:overheadのschema 2はJSON、SSE、ASR multipart、TTS WAV、SSE+ASR+TTS混在を対象とし、各系列で無効・metrics（sampling 0）・全件trace（sampling 1）を同条件で比較する。TTS runtimeの実行枠は1を維持し、同時要求を送っても生成を並列化しない。各caseのraw latencyは全HTTP要求を集計し、mixedは3種類の混合集計である。modeの順番はroundごとに回転する。

LARM_OVERHEAD_P95_BUDGET_MSを指定すると、各caseで有効modeのp95と無効modeのp95の差が指定msを超えた場合、budgetPassed=falseと終了コード1を返す。許容値は同じ機材・同じ条件で基準を作ってから設定する。既定ではhardware依存の閾値を強制しない。OS負荷、round数、concurrency、read delayが違う結果を同一の回帰基準として比較しない。

追加調査：状態通知と次のProfile要求までのモデル維持

変更先の契約、実装順序、認証・保持・API拒否・性能検証の詳細はEumenes保護・モデル維持の実装計画に整理した。下記は変更前の調査記録。後続の承認済み変更では内部待機の通知化と専用credentialによる保護・保持を実装しており、有効化条件と性能結果はリンク先の実装結果を参照する。

2026-10-16の利用者確認。内部状態の待機はイベント通知を使い、ロード済みモデルは次のProfile起動要求まで維持したいという意向がある。さらに、Eumenesの利用中および前のリクエストから10分間は他の利用要求をAPIで拒否する想定が示された。次のProfile要求が来ただけで保護中のEumenesから切り替える設計とはしない。以下は現状と変更候補の整理であり、今回の計測実装では待機方式・解放policyを変更していない。

  • ControlPlaneはallocation_ready、allocation_failed、allocation_released、allocation_expiredを既にemitし、mainのonEventでmetricsとevent出力に渡している。一方、ModelBroker.prepareは内部Allocationを既定500ms間隔で再確認する（mainが渡す設定値。class単体の既定は50ms）。既にreadyならsleepしない。
  • AgentConnectionController.waitForReadinessとrunBackgroundにも内部Allocationの再確認があり、間隔はmax(1000ms, pollIntervalMs)。Eumenesが利用する接続作成側にも関係する。ready検出後に別途semantic readinessを確認するため、内部ready通知だけで接続readyと判定してはならない。通常推論ごとの固定待ちではない。
  • 内部状態は状態遷移の通知で待てる。実装時は購読登録後の再確認で通知取りこぼしを防ぎ、失敗・期限切れ・解放・abort・timeoutのすべてで購読とtimerを解除する。通知は待機解除に使い、状態の正本は既存Allocationとする。計測やexporterへの配信失敗に待機解除を依存させない。
  • Runtime起動処理のObserver.tickはbackendの稼働・health情報を取得する別の確認である。外部engineが準備完了通知を提供しない場合は確認を残す。プロセス起動通知だけをモデル準備完了の証明には使わない。
  • 利用要求のAllocationや実行枠と、ロード済みProviderの保持を分離する。終了要求の枠を無期限に保持すると後続admissionやswapを妨げ得るが、枠を解放してモデルを次の要求まで再利用可能な状態に保つ設計は可能。現状はProfileのidleRelease、AllocationのTTL、Providerのwarm/idle停止が独立して存在し、単にBroker.closeを削除しても意図した保持policyにはならない。
  • 維持policyの候補は「同じRuntimeは再利用し、次のProfile要求で不要・競合となるProviderだけを、既存の優先度・共有参照・進行中要求を考慮して切り替える」。別Profileの到着だけで共有ASR/TTS等を一括停止しない。障害、明示停止、daemon終了は別の終了条件として扱う。これは現行の時間ベースのidle解放からのpolicy変更であり、性能計測の結果と混同しない。
  • 利用者の10分保護という想定と現状は一致していない。foreground-exclusiveの実行中はbackground-when-idleの接続作成・Provider利用を拒否するが、backgroundBlocked自体には実行後10分の保護判定がない。repositoryのforeground ProfileのidleReleaseは300秒で、最終対象要求の完了を基準に接続を解放する。別のProvider切替holdも既定300秒で、こちらはAllocation解放時が起点であり、同一Runtime・同等以上の優先度を対象外とする。この二つの300秒を足して最終利用後10分保護が実装済みとは解釈しない。稼働中releaseの設定は今回未確認。
  • 変更時は保護期限とProvider保持を分離する。Eumenesの進行中要求がある間は保護を解除せず、保護時間を過ぎたことだけでモデルを停止しない。Eumenes自身の継続要求は拒否対象にしない。他consumerへの拒否はキュー待機とは区別して記録する。10分の起点を要求完了とするか、および他consumerの共有可能なProvider利用も拒否するかは、動作変更前にAPI契約として明文化する。共有可能だから許可する例外を利用者の想定に追加しない。
