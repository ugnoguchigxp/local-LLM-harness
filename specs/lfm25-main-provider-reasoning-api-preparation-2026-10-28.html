LFM2.5メインProvider切替準備とReasoning API

2026-10-28。LFM2.5 24B A2Bをメイン会話Providerに切り替えるための実装・設定・受入記録。 作業中の設定ではLFMを既定にするが、稼働中daemonへの配備・既定切替はまだ実施していない。

利用側の契約

既存のOpenAI互換Chat CompletionsのURLとBearer認証を使用する。 公開モデルはlfm2.5-24b-a2b、Agent Profile selectorはlfm2.5。 Consumerはモデル名を固定せず、対象Profileを要求してclaimに返されたmodelとbaseUrlを使う。 指定する項目はreasoning_effortだけで、未指定・nullはmedium。 low、medium、high、maxを受理する。maxはこのAPIの拡張で、公式OpenAI APIの全モデルに共通する値ではない。 

{
  "model": "lfm2.5-24b-a2b",
  "messages": [{ "role": "user", "content": "こんにちは" }],
  "reasoning_effort": "medium",
  "max_tokens": 4096,
  "stream": true
}

内部の思考予算はAPIの公開設定に含めない。native budget、reasoning control等をConsumerが送ると400で拒否する。 このProviderはnoneをサポートしない。許可値は解決されたruntimeのpolicyに基づき判定するため、 名前やaliasでモデル固有の例外を判定しない。通常の本文、reasoning_content、tool_calls、JSON Schema、SSEは既存経路を通る。

旧固定版244ではChat APIがthinking_budget_tokensを読み、以前送った reasoning_budget_tokensでは予算が効かなかった。新しい公式版では reasoning_budget_tokensを使う。adapter名とエンジンのpinを合わせ、 default mediumも含めて各リクエストで予算を設定する。サーバー起動時の既定は-1とし、maxが有限の既定値へ戻らないようにする。

JSON Schemaでtoolsがなくtool_choice未指定の場合、adapterはtool_choice: noneを内部で補う。 toolsがある場合や明示的なtool_choiceは維持する。旧エンジンでmath＋Schemaのstream終端に peg-native parser errorを再現したため、その版での本番切替準備は不採用にした。

プロファイル・容量・切替

Agent Profile lfm2.5からroute llm-lfm25、runtime lfm25-conversation、llama-swap model lfm25-conversationへ解決する。 llm-defaultもLFMを第一候補にする。既定warmはLFMの1インスタンスで、Ornithのwarm floorを0にする。 既存のOrnith Profileは明示選択として保持する。Consumerが旧Profileを明示要求すれば旧モデルへ解決される。 公開モデルをOrnith名のままLFMへ差し替えない。

LFMのcontext windowは1会話131072、4 slots、総context524288、Q4 KV、推定予約40GB。 output reserve4096・safety margin1976。4 concurrent allocation・4 concurrent request、queue16。 この数値はランタイム設定で、長文4並列の性能・最大メモリ測定は未実施。 LFMはテキスト専用でvisionは広告しない。画像が必要なConsumerはOrnith Profileを選択する。

ASR、日英TTS、embedding、System Oneは現行Ornithの通常会話Profileと同じProviderを組み合わせる。 名前付きContextStill Profileの解決先は既存定義を維持する。 llama-swapのconversation swap groupにLFMを加え、要求Profileによる切替と既存の資源・優先順位制御を使用する。

実機検証

稼働中のLARMを変更せず、予定の524288 context・4 slotsで専用LFMエンジンを起動し、 作業中のdaemonの本物のHTTP listenerとModel Brokerから推論した。runtime lifecycleの観測は試験用backendで提供し、 実推論、gateway、公開model正規化、JSON SchemaとSSE検査、予算adapterは本実装を使用。 本番systemd・llama-swapによる配備後受入は別途必要。

利用側はreasoning_effortだけを指定。生成された思考を同モデルtokenizerで再計数。

この整数問題の正解は36。全5応答は構造が正しいJSONを返しSSEのstopとDONEで完了したが、low・medium・未指定の 算術回答は誤答。ここでの合格はAPIの予算変換・プロトコルの確認であり、全回答の内容品質の合格ではない。 mediumの採用は利用者の選択による。複雑な課題ではhighまたはmaxを明示選択できる。
