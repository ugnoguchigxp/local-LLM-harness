VOICEVOX話者・スタイル・韻律制御API 実装計画

LARMのPOST /v1/audio/speechに、VOICEVOXの話者、スタイル、話速、 ピッチ、抑揚を明示的に制御するcontractを追加する計画です。既存のOpenAI互換requestと Kasukabe_Tsumugi等のvoice指定を維持しつつ、複数VVMから男性系・女性系を含む 具体的な話者を選べるcatalogへ拡張します。

計画日
2026-09-22
状態
WP1〜WP3と複数VVM source境界を実装。男性系4.vvmはidentity固定済み、operator同意・staging・ local-node配備待ち
対象endpoint
POST /v1/audio/speech、GET /v1/audio/voices
対象Provider
voicevox-core

固定判断: 話者の男性系・女性系の切替はピッチ加工ではなく、catalogから具体的な voiceを選択して行います。pitch_scaleは選んだ話者の範囲内で声の高さを 微調整する機能です。表示上の分類はvoice_presentation metadataとし、生成requestで 「男性」「女性」だけを指定して話者を非決定的に選ばせません。

Source実装記録

  • Core schema、OpenAPI、typed clientへstyle、speed、pitch、intonationとvoice catalogを追加しました。
  • Gatewayは通常Bearer、Allocation、claimのspeech bodyを同じschemaで検証し、VOICEVOX固有fieldを 他modelへ送った場合はunsupported_parameterで拒否します。
  • Adapterはロード済みVVM metadataからtalk styleを列挙し、従来voice名・数値style IDとの互換性を 維持してAudioQueryへ3種の韻律値を反映します。
  • 必須VVMと任意VVMを分離し、任意assetが未stagingなら既存構成で起動し、存在する場合はidentity driftをfail closedにする検証へ拡張しました。
  • 男性系話者を含む公式4.vvmのversion、配布URL、bytes、SHA-256、termsをsource lockへ 固定しました。asset本体は利用規約へのoperator同意前に取得しません。
  • 実装後reviewで、voice catalogのdefault・重複・制御範囲整合、Gatewayのcatalog response検証、 明示AllocationのProvider別field拒否、VVM symlink拒否、任意assetの起動前identity検証を追加しました。 systemdは外部checkout内のcopyではなく、選択中LARM releaseのadapter sourceを直接実行します。

着手時点の現在地

  • 公開speech schemaはmodel、input、voice、 response_format、speedを受け付けます。
  • VOICEVOX adapterはspeedをAudioQuery.speed_scaleへ反映し、 WAVまたは24 kHz mono s16le PCMを返します。
  • 現在のvoiceは話者名とVOICEVOXのstyle_idを兼ねています。 style、pitch_scale、intonation_scaleは公開していません。
  • 現行0.vvmで広告するのは四国めたん、ずんだもん、春日部つむぎ、雨晴はうの 4 voiceです。男性系話者へ切り替えるには、利用条件と配布identityを固定した追加VVMが必要です。
  • GET /v1/audio/voicesはname、style_id、 creditだけを返します。

採用範囲

今回実装する高優先度の制御
field 意味 default 公開範囲
voice 安定した話者ID Kasukabe_Tsumugi catalogに存在するID。従来名と数値style IDも互換入力として維持
style 同一話者内のノーマル、ささやき等 話者catalogのdefault_style 選択した話者に属するstyle IDまたは安定名
speed 話速倍率 1.0 0.5以上2.0以下
pitch_scale VOICEVOX nativeの声高補正 0.0 -0.15以上0.15以下
intonation_scale 抑揚倍率 1.0 0.0以上2.0以下

volume_scale、前後無音、sample rate、stereo、辞書、accent phrase編集、previewは 今回の実装範囲に含めません。今回のcontractと計測が安定した後の別変更とします。

Request contract

POST /v1/audio/speech
Authorization: Bearer <token>
Content-Type: application/json

{
  "model": "voicevox-core",
  "input": "本日の予定をご案内します。",
  "voice": "Kasukabe_Tsumugi",
  "style": "normal",
  "response_format": "wav",
  "speed": 1.1,
  "pitch_scale": 0.03,
  "intonation_scale": 1.15
}

解決規則

  1. voiceをcatalogの安定した話者IDとして解決します。
  2. styleがあれば、その話者に属するstyleへ解決します。省略時は default_styleを使用します。
  3. 従来のvoice: "Kasukabe_Tsumugi"は同じ音声へ解決します。数値文字列による style_id指定も互換入力として受理しますが、新規clientには広告しません。
  4. voiceとstyleの組合せがcatalogにない場合は、合成を開始せずHTTP 400 invalid_voice_styleを返します。
  5. 数値fieldはfinite numberだけを受理します。NaN、infinity、文字列への暗黙変換、範囲外値は HTTP 400 invalid_requestとし、clampしません。
  6. VOICEVOX以外のmodelへstyle、pitch_scale、 intonation_scaleを送った場合、黙って無視せずHTTP 400 unsupported_parameterとします。

合成への対応付け

query = synthesizer.create_audio_query(input, resolved_style_id)
query.speed_scale = speed
query.pitch_scale = pitch_scale
query.intonation_scale = intonation_scale
audio = synthesizer.synthesis(query, resolved_style_id)

既存のWAV／PCM response、busy時の429、非日本語・native streaming・instructの拒否、 X-VOICEVOX-Creditは変更しません。creditは解決済み話者に対応する正式表記を返します。

Voice catalog contract

GET /v1/audio/voices?model=voicevox-coreを加算的に拡張します。既存client向けの name、style_id、creditを残し、新規clientは id、styles、default_style、capabilitiesを使用します。 

{
  "voices": [
    {
      "id": "Kasukabe_Tsumugi",
      "name": "Kasukabe_Tsumugi",
      "display_name": "春日部つむぎ",
      "speaker_uuid": "...",
      "voice_presentation": "feminine",
      "language": "ja",
      "default_style": "normal",
      "style_id": 8,
      "styles": [
        { "id": "normal", "display_name": "ノーマル", "style_id": 8 }
      ],
      "capabilities": {
        "speed": { "minimum": 0.5, "maximum": 2.0, "default": 1.0 },
        "pitch_scale": { "minimum": -0.15, "maximum": 0.15, "default": 0.0 },
        "intonation_scale": { "minimum": 0.0, "maximum": 2.0, "default": 1.0 }
      },
      "credit": "VOICEVOX:春日部つむぎ"
    }
  ]
}
  • voice_presentationはmasculine、feminine、 androgynous、unspecifiedのいずれかとし、LARMが音声から推定しません。 配布元metadataで確定できない場合はunspecifiedです。
  • UIはpresentationで候補を絞れますが、speech requestには最終的に具体的な voiceと必要ならstyleを送ります。
  • voice、style、credit、VVM identityの静的catalogをsource管理し、startup時に実際にロードした model metadataと照合します。不一致ならそのvoiceを広告せず、service readinessを失敗させます。

男性系・女性系voice asset

repositoryへVVM binaryをcommitしません。追加VVMは既存voicevox-vvmと同様に、 配布URL、release version、bytes、SHA-256、terms URL、operator同意要件を deploy/local-node/sources.lock.yamlへ固定します。

  1. 公式配布物から、少なくとも男性系1話者と女性系1話者を含む候補VVMを選定します。
  2. 各話者・styleの利用条件、credit表記、商用利用等の制約を確認します。
  3. source lockと外部asset検証へ各VVMのidentityを追加します。
  4. systemdは単一VVM_PATHではなく検証済みVVM directoryまたは明示manifestを渡し、 adapterが起動時に全対象をロードします。
  5. 追加後もCPU memory、startup時間、短文TTFA、既存話者のRTFを測定し、resident LLM・ASRとの 共存SLOを満たすことを確認します。

Test plan

  • Schema: default、省略可能性、各境界値、境界外、NaN／infinity、型違い、未知voice、 他話者のstyleを拒否します。
  • Adapter unit: resolver、legacy voice、数値style ID、default style、credit、busy、WAV、PCMを mock synthesizerで検証します。
  • Gateway integration: 新fieldを変更せずupstreamへ転送し、VOICEVOX以外の非対応modelで silent ignoreが起きないことを確認します。
  • Catalog: 広告された全voice・styleで短文合成が成功し、style IDとcreditが一致することを data-driven testで確認します。
  • Audio inspection: WAV header、24 kHz、mono、s16le、非空durationを確認します。pitchとintonationは 音声内容の完全一致でなく、request値がAudioQueryへ渡ることと出力が有限・非空であることを contract testにします。
  • Compatibility: fieldを追加しない既存requestのaudio format、credit、default voiceが変わらないことを golden fixtureで確認します。
  • Performance: 既存4話者と追加話者について短文TTFA、RTF、RSS、startup時間を測り、単体と resident LLM実行中の両方で比較します。

受入条件

  1. 既存requestが変更なしで同じ既定話者、形式、creditを返す。
  2. catalogから選んだ任意のvoiceとstyleでWAVおよびPCMを生成できる。
  3. 少なくとも男性系1話者と女性系1話者を、具体的なvoice IDで決定的に切り替えられる。
  4. speed、pitch、intonationのdefaultと上下限がOpenAPI、catalog、adapterで一致する。
  5. 範囲外、未知voice、無効なvoice/style組合せ、非対応modelのfieldを明示的な400で拒否する。
  6. すべての生成responseが正しいVOICEVOX creditを返す。
  7. bun run checkとattended voice smokeが成功する。
  8. 既定VOICEVOX経路のlatency／RTFが配備前baselineから許容範囲を超えて悪化しない。

Rolloutとrollback

  1. WP1からWP3をsourceへ導入し、既存VVMだけで後方互換canaryを行います。
  2. 追加VVMをstagingし、checksumと利用条件同意をpreflightで確認します。
  3. voice catalogを確認後、各voice・styleの短文WAV／PCM canaryと性能測定を行います。
  4. consumer UIはcatalog取得後に具体的なvoice IDを保存し、表示分類だけを保存しません。
  5. 問題時は追加VVM manifestを外し、既存0.vvmだけの構成へ戻します。

Rollbackで公開schemaのoptional fieldは残せますが、catalogに存在しない追加voiceは400になります。 そのためconsumerは保存済みvoiceがcatalogから消えた場合、catalogの default_voiceへ明示的に戻す必要があります。

Consumer側の実装範囲と受入条件は、 SAAA実装依頼：VOICEVOX話者・スタイル・韻律制御として引き渡します。
