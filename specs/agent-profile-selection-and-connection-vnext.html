公開Profile選択とAgent Connection作成契約 vNext

状態
LARM側実装済み。Consumer移行とlive E2Eは後続
対象
LARM、SAAA、ContextStill、その他のAgent Connection consumer
決定
ConsumerはConnection作成時に公開selectorを指定し、LARMが具体Agent Profileへ原子的に解決する。 Discoveryは任意の事前照会とし、旧入力agentProfileとexplicitAgentProfileは受理しない。

結論

GET /v3/agent-profiles?profile=SAAAは「SAAA構成の照会」、POST /v1/agent-connectionsは「その構成を今回使える状態へ確保する要求」として維持する。POSTには、内部Profile IDや別のbooleanではなく、 profile: "SAAA"を渡す。LARMはこのfield自体を明示的な起動・確保要求として扱う。

解決する問題

現行契約では、公開selectorを具体Agent Profileへ解決した後、Consumerが agentProfileとexplicitAgentProfile: trueをPOSTする。Profile IDの存在自体が 明示選択であるにもかかわらずbooleanを重ねるため、片方だけを送る実装不整合が発生する。また、事前照会を必須に すると、単にSAAAを起動したいConsumerにも不要な往復とcatalog保持を要求する。

2026-09-25のSAAA自己診断では、profile=SAAAのdiscoveryは成功したが、Connection作成bodyに explicitAgentProfileがなく、LARMが 409 explicit_agent_profile_requiredを返した。ネットワーク到達性とConnection契約失敗も一つの 「Harness到達性」へ集約され、原因表示が不明瞭になった。

操作の意味

Discovery、Connection、Claimの責務
段階 質問または命令 状態変更 成果
Discovery この公開selectorは何を提供するか なし 具体Profile、Provider、model、endpoint、catalog revision
Connection作成 このselectorの構成を今回使える状態にせよ Allocation作成、Provider確保、readiness開始 期限付きConnectionと固定された構成revision
Claim readyなConnectionの実行設定を発行せよ credential generationを確定 Provider別base URL、model、短期Bearer、capacity

Discoveryは任意であり、それだけではProviderを起動・予約せず、credentialも発行しない。Connectionを省略できるのは、長期API tokenで公開modelを直接呼び、複数Providerの一括readiness、短期credential、renew、releaseを必要としない Consumerだけである。

推奨wire contract

1. Discovery

GET /v3/agent-profiles?profile=SAAA
Authorization: Bearer <optional LARM_API_TOKEN>
{
  "contractVersion": "agent-connection.v3",
  "catalogRevision": "<64 lowercase hex>",
  "requestedProfile": "SAAA",
  "profiles": [
    {
      "id": "saaa-conversation-ornith15",
      "canonicalProfile": "saaa-conversation-ornith15",
      "selectionPolicy": "explicit-only",
      "providers": ["..."],
      "services": []
    }
  ],
  "audiences": ["saaa-desktop", "same-host"]
}

Consumerは事前表示や互換確認が必要な場合だけこのGETを使う。contract version、 requestedProfile、Profile件数、Provider契約を検証する。具体Profile IDは表示・整合検査に利用できるが、 vNextのConnection作成入力には使用しない。事前照会なしで直接POSTしてもよい。

2. Connection作成

POST /v1/agent-connections
Idempotency-Key: saaa-session-0182
Prefer: wait=300
Content-Type: application/json

{
  "profile": "SAAA",
  "audience": "saaa-desktop",
  "client": "saaa-desktop",
  "ttlSeconds": 900,
  "allowFallback": false,
  "deploymentPolicy": "existing-only"
}

profileの存在が明示選択と起動要求を表すため、explicitAgentProfileは送らない。LARMは一つの catalog snapshot内でselectorを具体Profileへ解決し、Allocationを作成する。事前照会との厳密な一致が必要な Consumerだけは、任意のexpectedCatalogRevisionへGETで得たrevisionを追加できる。 vNextの新規ConsumerはrequestへagentProfileを送ってはならない。

3. Ready待機

SAAAの通常起動と自己診断はPrefer: wait=300を送り、LARMへ最大300秒のbounded waitを要求する。 LARMはConnection resourceとAllocationを先に作成してから、ready、terminal failure、または待機期限まで応答を 保留する。Client切断は起動処理を取り消さず、取消はConnectionのDELETEだけで行う。同じ Idempotency-Keyによる再送は同じConnectionへ収束する。

作成時の待機結果
結果 HTTP Response
期限内にready 201 Created status: "ready"とConnection全体
期限時点で準備中 202 Accepted status: "pending"または"probing"、Retry-After
期限内にterminal failure 409または503 Connection ID、terminal status、型付きerror

Preferを省略した既存Consumerには従来どおり202を即時返す。これにより長時間HTTP requestを扱えない Consumerを壊さず、SAAAは通常成功時にpollなしでready Connectionを受け取れる。全responseに Location: /v1/agent-connections/:idを付ける。

4. Ready response

{
  "id": "aconn_epoch_uuid",
  "allocationId": "alloc_epoch_uuid",
  "profile": "SAAA",
  "agentProfile": "saaa-conversation-ornith15",
  "catalogRevision": "<要求と一致するrevision>",
  "profileRevision": "<具体Profile revision>",
  "audience": "saaa-desktop",
  "audienceRevision": "<audience revision>",
  "status": "ready",
  "providers": [{
    "name": "llm",
    "capability": "llm.general",
    "supportedCapabilities": ["llm.general"],
    "protocol": "openai.chat-completions.v1",
    "endpoint": "/v1/chat/completions",
    "model": "ornith-1.5-35b",
    "readiness": "ready",
    "claimable": true
  }],
  "services": []
}

HTTP 201とstatus: "ready"はProvider群のsemantic readiness完了を表す。裸のbooleanだけではclaim、renew、 releaseの対象を識別できないため、必ずConnection IDと状態を返す。待機期限までにreadyにならない場合だけ、同じshapeを status: "pending"または"probing"としてHTTP 202で返す。Responseは公開selectorと解決後の 具体Profileを両方記録する。 agentProfileは入力ではなく、LARMがどの具体Profileへ解決したかを示すresponse専用fieldである。 status、health、claim、renewでも両者を保持し、 Consumerは別selectorまたは別Profileへ変化したConnectionを受理しない。 providersとservicesはDiscoveryと同じ公開名、capability、protocol、endpoint、modelを持ち、 実際にAllocationへ固定されたprovidersにはConnection固有のreadinessと claimableを加える。servicesはDiscoveryと同じ補助service descriptorであり、 Connection readinessの対象外である。内部route、runtime、service unit、portは返さない。

検証規則

  • vNext入力では公開profile selectorを必須指定する。省略要求は400 invalid_requestとし、既定Profileへ暗黙解決しない。
  • 新形式のrequestはagentProfileとexplicitAgentProfileを受け付けない。具体Profileの選択はLARMの責務とする。
  • expectedCatalogRevisionは任意とする。指定された場合はSHA-256形式と現在値の一致をAllocation作成前に検証する。
  • Prefer: wait=NのNは1から300秒とする。待機時間はConnection TTLに加算せず、作成時点から TTLを計測する。
  • profile selector、任意のcatalog revision、audience、client、TTL、fallback、deployment policyをidempotencyのcanonical requestへ含める。
  • 同じIdempotency-Keyと同じcanonical requestの再送は、catalogが後で変わっていても最初の結果を返す。異なる requestへのkey再利用は409 idempotency_conflictとする。
  • revisionを指定した新規要求の不一致はAllocation作成前に拒否し、Consumerは再discoveryする。revisionを指定しない 要求は、POST処理開始時のcatalog snapshotを正本として解決する。
  • Connection作成responseとclaimのProfile、model、protocol、endpointがdiscovery結果と一致しない場合、Consumerは 推論を開始せずConnectionをreleaseする。

Profile競合と優先順位

pendingは、要求したProfileの起動またはsemantic readinessが進行中である場合だけ使用する。別Profileが 排他的資源を保持していて要求を開始できない状態をpendingや待ち行列として隠してはならない。

SAAAとContextStillの競合規則
現在の占有 新規要求 結果
なし、または共有可能 SAAA／ContextStill 受理し、必要なら起動してreadyまでbounded wait
SAAAが排他的資源を使用中 ContextStill 即時409。Allocationを作成せず、Provider状態を変更しない
ContextStillが排他的資源を使用中 SAAA foreground優先。安全な境界でContextStillをpreemptし、SAAAを受理してready待機
同一SAAA構成を既存Connectionが使用中 SAAA capacity内ならProvider instanceを共有し、新しい期限・credentialを持つConnectionを作成

ContextStillへの拒否は409 provider_conflictとboundedなRetry-Afterで返す。Responseは 占有中のConsumer名、Connection ID、model、内部runtimeを公開しない。ContextStillは同一job内でbusy loopせず、次の job境界またはRetry-After後に新しいIdempotency-Keyで再評価する。

エラーcontract

選択と作成の主要エラー
HTTP code 意味 Consumer動作
400 invalid_request 未知field、形式不正、移行中fieldの競合 retryせず実装または設定を修正
404 unknown_profile_selector 公開selectorが存在しない 設定を修正し、別Profileへ暗黙fallbackしない
409 catalog_revision_mismatch 任意のexpected revisionを指定した後にcatalogが変化した 再discoveryし、新しいIdempotency-Keyで再要求
409 idempotency_conflict 同じkeyを異なる要求へ再利用した 新しいkeyを発行する
409 provider_conflict SAAAなど高優先Profileが排他的資源を使用中 Retry-Afterまたは次job境界まで待ち、同じ要求をbusy retryしない
409または429 capacity_exhausted 構成は有効だが現在確保できない Retry-Afterに従い、明示許可なしに別Profileへ切り替えない
503 connection_not_ready Providerがsemantic readinessを満たさない 期限内pollまたは明示失敗

自己診断は、TCP／HTTP到達、catalog discovery、Connection作成、semantic readiness、claim、実推論を別項目として 表示する。Connection契約エラーを「到達不能」と表示してはならない。

Consumer移行

LARMは旧形式を同時受理する移行期間を設けず、新形式へ切り替えた。SAAAとContextStillは後続改修で profileと必要に応じてPrefer: wait=Nを送る。旧fieldを含むrequestはstrict schemaにより 400 invalid_requestとなる。ResponseのagentProfileは監査・整合検査用として維持する。

受入条件

  • SAAAについてdiscovery、create、poll、aggregate health、claim、LLM、backchannel、ASR、TTS、embedding、renew、releaseを 実daemonで完走する。
  • discoveryを行わないPOST {"profile":"SAAA",...}からも、同じ具体Profileを確保してclaimまで完走する。
  • warm状態とcold状態の両方でPrefer: wait=300を実行し、期限内ならpollを挟まず201 readyを返す。300秒を超えるProvider fixtureでは202とLocationを返し、後続pollでreadyへ収束する。
  • HTTP client切断後もConnection作成を継続し、同じIdempotency-Keyの再送が重複Allocationを作らない。
  • SAAAが排他的資源を使用中のContextStill要求は409 provider_conflictとなり、Allocation数とProvider PIDが変化しない。
  • ContextStill使用中のSAAA要求はforeground preemptionを経てreadyへ到達する。
  • expected revisionを使う経路ではdiscoveryとcreateの間でcatalogを更新し、旧revisionの要求がAllocationを一件も作らず catalog_revision_mismatchになる。
  • 同一Idempotency-Keyのresponse lost retryが、catalog更新後も最初のConnectionを返す。
  • selector省略と旧形式fieldを含む要求が400でfail closedする。
  • ログと診断にcredential、API token、claim tokenを記録しない。
  • 自己診断がnetwork成功とConnection契約失敗を別々に表示する。

非目標

  • Discovery GETだけでProviderを起動または予約すること。
  • Profile selectorをmodel IDとして扱うこと。
  • Consumerが内部runtime、service、port、artifactを選ぶこと。
  • Connection失敗時に別Profileへ暗黙fallbackすること。
  • 長期control credentialをclaim後の通常推論へ流用すること。
