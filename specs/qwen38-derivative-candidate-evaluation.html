候補群は試験に値するが、提示された根拠だけでは常駐modelの置換を正当化しない

結論は「候補選定は良いが、証拠の読み方と実験順を修正する」です。64K workerで隔離して A/Bし、成功task数を総経過時間で割る方針は妥当です。一方、Q3-LynnStyleの78/100を Baseからの改善量として扱うこと、QwopusのNVIDIA・10 parallel値をこのStrix Haloへ移すこと、 Sharpの2.7倍をdecode速度と読むことはできません。

local-node初期実測

2026-09-12にVulkan版llama-server build 10655、commit cb300598dで、64K、parallel 1、KV q4_0、temperature 0.2、top-p 0.9、 reasoning effort mediumを明示して比較した。throughput armは同じCoding promptを 128 completion tokensまで3回生成した探索試験である。LARMの実ジョブが開始前後とも0だったrunだけを 採用し、競合を検出したrunは除外した。

Base比はSharp +0.1%、EfficientThink +1.8%、Signal draft 3 -1.6%であり、この短いpromptでは 全て同等域である。Signal draft 2の単発runは22.961 tokens/s、acceptance 77.8%で、draft 3より 遅かった。作者がQ8_0、greedy、200 tokensで示したSignal +10%は、このAP-Q4_K_XL、sampling、 Coding promptでは再現しなかった。

Sharpはraw decodeを速めなかった。また同じuser promptのcold promptがBaseの61から216 tokensへ 増えたため、短いturnではprefill費用が増える。Sharpの価値は生成token数またはtask wall timeを 減らせるかでのみ判定する。EfficientThinkも速度昇格ではなく、作者が報告したCoding成功率改善を paired repo taskで再現できるかを次のgateとする。

この試験はload互換性と初期性能のscreeningで、Coding品質試験ではない。128 tokensで全armが length stopしたため、回答の短さも比較していない。常駐既定値やLARM releaseは変更しない。

有効なJSON evidenceは /srv/ai/evidence/qwen38-candidates/20260912に保存した。GPU競合が入ったSharp 3回runはbase-sharp-throughput-3x128.contaminated.jsonとして保持し、集計から除外した。

local-nodeにおける情報価値と導入riskを合わせた順序
順序 候補 評価 主な理由
対照実験 現行Base + Sharp template 最初に実施する価値が高い 同一weightでtemplate効果を分離でき、追加weightのdownloadが不要
1 EfficientThink Q3-LynnStyle + 専用MTP 有望なquality候補 約17 GBで現行weightと近い容量。Coding改善のBase対照信号が候補中で最も明瞭

3 Qwopus Q5_K_M + 内蔵MTP 有望だが現在は条件付き Agent向け信号は強いが、Python indentation既知不具合と対照不足を先に解消する

この順序は、先に安価な対照を取り、次に能力と完了時間の二つの仮説を別々に検証するものです。 最終的な一番手を事前に確定するものではありません。純粋にCoding正解率を優先するなら EfficientThink、成功task／時間を優先するならSignalまたはSharpが先に勝つ可能性があります。

未検証候補：GSQ-RCO IQ3_S-MTP

ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUFのQwen3.8-27B-GSQ-RCO-IQ3_S-mtp.ggufを、次回以降の比較候補へ追加する。 revisionはd562806dbafae37109975e970aae91b43e73b440、配布artifactは 12,120,016,960 bytes、配布元ETagのSHA-256は 58fd826723939933dc86f45b7fe04545cbc2de1c70f6fe2cdd3858c87a98c12fである。

これは標準GGUF内にMTP headを含む約3.50 bpwのmixed-precision量子化である。配布元は task-lossless operating pointと説明するが、local-nodeでは未取得・未検証であり、品質、tool call、 Vulkan性能、MTP acceptanceの保証には使用しない。今回の標準Profile変更には含めず、候補一覧への checksum固定だけを行う。

EfficientThink

作者のmodel cardは、同一protocolのdynamic FP8 + DFlash2、2 GPU、concurrency 24、xhigh条件で、 LiveCodeBenchをBase 69/100から74/100へ、Hardを20/46から24/46へ改善したと報告します。 timeout／request errorも6から2へ減っています。この結果はCoding候補として試す十分な理由です。

ただし、同じ比較で平均reasoningは12,167から12,514へ2.9%増え、P50も増加し、総経過時間は 2,060秒から2,067秒でほぼ不変でした。したがって、これは「Codingの提出成功率が改善した」信号であり、 「考える量もwall timeも減った」証拠ではありません。MMLU 500問は90.2%から88.4%へ 1.8 points低下しており、全面的な能力向上でもありません。

Q3-LynnStyleのLiveCodeBench 78/100は同model内のquant tier評価です。Base 69/100との比較は dynamic FP8 + DFlash2という別artifact条件であり、Q3-LynnStyleがBaseの同等quantより9 points 強いことを示しません。一方、 Q3-LynnStyle GGUFは約17 GBで、現行17,559,178,144-byte workerと近い容量です。このため、因果比較ではなく 「同程度の保存・memory費用で使う完成品候補」として最初に試すことには合理性があります。

EfficientThinkは専用のMTP sidecarを公開しており、Q4_0版は1,680,271,648 bytes、SHA-256 051a1764cff8c4f3ee6ae8b00593a0364c7539c67fa50ffc58f3f96509fca38eです。 現行Base sidecarの1,369,590,656 bytes、SHA-256 50d9ce5a6da381bbcfb31061cf73df94a90e6faf8efeddee379a9cb8f1501c6e とは別物なので、現行MTPを流用しません。作者がload確認したのはDGX Sparkであり、local-nodeの Vulkan buildでは組合せを改めて検証します。

Signal-3.8-27B

作者のmodel cardは、 BaseとSignalのQ8_0を同じStrix Halo + Vulkanで比較しています。200-token greedy出力では、 draft 3のproseが10%、JSONが20%、draft 4のJSONが22%速く、JSON acceptanceはdraft 3で 72%から94%へ上がったと報告します。候補中、local-node hardwareへの外挿riskが最も小さい throughput信号です。

ただし現在のworkerはdraft最大2で、公開値はdraft 3または4です。tool callはJSONを含みますが、 coding agentの全生成が200-tokenの純粋なJSONではないため、JSON +20〜22%をtask全体へ適用しません。 またCoding answerの中央値とP90は各11%、Coding reasoning中央値は26%短い一方、品質の定量確認は 小規模GSM8Kとstyle prompt中心で、repo修復のBase対照試験はありません。

したがってSignalは「より賢いmodel」ではなく、「同等成功率ならtask完了を速めるmodel」という 仮説で評価します。最初の候補は現行に近いAP-Q4_K_XL 16.35 GiBとし、 draft最大2、3、4を別条件として扱います。

Qwopus3.8-27B-Flash

作者のmodel cardは、 同一Q5_K_M + MTP条件でdecode 8.284から9.347 tokens/s、MTP acceptance 66.1%から 80.7%を報告します。14件のAgent batteryは13件成功で、実file・shell toolを使った点も 実用途に近い信号です。

この数値はRTX 5090、V100、GB10を含む環境で、throughput比較はcontext 327,680、parallel 10です。 各表とdeviceの対応も全ては明記されていません。13/14 batteryはRTX 5090上の一回実行でBase armがなく、 作者自身が楽観寄りになり得る一回のdemonstrationと説明しています。さらにPython codingで不正なindentationを 出す既知不具合があり、修正中です。coding-default候補ではこの不具合をblocking項目とします。

公開GGUFはMTP headをmain GGUFへ内蔵し、Q5_K_Mは19.5 GBです。公開benchmarkへ近づける初回再現試験では Q5_K_Mを使い、現行Base用-md sidecarは指定しません。MMLU-ProはBaseより1.45 points 低いため、Agent用途で勝っても汎用常駐modelへ自動昇格させません。

Dirk／Sharp template

Dirkのmodel cardは、 Base weightとMTP tensorは変更せず、Sharp chat templateだけをGGUF metadataへ差し替えたと説明します。 25件のSWE-bench-Liveで、stockとSharpの両方が解けた部分集合に限るmedian fix timeはstockの37%ですが、 全体のsolve数はstockより1件少ない結果です。

37%はdecode tokens/sが2.7倍になった意味ではありません。取得したSharp v22.5は既定の reasoning effortをmediumにするため、現行埋め込みtemplateの運用上の既定 xhighとは推論量のpolicyも異なり得ます。templateそのものだけを比較するA/Bでは、 両armへmediumを明示します。 「両方が解けた問題だけ」という条件付きmedianにはsurvivorship biasもあります。

それでも、local Vulkan llama-serverは--chat-template-fileを備えるため、 現行64K worker weightを使った安価な対照実験が可能です。serverの再起動・reloadは必要であり、template digest、system／developer message、tool schema、tool call parser、reasoning field、SSEの認定も変わります。 常駐coding-defaultへ直接適用せず、別のcandidate releaseとして試します。

NEO-CODER-MAX

公開model cardにはTerminal Bench 2.1の73.0、SWE-bench Proの61.7などが掲載されていますが、表の列名は Qwen3.8-27Bであり、派生model対Baseの同条件比較ではありません。名称、ARC系の作者計測、 human testingの説明だけでは、現在のcoding workerより成功task／時間が上がると判断できません。 比較可能なterminal／repo batteryが出るまで保留します。

実機試験で固定する判定契約

  1. stock Baseを同じ64K、KV q4_0、parallel 1、sampling、thinking effort、tool harnessで再測定する。
  2. template、weight、quantization、MTP、draft長は一度に一要因だけ変える。完成品candidate比較を行う場合は 複数要因が変わったことを明記する。
  3. 各artifactのMTP方式をheaderと起動logで検証する。EfficientThinkは専用sidecar、SignalとQwopusは 内蔵headを用い、Base用sidecarを混用しない。
  4. benchmark前にPython indentation、system／developer role、tool schema、tool call round-trip、 structured JSON、reasoning content、SSE終端、64K境界をfail-fastで確認する。
  5. 同じrepo task集合を複数seedでpaired実行し、成功数、総wall time、生成token、turn数、MTP acceptance、 timeout、loop、構文不良を全て保存する。失敗caseだけを再試行しない。
  6. 第一指標をsuccessful tasks / total elapsed hourとし、pass rateを独立したblocking gateにする。 少数taskでの単純な「+5 points」は1件差に過ぎない場合があるため、信頼区間とpaired差も確認する。

初回探索では「pass rateがBaseを下回らず、成功task／時間が15%以上改善」を昇格候補の目安とします。 これは導入前の仮説であり、task数と分散を見て固定gateを校正します。勝者だけを256KとROCmFP4_FAST 変換評価へ進め、常駐既定値の変更は別のrelease gateで判断します。

証拠の限界

  • 候補の数値は全てmodel作者または配布者の自己申告で、local-nodeによる再現値ではない。
  • hardware、runtime、quant、parallel数、sampling、thinking effortが候補間で一致していない。
  • LiveCodeBench、MMLU、短いJSON、Agent batteryは異なる能力を測り、順位へ単純合算できない。
  • fine-tuneの学習data全体を再監査できない候補があり、license表示だけでdata provenanceを証明しない。
  • 公開repositoryは更新され得るため、試験時はrevision、filename、byte数、SHA-256を固定する。
