固定したcontract

  • 通常requestはrouteだけを指定し、release ID、URL、path、serviceを指定しない。
  • release変更とcatalog reloadはBearer tokenに加えてmanagement tokenを要求する。
  • release IDの内容はdigestでimmutableとし、activeまたはrollback対象の差し替えを拒否する。
  • provider config revisionはreleaseに固定した起動contract識別子とし、active・previous stateと 同時にcommitする。任意の設定本文やpathをrequestから受け取らない。
  • Allocationへcatalog revisionとactive releaseを固定し、全responseへconfig revision headerを返す。
  • Resident contractを変えるcatalog reloadとResident artifact activationはattended手順へ残す。
  • live telemetryはPreferred・Elasticの新規起動だけをfail closedし、Resident経路を遮断しない。
  • catalog reload、artifact stage、release activation・rollback、allow-listed起動は単一mutation coordinatorで直列化し、shutdown時は新規予約を拒否してdrainする。
  • LARM releaseの切替とrollbackはLARM daemonだけをrestartし、Provider unitへ伝播しない。

完了条件の再監査で補完した項目

  • LARM releaseの保持数を2以上99以下に固定し、planが示した削除候補のdigest一致をapplyの preconditionにした。削除は新世代health成功後だけ行い、失敗時はcurrentとrollback pointerを 復元する。
  • OpenAPIの全operationへ実際の成功statusとresponse contentを割り当て、JSON、SSE、Prometheus text、audio binaryを区別した。legacy成功responseもstrict schemaで検証する。
  • Runtime release一覧へactive・previous・staged・availableを追加し、deployment planは実際の staging dataから不足bytesを算出する。
  • restart、Preferred kill・stall、artifact rollback、health stall、partial stream、disk不足、journal corruption、reload・shutdown raceを再現または実行するfault経路を揃えた。
  • benchmark summaryとallocation eventへroute・Runtime・releaseを含め、metricsでは高cardinality labelを除外した。leak gateへartifact operation gaugeを追加した。

検証

型検査、Core・Backend・Daemon・Client test、Spec HTML検査、systemd検査、source-only検査、 installerとtransactional releaseの隔離root testをbun run checkで一括実行します。 実機値はcommissioning evidenceへ分離し、 repository testの成功をproduction導入済みとは扱いません。

残るattended gate

  1. この変更をreviewし、clean commitとして固定する。
  2. release-larm.sh planでcommit、target、cleanup候補を確認し、候補があれば表示された digestをapplyへ明示する。
  3. versioned releaseをapplyし、LARM daemonだけを導入する。
  4. Resident、音声、Preferred release rollback、daemon restart、短時間soakを実測する。
  5. 上位Ambient clientをshadow、非音声、音声の順にcanaryへ進める。

これらは実装不足ではなく、live process、credential、GPU memory、実trafficを変更する運用gateです。 source worktreeがdirtyな状態ではrelease tool自身がapplyを拒否します。
