LARM v1 API仕様

この文書は、Route-aware Allocation、LLM・STT・TTS共通Gateway、Artifact管理APIの実装contractです。設計上の背景はProviderコンセプト、残るproduction工程と受入条件はProduction Completion実装計画を参照してください。

Security boundary

  • loopback以外でlistenする場合はLARM_API_TOKENと LARM_MANAGEMENT_TOKENをともに必須とする。
  • /healthと/ready以外は、原則としてLARM_API_TOKEN設定時にBearer tokenで保護する。Service Harness経路は LARM_SERVICE_HARNESS_AUTH_ENABLEDで独立に切り替える。
  • Artifact、Runtime release管理APIは追加で x-larm-management-tokenを検証する。
  • deploymentPolicy: allow-listedのAllocationも同じ管理tokenを必須とする。
  • 管理tokenはLARM_MANAGEMENT_TOKENで設定する。
  • 管理tokenが未設定なら、loopbackでもArtifact管理とallow-listed配備を無効化する。
  • API requestからupstream URL、filesystem path、checksum、service名、commandを受け取らない。
  • Registry、artifact manifest、制御API objectは未知fieldを拒否する。タイプミスを除去して既定値へ fallbackしない。

この節はLARM daemonのHTTP認証境界です。2026年8月29日に観測したlive Provider unitがport 8080から8084を全interfaceでlistenする移行状態は別のhost network境界であり、Gateway-only isolationの完了を意味しません。loopback bindと既存LAN ruleのlive収束は Production Completion実装計画で行います。

Machine-readable contract

GET /openapi.jsonはdaemonと同じCore schemaおよびroute metadataから生成します。全operationは実装が返す成功statusとresponse contentを持ち、JSON、SSE、Prometheus text、audio・image binaryのmedia typeを区別します。compatibility APIの成功responseもstrict schemaで検証し、実routeとの追加・削除driftと2xx response schemaの欠落をtestで拒否します。

/healthと/readyは常に認証不要です。Service Harnessの3経路は LARM_SERVICE_HARNESS_AUTH_ENABLED=falseならBearer不要、trueならLARM_API_TOKENのBearerを必要とします。Artifact、Runtime release、deployment、catalog、inspectionのendpointはmanagement tokenを必要とし、その他は LARM_API_TOKEN設定時にBearer tokenを必要とします。

GET /healthはlistenerと必須chat routeの実canaryが成功した場合だけ200/okを返し、 起動中、検証中、失敗、drain中は503を返します。payloadやcredentialを含めず、software version、配備release commit、 Registry・artifact manifest・runtime release catalogのcontent revision、process固有boot epochを返します。content revisionは論理ファイル名と内容だけから計算し、同一構成を別の絶対パスへ 配置しても変化しません。全responseにも x-larm-boot-epochとx-larm-config-revisionを付与します。

Allocation

Request

{
  "requirements": [
    { "capability": "llm.general", "route": "llm-default" }
  ],
  "client": "ambient",
  "allowFallback": false,
  "ttlSeconds": 300,
  "deploymentPolicy": "existing-only"
}
  • 任意のIdempotency-Keyは128文字以内の安全な文字列とし、同じkeyと正規化済みrequestの retryは同じAllocationを返す。requirementsの順序は正規化される。異なるrequestでの再利用は 409。
  • TTL内の成功結果と処理中entryは件数上限から追い出さない。上限へ達した状態で新しいkeyを受けた場合は、 二重Allocationを避けるため503 idempotency_capacityでfail closedする。
  • requirementsは一つ以上必要で、同じcapabilityを重複指定できない。
  • ttlSecondsは1から86400で、既定値は300。
  • allowFallbackの既定値は偽。
  • priorityは-1000000から1000000の整数で、既定値は0。 大きい値を先に選ぶ。
  • capacityPolicyはrejectまたはwaitで、既定値は reject。waitは同一Runtimeまたはswap groupのactive Allocation解放だけを待つ。
  • deploymentPolicyはexisting-onlyまたはallow-listed。
  • staleなobserver snapshot、memory不足、Runtime capacity超過、配備中Runtimeは起動前に拒否する。
  • Resident Runtimeのmemoryは観測状態にかかわらず常時予約する。
  • Preferred・Elasticの新規起動は静的memory gateに加え、freshなsystem・accelerator memory headroomを要求する。telemetry不能またはstale時もResident-only Allocationは維持する。
  • active AllocationとAllocationを持たないLegacy Leaseの合計を LARM_ACTIVE_ALLOCATION_LIMITで制限し、上限時は新規受付を503で拒否する。

Allocation responseはupstream endpointを隠します。明示的なresolveまたはGatewayだけが Bindingのendpointを使用します。一度作成したBindingは、別RuntimeがHOTになっても変更しません。 catalog revisionとactive releaseも作成時に固定します。 固定Runtimeが非稼働またはsnapshotがstaleなら、別Runtimeへ移動せずresolveを503で拒否します。

非同期operation phase

GET /v1/operations/:idはpending、running、 succeeded、failed、cancelled、 timed_outを返します。優先度付き待機はwaiting-for-capacity、admission後は scheduledを返します。allow-listed配備では checking-artifacts、staging-artifacts、 stopping-runtime、activating-artifacts、 starting-runtime、verifying-runtime、 rolling-back、runtime-readyのphaseで進捗を示します。

Route選択保証

  • llm-defaultはQwen 3.8 27B Residentを第一候補とする。
  • llm-speed、llm-long-context、llm-35b、llm-35b-speedはroute idの明示指定を必要とする。
  • fallback candidateはallowFallback: trueの場合だけ使用する。
  • llm-35bは公式Q5_K_MのOrnith-1.5-35B-A3Bをprimary、ROCmFP4速度版とQwen3.6-35B-A3Bを 明示fallbackとして選ぶ。llm-35b-speedではROCmFP4を固定できる。 llm-qwen36-35bでは比較・rollback用Qwenを固定でき、どちらもdefault routeの候補には含めない。
  • 追加27Bと35Bは一つのswap groupを共有する。優先度3000以上のforeground Allocationは 同groupの低優先active Allocationをforeground_preemptedで停止する。 それ以外のcapacityPolicy: rejectは従来どおり拒否する。 capacityPolicy: waitは解放後にpriority降順、同値FIFOで昇格する。foreground解放後300秒は 同じRuntimeを保持し、別memberへの切替を保留する。
  • Resident Runtimeはstop、無人activation、resource evictionの対象にしない。

OpenAI互換Gateway

全Gatewayにはx-larm-allocation-idを指定します。Runtimeのprotocolは openai.chat-completions.v1、openai.audio-transcriptions.v1、 openai.audio-speech.v1のいずれかです。requestのmodel、URL、pathから 別Runtimeやupstreamを選択しません。

  • Chat Completionsはrequestのstreamに従い、falseまたは省略時は application/json、true時はOpenAI互換 text/event-streamを透過する。
  • Chat Completionsのresponse_formatはtext、 json_object、OpenAI形式のjson_schemaを受理し、schemaを含むrequest bodyを変更せずProviderへ転送する。
  • STT uploadは全量をmemoryへbufferせず、転送中に上限を検証する。
  • TTS audio、content type、VOICEVOX credit、ProviderのRetry-Afterをallowlistして返す。
  • 同じprotocolのBindingが複数ある場合はx-larm-capabilityで明示し、曖昧な要求を拒否する。
  • client disconnectをupstreamへ伝播する。
  • body sizeとtotal timeoutを環境変数で制限する。
  • total timeoutはrequest upload、upstream接続、response streamの全区間へ適用する。
  • Bun固有のupstream socket idle timeoutは無効にし、長い非streaming生成を5分前後で切断しない。 停滞を含む全体上限はGatewayのAbortControllerだけで判定する。
  • stream開始後の別Runtime retryは行わない。
  • RuntimeごとのmaxConcurrentRequests、maxQueuedRequests、 queueTimeoutMsで実行枠を制御する。待機列はAllocationの優先度降順、同値FIFOとし、満杯と待機timeoutは429と Retry-Afterを返す。
  • 実行開始直前にAllocation、epoch、observer freshness、固定Runtimeを再検証する。
  • Allocation releaseまたはTTL満了はactive・queued Gateway requestへcancelを伝播する。
  • prompt、response、audio本文をmetricsまたは構造化eventへ記録しない。
  • request id、Allocation id、Runtime、結果は構造化eventへ記録する。Prometheus metricsからrequest・Allocation・client idを除き、時系列数をboundedに保つ。
  • latency metricはPrometheusの_sumと_countとして公開する。
  • larm_active_allocations、larm_execution_active、 larm_execution_queued、larm_artifact_operations_activeは現在値のgaugeとして公開し、canary後のleak検査に使用する。

Artifact lifecycle

  1. models.yamlのkind: fileまたはkind: snapshotから、 固定source、revision、配置先、検証metadataを読む。
  2. 同一filesystemのstaging directoryへ期限付きでstream downloadする。
  3. fileはsizeとSHA-256、snapshotはsorted file list、合計bytes、最大file数、各fileのSHA-256、 canonical snapshot digestをすべて検証する。
  4. snapshotの絶対・親参照・重複・case衝突path、symlink、device、未列挙fileを拒否する。
  5. Preferred Runtimeが他Allocationで使用中でないことを確認して停止する。
  6. 配備対象とartifactを共有する全Runtimeを予約し、別ownerが稼働中なら拒否する。
  7. 直前targetをfileまたはdirectory単位で保持し、検証済みartifactへ原子的に切り替える。
  8. Runtimeを起動し、health失敗時は直前targetへ自動rollbackする。
  9. rollbackはjournalに記録された直前targetだけを復元する。
  10. Allocationのrelease、TTL、startup deadlineをdownloadとactivationへ伝播する。
  11. operationは受付応答前にjournalへ保存し、terminal historyを設定上限内に保つ。
  12. artifact stage、release activation・rollback、allow-listed起動は単一mutation coordinatorで直列化し、競合をfail closedする。

非同期管理operation

Stage、activate、rollbackは202とArtifact operationを返します。呼出側は GET /v1/artifact-operations/:idを取得し、succeededを確認してから 依存する次の操作へ進みます。Runtimeが複数artifactを参照する場合は、全artifactのstage成功が activationの前提です。terminal statusはsucceeded、failed、 interruptedです。

自動配備の制限

directory modelは全fileを列挙したsnapshotだけが自動staging対象です。Qwen ASRのResident snapshotはstage可能ですがAPIからactivationできません。最初のPreferred activation対象はQwen TTSです。VOICEVOXの外部release bundleはmodel artifact manifestではなく、runtime source lockとoperator手順で管理します。

Runtime releaseとcatalog generation

deploy/local-node/releases.yamlは、release ID、Runtime、artifact集合、provider config revision、memory estimate、health pathを一つのimmutable contractとして定義します。同じIDの 内容差し替え、未知artifact、Runtimeの現行artifactと一致しないdefault releaseを起動時に拒否します。

GET /v1/runtime-releasesは各releaseの状態をactive、 previous、staged、availableで返します。deployment responseは active・previous・desiredのprovider config revisionを返し、plan responseはRuntime状態、停止要否、 staging実体から算出した不足bytes、rollback可能性、blockerを返します。provider config revisionは releaseに固定された起動contractの識別子であり、requestから任意の設定内容やpathは受け取りません。

Activation request

read-only planは{ "release": "..." }だけを受け取ります。activationは次のように 呼出側が観測したactive releaseを必須にし、staleな操作をartifact変更前に拒否します。 

{
  "release": "qwen-worker-fast-current",
  "expectedActiveRelease": "qwen-worker-fast-previous"
}
  1. planでRuntime class、staging、Allocation、共有artifact、transitionを評価する。
  2. release単位で全artifactをstageし、一部成功をactive状態にしない。
  3. expected active releaseが一致する場合だけPreferred releaseをactivateする。
  4. health成功後にactive・previous stateをrepository外へfsync付きで保存する。
  5. 失敗時は全artifactを直前releaseへ戻し、Resident RuntimeのAPI activationは常に拒否する。

Registry、artifact、release、Agent Connection catalogはdaemon起動時に一度だけ読み込み、相互検証した content revisionへ固定します。設定変更はversioned LARM releaseを適用してdaemonをrestartする attended操作です。稼働中のbackendやRegistryを差し替える管理APIは提供しません。これにより release scriptの原子的なcurrent切替・rollbackとdaemon内の世代切替を二重に実装しません。

SAAA Service Harness v2

GET /v1/servicesはrequest originを使って到達可能な9810 Gatewayを広告します。 個別Runtime portの8081はloopback-onlyのままです。Native ASR streamingは未実装のため streamingを広告せず、SAAAはPOST /v1/audio/transcriptionsを使用します。 Service Harnessからのbatch要求にはAllocation headerを要求せず、固定したResident qwen-asrへGateway内部で転送します。 

{
  "contractVersion": "saaa-service-harness.v2",
  "revision": "bounded-revision",
  "services": [{
    "capability": "asr",
    "protocol": "openai.audio-transcriptions.v1",
    "baseUrl": "http://provider.example:9810/v1",
    "model": "qwen3-asr-1.7b",
    "language": "auto",
    "healthUrl": "http://provider.example:9810/v1/services/asr/health"
  }]
}

認証のoptional性はrequest単位ではなくProvider設定単位です。OFFではcredentialを要求せず、 ONではBearerを必須にします。local-nodeのSAAA互換設定はOFFです。

Agent Provider Connection API

登録済みAgent profileからAllocationを作成し、動的なAgent設定に使用できるadvertised Gatewayの host、port、base URL、public model alias、Allocation限定credentialを返すAPIをAgent Provider Connection API実装仕様のcontractどおり実装しています。既存のendpoint非公開方針を維持し、llama-swap内部portや 個別Runtime portは通常のAgentへ返しません。ConnectionごとにProvider単位のsemantic health endpointを 必須とし、固定Binding上の最小LLM推論（max_tokens: 1）とresponse検証が成功するまでReadyまたは claimableとして扱いません。daemon、OpenAPI、TypeScript client、3つのLLM Profile、 same-hostとlocal-node LAN用saaa-desktop Audienceを実装済みです。

既存APIとの互換

unversionedのprepare、resolve、releaseは維持します。 default Routeが定義されたcapabilityは内部Allocationへ変換し、従来のlease response形へ戻します。新規clientはRuntime固定と期限を明示できるv1 Allocation APIを使用します。 機械可読な詳細は実daemonのGET /openapi.jsonを参照してください。
