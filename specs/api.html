Security boundary

  • loopback以外でlistenする場合はLARM_API_TOKENを必須とする。
  • /healthと/ready以外はBearer tokenで保護する。
  • Artifact管理APIは追加でx-larm-management-tokenを検証する。
  • deploymentPolicy: allow-listedのAllocationも同じ管理tokenを必須とする。
  • 管理tokenはLARM_MANAGEMENT_TOKENで設定する。
  • 管理tokenが未設定なら、loopbackでもArtifact管理とallow-listed配備を無効化する。
  • API requestからupstream URL、filesystem path、checksum、service名、commandを受け取らない。

Allocation

Request

{
  "requirements": [
    { "capability": "llm.general", "route": "llm-default" }
  ],
  "client": "ambient",
  "allowFallback": false,
  "ttlSeconds": 300,
  "deploymentPolicy": "existing-only"
}
  • requirementsは一つ以上必要で、同じcapabilityを重複指定できない。
  • ttlSecondsは1から86400で、既定値は300。
  • allowFallbackの既定値は偽。
  • deploymentPolicyはexisting-onlyまたはallow-listed。
  • staleなobserver snapshot、memory不足、Runtime capacity超過、配備中Runtimeは起動前に拒否する。
  • Resident Runtimeのmemoryは観測状態にかかわらず常時予約する。

Ready response

{
  "id": "alloc_example",
  "status": "ready",
  "requirements": [
    { "capability": "llm.general", "route": "llm-default" }
  ],
  "bindings": [
    {
      "capability": "llm.general",
      "route": "llm-default",
      "runtime": "qwen-general",
      "node": "gnosis",
      "status": "HOT",
      "candidateRank": 1,
      "fallback": false,
      "selectionReason": "primary-live"
    }
  ],
  "expiresAt": "..."
}

Allocation一覧responseはupstream endpointを隠します。明示的なresolveまたはGatewayだけが Bindingのendpointを使用します。一度作成したBindingは、別RuntimeがHOTになっても変更しません。 固定Runtimeが非稼働またはsnapshotがstaleなら、別Runtimeへ移動せずresolveを503で拒否します。

Status

pending
配備、起動、readiness待機中
ready
固定Bindingを利用可能
failed
起動、配備、deadlineの失敗
released
利用側が明示解放
expired
TTL満了による解放

非同期operation phase

GET /v1/operations/:idはpending、running、 succeeded、failed、cancelled、 timed_outを返します。allow-listed配備では checking-artifacts、staging-artifacts、 stopping-runtime、activating-artifacts、 starting-runtime、verifying-runtime、 rolling-back、runtime-readyのphaseで進捗を示します。

Route選択保証

  • llm-defaultはQwen 3.8 27B Residentを第一候補とする。
  • llm-speedとllm-long-contextはroute idの明示指定を必要とする。
  • fallback candidateはallowFallback: trueの場合だけ使用する。
  • 35Bはproduction Registryに未登録で、default routeの候補ではない。
  • Resident Runtimeはstop、無人activation、resource evictionの対象にしない。

OpenAI互換Gateway

POST /v1/chat/completionsにはx-larm-allocation-idを指定します。 Gatewayはllm.generalのready Bindingだけを使用し、requestのmodel値から 別RuntimeやURLを選択しません。

  • streamingとnon-streaming responseを透過する。
  • client disconnectをupstreamへ伝播する。
  • body sizeとtotal timeoutを環境変数で制限する。
  • total timeoutはrequest upload、upstream接続、response streamの全区間へ適用する。
  • stream開始後の別Runtime retryは行わない。
  • prompt、response、audio本文をmetricsまたは構造化eventへ記録しない。
  • request id、Allocation id、Runtime、結果は構造化eventへ記録する。Prometheus metricsからrequest・Allocation・client idを除き、時系列数をboundedに保つ。
  • latency metricはPrometheusの_sumと_countとして公開する。

Artifact lifecycle

  1. models.yamlに固定されたsource、revision、filename、bytes、SHA-256を読む。
  2. 同一filesystemのstaging directoryへ期限付きでstream downloadする。
  3. sizeとSHA-256が一致したfileだけをstagedとして扱う。
  4. Preferred Runtimeが他Allocationで使用中でないことを確認して停止する。
  5. 配備対象とartifactを共有する全Runtimeを予約し、別ownerが稼働中なら拒否する。
  6. 直前targetをhardlinkまたはsymlinkとして保持し、検証済みfileへ原子的に切り替える。
  7. Runtimeを起動し、health失敗時は直前targetへ自動rollbackする。
  8. rollbackはjournalに記録された直前targetだけを復元する。
  9. Allocationのrelease、TTL、startup deadlineをdownloadとactivationへ伝播する。
  10. operationは受付応答前にjournalへ保存し、terminal historyを設定上限内に保つ。

自動配備の制限

現在の自動staging対象は、bytesとSHA-256を持つ単一file artifactです。 directory modelはsnapshot hash manifestがないためfail closedとし、Resident artifactのactivationは attended operationに限定します。

既存APIとの互換

unversionedのprepare、resolve、releaseは維持します。 default Routeが定義されたcapabilityは内部Allocationへ変換し、従来のlease response形へ戻します。 新規clientはRuntime固定と期限を明示できるv1 Allocation APIを使用します。
