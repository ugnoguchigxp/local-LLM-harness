SAAA・ContextStill統合メモリーアーキテクチャ

SAAAへ搭載する個人メモリー、ContextStillのナレッジベース、LARMのManaged Contextを、 一つの巨大な保存層へ統合せず協調させるための設計です。目的は大量の情報を常時LLMへ渡すことではなく、 各turnで必要な事実、手順、tool、現在状態だけを、出典と有効性を保ったままActive Contextへ供給することです。

中心原則: LLMのattention weightを外部systemから直接指定することはできません。 systemが制御するのは、参照可能な候補の検索、有限Contextへの選択、配置、出典、更新、忘却です。 KV stateはこのread pathを速くする再生成可能なcacheであり、Memoryの正本ではありません。

採用する構成

SAAAは検索結果を一つの永続DBへ複製統合しません。各正本から候補を取得し、同じ候補形式へ正規化して、 requestごとに短命なContext Packを作ります。Context PackはMemoryではなく、あるquery時点のread modelです。

共通Memory envelope

本文だけのvector chunkを正本にせず、すべてのMemoryをversioned recordとして保存します。 kind固有payloadは別schemaで検証し、embedding、要約、検索indexは削除・再生成可能なprojectionにします。 

{
  "memoryId": "mem_...",
  "subjectId": "local-owner-subject",
  "kind": "preference | commitment | personal-claim | personal-episode | procedure-overlay | knowledge-ref",
  "revision": 4,
  "status": "active | superseded | disputed | expired | forgotten",
  "payload": { "kindSpecific": "strict schema" },
  "entities": ["entity:person:...", "entity:project:..."],
  "evidence": [
    { "authority": "saaa-event", "recordId": "evt_...", "version": 1, "digest": "sha256..." }
  ],
  "confidence": "asserted | observed | inferred | disputed",
  "importance": "normal | high | critical",
  "validFrom": "...",
  "validTo": null,
  "observedAt": "...",
  "expiresAt": null,
  "sensitivity": "normal | sensitive | restricted",
  "retention": "session | bounded | durable | explicit-only",
  "supersedes": "mem_...@3",
  "createdAt": "...",
  "updatedAt": "..."
}
  • assertedは利用者の明示発言、observedは検証済みtool結果を表します。
  • inferredを確定事実と同じ強さで回答へ使用しません。
  • 訂正と矛盾は過去recordを破壊せず、revision、valid time、statusで表現します。
  • 検索時刻と事実の有効時刻を分け、古い嗜好や既に完了した約束を現在形で提示しません。
  • 各書込みはidempotency keyと期待revisionを要求し、並行turnによるlost updateを防ぎます。

Event JournalとMemory projection

会話やtool結果をそのまま「記憶」にしません。SAAAは最初にEvent Journalへappendし、そのeventから Memory candidateを抽出します。原記録と解釈結果を分けることで、抽出modelを変更してもMemoryを再評価でき、 誤った要約だけを訂正できます。

RetrievalとContext Composer

各turnでSAAAがqueryからintent、entity、time、task、必要tool capabilityを抽出し、三経路を並行検索します。 最初から全Memoryをpromptへ入れず、明らかな候補だけprefetchし、追加情報が必要ならLLMが検索toolを呼びます。

  1. 現在のsubject、session、task、取消epochを固定する。
  2. Working Stateから現在goal、open commitment、直前のtool結果を取得する。
  3. SAAA Memoryをkeyword、entity、time、必要ならembeddingで検索する。
  4. ContextStillを文書scope、source、期間、knowledge kind付きで検索する。
  5. Tool Registryをcapabilityで検索し、実在するtoolの最新schemaだけを取得する。
  6. 権限、subject、forget tombstone、valid time、status、tool versionでhard filterする。
  7. authority、query relevance、entity一致、freshness、confidence、task continuity、token costでrerankする。
  8. 同じclaimの重複をまとめ、矛盾するrecordは隠さず一つのconflict setとして扱う。
  9. required itemを先に置き、optional itemをtoken budgetへpackしてContext Packを確定する。

vector類似度を単独の真理判定に使いません。識別子一致、現在task、時間、authority、利用者の訂正を semantic similarityより強いsignalとして扱います。初期実装では検索経路ごとの上位候補を統合する rank fusionで十分であり、学習済みrerankerは評価集合ができてから導入します。

Context Pack contract

Context PackはSAAAが一回の推論用に生成するimmutable manifestです。本文だけでなく、出典、型、 version、digest、選択理由、token見積りを持ちます。LARMへ渡すときは選択itemをimmutable sourceとして provisionし、既存Context Viewのrequiredとutilityへ写像できます。 

{
  "schemaVersion": "saaa-context-pack.v1",
  "packId": "cp_...",
  "subjectDigest": "sha256...",
  "queryDigest": "sha256...",
  "taskId": "task_...",
  "asOf": "...",
  "budgets": {
    "maxInputTokens": 225280,
    "reservedOutputTokens": 32768,
    "memoryTokens": 24000,
    "knowledgeTokens": 48000,
    "toolTokens": 12000
  },
  "items": [{
    "authority": "saaa-memory | contextstill | tool-registry",
    "recordId": "...",
    "version": "...",
    "digest": "sha256...",
    "kind": "...",
    "required": false,
    "utility": 0.82,
    "confidence": "asserted",
    "validAt": "...",
    "tokenEstimate": 640,
    "rendering": "data-block"
  }],
  "omitted": [{ "recordId": "...", "reason": "budget | stale | unauthorized | superseded" }]
}

Context内は次の境界を守ります。

  1. system policy、tool schema、Memory／Knowledge本文を別sectionにする。
  2. MemoryとContextStill本文は原則として命令ではなくdataとして包装する。
  3. 実tool schemaはMemory本文から復元せず、requestのtools fieldへ渡す。
  4. 重要recordを長い文書中へ埋めず、短いtyped summaryとevidence参照を併記する。
  5. 回答がMemoryに依存した場合、UIや内部traceから根拠recordへ戻れるようにする。

Toolの使い方を覚える仕組み

Tool Memoryは一枚の自由文ではなく、実行contract、review済みprocedure、個人overlay、実行履歴を分離します。 古いprocedureが最新schemaを上書きすると危険なため、次の優先順位を固定します。

  1. Tool Registry: tool名、JSON Schema、権限、side effect、version、availabilityの正本。
  2. Trusted Procedure: intent、前提条件、手順、成功条件、rollback、対応tool version。
  3. Personal Overlay: 利用者固有の既定値、承認規則、保存先。base procedureを参照する。
  4. Execution Ledger: 実行request、result、取消、失敗分類。学習材料であり直接の命令ではない。

実行時はtool.search(intent)で候補を探し、tool.describe(id)で最新schemaを取得し、 対応versionのprocedureとoverlayだけをContextへ加えます。LLMが提案した未review手順や、ContextStillの未信頼文書を、 side effectのある自動実行権限へ昇格させません。

ContextStillとの統合境界

ContextStillはdocument、chunk、Finding、Episode、Procedureとそのprovenanceを所有します。SAAAは KnowledgeProvider adapterを通して検索し、結果を共通Candidateへ変換します。 

KnowledgeProvider.search({
  query,
  kinds,
  sourceScopes,
  entityIds,
  validAt,
  limit
}) -> [{
  authority,
  recordId,
  version,
  digest,
  kind,
  text,
  sourceRefs,
  score,
  validFrom,
  validTo
}]
  • SAAAのpersonal claimとContextStillのFindingが一致しても、一つのrecordへmergeしません。
  • 個人固有の注釈はSAAAのknowledge-refまたはoverlayとして保存します。
  • 一般化できるprocedureをSAAAからContextStillへ送る場合は、明示publish、個人情報除去、reviewを要求します。
  • ContextStillのrecord更新・削除時はversionまたはdigest不一致でSAAAのbookmark cacheを失効させます。
  • ContextStill停止時もSAAAの個人Memory、Working State、tool schemaだけで縮退動作できるようにします。

ConsolidationとDream処理

背景consolidationはMemoryの正しさに必須の同期処理にしません。foreground writeは常にEvent Journalと typed Memoryだけで完了し、idle時に次のbounded jobを一件ずつ実行します。

  • 重複候補のcluster化と既存recordへのevidence追加。
  • 期限切れWorking Stateのepisode候補化または破棄。
  • 矛盾、古いtool version、未完了commitmentの検出。
  • 長いepisodeの短いretrieval summary生成。
  • FTS、embedding、entity link projectionの差分再構築。

LLMが生成したsummaryやrelationはpending projectionとしてschema、evidence、対象revisionを検証してからpublishします。 foregroundが始まればjobをcancelまたは延期し、古いepochの結果をcommitしません。

訂正、Retention、Forget

  1. forget対象をMemory ID、event範囲、subject、source参照のいずれかで解決する。
  2. SAAAへtombstoneと単調増加data epochを先にcommitし、新しいContext Packへの採用を止める。
  3. Memory record、event payload、summary、embedding、FTS、entity link、短命cacheを依存indexから除去する。
  4. Personal StateとしてLARMへ配送済みなら既存の多層forget operationを実行し、source、View、slot、snapshot、auditのabsenceを確認する。
  5. ContextStillが個人sourceの正本を所有する場合だけ、認可されたdeleteを依頼する。共有知識なら参照だけを切る。
  6. 応答紛失後も同じforget IDで再照会し、全phaseがabsenceになるまで完了扱いにしない。

provenance維持のために必要な最小tombstoneは本文、entity、自由文を含めず、再作成を拒否するtarget digest、 fence epoch、完了状態だけを保持します。単なる検索index削除をforget完了とはみなしません。

初期storage構成

SAAA側は最初から別graph DBや分散vector DBを導入せず、単一owner向けSQLiteを正本にします。 metadataと小さいtextはSQLite、巨大なimmutable payloadだけcontent-addressed local blobへ分離します。

memories／memory_revisions typed payload、valid time、status、retention、sensitivity 正本

working_state／commitments task状態、期限、完了状態、TTL 正本

初期検索はSQLite FTS、entity、time filterを中心にします。embeddingは精度評価後に追加し、規模がSQLiteの bounded scanを越えた場合だけ専用vector indexを導入します。vector DBを導入してもMemory recordの正本にはしません。

評価指標

cache hit率や保存量だけでMemory品質を評価しません。同じtask集合でMemoryなし、SAAA Memoryのみ、 ContextStill併用、KV cache併用を比較します。

  • Recall: 必要なMemory／KnowledgeがContext Packまたは検索toolで取得された割合。
  • Precision: 取得したitemのうち回答やtool選択に実際に必要だった割合。
  • Staleness: superseded、期限切れ、古いtool versionを利用した件数。
  • Contradiction handling: 矛盾を黙って一方へ固定せず、正しく解決・確認できた割合。
  • Write precision: 自動commitしたMemoryのうち利用者訂正や削除を受けた割合。
  • Tool success: schema違反、誤tool選択、不要なside effect、retry回数。
  • Context cost: injected tokens、TTFT、prefill時間、回答品質当たりのtoken数。
  • Forget completeness: tombstone後の再採用0件と、全projection／LARM replicaのabsence。
  • Provenance: Memory依存claimから有効なevidenceへ辿れる割合。

実装順序

  1. M0: contract。 Memory kind、record envelope、authority reference、Context Pack、 forget target、tool registry境界を固定する。
  2. M1: SAAA最小Memory。 SQLite Event Journal、typed Memory、Working State、FTS、 明示remember／correct／forget、read UIを実装する。
  3. M2: Retrieval。 entity・time・FTS検索、conflict set、budgeted Context Composer、 memory.search／memory.get toolを実装する。
  4. M3: ContextStill連携。 KnowledgeProvider adapter、version付きknowledge-ref、 source citation、停止時fallbackを実装する。
  5. M4: Tool Memory。 tool search／describe、review済みprocedure、personal overlay、 execution ledgerからの候補抽出を実装する。
  6. M5: 安全な自動記憶。 pending candidate、重複・矛盾検出、sensitivity policy、 bounded consolidationをshadow評価してから有効化する。
  7. M6: 推論最適化。 source rebuildをbaselineに、RAM prefix cacheとsession snapshotが task成功率を変えずTTFTを改善すると実測できた場合だけ有効化する。

最初の利用可能版はM1からM3です。graph DB、巨大vector DB、自律Dream Cycle、512 GiB超のKV保存は 初期Memory systemの成立条件ではありません。

非目標

  • 全会話と全Knowledgeを毎turnのpromptへ投入すること。
  • SAAAとContextStillのDBを双方向同期して同じ事実の正本を二つ作ること。
  • embedding類似度だけで事実性、重要度、保存可否を決めること。
  • LLMへ無検証のMemory書込み権限やtool実行権限を与えること。
  • KV snapshotをLong-term Memory、forget保証、knowledge sourceの代替にすること。
  • background consolidationが停止するとforeground会話も停止する構成にすること。

結論

構築すべきものは巨大なKV Memoryではなく、SAAAを中心とする provenance-aware Context Composerです。SAAAは個人Memoryと現在状態、ContextStillは 文書Knowledge、Tool Registryは実行contract、LARMはbounded inferenceとcacheを所有します。 この分離により、必要なときだけ必要な情報へattention可能なContextを作りながら、訂正、出典、権限、forget、 tool versionを失わずに運用できます。
