認可原則: SAAAがowner ID、principal、検証済みflagを自己申告して認可に使うことは できません。Agent Connection claimに含まれる短期Provider Bearerと contextControl.subjectDigestを使用します。本文、Bearer、owner IDをlogやmetric labelへ 出力しないでください。

認証とidentity binding

  1. 通常BearerでSAAA用Agent ProfileのAgent Connectionを作成し、ready後のclaimにも同じ通常Bearerを 使用します。匿名ConnectionにはPersonal State scopeを付与せず、認証済みConnectionとは別主体として 取得、claim、renew、releaseの所有権を検査します。匿名経路はAuthorizationを 省略したrequestだけに適用し、不正なcredentialを匿名へdowngradeしません。
  2. claimのOpenAI Chat Completions Providerが返すcredential.tokenを、以下の全requestへ Authorization: Bearer …として付与します。
  3. claimのallocationIdとcontextControl.subjectDigestをlocal ownerへbindして 保護領域へ保存します。owner文字列そのものをLARMへ送信しません。
  4. GET /v1/personal-state/capabilityでsubject、Allocation、runtime、release、lease、 credential期限、tokenizer、chat template、input／output／source／byte予算を照合します。
  5. Connection renew後は新しいProvider tokenを使用します。release／lease identity変更後は再計測します。

tokenはsubject、Connection generation、Allocation、Provider、capability、audience、期限、7個の Personal State scopeへ署名されています。別subject／別Allocationのreceiptは401または 403で拒否されます。

配送・登録contract

source POSTはContent-Type: text/plain; charset=utf-8と、 X-LARM-Source-Incarnation、X-LARM-Allocation-ID、 X-LARM-Runtime、X-LARM-Source-Digestを要求します。digestは送信UTF-8 bytesの SHA-256です。LARMはbyte上限を本文展開前後に検査し、認定runtimeのcanonical tokenizerでtoken数を 計測してからsourceとattestationをそれぞれfsync＋atomic renameでpublishします。途中停止による片側だけの 状態は同じincarnationの再送で照合・修復し、forgetは両fileのabsenceを別々に確認します。

  • 同じsubject＋incarnation＋本文の再送は同じsource handleを返します。
  • 同じincarnationを異なるdigestへbindする再送は409 incarnation_conflictです。
  • 登録fieldは成功したprovision receiptと完全一致し、Provider tokenのAllocationに属する必要があります。
  • response receipt期限後もlive sourceのincarnation indexは保持し、孤立sourceをforget可能にします。
  • 成功済みforgetのreceipt期限後も構造化tombstoneを保持し、同じtargetの再作成を拒否します。

canonical measurementとView v2

  1. generationへ送る完全なrequest objectをrequestとして計測します。
  2. LARMはmessages、tools、tool choice等をchat templateへ適用したtoken数を返します。
  3. View候補はrequiredを先に、optionalをutility降順・ID順でexact recountして決定します。
  4. View作成時とgeneration直前にcanonical request digestを再照合します。
  5. release、lease epoch、tokenizer、chat template、data epochの変更時はstaleとして拒否します。
  6. ready Viewはdaemon再起動時にinvalidとなり、durable receiptだけが照会可能です。

viewRequestIdとHTTP Idempotency-Keyはnetwork送信前にoutboxへ保存し、同じ組を 再利用します。どちらか一方を別requestへ再利用すると409 request_digest_mismatchです。

generation attemptと遅延output fence

Chat requestへX-LARM-Allocation-ID、X-LARM-Attempt-ID、View利用時は X-LARM-Context-View-IDを付けます。attempt IDは送信前にoutboxへ保存し、responseの X-Request-IDとは別に管理します。同じattempt IDを別requestへ再利用できません。

停止stateの意味
stopState 意味 SAAAの扱い
cancel_requested 取消をjournalへ保存済み 結果を使用せず、停止照会を継続
transport_closed HTTP transportは閉じたがbackend停止は未証明 成功扱いしない
backend_stopped slot erase成功を確認 remote stop完了として照合可能
stop_unknown backend停止を証明できない 同じruntimeを再利用せず、cancel／forgetを同じIDで再送

LARMはstop_unknownのruntimeをexecution gateで隔離し、通常推論を含む後続requestを 503 runtime_quarantinedで拒否します。slot absenceを確認した再取消／forgetだけが隔離を 解除します。SAAAはforeground復帰やforget開始後の遅延response、表示、projection保存、tool副作用を local attempt fenceで拒否する必要があります。

forget完了条件

forget requestには把握しているincarnation、context ID、source handle、attempt IDをすべて 含めます。LARMは最初にsubject data epochを進め、構造化tombstoneをfsyncします。その後、 attempts、views、runtime、snapshots、 registry、sources、auditを個別に処理します。

  • 全phaseがabsentでabsenceVerified=trueのときだけ成功です。
  • result_unknown、failed、stop_unknownをcleanup完了として扱いません。
  • 同じforget IDの再送は完了済みphaseを含む同じoperationを照合し、未完了cleanupを再試行します。
  • Personal State製品gateがOFFでもforgetとreceipt照会は利用可能です。
  • 保証はlive file、attestation、registry、snapshot、RAM slot、audit payloadの論理absenceです。
  • 物理媒体上のsecure eraseやhost管理者に対する機密性は保証しません。

SAAA側の必須実装

  1. Delivery traitへ全endpointとreceipt照会を実装し、UnavailableDeliveryを置換する。
  2. incarnation、measurement、view request、attempt、forget IDを送信前にtransactional outboxへ保存する。
  3. response紛失時は新IDを生成せず、GET照会または同じIDの再送でreconcileする。
  4. owner–subject bindingとProvider tokenをKeychain相当の保護領域で扱い、診断へ露出しない。
  5. request本文／tools、release、lease、tokenizer、template変更時にmeasurementとViewを再作成する。
  6. attempt fenceより後のoutput、projection、tool callを永続化・表示しない。
  7. 登録、source、snapshot、slot、audit、remote stopを別fieldで保存し、全absenceまでcleanupを継続する。
  8. 全Provider／外部subprocessを列挙し、未対応経路へPersonal Stateを送らない。

rollout前の受入

claimed Provider tokenを環境へ渡し、repository外の証跡先で次の合成data conformanceを実行します。 scriptはsource作成、同内容再送、receipt照会、登録、tools込み計測、View、実generation、attempt照会、 全層forgetを一巡し、cleanup失敗時はpassを出しません。

2026-09-13 SAAA接続と実機確認の追記

SAAAはSQLite v18のoutbox、短期Provider tokenとKeychainによるowner–subject binding、View v2、attempt取消、多層forgetを接続した。配送応答紛失、別subject拒否、配送中forget、future破棄、OFF、部分cleanupを合成HTTP試験で検証した。

分離した一時daemonと合成sourceを使い、常駐27B qwen-generalでprovision、登録、計測、View v2、generation completedまで通過した。forgetはruntime phaseだけstop_unknownで、全体はresult_unknownのまま。エンジンがslot actionへHTTP 501を返したため、完了扱いにしていない。

slot actionには明示したslot-save-pathが必要。service定義へ保存先を追加し、q38rocm launcherのspeed profileがこの引数を捨てない修正と回帰試験を用意した。cache reuseは有効化しない。実際のservice適用と再起動には管理者認証が必要で、未適用である。

Personal State journalのboot epochはUUID契約のため、接頭辞付きdaemon IDを渡さず、journalの既存UUID発行を利用するようmain.tsを修正した。起動とtypecheckを確認した。

一時daemonのorphan回収が別consumerのworkerを停止した記録があったためhealthを回復し、以降は検証daemonの回収猶予を86400秒とした。本番を共有する追加controllerに既存runtimeの自動回収を任せない。本来のworker品質経路は別推論とのスロット競合により受入待ち。SAAAの人手確認済みgold、snapshot ON/OFF、全race、性能比較も未完了であり、既定OFFを維持する。
