Milestone 22 repository結果

  • 一般向けRuntime・state schemaをcapability中心へ縮小し、backend、node、service、model ID、endpoint、resource、health detailを除外した。
  • 完全な定義とstateはmanagement token保護の/v1/inspection/*へ分離し、OpenAPIと strict contract testで公開・管理境界を固定した。
  • 全Provider unitを127.0.0.1 bindへ変更し、host準備からport 8080–8084の新規LAN allowを除外した。installだけではlive processをrestartしない。
  • network convergence toolはlistener、IPv4・IPv6 UFW rule、対象外ruleを棚卸しし、 reviewしたdigestと完全一致する場合だけ既知CIDRの既知Provider ruleを削除する。 rollbackも一つのProviderとIPv4 /24–/32に限定した。
  • installerが上書きする6 unitと既存current pointerを、変更前digestとservice状態を含むmode 0600のoperator backupへ保存するplan・confirmation付きtoolを追加した。
  • preflightへrepository・installed unit digest、active・enabled、listen address、UFW読取可否を 追加した。権限不足を安全とは判定せずunknownとして残す。
  • VOICEVOX 0.vvmはversion 0.16.4、upstream revision、bytes、SHA-256、terms、 operator同意要件を固定し、regular fileとchecksumの一致をpreflightの必須条件にした。

Milestone 25 repository結果

  • 通常LLM、リアルタイム相当、STT、通常TTSの4 seriesに対し、prompt class、token上限、 concurrency、sample下限、TTFB・total・startup p95、memory headroom、error率、queue、 Provider 429、fallback、route・Runtime・release identityをstrict schema化した。
  • benchmarkはdeployed release commitと指定commitの一致を要求し、raw sampleをmode 0600の repository外fileへ、匿名化aggregate summaryを別fileへ排他的に保存する。prompt、transcript、 audio path、credentialは出力しない。
  • comparatorは未校正manifest、identity不一致、series欠落、sample不足、NaN、epoch変化、fallback、 latency・memory・error・queue・429逸脱をすべて拒否する。
  • deploy/local-node/slo.yamlは実測前のため意図的にuncalibratedであり、 production comparatorは必ず失敗する。数値はversioned deployment後の実測からだけ設定する。
  • canary gateはclean worktree、daemonのreleaseCommit、config revision、boot epoch、 4-series SLO、shadow一致、voice smoke、Allocation・queue・artifact operation leak 0を要求する。

同日時点のread-only host差分

2026年8月29日00:42 UTCのpreflightではLARM daemon、credential、port 9810 listenerは未導入でした。 既存5 Providerはactiveで、installed unitはrepository desired stateと不一致、port 8080–8084はwildcard listenerでした。Qwen TTSもenabledかつactiveです。非root実行ではUFWを読めず、 network境界は証明していません。VOICEVOX VVMの実file identityだけは固定metadataと一致しました。

最終code review hardening

repository実装後の再レビューで、成功HTTPを機能成功と誤認する余地、証跡の競合上書き、複数rule 削除の途中失敗、backup中のhost drift、既存release dependencyの改変を残存riskとして検出し、次の fail-closed保証へ更新しました。

  • benchmarkはLLM SSEの正常終端とJSON event、STTの非空text、TTSのcontent typeとcreditを検証し、 series実行中も100 ms間隔でmemory・queue telemetryを採取する。失敗時もbounded error codeと途中sampleを raw evidenceへ保存してから非0終了し、passing summaryは作らない。
  • raw、summary、comparison evidenceはrepository外のcanonical pathへmode 0600で原子的に作成し、 既存targetを上書きしない。symlink経由でrepositoryへ戻るpathも拒否する。
  • SLO schemaはbyte値の整数性、count・latencyの物理的整合、identity形式、acceptanceとrollback thresholdの順序を検証する。
  • network applyは途中のUFW失敗またはpost-check失敗時に削除済みruleを補償復元し、明示rollbackも ruleの再観測まで成功条件に含める。
  • host backupはcopy後digestとcapture終了時のplan identityを再検証し、途中変更またはtarget競合時に stagingだけを破棄する。
  • release manifestへdependency tree digestを追加し、既存世代の再利用とrollback前にGit source、 lockfile、dependency treeの内容・型・mode、version、config revisionを再検証する。
  • installerはunit、polkit、credentialのsymlink・特殊fileを、いずれのinstall mutationより前に拒否する。 external assetはO_NOFOLLOWで開き、公式version URLとの整合も検証する。

検証と残件

strict schema、API認証・reload、external asset checksum・symlink、networkの対象限定・IPv6・ unsafe root、release identity、SLO境界・逸脱fixtureを自動testへ追加しました。全repository gateは288 unit test・804 assertionと、10 Bun deployment test・4 shell integration suiteを含めて 成功しました。結果はStable Release Gateへ記録します。

次の安全な工程はclean commitの作成、operator backup、root権限でのinstallerとversioned LARM releaseです。その後にcommissioning、4-series校正、Ambient canaryを行います。Provider restartと UFW変更は、対象、順序、rollback、confirmation digestをoperatorが確認するまで実行しません。
