SAAA向けLARM REST接続有効化計画

既にgnosisへ恒久配備されている常用LLM、on-demand worker、model artifactを変更せず、SAAA desktopがLARM Agent Connection APIをRESTで利用できるようにするための小さな接続有効化計画です。 SAAAはprofileとaudienceを要求し、claim responseからOpenAI-compatible接続設定を動的に構成します。

「恒久配備」の対象を混同しません。常用LLMとProvider基盤は既に恒久配備済みです。今回追加するのは、 その既存基盤をSAAAから利用するためのLARM REST Gateway常駐serviceとSAAA adapter接続です。

今回やりたいこと

  1. gnosisでLARM daemonを常駐させ、認証付きREST APIをTCP 9810で利用可能にします。
  2. SAAAはdeep-reasoning-35bとsaaa-desktopを指定してConnectionを作成します。
  3. SAAAはclaim responseのbaseUrl、model、短期tokenからOpenAI clientを動的に 構成します。
  4. SAAAはSSE inferenceを実行し、終了時にREST DELETEでConnectionを解放します。

SAAAからgnosisへの接続はREST APIだけを使用します。SSH、SFTP、SCP、SSH tunnel、port forwardingは 使用しません。

実装手順

1. SAAAとの入力確認

  1. SAAA Macの送信元IPv4を確認します。firewall ruleはこのhostだけに限定します。
  2. SAAAがREST-onlyとdynamic claim contractを受け入れることを確認します。
  3. 長期API tokenをSAAA processへ設定するoperator secret channelを確認します。

2. GnosisでREST Gatewayを有効化

  1. clean commitでbun run checkを実行します。
  2. read-only preflightと既存host stateのbackup planを保存します。
  3. LARM_INSTALL_SCOPE=gateway install-services.shでLARM unit、credential、polkit、LARM state directoryだけを導入します。既存Provider unitとそのenable状態は変更しません。
  4. release-larm.shで同じclean commitをversioned releaseとして適用します。
  5. daemonがenabled・activeで、/healthと/readyが成功することを確認します。

現行prepare-host.shはTCP 22のallow ruleも追加するため、今回のnetwork設定には使用しません。 SAAA送信元から9810へのallowだけを個別にreviewし、既存ruleを変更せず適用します。SSH用ruleは追加しません。

3. Gnosis local REST acceptance

  1. deep-reasoning-35b、saaa-desktop、 existing-only、allowFallback:falseでConnectionをcreateします。
  2. pendingまたはprobingをpollし、readyを待ちます。
  3. claim responseのaudience、base URL、model、health URL、expiryを検証します。
  4. 短期tokenでsemantic healthとSSE inferenceを実行します。
  5. 非空completionとSSE [DONE]を確認します。
  6. REST DELETEが204となり、Connectionとworkerが解放されることを確認します。

4. SAAA adapterとLAN canary

  1. Operatorが長期API tokenだけを承認済みsecret channelからSAAA processへ設定します。
  2. SAAA adapterがcreate、poll、claim、dynamic OpenAI client、SSE、releaseを実行します。
  3. SAAA Macから9810の認証付きREST APIが成功することを確認します。
  4. SAAAがSSH、direct Provider、保存済みdescriptorを使用していないことを確認します。
  5. 双方が同じrelease commitとconfig revisionを記録します。

完了条件

  • LARM daemonがenabled・activeで、health、ready、release manifestのidentityが一致する。
  • SAAAから9810の認証付きREST APIへ接続でき、未認証requestは401となる。
  • deep-reasoning-35bをfallbackなしでcreate、poll、claimし、claim responseだけから OpenAI clientを構成できる。
  • SSE inferenceが完了し、DELETE release後にConnectionとworkerのleakがない。
  • SAAAが長期API token以外のGnosis secretを保持しない。
  • SAAAからの接続・運用にSSH、SFTP、SCP、tunnel、port forwardingを使用しない。

Rollback

  1. SAAA側のLARM provider設定を無効にし、保持するConnectionをREST DELETEします。
  2. release-larm.sh rollbackでLARM daemonだけを前releaseへ戻します。
  3. 初回導入で前releaseがない場合はdaemonを停止し、current pointerを未導入状態へ戻します。
  4. 今回追加した9810 allow ruleだけを削除します。

常用LLM、model artifact、既存Provider serviceはrollback対象にしません。SSHをrollback経路にしません。

証跡

full commit、config revision、boot epoch、health・ready、REST status、SSE完了、release結果だけを記録します。 API token、management token、signing key、短期token、Authorization header、prompt、completion本文は 標準出力、evidence、Gitへ保存しません。
