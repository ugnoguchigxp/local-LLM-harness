2026年8月28日にMilestone 15–21のrepository実装を完了しました。実装結果と残るlive gateは 完了記録、host preflightは commissioning evidence、現在の着手順はProduction Completion実装計画を参照してください。

結論

最初のblocking gateはコード追加ではなく、現在のcommitをgnosisへ導入して実測することです。LARM daemonがまだ実ホストへ導入されていない状態でcatalog reloadや追加モデルを実装しても、 実際のstartup latency、memory peak、音声経路、rollbackの前提を検証できません。

commissioning完了後は、LARM自身の更新をversioned releaseとしてrollback可能にし、 machine-readable API contractと参照clientを固定します。その上で、現行の「Runtimeごとに一つの artifact集合」という制約を、immutableなmodel release catalogへ発展させます。推論requestは 引き続きRouteだけを指定し、artifact revisionの変更は管理APIへ分離します。

35Bはこの計画の実装対象ではありません。Qwen 3.8 27Bがリアルタイム要求を含むResident defaultであり続けます。35BはMilestone 21完了後、特定taskの速度SLOと品質下限を満たす場合にだけ、独立したdecision recordを経て明示的な速度route候補として評価します。

Milestone 21完了時の状態

  1. LARM daemonがgnosisで常駐し、実測を含むcommissioning evidenceを持つ。
  2. LARM自身をcommit固定releaseとして導入し、Resident Runtimeに触れず前世代へ戻せる。
  3. 利用側は生成されたcontractと参照clientでAllocation、renew、Gateway、releaseを扱える。
  4. 推論requestはcapabilityとrouteを指定し、port、service、artifact revisionを指定しない。
  5. 管理者はallowlist済みmodel releaseを明示的にplan、stage、activate、rollbackできる。
  6. catalog更新は世代単位で検証・原子切替され、active AllocationのBindingを暗黙に変更しない。
  7. Preferred起動は静的memory budgetとfreshな実測headroomの両方を満たす場合だけ許可される。
  8. fault testと実client canary後もQwen 3.8 27BがResident defaultであり続ける。

先に固定する設計判断

  • Request-time routingとrelease-time deploymentを分離する。通常のAllocation APIへURL、path、 checksum、artifact revisionを追加しない。
  • Model releaseはversion管理されたcatalogに事前登録されたIDだけを受け付ける。APIから任意URL、 任意path、任意command、任意systemd unitを受け取らない。
  • Release IDと内容digestはimmutableとし、同じIDの内容差し替えを拒否する。
  • Activationはoptimistic concurrencyを使い、呼出側が認識するactive releaseと実状態が異なる場合は 409で拒否する。
  • Active AllocationのBinding、catalog generation、active releaseは処理途中で変更しない。 変更後のgenerationは新規Allocationからだけ使用する。
  • Resident artifactのAPI経由activation禁止を維持する。Resident更新は別のattended手順とし、 rollback確認なしに自動化しない。
  • Catalog reloadは設定済みdirectoryだけを再読込し、request bodyからfilesystem pathを受け取らない。
  • Live telemetryは静的memory reserveを置き換えない。telemetryがstaleまたは取得不能なら、 Preferred・Elasticの新規起動をfail closedする。
  • Allocationはdaemon再起動後に復元しない。boot epoch変更と再Allocation contractを維持する。

依存関係と着手順

Milestone 17のschema整備はMilestone 16と並行設計できますが、productionへ有効化する順序は固定します。Milestone 18以降を実装しても、Milestone 15を通過するまで実ホストの管理APIでは有効にしません。

Milestone 15: Current release commissioning

目的
現在の実装をgnosisへ安全に導入し、次の設計判断に使えるbaselineを採取する。
優先度
P0・後続のblocking gate
変更種別
attended operationと不足した検証toolの補完

実施項目

  1. preflightでcommit、dirty tree、config revision、unit差分、credential mode、active service、 port、disk headroomを記録する。secret、prompt、transcript、audioは記録しない。
  2. 既存unitを退避し、installerをdry-run相当で確認してからLARM unitだけを導入する。Resident Providerを一括restartしない。
  3. /healthと/ready、Resident 27B Allocation、streaming Gateway、releaseを検証する。
  4. 非機密sampleでSTT、通常TTS、voice creditを確認する。Qwen TTSの外部直接利用がないことを確認後、enabled driftとorphan reconciliationを検証する。
  5. Qwen TTS snapshotをstageし、Preferred Allocation経由のactivate、health、自動rollback、明示rollbackを 一回ずつ確認する。
  6. daemon process restartでboot epochが変わり、旧Allocationが409、新Allocationがreadyになること、execution gaugeが0へ戻ることを確認する。
  7. 反復canaryと短時間soakでTTFB、完了時間、startup、error率、memory peak、gateway overheadを採取し、新しいSpec HTML evidenceへ要約する。raw outputはrepository外へ保存する。

完了条件

  • larm-daemon.serviceがenabled・activeで、再起動後もreadyになる。
  • llm-defaultが常にqwen-generalを第一候補として返す。
  • 通常・リアルタイム、STT、通常TTSが追加Preferred Runtimeなしで完走する。
  • Qwen TTSは明示要求時だけ起動し、release後に回収される。
  • rollbackでLARMだけを外し、既存direct Provider経路を維持できる。
  • 測定条件、commit、config revision、boot epoch、結果、逸脱がevidenceに残る。

Milestone 16: Transactional LARM release and rollback

目的
Git checkoutとservice実行位置を分離し、LARM自身の更新を世代管理する。
優先度
P0

実装項目

  1. release manifestへcommit、LARM version、Bun version、lockfile digest、config revision、作成時刻を固定する。
  2. source-only release directoryをrepository外に作り、frozen installと全gate成功後だけ currentを原子的に切り替える。
  3. installerへplan、apply、rollbackを追加し、排他lock、 precondition、途中失敗時のcleanupを実装する。
  4. service unitはversioned releaseのcurrentだけを参照する。更新時にrestartするのは LARM daemonだけで、Resident・Preferred Providerへ連鎖restartしない。
  5. credential、artifact journal、model dataをrelease directoryから分離し、rollbackでも保持する。
  6. filesystem root、symlinked release root、dirty source、digest不一致、並行applyをfail closedする。

完了条件

  • 隔離rootで初回導入、再実行、upgrade、途中失敗、rollbackを自動testできる。
  • rollback後のhealthが前releaseのversionとconfig revisionを返す。
  • release切替中もResident Provider processとmodel weightを変更しない。
  • 保持世代数がboundedで、削除対象をplan表示してからだけcleanupする。

Milestone 17: Machine-readable contract and reference client

目的
Ambient Agent側がlifecycleの細部を再実装せず、安全にLARMを利用できる境界を作る。
優先度
P0

実装項目

  1. Coreにrequestだけでなく、公開response、error、operation、health、stateのstrict schemaを追加する。
  2. route metadataとschemaからOpenAPI 3.1を生成し、GET /openapi.jsonで現行processの contractを返す。手書きの別schemaを正本にしない。
  3. packages/clientへ薄いTypeScript clientを追加し、Allocation作成、operation polling、 renew、Gateway、release-in-finally、timeout、AbortSignalを実装する。
  4. clientはIdempotency-Keyとboot epochを扱い、epoch変更時は明示的な再Allocation結果を呼出側へ返す。 route、fallback、releaseをclient内部で勝手に変更しない。
  5. loopback、Bearer token、management tokenのcredential注入を分離し、tokenをerrorやdebug logへ含めない。
  6. unversioned compatibility APIは維持するが、新規例と参照clientはv1だけを使用する。

完了条件

  • 実daemon routeとOpenAPI operationの追加・削除driftをtestで検出する。
  • schemaで全成功responseと主要error responseをparseできる。
  • 参照clientのcancel、timeout、renew失敗、epoch変更、release二重実行testがある。
  • 一つのvoice AllocationからSTT、LLM、TTSを呼ぶE2E例が個別portを参照しない。

Milestone 18: Immutable runtime release catalog

目的
allowlist済みの複数model revisionから、Runtimeへ適用するreleaseを明示選択できるようにする。
優先度
P1

Release contract

新しいrelease catalogは、Runtime ID、release ID、artifact ID集合、resource estimate、provider config revision、health contractをimmutableな一単位として持ちます。Artifact manifestは download元とdigestの正本、release catalogはRuntimeへ同時適用する組合せの正本です。 

{
  "runtime": "qwen-worker-fast",
  "release": "qwen-worker-fast-2026-08-r1",
  "expectedActiveRelease": "qwen-worker-fast-2026-07-r3"
}

提案API

管理credentialで保護するversioned release API
Method Path 意味
GET /v1/runtime-releases 公開可能なrelease ID、runtime、状態、digestの一覧
POST /v1/runtime-releases/:id/stage releaseが参照する全artifactの検証済みstaging
GET /v1/deployments/:runtime active、previous、staged、health、generationの取得
POST /v1/deployments/:runtime/plan 停止、artifact、disk、allocation、rollback可能性を変更なしで評価
POST /v1/deployments/:runtime/activate expected active release一致時だけPreferred releaseを切替

実装項目

  1. Coreへrelease schema、digest、Registry・artifact参照整合性検証を追加する。
  2. 同じRuntime・release IDの内容差し替え、重複active target、未登録artifactを拒否する。
  3. stageはrelease単位のoperationとし、一部artifactだけ成功した状態をactiveにしない。
  4. activate前にexpected active release、active Allocation、共有artifact、disk、staged digestを再確認する。
  5. active、previous、candidate、operationをrepository外へ永続化し、crash後にprepared phaseを回復する。
  6. 最初のproduction対象はPreferred Qwen TTSと27B workerだけとする。

完了条件

  • 同じrelease指定のretryは同じoperationまたは同じactive状態へ収束する。
  • staleなexpected active releaseは409で、artifact変更を開始する前に拒否される。
  • health失敗時は全artifactとprovider configを同じprevious releaseへ戻す。
  • Resident Qwen 3.8 27BのAPI activationは引き続き拒否される。

Milestone 19: Atomic catalog generation activation

目的
daemonを再起動せず、検証済みRegistry・Route・release catalog世代を安全に反映する。
優先度
P1

実装項目

  1. Registry、artifact manifest、release catalogを一つのCatalogGenerationとしてloadし、content digestを計算する。
  2. 管理APIは設定済みdirectoryの再読込だけを要求できる。candidate generationをparse・cross validateし、diffとblock理由を返すplan phaseを持つ。
  3. active Allocation、execution、artifact operation、Runtime transitionが参照する定義を変更・削除する generationはquiescentになるまでactivateしない。
  4. activateは短時間だけ新規Allocationをdrainし、observerとBackend routingを構築後にpointerを原子的に 交換する。失敗時は旧generationで受付を再開する。
  5. Allocationへcatalog generationとactive releaseを固定し、response headerへ x-larm-config-revisionを追加する。
  6. 同時reload、同時activation、daemon shutdownとの競合を単一coordinatorで順序付ける。

完了条件

  • 不正candidateは現行generation、ready、既存Allocationへ影響しない。
  • reload前のAllocationが別Runtimeまたは別releaseへ暗黙移動しない。
  • Resident defaultを変更するdiffは通常reloadで拒否し、attended decisionを要求する。
  • reload、allocation、activation、shutdown raceの決定的testがある。

Milestone 20: Resource telemetry, SLO calibration, and fault injection

目的
推測値ではなく実測に基づき、Resident 27Bを守るadmissionとexecution設定を確定する。
優先度
P1

実装項目

  1. Backend境界へLinux node telemetry adapterを追加し、system memory、利用可能headroom、GPUまたは unified memory、採取時刻、取得状態を正規化する。
  2. Core admissionは静的estimated memoryを第一gateとして維持し、Preferred・Elastic起動だけをfreshな live headroomで二重確認する。
  3. metricsへ固定bucketのstartup、queue、TTFB、total duration、memory headroomを追加する。 request、Allocation、client、promptをlabelにしない。
  4. benchmark runnerはraw JSONをrepository外へ保存し、commit、config、release、prompt class、token数、concurrencyだけを匿名化summaryへ変換する。
  5. fake Backendでprocess crash、health stall、partial stream、disk full、journal corruption、reload race、shutdown timeoutを再現するfault testを追加する。
  6. attended testでdaemon kill、Preferred provider kill、network stall、artifact rollbackを確認し、Resident providerを意図せず停止しないことを監査する。

完了条件

  • telemetryがstaleでもResident経路は維持し、Preferredの新規起動だけを拒否する。
  • Qwen 3.8 27Bの通常・リアルタイムSLOと測定条件がSpec HTMLで固定される。
  • slot、queue、timeout、memory estimateの変更は実測根拠とrollback値を持つ。
  • fault test後にallocation、execution、operation gaugeが0または実状態へ収束する。

Milestone 21: Ambient client canary and stable release gate

目的
上位Runtimeの実trafficを個別portからLARM contractへ段階移行する。
優先度
P0・最終production gate

Rollout

  1. shadow接続テストでAllocationとresolve結果を比較し、推論trafficはまだ切り替えない。
  2. 非音声の一部taskを参照client経由へ切り替え、direct Providerへの即時rollbackを保持する。
  3. 通常・リアルタイムLLM、STT、通常TTSの順にcanary範囲を広げる。
  4. expressive TTSは明示routeだけを別canaryにし、通常TTSと混ぜない。
  5. soak中にdaemon restartとPreferred release rollbackを一度ずつ実施する。
  6. error budget、latency、memory、fallback、epoch変更、leakが基準内ならstable releaseとする。

完了条件

  • 上位clientは8080から8084の個別port、service名、artifact pathを参照しない。
  • 全turnで実際のRuntime、route、release、fallback理由を本文なしで監査できる。
  • daemon停止時にResident Providerを止めず、client設定だけでdirect経路へ戻せる。
  • soak後にactive Allocation、execution queue、artifact operationのleakがない。
  • commissioningとcanaryのevidenceがstable releaseのcommitへ相互linkされる。

この計画で行わないこと

  • 35Bをproduction Registryまたはllm-defaultへ追加すること。
  • Qwen 3.8 27B Residentを自動停止、memory pressure evictionすること。
  • API requestから任意model URL、path、command、systemd unitを受け取ること。
  • daemon再起動をまたいでAllocationを復元すること。
  • 複数hostのremote agent、distributed scheduler、leader electionを実装すること。
  • Cloud Provider選択、Situation判断、Conversation、UI、設定SQLiteをLARMへ入れること。
  • raw prompt、response、transcript、audio、credential、model weightをrepositoryへ保存すること。

各Milestone共通のDefinition of Done

  • CoreのOS非依存境界とBackend adapter境界を維持する。
  • 成功、拒否、timeout、cancel、restart、rollback、並行実行のtestを追加する。
  • queue、history、journal、release保持、telemetry labelへ明示上限を持たせる。
  • public contract変更と運用手順を同じcommitのSpec HTMLへ反映する。
  • bun run docs:check:fixとbun run checkを通す。
  • weight、binary、build、cache、log、raw benchmark、生成mediaをGitへ追加しない。
  • live変更は対象、影響、precondition、rollbackを表示し、attended gateとして実行する。
