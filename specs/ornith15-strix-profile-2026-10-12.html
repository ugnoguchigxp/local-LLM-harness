画像の送信形式

質問文と画像を、同じuser messageのcontent配列に入れてChat Completionsへ送る。 ローカル画像はBase64化したdata URLを使えば、consumerとserver間でファイルパスを 共有する必要がない。Base64は転送用の表現であり、画像encoderの代替ではない。 HTTPS画像URLもllama-serverで使用できるが、serverから取得可能である必要がある。 

{
  "model": "ornith-1.5-strix-lean",
  "messages": [{
    "role": "user",
    "content": [
      { "type": "text", "text": "この画像に何が写っていますか？" },
      { "type": "image_url", "image_url": {
        "url": "data:image/png;base64,ここに画像のBase64データ"
      }}
    ]
  }],
  "max_tokens": 512
}

上記は形式例で、Base64部分を実データへ置き換える。LARM経由では選択したAgent Profileの llm Providerが返すendpoint・公開model・資格情報を使う。現在のChat Completions schemaと 通常gatewayはcontent配列を文字列限定にしておらず、画像partを保持して転送できる構造である。 画像を含む実リクエストのLARM経由E2E検証は未実施。request body上限には画像のBase64と テキストの両方が含まれる。consumer側にも画像選択・エンコード・送信処理が必要である。

追加構成と残る検証

llama.cppではprojectorを同じllama-serverへ読み込む。独立したOCR serverや別の会話LLMは 通常の画像理解には必須ではない。STRIX_LEANでの指定候補は --mmproj /srv/ai/models/ornith-trial-20261012/strix-lean/mmproj-Ornith-1.5-35B-BF16.gguf。 projector内の画像encoderが画像を特徴量へ変換し、LLMが質問文と合わせて解釈する。 約903 MBはファイル容量であり、実行時の追加memoryや画像token、latencyを示す値ではない。

projectorの常駐とmemory見積もり

通常のllama-serverでは、projectorを起動時にLLMと一緒に読み込み、同じruntimeの稼働中は 保持する。画像requestのたびにロード・解放する方式ではない。テキストだけのrequestでは 画像encoderを実行する必要はないが、projectorの重みは保持される。LARMがruntimeを停止すれば プロセスのmemoryも解放される。同じserverの4 slotはprojectorの重みを共有し、 4 sessionだから重みが4倍になるわけではない。別プロセスで起動したruntimeは別の保持単位になる。

保存済みSTRIX_LEAN側projectorのGGUF tensor一覧を読み取り、334 tensorの重みデータを 合計902,802,368 bytes、860.98 MiB、約0.841 GiBと確認した。内訳は BF16が883,482,624 bytes、F32が19,319,744 bytesである。この値は重みデータ容量であり、 プロセスの実測RSSやGPU allocationではない。ファイル全体の902,822,016 bytesには metadataとalignmentも含まれる。

追加memoryはprojectorの重みだけでなく、backend管理領域、画像encoderの計算buffer、 画像展開・前処理・特徴量bufferも含む。計算bufferを起動時に確保するか画像処理時に確保するかは engineの版と実装による。画像由来tokenもLLMのcontext容量を使うが、既に確保済みのKV poolが 同じ量だけ追加確保されるとは限らない。解像度、画像token上限、画像枚数、並行処理でpeakは変わる。 従って約0.9 GBは重み部分の目安であり、idle差分・画像推論peakは未測定である。 AI MAX 395のGPU offloadも同じ物理RAMを使うので、CPUに移すだけで総容量を節約できるとは限らない。

有効化前には対象artifactとengineで隔離試験し、既存のcontext-shift、KV cache、複数slot、 speculation設定との組み合わせを確認する。物体説明と文字読み取りを分けて評価し、 peak memoryと既存sessionへの影響を測る。本調査では稼働設定の変更、restart、重みの取得を 行っていない。
