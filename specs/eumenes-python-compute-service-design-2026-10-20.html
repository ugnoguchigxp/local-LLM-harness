推奨構成

LARMの非同期HTTP Job APIを本体とし、MCPは同じAPIへの薄いadapterにする。ジョブ保存、資源上限、取消、成果物、保持期間を一元化する。Eumenes backendはcatalogで発見したAPIを直接利用し、他のMCPクライアントには同じAPIを包む窓口を提供できる。

計算の種類と担当
種類 用途 実行方針
calculate 四則演算など小さな確定的数式 Eumenes側の制限付きparser。任意Pythonやshellの権限を持たせない。
Python CPU SymPy、SciPy、統計、pandas、scikit-learn、作図、小規模PyTorch 初期提供範囲。最大2ジョブ、各ジョブに時間・CPU・メモリ上限。
Python GPU ROCm版PyTorchの学習など 同時1ジョブ。推論優先の調停と実機検証を通過してから公開。

Terminal経由の実行は運用者の調査用として残せるが、エージェントには構造化したツールを提供する。1時間の処理を1本のHTTP要求やMCP tool callで待ち続けず、投入時にjobIdを返して後から照会する。MCP Tasks拡張は対応クライアント向けの追加機能とし、基本経路はsubmit/status/cancelで成立させる。

GET /v3/agent-profilesの対象profileのservicesにcomputeを追加する。protocolごとのschema分岐とし、既存image/musicのmodel・endpoint制約は維持する。computeにはmodelを要求しない。以下はCPU版公開時の例であり、現在利用できるURLの宣言ではない。

  "name": "compute",
  "capability": "compute.python.execute",
  "protocol": "larm.compute.v1",
  "endpoint": "/v1/compute",
  "url": "https://control.example.invalid/v1/compute",

URLは設定した外部Control originから構築し、任意のHost・転送headerをそのまま信頼しない。catalog閲覧、environment、status、成果物取得ではworkerを起動しない。backend未導入なら広告せず、GPUだけ未検証ならCPU serviceとして広告する。無指定一覧ではcompute対象のcanonical profileに表示し、selector指定でも同じ項目を得られるようにする。selectorごとに異なる既存image/musicの挙動は維持する。

compute API全体を既存Control Bearerで保護し、匿名アクセス・Provider Bearerを拒否する。共有Bearerを使う初版では利用者は同じ計算権限を持ち、ユーザー単位の隔離を提供済みとは説明しない。将来複数principalを使う場合はjob・artifact・idempotency・quotaをprincipal単位に分離する。Bearerはbackendまたはadapterに留め、LLM、ブラウザ、container、生成物URLに渡さない。

HTTP契約案

base URLはcatalogのurl。通常応答はJSON、成果物取得成功時のみ対応MIMEの本体。HTTP失敗は{"error":{"code":"snake_case","message":"..."}}。状態照会のHTTP 200内にあるjob.errorと、API自体の入力・認証エラーを区別する。時刻はUTCのRFC 3339、未開始・未終了はnull。未知のrequest fieldは拒否する。

公開操作の提案
操作 path 応答・補足
環境 GET /environment 200。実行imageのpython、packages、accelerators、limits。imageDigest、environmentRevision、GPU admissionの可否を追加。hostのPython版で代用しない。
投入 POST /jobs Idempotency-Key必須。202 {jobId}、Locationに状態URL。永続化完了後に応答する。
照会 GET /jobs/:jobId 200。添付のstatus/stage/時刻/progress/result/errorに、resolvedAccelerator、environmentRevision、expiresAt、cancelRequestedを追加。
成果物 GET /jobs/:jobId/artifacts/:artifactId 200。completedの公開済み成果物だけ。IDから保存先を引き、任意pathを受け付けない。
取消・削除 DELETE /jobs/:jobId 添付の複合動作を維持。実行前・中なら取消。停止・回収確認後は200 cancelled、未完了なら202の状態表現。終端jobは結果・成果物を削除して204。
取消専用 POST /jobs/:jobId/cancel 追加提案。終端jobは削除せず200で現在状態を返す。取消受付中は202。MCP cancelはこの操作を使う。

  "inputs": {"a": 1, "b": 1},

codeは空でないUTF-8文字列、inputsはJSON object、timeoutSecは1〜3600の整数で省略時60、acceleratorはauto/cpu/gpuで省略時auto。非JSON値は拒否する。Idempotency-Keyは1〜128文字のASCII識別子。同一principal・key・正規化本文なら処理中でも同じjobIdを202で返す。objectのkey順は無視し、code文字列の差は維持する。省略値と既定値の明示は同じ意味とする。競合検査とjob作成は1 transaction。

本文hashとenvironmentRevisionを初回受理で固定し、同じkeyの再照会でimageを変更しない。削除・失効後も受理から7日間はkey/hashのtombstoneを保持し、同じ本文には410 job_expired、異なる本文には409 request_conflict。7日後のkey再利用は新規jobになり得る。生成POSTを内部で自動再送しない。通信失敗後の照合が必要なら、呼出元の明示操作で同じkeyを再使用する。

HTTP失敗の分類
HTTP code 意味
400 invalid_request / limit_exceeded 型・必須header・値が不正、またはcode/input/request上限超過。
401 / 403 unauthorized / forbidden Control認証失敗、または認めていないcredential・操作。
404 not_found 未知または閲覧できないjob/artifact。
409 request_conflict / artifact_not_ready keyの本文不一致、または成果物未公開。
410 job_expired 削除・失効済み。tombstone期間のみ判別可能。
429 queue_full 受付件数・保存容量の予約上限。Retry-Afterを返すがPOSTを自動再試行しない。
503 unavailable 実行環境が不健全、GPU未公開、必要な上限制御やtelemetryが利用できない。

job.error.codeは添付のtimeout、memory_exceeded、gpu_memory_exceeded、runtime_error、syntax_error、limit_exceeded、output_exceeded、unavailable、cancelledに、preemptedとqueue_timeoutを追加提案する。前者は高優先推論による中断、後者は実行前の待機期限切れで、いずれもfailed。自動再実行しない。runtime_error・syntax_errorはtraceback末尾8 KiB以内をmessageに返す。exit code 137だけでOOMと断定せず、cgroup event・監督側の停止理由で分類する。

状態・取消・再起動

statusはqueued/running/completed/failed/cancelled。queuedのstageはqueued/waiting_gpu、runningはstarting/running/collecting、終端は同名stage。startingへの遷移をstartedAtと実行時間の起点とし、起動・実行・変換・成果物回収をtimeoutSecに含める。queued/waiting_gpuは含めず、別のmaxQueueWaitSecを設ける。

report(message, ratio=None)はmessageをUTF-8最大1 KiB、ratioを有限の0〜1または省略に限定。hostで最大2回/秒に間引き、最新値だけ保存する。進捗は自己申告であり、実行完了や資源使用量の根拠にしない。stdoutを進捗として解釈しない。通常poll間隔は2〜5秒、短いUI待機は最初の数秒だけにする。

取消受付と完了公開はversionを使う原子的更新で順序を決める。取消が先なら即座に結果公開を禁止し、部分結果・成果物を削除し、子孫processを含むcontainer全体を停止する。停止・除去確認まではcancelRequestedとし、cancelled確定・資源枠返却をしない。完了が先ならcancel専用APIはcompletedを維持し、DELETEは完成結果を削除する。DELETEの再試行では取消済みmetadataも削除され得るため、取消再試行にはcancel専用APIを使う。

cancelled jobにはvalue/stdout/stderr/artifactsを残さず、最小の状態・時刻・分類だけ保持する。結果保持は終端から24時間。code・inputsは実行に不要になった時点で削除し、結果APIに返さない。起動時と定期GCで期限切れを削除する。

HTTP接続切断後もジョブは継続する。SupervisorはHTTP処理とは別processとし、Control再起動後は永続storeで追跡を再開する。Supervisor自体を失った場合は、回復時に所有label・container ID・cgroupを照合して残存processを停止する。起動前queuedだけ再開可能とし、開始済み計算は自動再投入しない。回復不能はfailed/unavailable。停止不能・資源解放未確認ならlaneを隔離し、既存推論のunitやGPU全体をresetしない。

コンテナ・runner・成果物の境界

第一候補は専用OS利用者のrootless Podmanとcrun。cgroup v2のcpu/memory/pids delegationと実際の設定を検査し、上限を適用できなければunavailable。rootfulへ自動fallbackしない。Supervisorはcompute所有labelのcontainerだけを管理する。Controlに汎用container socketを渡さない。固定argvとstdinの長さ付きデータで入力を渡し、code・inputsをshell、argv、環境変数、labelに埋め込まない。

AMDのUbuntu 24.04ベースROCm PyTorch imageを候補とし、gfx1151対応を検証後、baseと最終imageの両digest、Python・全package・runner版をmanifestに記録する。今回は取得・buildをしていないためdigestと実際のpackage版は未確定。pip実行file除去、read-only、network noneで通常の実行中installを防ぐ。任意Pythonが入力からmoduleを生成することまで禁止できるとは説明しない。

runnerはinputs、report、作業directory、Agg、result収集を用意する小さなbootstrap。任意Pythonと同居するrunnerは改変可能なので、時間・メモリ・受信byte・件数の信頼境界はhost側Supervisorに置く。result/progress/artifactのframeはすべて信頼しないデータとして型・長さ・件数を検査する。host pathやcommandを解釈する機能を持たせず、frameだけで完了を確定しない。

result未定義はnull。NumPy・pandas・torch値はcontainer内でJSON互換に変換し、非有限数はnull、大きな整数は精度を保つ10進文字列、非対応objectは上限付きrepr。循環・深さ・要素数・repr実行も制限し、value上限超過はoutput_exceeded。hostはJSONだけを読み、pickle・任意Python object・torch checkpointをdeserializeしない。

成果物は作業領域のartifacts directoryに保存したPNG/SVG/CSV/JSONと、終了時に開いているmatplotlib図のPNG。自動作図回収も件数・byte・時間上限の対象。tmpfsはcontainer除去で失われるため、runner終了前に成果物byteを長さ付きstreamでexportし、hostが上限付き一時storeに受ける。除去後のtmpfs回収、任意tar展開、host directory mountを前提にしない。hostは保存名を生成し、nameをpathに使わず、MIMEを検査する。成功・清掃完了後に結果を原子的公開し、失敗・取消では一時storeを削除する。

SVGは初版ではattachment取得だけとし、直接inline描画しない。Content-Disposition・nosniffを設定し、表示UIでscript・外部参照を実行しない。job出力は認証された結果storeだけに保存する。HTTP access log、container log、trace、例外logにcode・inputs・結果・progress・tracebackを複写せず、jobId・分類・所要時間・使用量だけを記録する。

推論優先の調停とauto

computeは低優先laneとし、要求者によるpriority指定は認めない。active requestだけでなく、解決したruntimeのcontext/KV/slot、resident予約、保護期間、media実行、host RAM reserve、GPU telemetryから開始可否を決める。telemetry不明時は開始しない。CPU jobも共有RAM・CPUを使うため、GPU deviceがないことだけで推論に無影響とは扱わない。

  1. CPUはCPU laneと総予算が空くまでqueued。GPU backend未公開なら投入時503、有効だが競合中ならqueued/waiting_gpu。
  2. GPU開始は資源予約と実行権を原子的に確保してから行い、推論admissionと同じ排他境界で判定する。isOccupiedのpollだけで開始しない。
  3. 計算のためにLLM・TTS・ASR・画像・3DのProviderを停止、置換、unloadしない。mediaの開始・切替も共通予約と競合判定する。
  4. 高優先推論が来たら低優先GPU計算を中断して枠を回収する。failed/preemptedとし、途中再開・自動再投入は行わない。
  5. GPU kernelが即座に中断できるとは仮定しない。停止・解放時間を測定し、長いkernelやdriver異常で推論SLOを守れなければGPU公開の条件を満たさない。

autoは開始時点でGPU laneと安全な予算が空いていればGPU、そうでなければCPU。import文を解析してGPU要否を推測しない。動的importやaliasでは判定できないためである。CPUに決めた後でGPUに移行したり、失敗後にCPUで自動再実行したりしない。GPU必須コードはgpu、CPUで十分な処理はcpuを明示する。GPU未公開の初版ではautoもCPU。resolvedAcceleratorで実行先を確認できる。

同じGPU・メモリ帯域を使う任意計算に「既存推論の遅延増加ゼロ」は保証しない。厳密に無影響が必要なら別host/GPUが必要。共有hostでは同条件baselineとLLM TTFT・tokens/sec、TTS初回音声時間、ASR遅延を比較する。profileごとのSLO、許容変化、回収時間を公開条件として先に定め、未測定の状態でGPU併用を検証済みとしない。

EumenesとMCPのtool契約

EumenesはHTTP clientを使うnative toolを先行し、必要なclientに同じschemaのMCP adapterを追加する。MCPは最初はbackend内stdioを候補とし、remote公開が必要になった時点でStreamable HTTPと認証を設計する。Controlの管理BearerをMCP clientへ配布しない。adapter credentialの権限を共有できない利用者には任意コード実行を公開しない。

tool名案とHTTP APIへの対応
tool 入力 役割
compute_environment なし package・accelerator・上限取得。投入時はLARMが再検証。
python_submit code、inputs、timeoutSec、accelerator、requestKey jobIdを返す。requestKeyはEumenesの永続tool実行記録で生成し、同じ計算意図に固定。
python_status jobId status・progress・result/error。GUIはbackendでpollし、毎回LLMを起動しない。
python_artifact jobId、artifactId backendが認証付き取得を代行。PNGは対応client向けimage、他は安全なresource/添付。Bearer付きURLを返さない。
python_cancel jobId 取消専用API。完了競合でも完成結果を消さない。取消後の古い完了通知を採用しない。
python_delete jobId DELETEの取消・削除動作を明示し、破壊的操作として説明。

Eumenesの永続tool実行IDとjobIdを対応付け、会話再開後も追跡する。tool callの取消と受理済みjobの取消は区別する。structured outputにはjobId・status・数値/表・artifact metadataを返し、大量stdoutや画像base64をLLMに展開しない。code・progress・resultは外部データで、次のtool権限を与える指示として扱わない。MCP Tasks対応時はversion/capabilityを確認してjobIdへの対応を追加し、Job Storeを二重化しない。

calculateはLARM公開待ちにせずEumenes側で独立して着手できる。ただし未確認のQ1〜Q9を一括承認する意味ではない。最初は数値literal・括弧・許可した算術演算に限定し、decimal精度・丸め・ゼロ除算を明示する。token・桁数・指数・深さ・処理時間を制限し、JS eval、Python eval、任意関数、import、filesystem、networkを使わない。記号計算や学習はPython jobに送る。

実装順序と責務

  1. 契約とCPU版：schema、永続store、idempotency、取消・GC、fake backendによる状態競合検証、CPU Supervisor/runner、catalogを追加。
  2. CPU実機受入：rootless制限、隔離、OOM、timeout、fork、出力量、取消、再起動回復を検証。既存サービス操作が必要な導入・配備は具体的手順を用意して事前許可を得る。
  3. Eumenes接続：native toolと永続ジョブ追跡、必要ならMCP adapterを追加。CPUだけでもtoolチェーンを利用可能にする。
  4. GPU試験：gfx1151、既定seccomp、メモリ課金、dmem/GTT、停止時間、推論SLOを検証し、条件を満たしたGPU版だけ公開。

添付案との差分と引き渡し

  • 非同期HTTP APIを本体とし、MCP adapterとEumenes tool mappingを追加。
  • 取消・削除競合を避けるPOST cancelを追加提案。DELETEの複合動作は維持。
  • GPUはCPU版と分けて公開。autoは開始時の安全な空きで選択し、import解析はしない。
  • HTTP共通エラー、待機期限・容量、value/結果byte定義、保存quota、削除後idempotencyを補完。
  • preempted・queue_timeoutと実行先・環境版・取消受付fieldを追加提案。
  • GPU 24 GiBとmemory 16 GiBの関係、dmem検証、監視killの限界、推論SLOを公開条件に追加。
  • host mountなしの成果物export、追加tmpfs、container log無効化、runnerを信頼境界にしない設計を追加。

Eumenes §4の置換用「確定仕様」は、schema・OpenAPI・client・契約試験が揃った時点で引き渡す。その際にcatalogの実URL、image digest/package版、統合メモリ課金、seccomp、受入結果を併記する。本書のAPIと値を利用可能な本番契約に置き換えてはいない。
