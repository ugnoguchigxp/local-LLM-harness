ContextStill Context Window tier選択の再評価と実装

ContextStill向けに64K、64K、256Kを一つのllama-serverへ固定配置する案を、現行の LARM、実機binary、workload証跡に照らして再評価した。結論は固定3 slot案を不採用とし、 ContextStillが最終promptをtokenizeして、受入済みの64Kまたは128K Providerのうち最小のtierを 明示選択する。125,000 input tokenを超える要求は、受入済み256K Providerが追加されるまでfail closedとする。

判断根拠

添付案と現行実装の照合
観点 確認結果 判断
ContextStill実要求 完了証跡のpromptは1,661 token、既存出力上限は4,000 token 通常jobに256K予約は不要。64Kに十分収まる。
現行標準Provider Qwen3.8-27B Q4_0 + MTP、131,072 context、125,000 input受入済み 64Kを超える実要求の昇格先は128Kとする。
256K証跡 機能試験は成功したが、長文試験は104K token超で運用停止。現行daemonも131,072設定。 production tierとしては未受入。model名も公開しない。
llama.cpp build 10655 --parallel、--kv-unified、--cont-batchingはあるが、--kv-unified-per-slotはない。 64K / 64K / 256Kの非対称なslot物理上限を添付コマンドでは保証できない。
TTFTとmemory ContextStillはbackground優先度1000。128GB unified memory上でresident、ASR、TTSも共存する。 全要求に384K KVを常時確保せず、最小tierだけをswap group内でloadする。

選択contract

promptTokensはsystem prompt、tool schema、会話履歴、検索結果、現在入力を、実modelと同じ tokenizerで数えた合計である。consumerは送信直前の最終bodyから次を計算する。 

requiredTokens = promptTokens + requestedMaxOutputTokens + safetyMarginTokens
公開するContextStill tier
Profile Model window output reserve safety margin 最大input
contextstill-background-64k qwen-contextstill-64k 65,536 4,096 1,976 59,464
contextstill-background-128k qwen-contextstill-128k 131,072 4,096 1,976 125,000
  1. requestedMaxOutputTokensが4,096を超える場合は不適合とする。
  2. requiredTokens <= 65,536なら64Kを選ぶ。
  3. それ以外でrequiredTokens <= 131,072なら128Kを選ぶ。
  4. それ以外は必要量と最大許容量を返して失敗する。暗黙truncateはしない。

LARM coreのmatchAgentProfileContextWindowはこの判定を型付きで実装し、設定された候補のうち 完全なrequest budgetを収容する最小windowを返す。token数そのものの算出は、最終promptを所有する ContextStillの責務である。

runtimeとdaemon所有権

64K routeはqwen-contextstill-64k、128K routeはqwen-worker-fastだけを候補に持つ。両者は同じQwen3.8-27B Q4_0 main weight、同じQ4_0 MTP、batch設定、KV型を使い、Context Windowだけを変える。 fallbackは置かないため、128K要求が64K backendへ暗黙降格しない。両runtimeは既存の qwen-worker-slot swap groupを共有し、同時にloadされない。したがって新しいdaemon lifecycle、session-to-slot mapping、KVを正本とする会話状態は追加しない。

生成される主要起動引数 
# 64K tier
llama-server ... --ctx-size 65536 --parallel 1 --cache-type-k q4_0 --cache-type-v q4_0 ...

# 128K tier
llama-server ... --ctx-size 131072 --parallel 1 --batch-size 2048 --ubatch-size 256 \
  --cache-type-k q4_0 --cache-type-v q4_0 ...

ContextStill移行

  1. 最終Chat Completions bodyを組み立てた後、Qwen tokenizerでprompt tokenを数える。
  2. 上記contractでqwen-contextstill-64kまたはqwen-contextstill-128kを選ぶ。
  3. /v1/modelsに選択modelがなければjob failureへ数えず、Provider unavailableとして再試行する。
  4. 選択modelを通常の/v1/chat/completionsへ送る。既存のpriority 1000とqueue契約を維持する。
  5. 125,000 inputを超えたら履歴削除をせず、明示的な圧縮policyまたは将来の受入済みlong tierへ委ねる。

既存のcontextstill-backgroundとqwen-agent-workerは破壊的に改名せず互換用に残す。 新規consumerだけが明示tierへ移行する。

検証範囲と残課題

unit testは1,661 + 4,000 tokenが64Kを選ぶこと、59,464 inputの境界、64K超の128K昇格、 125,000超とoutput reserve超過の拒否、各routeが単一candidateであること、両runtimeが同じswap groupに属することを検証する。巨大modelを使う新規benchmarkは設定変更をliveへ配備していないため 実行しない。256K tierを追加する前に、同一artifactとMTPで125K超の完走、TTFT、peak memory、 ContextStill job品質を記録し、専用releaseとfail-closed routeを追加する必要がある。
