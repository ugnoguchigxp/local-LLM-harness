実行topology

追加27Bへtaskを割り当てると、Resident 27Bとworker 27Bの二つのinstanceで並行処理できます。 35B要求はworker slot内の未使用workerだけを置き換え、Resident 27Bを停止しません。

worker routeはすべてexplicitOnlyです。35Bを明示しない要求は35Bを起動しません。 allowFallback: trueの場合だけ、workerが利用不能な要求をResidentへ戻せます。

Swap-aware admission

  • 同じswapGroupのHOTなpeerにactive Allocationがなければ、そのmemoryを回収可能として評価します。
  • active Allocationがあるpeerは通常preemptしません。ただし優先度3000以上のforeground Allocationは、競合する低優先Allocationをforeground_preemptedで停止します。 既定の明示Allocationは resource_exhaustedで拒否し、動的ProviderのcapacityPolicy: wait要求は 優先度付き待機列へ入れ、peer解放後に昇格します。
  • foreground解放後300秒は、同じswap groupの別Providerへの切替を保留します。
  • 一つのAllocationから同じswap groupの二つのRuntimeを同時要求した場合は拒否します。
  • Runtime mutationまたはlifecycle transition中のpeerがある場合も新しいgroup memberを起動しません。
  • Residentと音声Runtimeのmemory floor、host reserve、live telemetryを常に先に確保します。

35B artifacts

ornith15-35b-qualityはOrnith公式のQ5_K_M GGUFです。 25,347,532,544 bytesで、revisionとSHA-256を固定します。stock llama.cppで実行し、MTPとngramを 無効、K/V cacheをともにq8_0としたplain decodeをllm-35bのprimaryに します。

ornith15-35b-speedはOrnith-1.5-35B-A3Bのgfx1151専用 Q4_0_ROCMFP4_STRIX_LEAN GGUFです。19,052,439,552 bytesで、artifact revisionとSHA-256を固定します。元checkpointのMTP headを内包しますが、実測でplainより遅いため MTPは起動contractで無効です。ngram-modも同一requestの反復で大幅な速度低下を 確認したため無効にし、plain decodeを採用します。V cacheのturbo4はfull PPLが 208.89へ破綻したため使用せず、K/Vともにq8_0です。q38rocm prompt cacheのsequence再利用assertを回避するため、prompt cacheとidle-slot cacheも無効です。配布物とspeculative decodingの比較根拠はOrnith-1.5-35B-A3B 配布物選定に固定します。

qwen36-35b-speedはQwen3.6-35B-A3Bの UD-Q4_K_M GGUFです。取得元revision、22,134,528,992 bytes、SHA-256を deploy/local-node/models.yamlへ固定し、qwen36-35b-current releaseだけが参照します。 request bodyから別URL、path、quantizationを指定することはできません。

Live適用条件

  1. 固定artifactをrepository外のmodel storeへstageし、sizeとSHA-256を検証する。
  2. worker Allocationがないことを確認してllama-swap設定を反映する。
  3. Resident PIDとhealthを維持したまま35Bを起動し、streaming completionを確認する。
  4. 35B解放後に追加27Bを要求し、35Bが停止して27B workerがreadyになることを確認する。
  5. Residentとworkerへ別Allocationを作り、二つの27B instanceで並行requestを完了する。
  6. startup、TTFB、total、memory peakを実測し、一般256K workerと64K Agent workerのadmission estimateを個別に校正する。

Artifact未stageのexisting-only要求は起動に失敗します。 allow-listedは管理credential付きでstagingを開始できますが、19から26 GB級の初回downloadを含むため即時経路とは扱いません。
