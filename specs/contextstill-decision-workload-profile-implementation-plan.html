ContextStill Decision Workload Profile 実装計画

本計画は、ContextStill／DeepStillの探索workloadだけに動的なDecision cascadeを追加し、 通常会話、SAAA、NightWorker、既存ContextStill background処理には影響させないための実装順序を定義する。 LARMにはmodel lifecycleとresource controlだけを追加し、探索の意味判断、confidence escalation、 budget、branch終了はconsumer側へ残す。FunctionGemma 270Mはshadowから開始し、Qwen 3.5 2Bも host実測とquality gateを通過するまでproduction判断へ使わない。

実装後の到達状態

  1. 探索開始時だけ、明示指定のcontextstill-explore Agent Profileから TTL 300秒のAgent Connectionを作成する。
  2. 同じconnectionからdecision-fast、decision-default、 llm-generalの三つの公開providerを取得する。
  3. deterministic pre-checkの後、FunctionGemma 270M、Qwen 3.5 2B、resident Qwen 27Bの順に、 consumerが明示的にescalateする。LARM route fallbackに意味判断を持たせない。
  4. 探索中はSession Managerがconnectionをrenewし、終了時にreleaseする。heartbeat断でもexpiryし、 Qwen 3.5 2Bはllama-swapのidle TTL後にunload可能になる。
  5. small modelが失敗、timeout、不正出力、未校正、または未昇格でも、既存探索経路は継続する。 small model availabilityを探索可否の条件にしない。
  6. shadow outcomeを、bounded ML Compute MCPの評価、校正、ranking、clusteringへ再利用できる。 MCPはLARM schedulerやper-candidate hot pathを置換しない。

Agent Connection request

数分を超える探索ではwithAgentConnectionへrenew機能がないため、専用Session Managerが create、wait、claim、renew、releaseを順に管理する。renewはTTLの3分の1を基準にjitterを加え、 同一sessionに複数timerを作らない。終了、cancel、例外ではfresh bounded requestでreleaseを試み、 release失敗時もexpiryを最後の安全網にする。

    schedulingPriority: 1000

        capability: llm.decision.fast
        route: llm-decision-fast
        publicModel: decision-fast
        readiness: llm-inference
      - name: decision-default
        capability: llm.decision.default
        route: llm-decision-default
        publicModel: decision-default
        readiness: llm-inference
      - name: llm-general

三つのrouteはexplicitOnly: trueかつprimary一件だけにする。tier変更をroute fallbackで 隠さず、evaluation recordへ実際に選んだtierを残す。legacy profiles.yamlは変更しない。

Decision v1

{
  "schemaVersion": "contextstill-explore-decision.v1",
  "action": "fetch",
  "confidence": 0.91,
  "novelty": 0.81,
  "relevance": 0.92,
  "expectedKnowledgeGain": 0.77,
  "reasonCode": "high_value_source"
}
  • actionはskip、fetch、extract、expand、 requery、escalateだけにする。
  • JSON Schema constrained decodingに加え、duplicate keyを拒否できるparserとstrict Zod schemaを使う。 未知field、trailing data、NaN、Infinity、0〜1外、version不一致を拒否する。
  • thinking: false、temperature 0、input 4K、output 128 tokenから開始する。 live検証で48 tokenではreasoningだけで空contentになったため、原案の64 tokenは初期値にしない。
  • HTTP非2xx、timeout、空content、finish_reason=length、schema不正、未校正actionは すべて明示的なescalation reasonへ正規化する。
  • modelのconfidenceは直接実行thresholdにしない。action別calibration artifactとpolicy versionを risk gateへ入力する。

実装work package

repository全体のMilestone 22〜28とは番号を共有せず、本機能内のWP0〜WP8として管理する。 各WPはexit criteriaを満たすまで次のproduction段階へ進めない。

WP0: ownership、baseline、feature flag

目的: repositoryをまたぐcontractとrollback authorityを最初に固定する。

  • ContextStill／DeepStill source repositoryとtest commandを特定し、module対応表を記録する。
  • consumerにoff、shadow、limited、activeの 一つのversioned feature flagを定義する。既定値はoffにする。
  • LARM、consumer、ML serviceそれぞれのownerと、promotion／rollback実行者を決める。
  • 現行ContextStillのaccuracy、fetch数、27B call数、latency、resource SLOを固定datasetでbaseline化する。

Exit: source位置、owner、baseline artifact digest、feature flag既定値、rollback責任者が review済みである。hostやproduction configは変更しない。

WP1: consumer Decision contractとreplay harness

目的: modelを増やす前に、判断の意味と失敗動作をcodeで固定する。

  • 論理module decision-contractへJSON Schema、strict validator、duplicate-key rejection、 canonical serializationを実装する。
  • decision-policyへaction別risk class、calibration lookup、escalation reason、 deterministic termination state machineを実装する。
  • decision-clientへprovider adapter、timeout、non-thinking request、finish reason確認、 tool-call／content normalizationを実装する。
  • decision-sessionへAgent Connection lifecycleとTTL/3 heartbeatを実装する。 create／waitに失敗した場合は既存探索経路へ戻す。
  • decision-evaluation-storeへredacted append-only recordとschema migrationを実装する。 Prometheus labelへtrace IDやcandidate IDを入れない。
  • 現行27Bまたはfixtureをproviderにしたreplay testを作り、model processなしでも全分岐を検証する。

Exit: invalid JSON、duplicate key、unknown enum、length終了、timeout、cancel、renew失敗、 double releaseを含むunit／integration testが成功し、shadowではmodel actionが一件もexecutorへ 到達しない。

WP2: LARM catalog scaffold

目的:既存contractだけで三providerのbindingを表現する。

  • config/local-node/runtimes.yamlへfunctiongemma-decisionと qwen35-decisionを追加する。capabilityはそれぞれllm.decision.fastと llm.decision.defaultにする。
  • config/local-node/routes.yamlへ三つのexplicit-only routeを追加する。 すべてprimary一件で、decision tier間fallbackは置かない。
  • config/local-node/agent-connections.yamlへcontextstill-exploreを追加する。 default profileと既存profileは変更しない。
  • config/local-node/profiles.yamlは意図的に変更しないことをreview checklistへ残す。
  • registry、Agent Connection catalog、explicit selection、public model、atomic preparationのtestを追加する。

Exit: config parseとAgent Profile list／create contract testが成功し、既存default route、 resident Qwen 27B、profile revisionが意図せず変わっていない。artifact未配置の段階ではproductionへactivateしない。

WP3: model artifactと隔離runtime staging

目的: identityを固定したmodelをproduction trafficから隔離して測る。

  1. operatorがFunctionGemmaとQwen 3.5 2Bの配布元、revision、license、量子化を選び、termsを受諾する。 GGUFごとにbytesとSHA-256を記録する。weightをGitへ入れない。
  2. deploy/local-node/models.yamlへartifact、deploy/local-node/releases.yamlへ immutable runtime releaseを追加する。checksum未確定のplaceholderはmergeしない。
  3. FunctionGemmaはCPU専用systemd providerとして4K context、parallel 1、loopback bindで起動する。 service unit、installerのunit／directory allowlist、install testを更新する。
  4. Qwen 3.5 2Bはconfig/local-node/llama-swap.yamlへ独立model IDとして追加し、 4Kから開始する。既存qwen-worker-slotへ入れず、27Bとの同時常駐を許す。
  5. 未使用port、read-only model path、cache path、cgroup／systemd memory制約をpreflightで確認する。 port番号はhost inventory後に確定し、本文の推測値で固定しない。
  6. semantic canaryを追加し、JSON Schema、native tool-call、thinking: false、128 token上限、 malformed output、cold／warm startを固定prompt setで検証する。

Exit: artifact identity、license evidence、provider config revision、cold／warm latency、 peak RSS／UMA、schema-valid率が外部evidence artifactとして保存され、認証済みexplicit route以外から到達できない。

WP4: resource interferenceと条件付きexecution domain

目的: UMA hostで必要な範囲だけdecode concurrencyを制御する。

  1. 27B単独、2B単独、27B＋2B同時の固定seed benchmarkを同じcommitとconfig revisionで採取する。
  2. p50／p95／p99、TTFB、prefill、decode、system available memory、accelerator／UMA、GPU busy、 token throughput、429、queue depthを比較する。
  3. 同時実行が既存SLOを破る、memory floorを破る、または単独比でp95 latency／throughputを10%以上 悪化させる場合だけexecutionDomain実装へ進む。
  4. 条件を満たさない場合はruntime別Execution Gateを維持し、不要なqueue latencyを増やさない。
execution domainが必要な場合のLARM変更
  • packages/core/src/schema.tsのruntime resourcesへoptional executionDomainを追加する。
  • packages/core/src/registry.tsで、同じdomainが同一nodeに属し、 maxConcurrentRequests、queue limit、timeoutを共有することを検証する。
  • apps/daemon/src/execution-gate.tsは内部queue keyを executionDomain ?? runtime.idにする。QueueEntryには実runtime IDを保持し、event相関を失わない。
  • tryAcquireを含むsemantic readinessも同じdomainを尊重する。 priority、cancel、timeout、drainの既存意味は変えない。
  • apps/daemon/src/metrics.tsへ有限cardinalityのexecution_domain label／gaugeを追加する。
  • cross-runtime FIFO、priority、release、policy mismatch、probe busy、metricsをtestする。

Exit:実測結果と分岐判断を記録し、どちらの構成でもresident 27B、ASR、TTSの既存SLOと memory floorを満たす。FunctionGemma CPU laneはUMA LLM execution domainへ入れない。

WP5: counterfactual shadow

目的: 情報を捨てずにsmall tierの精度とcostを測る。

  • shadowをsource type、language、topic、新旧knowledge、duplicate難度で層化して開始する。
  • fast／defaultの提案に関係なく、baseline／teacherの判断と実際のfetch／extractを実行する。 small modelのskipでもcounterfactual outcomeを失わない。
  • recordへprofile revision、schema／policy version、public model、runtime release、config revision、 finish reason、latency、escalation、teacher action、actual knowledge gainを記録する。
  • raw本文は既存の暗号化・短期auditへ限定し、長期datasetはhash、redaction、provenance、retention、 opt-outを持つ。
  • profile準備失敗、connection expiry、runtime crash、429、timeout、daemon epoch変更をfault injectionする。

Exit:少なくともvaluable candidate 600件を含む固定holdoutができ、schema-valid率、 false skip、valuable-source recall、escalation、cost、tail latencyをtier／stratum別に再計算できる。

WP6: bounded ML Compute MCP

目的: shadow datasetから再現可能な評価／校正artifactを作る。

  • LARM repositoryとは別のserviceとして、rank_candidates、 cluster_candidates、calibrate_decisions、 evaluate_cascadeを実装する。
  • Tool inputはdataset handle、algorithm enum、fixed seed、bounded rows／dimension／bytes／timeだけを受ける。 outputはJSON Schema、artifact digest、library version、metrics、warningを持つ。
  • datasetとreportはMCP Resourcesとしてread-only公開し、filesystem path、URL、SQLを直接受け付けない。
  • auth、principal、quota、concurrency、timeout、memory／thread cgroup、auditを実装する。 modelがresource limitを上書きできないようにする。
  • 長時間batchはclient対応時だけTasks extensionを使い、未対応client向けの同期bounded subsetを維持する。
  • novelty featureをonlineで使う場合は同じpure libraryまたはtyped internal HTTPを呼び、 per-candidate処理をMCP round tripへ依存させない。

Exit:同じdataset handle、policy、seedから同一digestのreportを再生成でき、unauthorized、 over-limit、timeout、cancel、malformed inputがfail closedになる。Phase 1ではCPU中心とし、LARMへ MCP protocolやml.compute runtimeを追加しない。

WP7: limited activationとpromotion

目的: actionの非対称riskに従い、権限を小さく段階昇格する。

  1. fast tierはfetch、extract、expand、 requeryの低risk positive actionだけをlimitedで受理する。
  2. default tierのskipは専用gateを通過するまでgeneral／既存codeへescalateする。 fast tierへproduction skip権限を与えない。
  3. 1%、10%、50%、100%の層化canaryを順に行う。各段階でquality、tail latency、resource、 error budgetを再評価し、自動昇格はしない。
  4. 各段階でshadow control groupを残し、policy driftとsource distribution shiftを検出する。

Exit:後述のpromotion gateを満たし、operator review、rollback rehearsal、release evidenceを 完了したactionだけをactiveにする。branch終了は最後までdeterministic codeが所有する。

WP8: optional FunctionGemma fine-tune

目的: provenance付きdatasetが十分な場合だけdomain tuningの価値を測る。

  • training、calibration、固定holdoutをentity／topic／timeで分離し、data leakageを検査する。
  • baseとfine-tuned modelを同じprompt、parser、policy、resource gateで比較する。
  • model artifact、training code、dataset digest、hyperparameter、licenseを再現可能に記録する。
  • fine-tune結果にもWP7と同じpromotion gateを適用し、改善がなければbase shadowへ戻す。

Exit: qualityまたはcostに統計的かつ運用上意味のある改善がある場合だけ新release候補にする。 このWPはWP7をblockしない。

rolloutとrollback

rollout順

  1. repository testだけをmergeし、feature flagはoffのままにする。
  2. artifactをstagingし、explicit routeの認証済みsemantic canaryだけを実行する。
  3. consumerをshadowにし、small tierの結果を実行しない。
  4. promotion gate後に低risk positive actionを1%から限定受理する。
  5. 各段階をreviewし、skipは別の明示承認後にだけ昇格する。

rollback順

  1. consumer feature flagをoffへ戻し、新規small-tier decision受付を止める。
  2. active Agent Connectionをbest-effort releaseし、失敗時はTTL expiryを待つ。
  3. Qwen 3.5 2Bをidle TTLでunloadさせる。resident 27Bと既存routeは変更しない。
  4. LARM config／runtime releaseを直前の署名済みreleaseへ戻す。
  5. 必要な場合だけFunctionGemma unitを停止し、evidenceとfailure reasonを保存する。

rollbackはdatasetを削除しない。新規writeを停止し、保持policyに従って隔離する。 model process停止より先にconsumer flagを戻すことで、途中のexplorationを壊さない。

推奨PR分割

  1. Consumer PR A: Decision v1、validator、policy、fixture replay。flagはoff。
  2. LARM PR A: runtime／route／Agent Profile catalogとcontract test。host未変更。
  3. LARM PR B: verified artifact／release、provider unit、installer、semantic canary。
  4. Evidence change: operator staging、benchmark、干渉判定。source commitと分離して保存。
  5. LARM PR C: 干渉gateを満たした場合だけexecution domain。満たさなければ作らない。
  6. Consumer PR B: Session Manager、shadow recorder、fault integration。flagはshadow。
  7. ML service PR A: bounded evaluator／calibrator、MCP Tools／Resources、auth／quota。
  8. Policy PR: signed calibration digestとlimited action allowlist。operator承認必須。

config、binary identity、live evidence、semantic policyを一つのPRへ混ぜない。各PRは単独rollback可能にし、 model weight、benchmark raw data、generated reportをsource repositoryへcommitしない。

Definition of Done

  1. 探索workload以外では新providerが選択されず、既存default modelはresident Qwen 3.8 27Bのままである。
  2. 探索ごとにAgent Connectionを作成、renew、releaseでき、heartbeat断でexpiryする。
  3. small tier停止時も既存ContextStill探索が継続し、global mode変更を必要としない。
  4. invalid／uncalibrated output、model出力によるbranch終了、任意tool実行がすべて拒否される。
  5. artifact、runtime release、profile、schema、policy、calibration、dataset revisionを相関できる。
  6. promotion gateとfault injectionを通過し、同じreleaseに対するrollback rehearsalが成功する。
  7. ML MCPが停止してもonline探索は継続し、同じinputから再現可能なbounded reportを返せる。
  8. LARM変更ごとにbun run check、文書変更ごとにbun run docs:checkが成功する。

最初に着手する順序

  1. ContextStill／DeepStill repositoryをworkspaceへ配置し、WP0のmodule／owner対応表を確定する。
  2. Decision v1とreplay fixtureをconsumer側へ実装し、27Bだけでrecord contractを作る。
  3. model artifact候補のlicense、revision、GGUF、SHA-256をoperatorが確定する。
  4. LARM PR Aを作り、未activateのcatalog contractをtestする。
  5. 隔離runtimeをstagingし、4K／8K、CPU／Vulkan、tool-call／JSON Schemaを測る。
  6. resource干渉の結果からexecution domainの要否を決め、shadowへ進む。

したがって最初のcode変更はmodel downloadやscheduler拡張ではなく、consumerのDecision contractと replay harnessである。ここを先に固定すれば、FunctionGemma、Qwen 3.5 2B、将来のfine-tuned modelを 同じgateで比較できる。
