調査制約

結論

  1. 300秒停止の直接原因はornith-generalのsemantic probeが provider_busyになり続けたことである。モデル未ロード、メモリ不足、Qwen 2Bの起動失敗ではない。
  2. SAAAはASR、backchannel、embedding、LLM、TTSの5 Providerを一つのAllocationと Connectionへ束ねる。Connectionは5 Providerすべてのsemantic probeが成功するまで probingのままで、credentialを一つもclaimできない。この全体ready gateが、既にreadyな Qwen 2Bの単体利用をOrnithの空き待ちへ結合している。
  3. 失敗回のQwen 2B probeは約80から187 msで繰り返し成功した。Ornithは常駐かつhealth正常だったが、 maxConcurrentRequests: 1の実行slotを長い通常推論が連続して占有し、non-queuing probeが 毎秒拒否された。
  4. qwen3.5-2b-fast-responseの直接Chat Completionsが model_not_foundとなるのは現行設定どおりである。このmodelは publishModel: falseで、Agent Connectionのclaimから返された短期credential専用である。
  5. 物理リソース枯渇は観測されなかった。調査時のMemAvailableは約88 GiBで、Ornithは resident processとして稼働し、Qwen 2BはSAAA Allocationでloadされた後、Connection解放に伴い停止した。 競合していたのは主にOrnithの実行slotと、Qwen 2Bの単一Allocation枠である。

失敗回の時系列

  1. 09:59:59.174 JST、公開model coding-defaultの通常推論が ornith-generalで開始した。
  2. 10:00:13.373、SAAAの5 Provider Allocationを作成した。10:00:14.381にConnection createは HTTP 202を返し、10:00:15.682にAllocation自体はreadyとなった。起動待ちは約2.3秒である。
  3. 10:00:17.020以降、Qwen 2B probeは成功した一方、Ornith probeは毎秒 probe_busyとなった。
  4. 最初のOrnith通常推論は10:02:46.649に完了したが、10:02:46.684に次の通常推論が開始し、 空き時間は約35 msしかなかった。1秒pollのsemantic probeはこの間にslotを取得できなかった。
  5. 10:05:11.917、SAAAがstartup timeout後にConnectionをDELETEし、10:05:11.920にHTTP 204で解放した。 Allocation作成から解放までは約298.5秒だった。二本目のOrnith通常推論はその後の10:05:39.363に完了した。

成功回では、Ornithの通常推論が09:56:58.619に完了し、09:57:00.949に同じSAAA Connectionをclaim、 09:57:01.000からQwen 2Bを実行して09:57:02.274にHTTP 200で完了した。次のConnectionも即時readyとなり、 Ornith推論が成功した。モデルの成否が不安定なのではなく、probe時点でOrnith slotが空くかどうかが差である。

コード上の発生機構

  • Agent Connection healthはProfile内Providerを順にprobeし、every(provider.ready)だけを aggregate readyとする。
  • semantic readinessはBUSYかつ10秒以内の成功cacheがない場合、通常queueへ入らず provider_busyを返す。失敗cacheは1秒なので、Connection background loopは毎秒同じ判定を繰り返す。
  • 初回全Provider成功まではConnectionがprobingからreadyへ遷移せず、claimは connection_not_readyとなる。既定ready deadlineは300秒である。
  • Qwen 2BはSAAA ConnectionのAllocationがmaxConcurrentAllocations: 1を保持するため、同じruntimeを 別の直接model requestや単体Connectionから使う要求も待機する。全体ready待ちがQwen側の個別経路も占有する。

再現手順

  1. coding-defaultへ300秒近く継続するChat Completionsを開始し、 ornith-generalの唯一の実行slotを占有する。
  2. その間にprofile: "SAAA"、audience: "saaa-desktop"、 deploymentPolicy: "existing-only"でAgent Connectionを作る。
  3. Connection resourceをpollする。Allocationはreadyになるが、公開phaseは probingに留まる。
  4. Connection healthを確認する。backchannel、ASR、embedding、TTSはreadyで、LLMだけが reason: "provider_busy"となる。
  5. Ornithの通常推論を切れ目なく継続すると、SAAA側の300秒上限で larm_startup_timeoutとなり、DELETEでAllocationが解放される。

LARM側で必要な修正

  1. 優先: Agent Connection createへProfile内Providerの明示的なsubset選択を追加する。 省略時は従来どおり全Providerとし、例えばproviders: ["backchannel"]または providers: ["llm"]なら、そのProviderだけをallocate、probe、claimする。 selector SAAAと保存済み設定は変更せず、単体テストだけがsubsetを要求できる形にする。
  2. subsetはProfileに存在するProvider名だけを許可し、空集合、重複、未知名をHTTP 400で拒否する。 idempotency hash、公開Connection response、claim、renew、release、priority、idle releaseにも選択集合を含める。
  3. Connectionのaggregate phaseと各Provider進捗を観測可能にする。GET responseで各Providerの reasonまたは最後のprobe結果を公開し、consumerが単なるprobingから provider_busy、load中、contract mismatchを区別できるようにする。
  4. BUSY時のsemantic保証は別途見直す。固定Bindingで直近の実推論成功とbackend healthが確認できる場合に、 10秒cache失効だけで初回Connectionを300秒阻害すべきかを再設計する。ただし、古い成功を無期限にready扱いする 変更は故障を隠すため、subset対応とは分離し、最大ageとbinding/release一致を明示する。
  5. qwen3.5-2b-fast-responseを通常model catalogへ安易に公開しない。現行のlifecycleと短期credential境界を 維持し、直接利用が必要ならsubset Agent Connection経由に統一する。

実装した是正

Agent Connection createへ任意のproviders fieldを追加した。selector SAAAと保存済み設定を維持したまま、要求されたProviderだけをallocate、probe、claimする。 field省略時は従来どおりProfile内の全Providerを対象とするため、既存の会話session契約は変わらない。

選択集合はProfile定義順へ正規化し、idempotency hashとsession scopeへ含める。同じclientでも backchannel-onlyとllm-onlyは別Connectionとして安全に併存できる。空集合、重複、8件超はrequest schemaで拒否し、Profileに存在しない名前は400 unknown_connection_providerで拒否する。

実機subset検証後に残ったOrnithの同一Provider競合も是正した。Ornithは maxConcurrentRequests: 1だけで複数Allocationを許していたため、優先度4000のSAAAと 優先度3000の通常OpenAI要求が同じ非プリエンプティブrequest queueへ入っていた。Qwen 3.8系と同じく maxConcurrentAllocations: 1を設定し、競合をrequest実行後ではなくAllocation admissionで 解決する。これによりSAAA Connection作成時に実行中の低優先度Allocationをlifecycle preemptionし、 SAAAが保持する間は新しい低優先度Allocationをwaitingに留める。

修正の受入条件

  • Ornithで300秒の通常推論中でも、SAAA backchannel-only Connectionがbounded時間でready、claim、Qwen 2B応答へ進む。
  • Qwen 2Bが利用中でも、SAAA llm-only ConnectionはQwenのAllocationやprobeを要求しない。
  • Provider subset省略時のSAAA会話sessionは従来どおり5 Provider atomic readyと一括claimを維持する。
  • 失敗時とcancel時は選択subsetのAllocationを必ずDELETEし、未claim Connectionを残さない。
  • direct model catalogでは非公開modelが引き続き404となり、claimed requestだけが短期credentialで成功する。

調査では保存済み設定、Agent Profile、Provider、systemd serviceを変更していない。進行中の利用を妨げないため、 追加のlive Connectionは作成せず、既存実行のHTTP event、allocation event、execution gate event、process、health、 memory状態を読み取り専用で照合した。
