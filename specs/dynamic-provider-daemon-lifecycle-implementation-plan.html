動的 Provider Daemon ライフサイクル実装計画

本計画は、LARMが全Agent ProfileのProvider Daemonをrevision単位で起動、共有、drain、停止し、 Provider設定変更の正常手順から手動systemctl restartを除くための実装順序を定義する。 設計上の不変条件は動的 Provider Daemon ライフサイクル仕様を正本とする。

2026-09-21時点で、canonical ProviderRevision、instance単位Backend互換API、single-flight Instance Manager、allocation／request／mutation参照、instance別idle停止、warm policy、claim credentialのgeneration固定、management inspection、全production runtimeのmanaged policy化を実装した。 個別systemd Providerはboot enableから外し、LARMが起動・停止する。llama-swap設定は検証済みreleaseから 安定pathへatomic publishし、supervisorは--watch-configで追跡する。

revision固有llama-swap model entryの新旧併存、systemd templateの動的port、durable instance journal、実machineでのconfig reload中request継続probeはrollout gateとして残る。これらが完了するまで、 「activeな旧revisionを保持したまま新revisionへ無停止移行」の完了を宣言しない。

現状と不足

現行実装からの差分
領域 現状 到達状態
Backend identity ensure(runtime)、stop(runtimeId) ensure(revision)、stop(instanceId)
Allocation binding runtimeとreleaseだけを固定 provider revision、instance、generation、endpointを固定
idle stop Control Plane全体で一つのtimer instanceごとの参照数とidle deadline
resident Backendがstart／stopを拒否 LARM管理下でwarm policyが最低instance数を指定

先に固定する不変条件

  1. 署名・検証済みrelease catalogにないlaunch specを実行しない。
  2. 公開APIからcommand、binary path、model path、systemd unit名を注入できない。
  3. Allocation作成時にProvider revisionを固定し、途中で新generationへ差し替えない。
  4. claimは全required Providerのsemantic readiness成功後だけcredentialを返す。
  5. 使用中instance、request終了処理中instance、mutation中instanceを停止しない。
  6. 新revisionの起動失敗は旧revisionの既存leaseへ影響させない。
  7. 公開claimのGateway URLとmodel aliasは維持し、内部instance endpointを公開しない。
  8. credential、launch environment、model pathをevent、journal、public inspectionへ出さない。

導入する型とBackend契約

type ProviderRevision = {
  runtimeId: string;
  runtimeRelease: string;
  revision: string;          // canonical SHA-256
  backend: "llama-swap" | "systemd";
  protocol: RuntimeProtocol;
  artifacts: string[];
  launchSpecDigest: string;
  resourceSpecDigest: string;
};

type ProviderInstance = {
  id: string;
  runtimeId: string;
  revision: string;
  generation: number;
  node: string;
  endpoint: string;
  backendEndpoint: string;
  status: RuntimeStatus;
  createdAt: string;
};

interface RuntimeBackend {
  listInstances(): Promise<ProviderInstanceHealth[]>;
  ensure(revision: ProviderRevision, signal?: AbortSignal): Promise<ProviderInstance>;
  health(instanceId: string): Promise<ProviderInstanceHealth>;
  drain(instanceId: string, signal?: AbortSignal): Promise<void>;
  stop(instanceId: string): Promise<void>;
}

AllocationBindingへproviderRevision、instanceId、 instanceGenerationを追加する。public responseでは既存の安全なfieldだけを返し、内部identityは management inspectionに限定する。

Work package

WP0: Characterizationとcontract固定

現行挙動を変更する前に、cold start、共有、release、idle stop、swap group、resident保護、daemon再起動時の orphan処理をcharacterization testへ固定する。

  • apps/daemon/src/controller.test.ts: instance共有とrelease競合の現状test
  • packages/backends/src/llama-swap.test.ts: load／unload APIとconfig reloadの実測fixture
  • packages/backends/src/systemd.test.ts: 固定unit lifecycleの現状test
  • llama-swapのconfig reloadがloaded modelを維持するかを実binaryでprobeする

config reloadでloaded modelが破棄される場合、同一supervisorでのhot reloadを採用せず、A/B supervisor generationを使う。WP0の結果をWP3開始条件とする。

WP1: Core schemaとrevision compiler

  • packages/core/src/schema.tsへmanaged lifecycleとwarm policyを追加する。
  • packages/core/src/releases.tsでruntime releaseとlaunch specからcanonical revisionを生成する。
  • packages/core/src/allocation.tsへinstance binding identityを追加する。
  • canonical JSON、sorted collection、digest domain separationを固定する。
policy:
  lifecycle: managed
  warm:
    minInstances: 1
    idleTtlSeconds: 60
  swapGroup: qwen-worker-slot

移行中は既存classを互換fieldとして維持し、residentをminInstances: 1、preferredをminInstances: 0へcompileする。現行の単一instance backendではminInstancesを0または1に制限する。

WP2: Provider Instance Manager

apps/daemonへProvider Instance Managerを追加し、Control Planeからprocess lifecycleを分離する。

  • revisionごとのsingle-flight ensure
  • allocation ref、active request ref、mutation ref、warm refの独立管理
  • instanceごとのidle timer
  • 停止直前のgenerationと参照数再検証
  • 複合Profile ensure失敗時の共有を壊さないrollback

apps/daemon/src/controller.tsの単一idleTimerとruntime ID単位の lifecycleReservationsは、instance ID単位の状態へ段階的に置換する。

WP3: llama-swap revision supervisor

  • source worktreeのllama-swap.yamlをruntime正本として直接参照しない。
  • 検証済みProviderRevisionから内部model entryを生成する。
  • 内部model IDを<runtime>-<revision-prefix>として衝突を防ぐ。
  • configを安全な専用directoryへatomic renameで公開する。
  • 新旧entryを併存させ、旧instanceの参照がゼロになってからunload・削除する。

第一候補は--watch-configを使用する一つのsupervisorである。WP0でgeneration分離を保証できない場合は、 loopback listen addressを分けたA/B supervisorをsystemd templateとして生成し、Gateway bindingで選択する。

WP4: systemd Provider instance化

  • larm-provider@.serviceまたはtransient unitのどちらかを一つに統一する。
  • instance specは/run/larm/provider-instances/配下のroot-ownedまたは厳格な専用権限で管理する。
  • loopback port allocatorへ予約、衝突検査、再起動後reconcileを実装する。
  • Provider commandはrelease catalogからだけ生成し、instance IDからshell commandを組み立てない。
  • stopはdrain完了、request refゼロ、generation一致後だけ実行する。

最初にqwen-ttsなど既存preferred systemd runtimeを移し、その後Qwen ASRとVOICEVOXを移す。 音声Profileの互換性を維持するため、公開model aliasとGateway endpointは変更しない。

WP5: Generation-aware GatewayとAgent Connection

  • Gateway resolveをAllocation bindingのinstance endpointへ固定する。
  • semantic readiness cache keyへrevisionとinstance generationを含める。
  • renewは同じinstance generationを維持し、再配置が必要なら新Connectionを要求させる。
  • claim credentialへ既存のallocation／provider scopeに加えてgeneration bindingを署名する。
  • release後は新requestを拒否し、進行中requestのterminal処理後にrequest refを解放する。

GET /v3/agent-profilesとclaimの公開shapeは変更しない。内部revisionをconsumerへ選択させない。

WP6: Reconcile、journal、障害復旧

  • instance ID、revision、endpoint、owner generationをdurable journalへ記録する。
  • 起動時にsupervisor／systemdの実instanceとjournalを照合する。
  • 未知instanceは即時killせず、drain状態を確認してbounded orphan cleanupする。
  • warm policy対象は再adoptし、それ以外の参照なしinstanceは停止する。
  • 破損journal、port再利用、半端なconfig generationはfail closedにする。

Agent Connectionはboot epochを跨いで復活させない。control plane再起動後は旧credentialを失効させつつ、 Provider instanceだけを安全に再発見または停止する。

WP7: Observabilityとoperator API

  • management inspectionへinstance ID、revision prefix、ref種別、idle deadline、warm reasonを追加する。
  • public healthには内部path、command、credentialを追加しない。
  • ensure、reuse、drain、stop、rollback、orphan cleanupをbounded labelでevent化する。
  • instance count、cold-start latency、idle-stop latency、revision overlapをmetric化する。

WP8: Production profile移行

  1. 明示canary Profileでllama-swap generation管理を有効化する。
  2. saaa-qwen38のQwenとLFMへ適用する。
  3. preferred systemd Providerへ適用する。
  4. Qwen ASRとVOICEVOXをmanaged warm policyへ移す。
  5. Qwen 3.8 resident defaultをminInstances: 1へ移す。
  6. 全runtime移行後にresident_protectedと旧class compilerを削除する。

実装レビューで追加した安全化

  • 共有single-flightではcallerごとにcancelを分離し、最後のwaiterだけがBackend起動を中断する。
  • 固定model ID／固定systemd unitを使う移行期間は、同一runtimeの異revision並行起動を revision_conflictとして拒否し、新世代の誤停止を防ぐ。
  • streaming requestの参照はResponse生成時ではなく、stream terminal callback後に解放する。
  • startup orphan reconcileはInstance Manager管理中runtimeをlegacy stopせず、request参照中のProviderを保護する。
  • tokenとallocationではinstance IDとgenerationの片側指定を拒否し、revisionとの結合を必須にする。
  • 停止失敗instanceは次回acquire時にcleanupを再試行し、失敗状態を再利用しない。

テスト計画

Unit／contract

  • 同一launch specは同じrevision、1 field変更は異なるrevisionになる。
  • 二つのAllocationが同じinstanceを共有し、片方のreleaseで停止しない。
  • 最後の参照解放だけがidle timerを開始する。
  • idle timer発火と新規Allocationの競合で使用中instanceを停止しない。
  • 新旧revisionを同じruntime IDで混同しない。
  • 複合Profileの部分失敗が共有instanceを停止しない。

Backend integration

  • llama-swapへ新entry追加中も旧model requestが完了する。
  • 旧entry unload後、旧endpointへrequestできない。
  • systemd instanceが動的portで起動、health、drain、stopする。
  • daemon crash後にinstanceを再発見し、重複起動しない。

Profile E2E

  • saaa-qwen38: Qwen、LFM、ASR、TTSをcoldから起動してclaimする。
  • LLM JSON／SSE、ASR、TTSを実行し、release後にpolicyどおり停止する。
  • ContextStill、decision、embedding、expressive TTSの既存Profileを回帰検証する。
  • credential失効、ログ非漏洩、old generation拒否を確認する。

Rolloutとrollback

  1. shadow inventoryで新Instance Managerの判断と現行controllerの判断を比較する。
  2. 明示canaryだけを新Backendへ送り、cold startとidle stop evidenceを保存する。
  3. SAAA Profileを有効化し、新旧revision overlapと音声経路を監視する。
  4. 各段階で24時間以上のorphan、unexpected stop、credential errorがゼロであることをgateにする。
  5. rollback時は新規Allocationを旧catalog generationへ戻し、新generationをdrainしてから停止する。

rollbackで使用中instanceを強制停止しない。旧supervisor configと旧systemd unitは、全新generation leaseが terminalになるまで削除しない。
