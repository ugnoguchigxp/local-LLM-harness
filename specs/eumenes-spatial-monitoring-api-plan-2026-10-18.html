JSON型・時刻・鮮度

合意用のJSON Schema Draft 2020-12はresponses.schema.json。 $defs.snapshot、$defs.events、$defs.errorが各response。現行OpenAPIの公開schemaではない。 合意後にCoreのZod schema・型・OpenAPI operation・SDKへ移し、文書との一致を試験する。 objectはadditionalProperties=false、必須計測keyを常に返す。nodes/GPU/Runtime/instance/モデル数は配列で表し固定しない。 不明なセンサー値は0にせず、value自体を持たない。要素配列の列挙失敗と、正常な空配列も区別する。

generatedAtは応答組立時刻、snapshotIdは観測viewの識別子、bootEpochはdaemon起動識別子。 センサー値の更新とGET応答生成は別であり、同じsnapshotIdを複数のgeneratedAtで返してよい。 日時はUTC、YYYY-MM-DDTHH:mm:ss.SSSZの正規ISO 8601。 intervalのdurationとuptime・保持期限・最古待ちは単調時計で測る。CPU counter減少・hotplug・計測時計不整合ではbaselineを再作成し、 最初の区間値はunavailable baseline_required。NTP変更はuptimeやcounterを巻き戻さない。 wall-clock不整合時は該当区間をunavailable clock_discontinuityとし、event順序はsequenceで確定する。 古い値のobservedAt・interval・lastAttemptを応答時刻に置き換えない。

coverageは観測経路ごとの取得条件で、since〜throughは連続して観測できた範囲を示す。 source停止・journal欠落後に回復した場合はsinceを新しい連続範囲の開始へ進め、 読者のwindow全体を覆わない範囲を完全履歴と解釈しない。eventStreamの保持欠落と、 sourceで観測できなかった欠落は別に検査する。snapshotとeventsは同一時刻のtransactionを保証せず、 値ごとのobservedAt、window、sequenceで解釈する。

メモリ集約の規則：host MemTotal/MemAvailable、VRAM、GTTは会計範囲が重複し得る。 GTT pool上限は物理メモリの追加容量ではない。初版は明示的に aggregationPolicy=do_not_add_host_vram_gttとし、 MemAvailable+VRAM空き+GTT空き、VRAM+GTTの「総空き」、GPU別GTTの合算を返さない。 process RSS、model見積り、Provider参照数も物理使用メモリへ足さない。 admissionで使っている従来accelerator合算値の意味変更は本変更に混ぜず、別の影響調査と合意対象とする。

前回取得以降の出来事と保持

既存ControlEventとGateway/media/controlの確定発生点から、本文を持たない監視event storeを daemon内に追加する。traceの有効/無効・採取率と独立し、GETが履歴の生成・削除・ackを起こさない。 eventはid、streamId、sequence、occurredAt、recordedAt、kind、target、workId、reasonCode、outcome、 fromState/toState、countDelta、observationInterval、source/sourceEventIdを持つ。使わない値はnull。 targetはRuntime/instance/node/GPU/daemon ID。workIdは監視用のopaque相関IDであり、client名や本文のdigestではない。 idはbootEpochと単調増加sequenceの組で、再送や複数読者の重複排除に使う。

イベントの意味と取得できる範囲
種別 発生元・意味 限界
daemon.started / readiness_changed 既存起動・Gateway transition。 startedとbootEpoch変更は再起動検出材料。強制終了前の最終eventは保証しない。
runtime.state_changed / model.load_* Observerの正式状態変化、明示されたload開始・完了・失敗。 load要求hookで短時間失敗を記録する。Observer差分だけで短時間処理を網羅しない。実測信号がないモデル状態は捏造しない。
request.started / queued / forwarded / terminal / rejected LARMを経由した利用者要求のphaseと確定結果。拒否は既存admission/executionコードを使う。 started/forwardedとterminalは別eventで、件数はterminalのみから集計。ExecutionGateのrelease completedは枠解放の意味で成功結果ではない。

host.oom_counter_changed / oom_kill_observed vmstat増分の検知、またはkernel明示logの観測。 counter増分とlogは別の証拠。同じOOMについて足さない。counter eventのoccurredAtは検知時刻で、厳密な発生時刻ではない。observationIntervalに前回から今回までの検知区間を返す。
gpu.*_observed kernel journalの明示reset/ring timeout/page fault、または明確に型付けできたROCm/HIP実行障害。 生logは保存/返却しない。ログ中の安定device IDが無ければnode targetにして対応不明を維持。一般的HTTP 500/timeoutをGPU障害へ変換しない。現行のProvider生応答をparseしてHIP障害を推測する実装は追加しない。

保持は同一daemon起動中に直近600秒を目標とし、単調時計で期限管理する。 上限100000件または64 MiBの早い方。全eventは最大1 KiB、保存前にallowlist projectionと長さ検査を行う。 上限は通常負荷で10分を保持するための提案値で、負荷評価後に合意して調整する。 容量圧迫時は制御処理を止めず古いeventを退避なしで破棄し、continuity=gap、droppedEventsTotal、availableSinceで欠落を通知する。 「常に10分完全」とは宣言せず、実際に読める範囲を返す。過負荷でも10分完全保持が必須なら、後述の永続化案を先に合意する。 event 0件の完全な窓と、観測機構が未取得・欠落の窓はcoverageで区別する。

  1. 初回GETはcursorなしで直近600秒の保存範囲を読む。window.from/throughとhighWaterSequenceを確定する。起動から600秒未満なら起動後だけでありpreviousBootHistory=false。
  2. hasMore=trueの間は、返されたnextCursorを使って同じ固定high waterまでページ取得する。既存ページ中に新eventが増えても読み終わりが動かない。
  3. hasMore=falseの応答のnextCursorはhigh water直後からの再開位置を示す。次の定期pollで新しいhigh waterを作り、前回以降を取得する。cursorは読者ごとのローカル保存で、サーバーにackしない。
  4. cursorは最大1024文字のopaque token。streamId、次sequence、固定窓等を含む版付き形式を起動ごとの鍵で検証する。cursorは認証credentialではなく、任意pathや時刻・メモリ量を操作できない。
  5. 同一streamで読むべきsequenceが期限切れ/容量破棄なら410 monitoring_cursor_expired。reasonCodeはretention_expiredまたはcapacity_evicted、recovery=restart_window。初回取得へ戻り、欠落をEumenes側に記録する。
  6. 過去streamのcursorは409 monitoring_epoch_changed、recovery=restart_window。再起動前の履歴は初版では復元しない。cursor形式検査後、stream相違を先に検出し、新起動鍵で検証失敗しただけの400に潰さない。同一streamの改変・将来sequenceは400。
  7. 複数読者や同じcursorの再読は、保持されている同じevent IDを返す。GETは他の読者の履歴を消費しない。10分を超える非表示期間は継続cursorの期限切れになり得る。

cancellationは既存のabort/terminal guardとoperation世代に結び付け、各workIdにつきterminalは一度だけcommitする。 cancelled確定後の遅延成功・遅延例外はterminalを変更せず、成功counter・障害counter・速度sampleに反映しない。 timeoutもtimed_outの一結果だけを残す。共有ensureのcaller取消と、Provider自体のload成功は別対象として記録する。 callerの取消をProviderロード失敗と見なさず、caller取消後に共有loadが成功してもそのcallerを成功へ変更しない。 再起動でterminal不明のworkを成功/失敗へ補完せず、stream resetとcoverageの限界を返す。

初版のkernel event取得は、既存user権限で読めるjournalをdaemonの同じ観測処理から固定引数で読む案とする。 shellは使わず、kernel分だけを前回journal cursorから最大1秒・1 MiB・5000 record/回、2秒周期で読み、 正規化したID/時刻/種別/device/reasonだけを監視storeへ入れる。生MESSAGEは通常logへも転記しない。 journal vacuum、cursor消失、上限打切り、権限エラー、未解釈driverはcoverageに欠落/未対応を返し、 internal journal cursorを監視読者のcursorとは共有しない。過去10分の初期backfillも同じ制限で段階実行し、完了までcoverageをavailableにしない。 journal由来eventのsourceEventIdはjournal cursorのdigestとし、再読で同じ事実を重複生成しない。 hostの既存oom_kill累積値を初期化時の新規OOM eventとして発行しない。

副作用を防ぐ変更境界と代替案

監視handlerが依存するのは認証、保存済みmonitoring view、イベントstoreのreadだけとする。 Provider backend、Control mutation、Lease managerの操作interfaceをhandlerへ渡さない。 getAllocations/getAllocation/verifyProviderToken等の失効処理を伴う参照も利用しない。 観測producerは通常のstate・計測の更新を受けるだけで、ensure、load/unload、dummy inference、probe追加、 Connection/Allocation/claim作成、lease renew、idleDeadline延長、Provider start/stop、設定更新を実行しない。

CPU baseline・vmstat前回値は一つのproducerが所有し、取得I/Oはsingle-flightにする。 周期実行とGETは分離し、GET頻度が1秒・60秒・複数読者でも区間を変えない。 既存Observerの制御用telemetryと監視が同じmutable CPU baselineを二重更新しないよう、共通sampleを配信するか独立baselineを持つ。 host sensorはbackend probe待ちに巻き込まれず、同一daemonの周期処理内で独立更新する。 各sensorに既定1秒budgetを設け、完了しない採取を次周期で重複起動しない。 timeout後の遅延完了はsample generationを検査し、古い値で新しいviewを上書きしない。 GETはobservabilityのactive workload対象から除外し、監視自身のeventが履歴を埋めないようtrace/履歴の対象外にする。

合意事項とEumenesへの引き渡し

推奨する合意内容は、二つの監視GET、既存Control認証に接続する専用read token、 値ごとの取得状態・時刻・区間、daemon内10分履歴と明示的な再起動reset、 既存権限のkernel観測、GPU要求対応付けと熱制限flagの未対応を含む初版である。 これらの案は利用者が承認し、sourceへ実装した。現行仕様と実測範囲は引き渡し仕様を参照する。

別途合意が必要なのは、再起動前履歴の永続化、上限超過時にも完全な10分保持を保証する負荷条件、 journal権限拡大、GPU bindingの新しい正式設定、thermal flagのdriver別decoder、 Provider内queue/直接接続観測、TTFT追加、旧admissionメモリ会計の変更、配備と破壊的実機試験である。 基準未確定の遅延・入れ替え頻度・高使用率に対する警報しきい値は、この合意とは別のEumenes設計対象とする。

  1. LARM source完成時に確定OpenAPI/JSON schema、認証手順、4種類の代表応答とcursor例、計測表、正式code一覧、保持・reset条件を渡す。
  2. 固定試験結果と実機確認結果を別に記載し、thermal flag、GPU binding、driver、権限等の未対応項目を列挙する。
  3. Eumenes backendにorigin/monitor token/timeoutを設定し、Spatial表示中だけ60秒pollする。同時pollは重複起動せず、cursorページは取得を完了してから保存する。
  4. Core/CPU/Memory/GPUへ観測scopeを割り当て、value=0、未取得、非対応、staleを維持する。MemAvailableとGPU poolを合算しない。GPU対応不明の要求をGPUへ割り振らない。
  5. event IDで重複排除し、terminal outcomeだけを要求結果へ集計する。410/409とbootEpoch変更時は履歴欠落を残して初回窓へ戻す。短い再試行でも取得済みIDを保持する。
  6. LARM到達不能、API非対応、認証失敗、応答はあるが個別センサー失敗、観測履歴の欠落を区別する。表示色・animation・複数対象集約はEumenesで定義する。

完了報告は「LARM source実装・固定試験完了」「LARM実機配備・受入範囲」「Eumenes backend接続・Spatial表示確認」の三段階を分ける。 計画作成時は調査・設計案のレビュー準備段階だった。合意後のsource実装と検証結果は引き渡し仕様へ記録し、本番配備・Eumenes接続は未実施として分ける。
