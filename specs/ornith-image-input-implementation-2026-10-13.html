Ornith画像入力の発見・事前計数・予算検査の実装

2026-10-13。Eumenesからの画像入力を使えるLARM側の契約として、公開schema、profile metadata、claim、入力token事前計数、推論前の検査を実装する。EumenesのUI・保存・設定は変更しない。モデル・projectorと1M共有KV／4枠は維持し、主profileとContextStillの解決先に明示したchatInput policyを適用する。廃止した64K selectorは復活させない。

2026-10-31の稼働確認では、release 95961280a2b4のOrnith公開contextWindowは200000、 outputReserveTokensは4096。解決先はornith15-strix-conversationで、実backendの max_tokensとn_predictの既定値はともに−1だった。4096の出力制限はLARMの事前検査・値の補完に存在した。 本変更はOrnithへ解決する主・画像・game・ContextStillの各Providerにremaining-contextを指定する。

2026-10-31、release 1bb672dd0530f467c0465520017cb14157f7039aを稼働環境へ反映済み。 同じ16 tokenの入力で、省略時のrequestedOutputTokensは4096から198008へ変わった。 明示max_tokens: 8192の事前計数はHTTP 400から200へ変わり、省略・8192指定とも実推論がHTTP 200、 finish_reason: stopで完了した。公開contextWindowのoutputLimitはremaining-context。 install・依存監査・全check・coverageのrelease gateはすべて成功し、coverage時は1047成功、10 skip、失敗0。 4096のoutputReserveTokensは互換metadataとして残るが、これらのProviderの生成上限には使用しない。

長時間推論のタイムアウト

2026-10-31に稼働中のdaemonの環境変数を確認し、LARM_GATEWAY_TIMEOUT_SECONDSは7200秒（2時間）だった。 HTTP serverのidleTimeoutは既定0、上流fetchはtimeout: falseのため、Bunの既定5分の無通信切断は適用しない。 10分程度の推論を待つためのLARM設定変更は不要。リクエスト全体の期限には待ち行列と前処理も含む。

稼働中のOrnith engineは--timeoutを指定しておらず、同じ実行ファイルのhelpはread/write timeoutの既定値を600秒と表示する。 これは通信の読み書き用で、生成全体の実行時間を600秒に制限する設定ではない。 接続元アプリ独自のリクエスト期限は今回の確認対象外。実際に10分間生成を続ける耐久試験は実施していない。

consumerから使う手順

  1. GET /v3/agent-profiles?profile=ornith1.5StrixでLLM ProviderのsupportedCapabilitiesにllm.visionがあり、chatInputが存在することを確認する。profileを指定してConnection作成・ready確認・claimを行う。
  2. claimのprovidersからname=llmのmodel・baseUrl・credentialを選ぶ。credentialはconsumer backend内だけで使う。catalog・Connection・claimのchatInputは同じ上限と保持方針を示す。
  3. 本文と保存画像をmessagesへ構成する。画像はuser roleの{"type":"image_url","image_url":{"url":"data:image/png;base64,BASE64_BYTES"}}。text partは任意で、画像だけ、2画像以上も許容する。providerがmedia marker・templateを挿入する。原本への認証付きURLは渡さない。
  4. 同じProvider bearerでPOST /v1/chat/completions/input-tokensへ最終的なChat Completions JSONを送る。endpointはchatInput.tokenCounting.endpointで発見する。claimのbaseUrlが/v1で終わる場合、相対operationは/chat/completions/input-tokens。
  5. fitsを確認し、同じ要求を通常のPOST /v1/chat/completionsへ送る。生成時にも再計数するので、計数結果だけでcontext超過を通せない。通信断後の推論POSTを自動再送しない。
  6. 次の質問でも必要な過去画像partsを再送する。renew後は再claimし、新しいcredentialを使用する。ConnectionやKVだけを画像保存場所として扱わない。

reference clientにはcountChatInputTokens(chatRequest, provider.credential.token, {signal})を追加した。control tokenをProvider操作へ流用せず、通常の画像推論もProvider bearerを使う。

事前計数の意味と応答

バックエンドの/private拡張は、Chat Completionsと同じoaicompat_chat_params_parseとprocess_mtmd_promptを使う。RGB decode・resize・MTMD tokenizationまで実施し、推論taskをenqueueせず、画像encoderやLLM decode、KV更新を行わない。従来の文字/tokenize応答を画像計数として採用せず、versionと合計・画像枚数を検査してfail closedする。

例の画像bytesはplaceholder。要求は{"model":"ornith-1.5-strix-lean","max_tokens":256,"messages":[{"role":"user","content":[{"type":"text","text":"この画像を説明してください"},{"type":"image_url","image_url":{"url":"data:image/png;base64,BASE64_BYTES"}}]}]}。次は応答構造の説明用例で、数値は実要求の結果で置き換える。 

{
  "contractVersion":"larm-chat-input-token-count.v1",
  "model":"ornith-1.5-strix-lean",
  "promptTokens":170,"textTokens":26,"imageTokens":144,"imageCount":1,
  "requestedOutputTokens":256,"safetyMarginTokens":1976,
  "inputBudgetTokens":259912,"maxContextTokens":262144,"fits":true,
  "requestDigest":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "runtime":"ornith15-strix-conversation","runtimeRelease":"RELEASE_ID",
  "configRevision":"CONFIG_REVISION","bootEpoch":"BOOT_EPOCH","engineBuild":"ENGINE_BUILD"
}

textTokensはrole・template・toolsを含む文字token、imageTokensはembeddingのtokenで、合計がpromptTokensとなる。APIはtemplateだけの独立内訳を返さない。超過でもcount-onlyは200かつfits=false。推論はcontext_budget_exceededで400となり、上流へ生成POSTを送らない。requestDigestは通常化した最終JSONのSHA-256で、deduplication key・推論予約・将来のreleaseにも有効なreceiptではない。計数と推論の間でlease・revisionが変わったら再計数する。

取消・deadline・lease失効は既存gatewayのexecution gateとabortを使う。計数中でも枠を占有して資源を保護し、終端で解放する。生成前にはtoken計数後にもbindingを再検査する。payload・Provider生応答・credentialは通常イベントに渡さない。responseのx-request-id、x-larm-boot-epoch、x-larm-config-revisionを追跡に使う。

実装境界とengine差分

core/chat-input.tsにpolicy・公開schema・bytes/header検査、backends/chat-input-tokenizer.tsにengine adapter、daemon/chat-input-gateway.tsとgateway.tsに計数・予算・取消を配置した。API catalog・OpenAPI・reference clientも更新。runtime設定で明示選択し、モデルfamily名による特権分岐はない。

engine拡張はdeploy/local-node/patches/llama-chat-token-count-v1.patch。Chat Completions形式の/tokenizeはllama-chat-token-count.v1を返し、従来content文字列の/tokenizeは保持する。同サイズの連続image_urlが動画batchへ併合されるengine経路を避けるため、各image marker間に改行を挿入する。特殊tokenと画像境界はProviderの責務。countと推論は同じ変更を通る。

debugのHTTP body dumpと、例外に入力値を含むwarningをchat/count操作で抑止した。専用画像storeやattachment IDは追加しない。requestのmemory解放の厳密な即時zeroizationは保証していない。実行engine・重み・合成画像・証跡はrepository外に置く。

準備scriptはdeploy/local-node/scripts/prepare-chat-token-count-engine.sh。外部source/build/outputを明示し、pinned commitとpatchを検査する。異なる既存binaryの上書きを拒否する。通常releaseの署名builder・activatorで配備し、別consumerのConnectionを解放しない。
