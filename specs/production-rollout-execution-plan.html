この文書のcommandは順序と証跡要件を固定するためのものです。root操作、service停止、Provider restart、firewall変更、traffic切替は自動実行せず、各checkpointでoperatorが対象とrollbackを reviewした後だけ実施します。

実行方針

次の作業は機能開発ではなくproduction収束です。一つの変更windowで全工程を連続実行せず、 各phaseのexit criteriaと証跡を確定してから次へ進みます。失敗したphaseを残したまま後工程へ 進めません。

実行前に確保する入力と権限

  • review済みでcleanなfull commitと、同commitで成功したbun run check。
  • root操作を一件ずつ確認できるoperatorと、Resident Providerを監視できる変更window。
  • repository外にあるmode 0700のevidence directoryと、mode 0600で保存する各結果file。
  • 利用規約を満たす非機密のSTT音声fixture。prompt、transcript、生成音声はcommitしない。
  • installed unitとrelease pointerのoperator backup、およびProvider単位の復元command。
  • UFWをread-onlyで確認できる権限と、LAN側から接続拒否を確認する別host。
  • Ambient client設定を変更・rollbackできる担当者、commitまたはconfig digest、対象task一覧。

上記のいずれかが欠ける場合、codeを追加して条件を迂回しません。該当phaseを開始せず、 入力または権限を確保します。

Phase 4: Milestone 26 Ambient shadow and canary

Ambient側のTask判断とconversationは変更せず、transportとRuntime bindingだけを段階移行します。 各段階の対象task、最低turn数または最低soak時間、error budget、即時rollback設定を開始前に記録します。 実測なしに共通の数値をこの計画では捏造しません。

  1. shadow-larm.shとAmbient側shadowを実行し、route、Runtime、release差分を比較する。 差分はcatalogとintentのどちらを直すかreviewし、自動fallbackで隠さない。
  2. 非音声の少数taskだけを参照clientへ切り替え、期限付きAllocationとfinally releaseを確認する。
  3. 事前定義した非音声soakを完了し、SLO、epoch、fallback、memory、leakを評価する。
  4. STTと通常TTSを追加し、音声canaryとsoakを同じgateで評価する。
  5. 明示routeを持つtaskだけへexpressive TTSを追加し、通常TTSとの暗黙切替がないことを確認する。
  6. 各段階でcanary-gate.shを実行し、不適合時は対象trafficだけをdirect Providerへ戻す。LARM自体が不安定な場合だけrelease rollbackを追加する。
  7. Ambient設定から個別port、service名、artifact path参照を削除し、変更commitまたはdigestを記録する。

Checkpoint R4

  • shadow差分が0、または全差分がreview済みの説明を持つ。
  • 非音声・音声・expressiveの段階canaryがSLOとerror budgetを満たす。
  • soak終了後のAllocation、queue、artifact operation、Preferred process leakが0である。
  • Ambientの通常経路から個別Provider依存が除去され、direct経路はrollback専用である。

Phase 5: Milestone 27 Gateway-only cutover and stable promotion

Ambient canary成功後にだけ、installed済みのloopback unitを実processへ反映します。影響の小さい Providerから開始し、Resident LLMを最後にします。一括restartは行いません。

  1. network-converge.sh planでlistener、UFW rule、対象、confirmationを保存する。
  2. inactiveなQwen TTSは次回起動時にloopback unitが使われることを確認し、不要な起動を行わない。
  3. VOICEVOX、Qwen ASR、llama-swap、Resident llama-serverの順に、一つずつunitを適用する。
  4. 各Provider適用後に対象portがloopbackだけでlistenすること、LARM health、該当capability smoke、 Resident default、memory、Provider PIDを確認してから次へ進む。
  5. 全Providerのloopback化後、reviewしたdigestを指定してnetwork-converge.sh applyを 実行し、既知のProvider LAN allow ruleだけを削除する。
  6. LAN側の別hostから8080–8084への接続拒否を確認し、local-node上のLARM Gatewayを再確認する。
  7. 最終canary-gate.sh、LARM release rollback rehearsal、Resident PID監査を行う。
  8. Commissioning Evidenceと Stable Release Gateを最終identityへ更新する。

Provider単位のrollback

capability smokeが失敗した場合は次のProviderへ進みません。まずLARM releaseをrollbackし、それでも 回復しない場合だけ、operator backupから対象Provider一つのunitを復元してlistenerを確認します。 direct経路が必要な場合も、network-converge.sh rollback-planでreviewした一つのportと 限定IPv4 CIDRだけを復元します。wildcard公開や全port一括開放は行いません。

Checkpoint R5

  • port 8080–8084はloopback以外でlistenせず、Provider LAN allow ruleがない。
  • 通常clientのdata planeはLARMだけで、direct Providerは通常設定に存在しない。
  • repository、commissioning、SLO、Ambient canary、network gateが同一deployed release commitを参照する。
  • Qwen TTSとoptional workerは不要時にCOLDへ戻る。
  • 未解決の逸脱、暫定threshold、manual exceptionがない。

共通停止条件

  • 候補commit、deployed commit、config revision、boot epoch、releaseの対応が崩れた。
  • Resident ProviderのPIDまたはhealthが意図せず変化した。
  • credential、prompt、transcript、audio、raw logが標準出力またはGitへ混入した。
  • Allocation、execution、artifact operation、Preferred processのleakが残った。
  • SLOを満たすために未承認fallback、optional Runtime、slot増加が必要になった。
  • backup、rollback target、UFW読取権限、Ambient rollbackのいずれかが失われた。
  • network applyの補償復元後も、削除前と同じrule状態へ戻らない。

計画の完了条件

Checkpoint R0からR5が順番に成功し、最終release identityへ更新した Stable Release Gateに保留項目がなくなった時点で完了です。 Milestone 28の35B評価はこの判定を妨げず、M25の実測が開始条件を示した場合だけ別decisionとして 計画します。
