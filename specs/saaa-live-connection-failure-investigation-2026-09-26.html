調査条件
設定、model、service状態を変更せず、credential、会話本文、利用者音声を記録しない。

結論

  1. LLMとASRのProvider自体は利用可能である。既にHOTなLLMへChat Completionsを実行してHTTP 200と応答本文を確認し、短い日本語音声をASRへ送ってHTTP 200と正しい文字起こしを確認した。
  2. harness-connection-schema-invalidの直接原因は、SAAAが期待する旧Connection Provider fieldとLARMの現行公開fieldの不一致である。
  3. 約90秒のready待ちはmodel起動失敗ではない。先行する未claimのSAAA Connectionが唯一のSAAA Allocation capacityを保持し、後続がwaiting-capacityになったためである。
  4. 対象系列にはclaim受理・拒否のどちらのeventもなく、SAAAからLLMまたはASRの実requestへ進んでいない。
  5. 稼働LARMは5分idle release実装前のreleaseである。readyだが未claimのConnectionが15分TTLまで残り、 後続を塞いだ。

HTTP契約の照合

SAAA sourceの旧requestを同じ形で送ると、Allocation作成前にHTTP 400となった。応答は Content-Type: application/json、x-larm-boot-epoch付きで、bodyは {"error":{"code":"invalid_request","message":"invalid agent connection request"}} だった。

LARMの現行create requestはselectorを表すprofile: "SAAA"を要求する。 agentProfileやexplicitAgentProfileはstrict schemaで拒否される。

正しいrequestで再現したcreateはHTTP 202、Location、Retry-After: 1、 Content-Type: application/jsonを返した。調査用Connectionは応答確認直後にDELETEし、HTTP 204を確認した。

SAAAと稼働LARMのConnection Provider field差分
意味 SAAAが要求 LARMの実応答
内部route route必須 非公開のためfieldなし
公開model publicModel必須 model
公開endpoint fieldなし endpoint
提供可能capability fieldなし supportedCapabilities

実応答のtop-levelにはprofile、agentProfile、servicesがあり、 Providerにはname、capability、supportedCapabilities、 protocol、endpoint、model、readiness、 claimableがある。SAAAのdeserializerは欠落したrouteと publicModelにより、成功HTTP responseを harness-connection-schema-invalidへ分類する。

約90秒待機の時系列

  • 12:05:58 JST、先行SAAA Allocationがpending。既存ASR、embedding、LLM、TTSは再利用され、 backchannelだけを起動した。
  • 12:06:00、Allocation ready。起動所要は約1.27秒だった。
  • 12:06:00から12:06:02、ASR、backchannel、embedding、LLM、TTSのsemantic probeがすべて成功した。
  • この先行Connectionにclaim eventはなく、15分TTLまでAllocationを保持した。
  • 12:09:00、後続SAAA Allocationがwaiting。12:09:01にcreate HTTP 202となり、12:10:39を過ぎても waitingだった。12:14:00にready timeout相当で解放された。
  • 12:10:42にも重複した後続Connectionがwaitingとなったが、12:10:58にclient DELETEで解放された。
  • 12:20:58、先行Connectionが15分TTLでexpiredし、待機中の別Allocationがadmitされ、全Provider probeが再び成功した。

LLM再現結果

inspectionではornith-generalがHOTだった。公開model ornith-1.5-35bへ短いChat Completionsを送り、HTTP 200、JSON応答、 finish_reason: stop、本文OKを確認した。対象時刻のAgent ConnectionでもLLM semantic probeは成功している。LLM ProviderまたはHTTP接続の故障ではない。

ASR再現結果

inspectionではqwen-asrがHOTで、Service Harness healthはHTTP 200、model qwen3-asr-1.7bだった。既に稼働中の音声合成serviceで作った短い日本語音声 「今日は良い天気です」をService Harnessの/v1/audio/transcriptionsへ送り、HTTP 200、application/json、文字起こし「今日は良い天気です。」、language Japaneseを確認した。

対象のSAAA Connection系列ではsemantic probe以外のASR requestはLARMへ届いていない。 target-speaker-emptyでSAAAが音声を破棄した場合、その音声はLARM側では観測できず、 LARM ASRの失敗には分類できない。

必要な修正

  1. SAAAのcreate requestをprofile: "SAAA"へ統一し、canonical agentProfileとexplicitAgentProfileを送らない。
  2. SAAAのConnection response型をLARMの公開契約へ合わせる。Providerはmodelと endpointを読み、非公開のrouteと旧publicModelを要求しない。
  3. readyになった同じConnectionをclaimし、create、poll、claimを一つの永続idempotency/session ownerで single-flight化する。失敗またはcancel時は必ずDELETEする。
  4. workspace mainの5分idle release実装を正規release手順でLARMへ配備する。稼働release 0e92750にはこの変更がない。
  5. 修正後に、create 202、poll ready、claim 200、claimed credentialによるLLMとASR、DELETE 204を一続きで canary確認する。

実装した是正

SAAA mainの016081bで、両方のAgent Connection consumerを現行公開契約へ 移行した。既定値とcreate bodyは公開selector SAAAを使用し、既存設定に保存された旧canonical profileは対応する公開selectorへ安全に移行する。

  • dynamic LAN consumerはGET /v3/agent-profiles?profile=SAAAから5 Provider構成を取得し、 全Providerがreadyかつclaimableであることを確認してから一意なLLMを選ぶ。
  • Connection responseはsupportedCapabilities、endpoint、modelを読み、 非公開fieldへ依存しない。
  • create responseの型検証より先にboundedなConnection IDを回収し、残りのschemaが不正でも best-effort DELETEを実行してAllocationを残さない。
  • 会話session consumerは同じsession ownerと永続idempotency keyを維持し、LARMのidle release後は 次回利用時に再接続する。

SAAAのstandalone session crateはclippyをwarning 0で通過し、unit・context testは計29件成功した。 settings regression 7件とTypeScript typecheckも成功した。desktop crate全体は、このLinux環境に pkg-configとGTK開発packageがないためproject sourceのcompile前に停止する。

LARM source側では、非同期202受付、最大3秒のbounded Prefer wait、同一SAAA sessionのsingle-flight、LLM・ASR・TTS無利用300秒後のbundle release、共有embedding常駐、 ContextStill再admitを実装済みである。全source・operation・document・type・531 unit・49 deployment testが成功した。次のgateはこのrevisionの正規配備と実環境canaryである。

調査終了時のLARM activityはidle、active workloadは0だった。LARM daemon、ASR、VOICEVOX、resident LLM、llama-swap serviceのactive開始時刻に変化はなく、調査によるmodel切替やservice再起動はない。
