Warm state

既定対象のqwen-general、qwen-asr、voicevox-ttsはResidentの 常時起動状態のまま測定します。Allocation解放でこれらを停止せず、Provider restartやmodel unloadも 行いません。warmupは各scenarioの最初の要求を集計から除くだけで、Cold cycleではありません。

同時利用scenario

mixedではLLM、ASR、TTSを一つのAllocationへ束ね、各1要求を同じevent loop turnで 開始します。reportには実際のlaunch skewを残します。各workloadのmixed p95 total latencyと p50 processing speedを単体系列と比較し、正の値が劣化を表す百分率として記録します。

評価専用のLARM_PERF_ASR_URLがある場合、ASR-onlyはAllocationなしでloopback endpointを直接測り、mixedはLLMとTTSだけをLARM Allocationへ固定して外部ASRを同時発射します。 これによりproduction routeを変更せず、CPU ASRが既存workloadへ与える影響を同じschemaで比較できます。

mixedは音声対話1セッション相当の異種Provider干渉を見る試験です。同一Providerへ複数要求を 投げる飽和試験、最大throughput探索、長時間soak試験ではありません。既定runtimeは各Providerの maxConcurrentRequests=1なので、それらは別の明示的な負荷契約が必要です。

同時に採取する観測値

  • 最小system memory available bytes
  • 最小accelerator memory available bytes
  • 最大active execution数と最大queue depth
  • Gatewayが返したHTTP 429の増分
  • route、runtime、release、fallbackの実identity
  • daemon boot epoch、config revision、release commitの開始前後一致

推論error、telemetry採取error、またはdaemon identity変化が一つでもあればpassed=false とし、processも非zeroで終了します。一方、性能値に合否閾値は置きません。まず同一hardware・同一 releaseのbaselineを複数回採取し、用途別SLOを校正してからgateへ昇格させます。

結果から、遅さはCold startではなく同時実行時のresource干渉として再現しました。特にGPUを使う LLMとASRを含むmixedでASRの影響が最大です。queue、429、memory不足がないまま両方が実行中なので、 admission待ちではなくaccelerator computeまたはshared memory bandwidthの競合と推定します。 CPU版VOICEVOXも16 thread構成で約2倍へ低下しており、CPU・memory fabric側の干渉も示唆されます。 原因の寄与率を確定するにはLLM+ASR、LLM+TTS、ASR+TTSのpairwise測定を追加します。 ASRのCPU軽量候補と比較gateは軽量日本語ASR 再選定調査・Shadow評価結果へ分離しました。

単体はいずれも5回のばらつきが小さく、ASRとTTSはmixedでもRTF 1未満を維持しました。LLM Providerはmodelを常駐させる一方、起動引数でprompt cacheとidle slot cacheを無効化しています。 そのため単体TTFTはCold loadではなく毎回のprefillを含みます。raw sample、生成音声、transcript、 response本文はrepositoryへ保存していません。
