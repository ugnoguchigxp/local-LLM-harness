2026-09-19 21:38 JSTから2026-09-20 21:58 JSTにContextStillで観測された 192.168.0.130:9810へのTCP接続失敗を調査した。LARM process、listener、 model登録、credential、release reloadは障害の発生源ではない。失敗requestのpacketは LARM hostへ到達しておらず、障害条件はContextStill hostの送信経路または同一LAN上の neighbor解決までに一意に局在する。これとは別に、従来のLARMはprocess livenessを readinessとして誤認できたため、listenerと実chat routeを検証するlifecycle gateを追加した。

原因判定

OS code 65のHostUnreachableはmacOS側connectで返り、HTTP response、LARM request ID、 LARM ingress eventが存在しない。対してLARM process、wildcard listener、host route、Wi-Fi carrier、 firewall構成は同じ時間に連続していた。この組合せから、直接原因はContextStill hostの route/neighbor状態またはLARM hostへ入る前のLAN経路である。LARM内のcredential不足、model未登録、 model cold startならTCP接続後にHTTPまたはserver eventが残るため、このerror chainの原因にはならない。

ContextStill source treeとhost shellはこのworktreeに存在せず、同hostのroute table、ARP/ND cache、 sleep/wake journalを取得できなかった。したがって、ContextStill host内部でroute消失とneighbor失敗の どちらかを選ぶ最終判定だけは未完である。再発時は同hostで route -n get 192.168.0.130、arp -an、interface状態を同時採取する。

LARM側の設計欠陥と修正

従来の/healthはprocessがHTTPを処理できれば無条件に200/okを返し、 /readyはobserver鮮度しか検査しなかった。systemdもType=simpleだったため、 process起動からbindまで約2.2秒、さらにroute受付確認までの状態をreadyから区別できなかった。

  • starting → verifying → ready → drainingとfailedの明示lifecycleを追加。
  • 9810 bind後、同じlistenerで認証付きmodel catalogとqwen-agent-worker実chatを確認してからready。
  • starting、failed、draining中はhealth/readyと新規data-plane requestを503にする。
  • systemdをType=notifyへ変更し、実chat canary成功後だけREADY=1を通知。
  • shutdownではsocket停止前にnot-readyへ遷移し、既存requestをdrain。
  • release activationのreload開始・成功・rollbackを時刻、commit、revision付きでjournalへ記録。

再現とtest

修正前は新しいlifecycle testがmodule不存在で失敗した。修正後は、bind前、bind後の検証中、 verification失敗、ready、drainの各境界を時刻や外部networkに依存せず検査する。 app testはnot-ready中のhealth、ready、chatがすべて503であり、ready遷移後のみ200になることを確認する。 stability verifier testはmacOS code 65相当のerror chainをTCP connect errorとして独立集計する。

観測方法

journalctl -u larm-daemon.service -o cat |
  jq -c 'select(.event == "gateway_readiness_transition"
    or .event == "listener_bound"
    or .event == "listener_accept_verified"
    or .event == "listener_bind_failed"
    or .event == "listener_accept_failed")'

curl -fsS -H "Authorization: Bearer $LARM_TOKEN" \
  http://192.168.0.130:9810/metrics |
  grep '^larm_gateway_readiness'

LARM_BASE_URL=http://192.168.0.130:9810 \
LARM_TOKEN="$LARM_TOKEN" \
bun run verify:qwen-agent-worker-stability

transition logにはtimestamp、bootEpoch、configRevision、状態、理由、listenerを含む。 bind/accept失敗とrelease reloadにも専用eventを持たせる。Authorization headerやtokenは log、metric、検証JSONへ保存しない。
