LARM saaa.llm-stream.v1 Native WebSocket 実装計画と実装証跡

本計画は、SAAA desktop側を変更せず、LARM側をSAAA Provider LLM WebSocket Protocol saaa.llm-stream.v1へ適合させるためのserver-side実装計画である。HTTPはallocation、 poll、renew、release、health、管理および非streaming requestへ限定して維持し、LLMのrealtime data planeはWebSocketへ集約する。target profileではSAAA、LARM、Provider内部のSSEを廃止する。

現行openai.chat-completions.v1のHTTP/SSE応答をWebSocketへ包装する方式は採用しない。 normative contractのPWS-DEC-08によりSSE bridgeは非準拠である。ProviderからLARMまで native event streamまたはWebSocketで接続できない限り、LARMは saaa.llm-stream.v1を広告してはならない。

1. 固定する構造判断

  1. Mac側contractを変更しない。 subprotocol、message名、field、上限、sequence、 ACK、resume、error、close codeをLARM都合で別名化または簡略化しない。
  2. Controlとrealtime dataを分離する。 allocation lifecycleは既存RESTを維持し、 prompt、delta、tool、terminal、cancel、ACK、resumeはWebSocketだけを通す。
  3. Providerまでnative化する。 LARMの外面だけでなく、LARMから推論runtimeまで SSE framing、text/event-stream、[DONE]を残さない。
  4. connection poolとrunを1対1に固定する。 広告値までprewarmするが、一つの connectionへactive runを一つだけpinし、run multiplexingを行わない。
  5. hot deltaを固定binary frameにする。 16 byte headerとUTF-8 payloadを一度だけ assembleし、JSON envelope、全文再送、application compressionを入れない。
  6. replay stateをsession ownerへ集約する。 seq、incremental SHA-256、累積byte数、 unacknowledged event、terminal retentionを一つのrun actorが所有する。
  7. queueを重ねない。 runtime admission、unacknowledged replay buffer、native socket buffer以外のchunk queueを作らない。run admissionはqueueせずcapacityで終了する。
  8. 本文の永続監査をhot pathから外す。 target profileはprompt、delta、tool、finalを logまたは永続化せず、metadata counterだけを非同期記録する。application-layer暗号化を追加しない。

3. Discoveryとclaim advertisement

LARMのallocation、poll、renew、releaseは現行RESTを維持する。readyなLLM allocationは saaa.llm-stream.v1、credentialを含まないstream URL、同時実行数、resume window、 native upstreamを広告する。現行local-nodeのQwen runtimeは maxConcurrentRequests: 1であるため、初期releaseはconnection一つ、run一つを広告する。

  • maxConnectionsとmaxConcurrentRunsは同値かつ1〜8とする。
  • 実効値はruntimeの安全な同時生成数を超えてはならない。
  • 一部connectionのprewarmに失敗した場合は利用可能slotだけへ縮退する。
  • loopback以外はwss、literal loopbackだけはwsを許可する。
  • URLへtoken、query、fragmentを含めず、descriptorとstream URLを同一hostにする。
  • native backend readinessが未確認ならHTTP controlはreadyでもstreaming capabilityを広告しない。
  • 既存HTTP chat completionsのstream: falseは維持する。 stream: trueは400 streaming_requires_websocketで拒否し、 text/event-streamを返さない。

4. Transportとconnection pool

  1. ClientはSec-WebSocket-Protocol: saaa.llm-stream.v1と必要なBearer tokenをhandshakeへ送る。 LARMはsubprotocolをexact echoし、不一致、無認証、別allocation scopeをupgrade前に拒否する。
  2. LARMは最初のapplication messageとして5秒以内にconnection.readyを一度だけ送る。
  3. pool keyは(stream URL, credential fingerprint, subprotocol)とし、credentialの異なる connectionを共有しない。
  4. connectionはReadyから一つのrunだけを所有し、terminal ACK後にidleへ戻る。 二件目のrun.startはqueueせずrun-level capacity failureにする。
  5. 15秒application trafficがなければRFC 6455 Ping、5秒以内のPongを要求し、二回連続失敗後に closeしてresumeへ移行する。JSON ping/pongは作らない。
  6. permessage-deflateをofferまたは選択しない。redirectによるcredential転送も行わない。

5. Wire実装

response.delta以外は、1 text messageにつきUTF-8 JSON object一つとする。 unknown field、重複key、NaN、Infinity、末尾dataをstrict parserで拒否する。deltaだけは 16 byte固定headerを持つbinary WebSocket messageで、run IDはconnection scopeから得る。 

Binary response.delta v1
offset  size  field
0       4     magic = ASCII "SAD1"
4       1     messageType = 0x01
5       1     flags = 0x00
6       2     headerLength = 0x0010
8       8     seq: unsigned u64, big endian
16      N     append-only UTF-8 payload, 1..16,384 byte

encode pathは16 byte headerを直接書き、payloadと合わせて一つのbinary messageとして送る。 deltaをJSON DOMへ投影せず、payloadをincremental SHA-256とcanonical byte countへ一度だけappendする。 terminalへcontentを含めず、全文再serialize、全文再hash、暗号化監査copyを行わない。

固定limit
項目 limit 処理
Client control 1,048,576 byte 超過はClose 1009
Server message 524,288 byte 生成前に上限検査
Delta payload 1〜16,384 UTF-8 byte 超過または不正headerはprotocol failure
Assistant accumulator 64,000 Unicode scalar / 262,144 UTF-8 byte response-too-large
Unacknowledged 64 eventまたは524,288 byte 該当runだけをpause
Resume retention 最低120,000 ms 期限後はresume rejected

Delta batching

  • 最初の非empty deltaは待たずに送る。
  • 二件目以降は未送信開始から5 ms、256 byte到達、upstream idleまたはterminalの最初の条件でflushする。
  • TTSの自然境界を跨いで追加待機せず、16,384 byte未満で分割する。
  • 1 byte単位の大量eventでもmemory boundを破らない。

7. ACK、backpressure、resume

  1. RunActorは送信済みeventをseq順に保持する。run.ackは累積ACKで、古いACKを無視し、 未送信seq、飛び越し、hash不一致をprotocol violationにする。
  2. 64 eventまたは524,288 byte到達時、Provider readerをpauseし、そのrunの新規送信を止める。 ACK、cancel、Ping/Pong、別connectionは止めない。
  3. native backendがpauseを伝播できない場合、unbounded queueを作らず backpressureでそのrunだけをfailする。
  4. disconnect後もrun、authorization、allocation lease、ACK cursor、hash checkpoint、未ACK event、 terminalを最低120秒保持する。process restartを跨ぐ永続resumeは行わない。
  5. 新connectionのrun.resumeを検証し、成功時はrun.resumed後に ackSeq + 1から元と同じseqでreplayする。terminal未ACKならterminalも再送する。
  6. terminal ACKまたはretention expiryでbuffer、hash checkpoint、run ownerを一度だけ解放する。

64 event / 524,288 byteへ到達した後もterminalをACK待ちにしないため、実装はProvider delta/toolへ使用できないterminal専用の1 event / 4,096 byte固定slotを持つ。これは一つだけの terminalを優先送信・再送するためのbounded control reserveであり、Provider readerの unacknowledged上限を拡張しない。

replay bufferをsocket write bufferへ兼用しない。前者はresumeのためのapplication state、後者は kernelへ渡す一時的な送信stateであり、寿命と解放条件が異なる。

8. Native Provider prerequisite

現行runtime registryはLLMをopenai.chat-completions.v1としてHTTP endpointへ解決する。 このままではtarget protocolへ適合しない。LARM側で次のinterfaceを新設し、実Providerがすべてを nativeに提供できることをPhase 0で実証する。 

interface NativeLlmStreamBackend {
  open(input: RunStart, signal: AbortSignal): AsyncIterable<NativeLlmEvent>;
  pause(runId: string): void;
  resume(runId: string): void;
  submitToolResult(result: ToolResult): void;
  cancel(runId: string): Promise<void>;
}

WebSocket companionはSec-WebSocket-Protocol: larm.native-llm-stream.v1をexact echoし、最初のmessageで次のsemantic readinessを返す。field欠落、unknown field、falseの capability、または広告に必要なcapacity未満ならLARMは未readyとしてstreamingを広告しない。 

{
  "type": "native.ready",
  "protocol": "larm.native-llm-stream.v1",
  "encoding": "sad1-binary-delta-v1",
  "maxConcurrentRuns": 1,
  "capabilities": {
    "pauseResume": true,
    "cancel": true,
    "toolContinuation": true,
    "usage": true
  }
}

LARMからはnative.run、native.pause、native.resume、 native.cancel、native.tool-resultを送る。Providerからのtext controlは native.tool-call、native.completed、native.failedだけで、deltaは SAD1 binaryだけを使う。各runは独立したnative connectionを所有し、terminal後に閉じる。

eventは確定text bytes、完成済みtool call、usage、finish reason、failureだけを含む。OpenAI SSE chunkや[DONE]をinterfaceへ流入させない。Provider processまたはengineがnative callback、 IPC、もしくはWebSocketを提供できない場合は、target profile専用Provider sidecar/runtimeをLARM側へ 用意する。model weightやengine binaryはrepositoryへ含めない。

9. Daemon実装方針

  • HTTP routingは既存Hono appを維持し、/v1/llm/streamのupgradeとhot send pathだけを Bun native WebSocket handlerへ置く。
  • native sendBinaryの戻り値とdrainを直接観測し、hidden queueを避ける。
  • WebSocketConnectionがsocket、authorization context、active RunActor、heartbeat、 drain stateを単独所有する。
  • RunActorがprovider iterator、AbortController、seq、hash、byte count、replay ring、 outstanding tool call、deadline、terminalを単独所有する。
  • current ExecutionGateのqueued acquireを使わず、WebSocket専用の即時 admissionを追加する。active run数はadvertisementとruntime capacityの双方で制限する。
  • allocationはrun.startとresumeの両方でidentifier、lease、owner、model、capabilityを O(1)検証する。connectionをallocation間で再利用してもrun stateは混在させない。
  • shutdownはReadyをDrainingへ移し、新runをcapacityでfailし、active run完了または期限後に terminalを出してClose 1001にする。

10. 速度優先のprivacyとobservability

local LLMのtarget profileではapplication-layerのprompt暗号化、delta暗号化、全文監査materializationを 行わない。非loopbackのtransport TLSとBearer認証はMac contractへの適合条件なので維持する。 これは暗号化機能を一般用途から削除する判断ではなく、WebSocket realtime routeを metadata-only、payload非永続にする明示的profile分離である。

  • 記録可: connection/run count、TTFT、inter-delta、duration、byte、ACK lag、replay、error code。
  • 記録禁止: prompt、delta、final、tool argument/result、Authorization、内部endpoint、stack trace。
  • metric labelへrun ID、allocation ID、prompt由来値を入れない。
  • hot loopではcounter更新だけを行い、log formattingとcallbackを行わない。

12. 実装順序

  1. Phase 0 — Native Provider spike。 Qwen 3.8 27B resident runtimeでnative delta、 cancel、pause、tool continuation、usageを実証する。SSEしか使えなければ実装を先へ進めず、 LARM側Provider runtimeを変更する。
  2. Phase 1 — Contract lock。 Mac正本からJSON schema、16 byte codec vector、hash vector、 close mapping、PWS-C01〜PWS-C19 fixtureをLARMテスト資産へ取り込む。手書きの類似schemaを作らない。
  3. Phase 2 — Core discovery。 protocol type、stream advertisement、runtime capability、 claim response、readiness gatingを追加する。未準拠runtimeは広告しない。
  4. Phase 3 — Minimal vertical slice。 upgrade、connection.ready、run.start、accepted、 binary delta、completed、terminal ACK、cancelを一connection、一runで完成させる。
  5. Phase 4 — Integrity。 strict seq、incremental hash、byte count、size limit、 duplicate/gap detection、exact terminal semanticsを完成させる。
  6. Phase 5 — Flow control/resume。 64 event / 524,288 byte pause、120秒retention、 disconnect、resume validation、replay、terminal replay、expiry cleanupを追加する。
  7. Phase 6 — Tool。 最大4 parallel tool call、result idempotency、priority writer、 timeout、同一run continuationを追加する。
  8. Phase 7 — Pool/TLS/lifecycle。 advertisement数prewarm、capacity縮退、heartbeat、 WSS、credential rotation、drain、service restartを実装する。
  9. Phase 8 — Conformance/cutover。 PWS-C01〜PWS-C19と30分network flapを通し、 LARM target profileのSSE route、fixture、benchmarkを削除する。

13. Verification gates

protocol正本のPWS-C01〜PWS-C19をすべてmandatoryにする。特に次をrelease blockerとして扱う。

  • 101 responseのexact subprotocol echoと5秒以内のconnection.ready。
  • 8 connection / 8 run fixtureでもrun間seq混在なし。local-node初期releaseは広告値1で同じ試験を行う。
  • 20 byte × 10,000 deltaが250 ms以内、peak RSS増加16 MiB以下。
  • ACK 7から8以降を同じseqでreplayし、delivery/TTS重複0。
  • terminal hash、content byte、content field混入を確実に拒否する。
  • 別connectionの1 MiB upload stallによる追加p95 5 ms以下、cancel p95 50 ms以下。
  • ACK停止時に64 eventで該当runだけpauseし、ACK後に65から再開する。
  • 1,000 turn / 30分 / network flapでunbounded memory、zombie run、重複、欠落0。
  • Provider内部を含めtext/event-stream、SSE parser、[DONE] dependencyが0。
  • HTTP allocation lifecycle、health、管理、非streaming requestの回帰がない。

controlled Harnessでrelease buildを1,000反復以上実行し、p50、p95、p99、peak/settled RSSを保存する。 case欠落、sample不足、0 test、閾値超過は失敗とする。

14. Cutover、rollback、完了条件

  1. native Provider endpointを先行配備し、LARMからのみ接続してcontract testを通す。
  2. WebSocket capabilityを未広告のままLARM canaryを行う。
  3. 一つのtest allocationだけへ広告し、Mac canaryでprewarm、run、tool、cancel、resumeを確認する。
  4. 全LLM allocationへ広告し、SSE利用数が0であることを観測する。
  5. target profileからLLM SSE route、fixture、benchmark、設定を削除する。

rollbackは旧release全体へ戻す。v1と異なるfieldや意味を同じsubprotocolへ混ぜず、旧SSEへ per-run fallbackしない。WebSocket conformanceに失敗したreleaseはstream capabilityを広告しない。

Definition of Done

  • Mac側のcode、schema、protocol文書を変更せず接続できる。
  • LARMとMacが同じgenerated schema / golden fixtureを使用する。
  • advertised connectionがprewarmされ、active run / connectionが常に1である。
  • binary delta overheadがexact 16 byte、terminal本文再送が0 byteである。
  • tool、cancel、ACK、resume、terminal integrityが正本どおり動作する。
  • 非loopbackはWSSで、payloadとsecretがlog、metric、永続監査へ出ない。
  • SAAA data plane、LARM、Provider内部にSSE bridgeが残っていない。
