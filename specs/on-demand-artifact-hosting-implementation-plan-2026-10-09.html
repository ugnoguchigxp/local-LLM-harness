予定の正本はカレンダーアプリのDB内のeventとrevision。Markdownは版別本文とDBの公開版参照、Excalidrawはscene JSONと画像asset、Archifyは入力JSONと検証済みHTMLを正本として保存する。 利用者が保存したexportもdata対象とする。再生成可能なthumbnailと一時出力だけをcache/workにする。 sqlite-wal、sqlite-shm、rollback journal等のDB付随ファイルはDBと同じSSD directoryに置く。個別に内蔵へ分離したり、稼働中の付随ファイルをcleanupしたりしない。

DoclingにはKNOWLEDGE_STATE_DIRをstate/knowledge、KNOWLEDGE_ARTIFACT_ROOTをdata/knowledgeへ明示する。APIとprocessorのartifact rootを一致させる。 clients、worker token、lifecycle tokenとviewer設定は固定Secret fileへ明示し、既定のcheckout内dataや.envに依存しない。 通常Docling画面の旧dataと独立Knowledge APIの資料は形式もIDも異なるため、自動混在・自動移行しない。 Eumenes自体の既存DBを一括移行する作業は本計画に含めず、新規ホストサービスのDBと成果物を対象にする。

専用UID、HOME、XDG_DATA_HOME、XDG_STATE_HOME、XDG_CACHE_HOME、TMPDIRとcwdを固定する。 SSDのmount UUID、rw、realpath、最低空き2 GiBをDB openより前に検証する。大容量入力には追加の必要容量も見積もる。 pathが存在するだけでは起動せず、媒体不在・別UUID・read-only・容量不足では受付を拒否する。内蔵directoryへのfallbackと空DBの自動作成を禁止する。 初回DB作成は正しい媒体確認後の明示bootstrapに限定し、通常起動で既存DBが消えていた場合は復旧要求とする。

SSD依存memberにはRequiresMountsFor、mount unitへのBindsTo/Afterを設定する。未mount時の基底directoryをservice UIDから書込み不可にする。 使用中に媒体が失われたら新規書込みを止め、I/O障害として応答し、復帰後にDBとjobを再照合する。 起動時のUUID確認だけでは運用中の正常性を保証しないため、活動・readinessとAppのI/O失敗検知も使う。

要求から起動・復帰まで

  1. Eumenesが利用者と対象artifact/sourceの権限を確定する。停止中でもtool一覧は固定版のschemaから取得できるようにする。
  2. backendのClientLocalServicesでservice IDを固定してensureする。同じensureの再送には同じkeyを使い、別要求の利用権と混同しない。
  3. startingでは待機表示を出し、resolveで同じrevision・generation・bootEpochを追跡する。初期の起動待ち上限は180秒、待機中もleaseを更新する。
  4. ready endpointだけを使ってMCPまたはHTTP APIへ接続する。LARM用tokenとアプリの業務tokenを分ける。
  5. 結果をartifact参照へ変換し、対応するhost画面を開く。Doclingはsource・原本版・根拠版・位置の参照を使う。
  6. idle停止後の次の操作は同じ入口へ戻り、ensureして新世代へ接続する。資料が更新されていれば再検索し、古いsessionは再発行する。

初期はサービスごと最大1 instanceとし、同時要求を既存Managerで起動集約する。各利用者・画面・agentの利用はbackend側で識別する。 LARM上のprincipalがEumenesサービス主体であっても、Eumenes内で利用者別の参照を管理し、一人の退出で他人のleaseを解放しない。 接続先は承認済みservice定義と固定hostのみを使い、モデルから任意URL・port・unit・commandを指定させない。

SDKの既存waitUntilReadyは待機中のrenewを自動では行わない。今回はconsumer adapterでrenewとresolveを組み合わせ、起動待ちがlease期限を越えないようにする。 呼出し取消時は専用leaseを解放し、複数利用者が共有する起動まで無条件に取り消さない。 応答不明の作成・更新は新しいkeyで再実行せず、保存済み再送識別またはjob状態を確認する。

操作・lease・jobと停止判定

未適用の初期値。単独利用で正常解放できた場合は最後の操作から約5分で停止判定へ進む。
項目 開始値 意味
画面の無操作 180秒 最後の編集・検索・ページ移動等から計る。保存済みならleaseを解放し、受動pollを停止する。
lease TTL / renew 120秒 / 30秒 操作中、起動待ち、保存中、未完了toolのためにbackendが更新する。利用終了後の無条件renewは禁止。
service idle 120秒 全leaseなし、全活動ゼロ、freshな観測が継続した時間。画面無操作時間とは別にLARMが計る。
活動poll / stale 5秒 / 15秒 制御上の観測。観測不明や空白をidleとして扱わない。
起動 / 停止上限 180秒 / 180秒 開始値。期限超過でも停止完了を捏造せず、残るprocessと資源予約を報告する。

起動を維持する実操作は編集、保存、検索、予定変更、資料のページ移動、図の操作と実際のtool実行である。 画面が存在すること、接続が開いていること、heartbeat、readiness、activity、viewerの受動manifest確認、描画animationだけでは維持しない。 初期はidle画面のpollを停止または表示sessionを閉じ、監視要求でactiveRequestsや活動sequenceが増え続けることを防ぐ。 lifecycle/readiness自身を業務活動counterへ入れない。iframeからの活動通知は送信元window・message schema・session対応を検証する。

auto-saveは変更をまとめて行い、未保存変更や保存失敗がある間は意図的にleaseを解放しない。 通信切断時の未送信変更は復旧可能なローカル下書きとして保持し、画面に未保存を示す。ローカル下書きはSSDの保存成功とは区別する。 backendやブラウザーの終了では最後のrenewから期限で回収されるため、固定の「5分停止」を保証せず、lease残時間とservice idleの合計で説明する。

抽出、保存、Archify生成はqueuedJobs・runningJobs・activeRequests等で保護する。画面を閉じても受付済みjobは完了または失敗が確定するまで活動に残る。 DoclingのAPI・processor・viewerを集約したboot識別と活動契約を用意し、既存APIのactivityだけでviewerの実操作を見落とさない。 gatewayのsessionがメモリーに存在することだけをbusyにせず、操作中はEumenes lease、実行中の取得は適切な活動counterで保護する。

idle成立後は既存Managerでdrainし、新規受付を閉じ、同じinstanceToken・App boot・drain tokenの活動ゼロとleaseなしを再確認してTERM停止する。 停止確定前のensureは既存契約どおり再開し、停止確定後は完全停止して次世代を起動する。 子孫processとlistenerの終了観測後にだけ資源枠を返す。自動SIGKILLとjobの無条件再実行は追加しない。

保存、MCP、表示の共通契約

artifact metadataはid、kind、schemaVersion、revision、owner、許可範囲、公開版参照、asset一覧とhashを持つ。 kindはmarkdown、calendar、excalidraw、archifyを初期対象とする。Doclingのsource参照は既存の版契約を保持し、workspace DBへ原本を二重保存しない。 UI stateは文書内容と分け、表示位置の変更だけで内容revisionを更新しない。 calendarは安定event ID、開始・終了、timezone、終日区分とevent revisionを持ち、繰返し予定、通知、外部同期は後続とする。

workspaceの公開APIは作成・取得・版指定更新・一覧・export・job照会に限定し、全更新で利用者認可、expected revision、再送識別を確認する。 MCPと画面は同じ業務操作を使う。MCP用のactor対応はEumenesが認証済み利用者から確定し、tool引数で利用者を選ばせない。 初期workspace MCPはStreamable HTTPを採用し、業務toolとread-only参照を固定schemaで公開する。接続だけではbusyを維持しない。

SQLiteは一つのAPI writerとし、同じDBへ別プロセスから直接書かない。rendererはDBを開かず、固定job directoryの入力を読み結果を返す。 fileは同じSSD内の候補へ書込み、sync・renameで不変版を確定してからDB transactionで公開参照を切り替える。 DB transactionとfile操作は一つの原子的操作ではないため、crashで残る未参照候補をreconcileし、DBから存在しないfileを公開しない。 更新競合は既存版を残して返し、失敗した再生成で最後の成功HTMLを上書きしない。asset回収は参照版と実行中jobを確認して行う。

workspaceのhost画面には、Eumenes backendが対象artifactとread/write権限を確定して発行した短期sessionだけを渡す。 sessionはiframeのメモリー内で保持し、model文脈、会話履歴、localStorageや永続URLへ保存しない。service tokenやactor署名鍵はbackendに留める。 発行・renew時と各取得・保存で利用者の現在の権限と対象版を確認し、idle復帰では新しいsessionを発行する。 短期sessionの発行・message交換・失効と公開asset取得はWP2・WP4の契約としてschema化する。

Archifyは固定revisionのCLI・schema・templateで入力を検証して生成する。自由なshell・任意path・任意package取得は公開しない。 図のJSONや添付assetはサイズ上限を設け、job同時実行は初期1。期限超過はcancel要求と終了観測を分け、未終了ならbusyと資源枠を維持する。 HTMLは隔離したiframeでscriptを許可しつつ同一origin権限とEumenes credentialを渡さず、必要な通信とasset取得だけを定義する。 renderer固有のfont・assetはprepare時に固定し、実行時downloadを前提にしない。

初期Doclingは既存read-only MCPと接続コードによるviewer承認を再利用する。 起動し直すと失効するsessionやMCP接続は再接続し、履歴にはsourceの版と位置を残す。 Eumenesの信頼済み利用者対応、iframe表示、選択箇所から会話へ戻す通信を別途実装する。 LARM用lease token、Knowledge API actor token、MCP token、viewerの短期sessionは混同しない。

資源と受入計測

両サービスは初期CPUのみ、minInstances=0、maxInstances=1とする。workspaceとArchify子processは一つのcgroup予算へ含める。 DoclingのAPI・processor・viewer全体を合算してadmissionへ反映する。memory/CPU/pidsと起動予約の値は固定fixtureのpeakを測ってから配備manifestへ確定する。 旧Docling計画の9 GiB等は測定済み値として転用せず、必要なら検証開始の保守的候補として扱う。

idle停止までの時間、cold起動・warm応答、同時ensureの起動数、DBとassetのI/O、生成・抽出peak、停止後のanon memory回収と残るfile cacheを記録する。 会話中のAI遅延も要求するAgent ProfileとProvider subsetを固定して測る。現在動いているモデルを評価対象の代わりにしない。 Embeddingや回答生成の追加はProfile→route→runtime→backendで解決し、App内に同じLLMを重複配置しない。

backup、復旧、データ移行

初期backupは新規受付を止め、全consumer利用とjobを確認してserviceを正常停止し、DB・全付随file・data・schema版と公開版manifestを同じ時点で取得する。 停止できない場合は延期し、稼働中DBファイルだけをコピーする手順にしない。cache/workは原則対象外、秘密設定は別の暗号化した復旧用backupへ含める。 同じSSD内のsnapshotは更新rollbackには使えるが、媒体故障対策にはならないため、独立したbackup保存先を本番受入前に決める。

restoreはservice停止下で別directoryへ展開し、checksum、DB整合、artifact参照、UID・権限とschema対応を確認してから保存先を切り替える。 release更新はdataを保持し、schema migration前に整合snapshotを取得する。rollbackでdataRootを削除せず、code・schema・データ版の組合せを確認する。 既存資料を移す場合は別工程として入力元、対象件数、停止点、checksumと切戻しを決め、旧配置を検証完了前に削除しない。

正式配備の手順と残条件

prepareは独立repositoryを検査・buildし、Bun、UI、fonts、server、gateway、controllerをGit外のexcalidraw-productionへ固定する。prepared.jsonに全ファイルhashとdigestを記録する。installerの既定動作はdry-runであり、--applyにはrootと--expected-digestが必要。初回登録専用で既存deployment・DBを上書きしない。--bootstrapを明示した場合だけ専用UIDで初期DBを作る。 

bun deploy/local-node/scripts/prepare-excalidraw-hosting.ts
python3 deploy/local-node/scripts/install-excalidraw-hosting.py
sudo python3 deploy/local-node/scripts/install-excalidraw-hosting.py --apply --bootstrap --expected-digest 3d876781599cab9411909511e31ec76502043b8184224ff8e071ac32cb78f376

上記digestは今回の固定成果物の値。再prepareした場合は直前のprepared.jsonのdigestに置換する。installerはSSDのUUID/ext4/rw/空き容量を確認し、root固定unitとmanifest、サービスに限定したpolkit、別々の認証設定を配置する。gatewayの正式portは18790、アプリは18791。LARM leaseが返すpublicEndpointは認可されたgateway consumer用の18791に固定し、gateway自身を返す循環を避ける。利用画面とMCP clientの入口は18790である。登録後もLARMのrestart・gatewayのenable・アプリのensureを自動実施しない。

この環境ではsudoの非対話認証が利用できず、root管理先への正式配置は未実施。稼働中LARM releaseにはv2とSystemdProcessBackendが存在することを読取り確認した。管理者登録後は固定releaseとの対応、既存local-servicesとconsumer設定との統合、larm-daemon-dropin.review、資源受付の実telemetry、専用UIDの停止観測とSSD障害復帰を確認してから有効化する。検証用child process backendは実際のアプリを起動・停止したが、productionのsystemd/cgroup・共通資源受付の認証ではない。

アプリのtypecheck・7単体試験・buildとLARMのbun run checkは合格。追加修正後にもsource-only、operations、typecheck、gateway・installer試験とdocs検査を実施した。独立アプリの出荷buildは約420ファイルで、上流依存の大きなchunk警告は残る。

まだ共同編集・削除・外部共有・上流excalidraw.com互換の共有serverは提供しない。sceneをDBへ登録する前にファイルを公開するため、途中異常では未参照候補が残り得る。削除・容量回収と独立媒体backupは運用工程で設計する。下書きは同じタブ内で復元・exportでき、永続正本は保存成功したSSD版である。
