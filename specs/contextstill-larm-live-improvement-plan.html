ContextStill向けLARM HTTP Provider live改善方針

2026-09-06のlive未到達調査で確認したrelease不一致を解消し、同じ種類の不成立を配備時に検知するための改善方針です。 ContextStill専用endpointは追加せず、Service Activity、公開model catalog、OpenAI互換Chat Completionsという汎用HTTP contractへ統一します。Agent Connectionとclaimは新consumerの依存にしません。

最優先目標
対応済みreleaseをliveへ配備し、Bearer＋modelだけのJSONとHTTP SSEを実通信で受入する
再発防止目標
release identity、公開contract、Provider意味互換、client設定の四層でfail closedにする
Repository実装状態
2026-09-06に標準LLM／ASR／TTS API、model broker、厳密なSSE client、署名済みdesired release、 root activator、収束status、HTTP canary、Queue回復の純粋状態機械を実装。live配備と実consumer組込み待ち
対象外
未承認のsource HEAD自動配備、ContextStill専用API、Provider portのLAN公開、静的Providerへの暗黙fallback

固定する判断

  1. 今回の復旧は新たなSSE実装ではなく、対応済みcommitまたは承認済み後続commitのtransactional releaseで行う。
  2. openai.chat-completions.v1は非streaming JSONとHTTP SSEの両方を含む。 HTTP SSE対応はChat Completionsの標準stream fieldで判定する。
  3. /healthと/readyだけでは配備成功にしない。release identity、公開model、通常Bearer、 JSON、SSE、consumer一件完了までを一つのlive contract gateにする。
  4. source HEADとliveの単純な不一致は即時自動配備の理由にしない。承認済みdesired commitとlive releaseCommitの不一致を警告・停止条件にする。
  5. clientはfail closedを維持するが、待機理由を一つの waiting_for_dynamic_providerへ潰さず、運用者が故障層を判別できる状態を公開する。

根本原因分析

直接原因は、対応済みsourceが1b5e427d5d655e7fb8d2abf10ff46a113f6ae2e0まで進んだ一方、 live daemonが01667fe1a4f9acc18794ae9fd4264487c1063647を実行し続けたrelease driftである。旧releaseは/v1/activityをHTTP 401で拒否し、 contextstill-backgroundをcatalogに持たないため、ContextStillはConnection作成前に fail closedとなる。

障害を継続させた制御上の原因
層 現状 根本的な欠落
Release intent Git commitと人手の依頼書だけが配備対象を示す 承認済みdesired commitを機械が継続監視できる正本がない
Privileged activation release-larm.sh applyは対話的root権限を要求する 承認とactivationの安全な自動handoffがなく、作業者交代で停止する
Completion gate repository testとshadow canaryはlive切替なしでも成功する live identityとconsumer一件完了を満たすまで「完了」を拒否する共通状態がない
Consumer recovery 一時的なProvider不通でも再試行上限後にjobがpausedへ固定される Provider世代の回復を検知してinfra起因jobだけを安全に再開する経路がない
Health semantics 旧static port 44448の不在が障害根拠として扱われる 標準HTTPのcatalog、JSON、SSE、consumer完了で測る統一runbookがない

したがって、単発のsudo実行だけでは今回を復旧できても再発を防げない。また現行 release-larm.shをそのままNOPASSWD化してはならない。候補repositoryのinstall、test、 scriptをrootで実行する経路を非特権利用者へ開くことになり、任意コード実行境界を壊すためである。

恒久対策: 承認済みRelease収束Controller

source、desired、live、consumerを次の一つの状態機械で管理する。source HEADを自動配備せず、 保護されたrelease intentに完全commit IDが承認された場合だけ収束を開始する。

Release intentと状態

  • repository外のroot管理領域へ、完全commit ID、manifest digest、承認者またはtrusted signer、 承認時刻を持つimmutableなrelease intentを置く。
  • reconcilerはdesiredReleaseと/health.releaseCommitを比較し、不一致を pending_activationとして保持する。単発logだけで済ませず、metricsとread-only statusで公開する。
  • statusはvalidated、approved、activated、 contract_verified、canary_verified、consumer_verified、 completeを単調に進め、 failure stage、bounded reason、observed releaseをsecretなしで記録する。

権限境界

  • candidate展開、依存install、全test、manifest生成はugnoguchi権限のbuilderが行い、 rootはcandidate codeを実行しない。
  • root activatorは固定実装で、trusted intent、path、owner、mode、manifestとtree digestを再検証し、 atomic symlink切替とlarm-daemon.service restartだけを行う。
  • post-activation contract gateと推論canaryはdaemon利用者権限で実行する。失敗結果だけをroot activatorへ返し、 activatorは前世代へrollbackする。
  • 無人配備が必要ならprotected CIがrelease intentへ署名し、hostはallowlistした公開鍵だけを信頼する。 任意のworktree HEAD、branch名、環境変数で承認を代用しない。

収束と失敗動作

  1. 同じdesired commitの重複要求は同一operationとして扱い、二重restartしない。
  2. assembly中はliveを変更せず、activationは既存lockの内側で一度だけ行う。
  3. identityまたは軽量contract不一致は自動rollbackし、desiredを未達のまま保持する。
  4. JSONまたはSSE canary失敗もrollbackし、ContextStill Queueを再開しない。
  5. 成功時だけcanary_verifiedへ進め、consumerの一件完了を別の最終ackとして待つ。
  6. 一定時間収束しない場合は状態遷移時と低頻度継続警告だけを通知する。

  1. 調査記録をreviewしてcommitし、release元worktreeをcleanにする。
  2. release-larm.sh planを再実行し、target commit、現在のrelease、cleanup対象、確認digestを operatorが照合する。
  3. 既存のtransactional applyを実行し、失敗時の自動rollbackを維持する。
  4. /healthのreleaseCommitとconfigRevisionが候補manifestと一致し、 bootEpochが旧値から変化したことを確認する。
  5. ContextStill hostと同じLAN経路から/v1/activityが200、 /v2/agent-profilesにcontextstill-backgroundが一意に存在することを確認する。
  6. Activityがidleのときだけ同ProfileをexplicitAgentProfile: true、 allowFallback: false、deploymentPolicy: existing-onlyで作成する。
  7. claimされたbase URL、model、短期Bearerだけで、短いJSON completionとHTTP SSE completionを行う。 SSEは有効なdelta一件以上、全choiceのfinish reason、終端data: [DONE]を必須にする。
  8. Connectionを解放してtoken失効、active allocation 0、workerのidle回収を確認してから、ContextStillの LLM必須jobを一件だけ実行する。
  9. 次job境界でActivityを再確認し、旧127.0.0.1:44448への接続が0件であることを確認する。

P1: live contract gate

従来のsmokeはResident Allocationと独自transportを別々に検証していた。 contextstill-backgroundをAgent Connectionの短期credentialでHTTP SSEまで通す 汎用HTTP Provider smokeへ置換する。

新しいgateはprofile、audience、期待model、期待release identityを引数化し、次を検証する。

  • desired commitと/health.releaseCommit、manifest config revisionの一致
  • Activityのstrict schema、freshness、idle条件
  • Profileのselection policy、deprecated、protocol、public model、Audience
  • create、ready poll、claim、provider health、JSON completion、HTTP SSE completion
  • SSEのstatus、media type、event区切り、chunk JSON、delta、finish、[DONE]
  • release後のtoken 401、Allocation・execution slot漏れなし、worker idle回収

tokenはprocess memoryまたはmode 0700の一時directoryだけで扱い、標準出力、journal、証跡JSONへ 書かない。cleanupはsignalと途中失敗を含む全経路で実行する。

release script自身には、推論を伴わない軽量post-activation contract検査を追加する。release identity、ready、Activity、catalog revision、設定済みProfile全体のいずれかが候補releaseと異なる場合は 自動rollbackする。OpenAPIのtext/event-stream広告はrelease前の自動testで固定する。 モデルloadを伴うHTTP Provider smokeはattended canaryとして直後に実行する。

P1: Provider意味互換の強化

現行のLLM semantic readinessはstream: falseの一token JSONだけを検証するため、Providerが HTTP SSEを返せなくてもclaim可能になる。Chat Completions Providerには、短いSSE probeを追加する。

  • stream: true、max_tokens: 1、Accept: text/event-streamを使用する。
  • 200とSSE media type、bounded bytes、valid UTF-8、少なくとも一つのchunk、[DONE]を検証する。
  • JSON probeとSSE probeが両方成功した場合だけready: trueにする。
  • probe結果は現行と同様に短時間cacheし、同時health requestは一つへ集約する。
  • timeout、client切断、Allocation失効時はupstream bodyをcancelし、execution slotを必ず解放する。

Gatewayは引き続きSSE bytesを再構成せず透過する。runtime中の形式違反はstreamをabortし、metricsへ boundedなreasonを記録するが、不正なeventを補正したり[DONE]を捏造したりしない。

P1: release driftと待機理由の可観測化

  • operatorが承認したdesired commitをrepository外のroot管理stateへ記録し、live releaseCommitとの差をread-only auditで検出する。
  • source HEADとの差だけでは自動切替しない。未reviewのcommitを本番へ流さない。
  • release_identity_mismatch、activity_unauthorized、 profile_missing、connection_rejected、sse_contract_failureを区別する。
  • ContextStillはQueueをfail closedで保持しつつ、現在理由、最終HTTP status、失敗段階、最終成功時刻を secretなしで状態表示する。
  • 同一失敗を毎pollでlogせず、状態遷移時と低頻度の継続警告だけを記録する。
  • LARM metricsにはstream request結果、upstream media type mismatch、client cancel、timeout、 release identityをbounded labelで追加し、request IDやConnection IDをlabelにしない。

P1: ContextStill側の改善

  • resident daemonの実効設定でProvider kind、control host、Profile、Audienceをstartup時に記録する。
  • /v1/activityへqueryとbodyを送らず、optional bearerは設定時だけ送る。
  • 401、404、invalid schema、stale activityをidleへ読み替えず、静的Providerへfallbackしない。
  • claimのbase URL、model、tokenを上書き・永続化せず、Connection世代をまたいで再利用しない。
  • SSE response bodyの完了または失敗までtimeoutを維持し、次jobの前にActivityを再確認する。
  • 再試行は上限付きexponential backoffとjitterを使い、Queue item自体はclaimしない。
  • Provider取得失敗をjob実行失敗のattempt budgetへ加算しない。 provider_unavailable_exhaustedは終端pausedではなく、Provider世代の変化を待つrecoverable状態にする。
  • LARMのreleaseCommit、configRevision、bootEpochでProvider世代を識別し、 新世代のActivity、Profile、canary成功後に同理由のjobだけをwaitingへ戻す。
  • 自動回復は最初に一件、その成功後にbounded batchへ広げる。LLM response、入力、永続化など Provider可用性以外の失敗265件は自動対象に含めない。

導入順序

  1. 復旧: 現行候補を配備し、手動のContextStill HTTP canaryを完了する。
  2. 状態正本: root管理のrelease intentとsecret-freeな収束status schemaを追加する。
  3. 権限分離: 非特権builderとcandidate codeを実行しないroot activatorへrelease処理を分割する。
  4. 収束制御: approved、activated、contract、canary、consumerの各gateを状態機械で接続する。
  5. Queue回復: Provider世代回復後、infra起因paused jobを一件canaryから段階再開する。
  6. 監視移行: static port監視を廃止し、9810のcatalog、JSON、SSE、consumer completionをSLIにする。

P1実装を待ってP0復旧を遅らせない。最初のlive受入はattendedで行い、受入後にだけContextStillの Queueを一件ずつ再開する。

標準HTTP統一のRepository実装記録

  • GET /v1/models、LLM JSON／SSE、ASR multipart、TTS audioを通常Bearerと公開modelだけで 呼べる。事前allocation、Profile、claim headerを要求しない。
  • model brokerが公開modelから内部Routeを一意に解決し、Residentの即時利用、Preferredの single-flight起動、参照数、cancel／完了後の解放を管理する。
  • SSEはUTF-8／CRLF／任意chunk境界、tool delta、finish、[DONE]を増分検証し、 invalid EOFを成功にしない。clientは検証済みchunkをAsyncIteratorで直ちに渡す。
  • 音声例はASR→LLM SSE→句単位TTSをpipeline化し、LLM全文完成前に最初の発話を合成する。
  • 非特権builder、署名済みdesired intent、候補コードを実行しないroot activator、atomic rollback、 /v1/release-convergence、canary→consumer順序gateを実装した。
  • larm-http-provider-monitor.timerは9810のcatalog、JSON、SSEを検査し、同一 release／config／boot世代のsample、失敗、最大gapを永続化する。24時間、96 sample以上、失敗0、最大gap 30分以下になるまでcompleteへ進めず、44448を監視しない。
  • packages/core/src/provider-recovery.tsは新しいcanary済みProvider世代でinfra起因pauseだけを 1、2、4件と段階再開し、同一世代、手動pause、business pause、失敗waveをfail closedにする。

repository完了はlive完了ではない。rootによるinstall／activation、live identity、HTTP canary、 ContextStill sourceへの状態機械組込み、実job一件完了、24時間soakが残る。

標準HTTP統一前のAgent Connection参考実装記録

  • packages/core/src/openai-sse.tsにboundedなOpenAI SSE検査器を追加し、valid UTF-8、SSE field、chunk JSON、meaningful delta、finish reason、終端[DONE]を検証する。
  • 最終code reviewでJSON検査器を共通化し、必須response identity、stream内model一貫性、choice index、finish状態遷移を追加した。要求aliasは解決後model名へ正規化可能とし、公開modelはProfileと claim descriptor間で固定する。厳密なmedia typeとfatal UTF-8を使い、拒否した未読bodyをcancelする。
  • LLM semantic readinessをJSONとSSEの二段probeへ変更し、同じ固定Bindingとexecution slotの中で両方が成功した場合だけclaim可能にした。
  • deploy/local-node/scripts/smoke-agent-http.tsを追加した。Profile discovery、create、ready、claim、semantic health、JSON、SSE、release、token 401、最終Activityを secret-freeな一つの結果として検証する。途中失敗でもConnectionを解放する。
  • deploy/local-node/scripts/verify-live-contract.tsをrelease後gateへ組み込み、候補manifestと live identity、Activity、Agent Profile全体の一致を確認する。新releaseの不一致は既存のtransactional rollbackを発火し、旧releaseへのrecovery確認は後方互換のidentity・ready検査を使う。
  • release gateは候補release内の検証コードを一度だけ実行し、release versionを限定SemVerとして 検証する。契約失敗を60秒間再試行して診断を隠す挙動を廃止した。
  • 後続の恒久実装で、非特権build-larm-release.shとinstall済みroot activate-larm-releaseへ分離した。builderは明示した完全commitだけを検証・buildし、 tree digestを含むmanifestとdesired intentへ署名する。rootは候補をcopy後に署名・digestを再検証し、 候補コードやtestを実行せずatomic切替、軽量contract、失敗時rollbackだけを行う。
  • /v1/release-convergenceへsecret-free statusを公開し、HTTP Provider canary evidenceより前に consumer evidenceを受理しないgateを追加した。ContextStill一件完了、成果一回保存、次job境界の Activity再評価後はconsumer_verifiedとなり、さらに同一世代の24時間HTTP soakが揃った場合だけcompleteになる。
  • 定期監視はlarm-http-provider-monitor.timerから9810のmodel catalog、JSON、SSEを検査する。 旧static port 44448は監視しない。

最終code review後のshadow再受入でも、JSON、SSE 10 chunk、meaningful delta 8件、finish reason 1件、[DONE]、release、token 401、Activity idleを確認した。cleanup後はAllocation、worker、 旧静的Provider port接続、一時資産がすべて0である。

最終受入条件とrollback

  • desired commit、live release、catalog revision、boot epochが証跡上で一貫する。
  • ContextStill hostからActivity、model catalog、Bearer認証、JSON、SSEが独自bootstrapなしで成功する。
  • SSEは一貫したchunk identity、有効delta、全choiceのfinish、[DONE]を受信し、 成功JSONをSSE成功として扱わない。
  • HTTP完了またはcancel後にactive workload、内部Allocation、execution slotが0へ戻る。
  • ContextStillのLLM必須jobが一件完了し、次job境界でActivityが再評価される。
  • Provider portおよび旧127.0.0.1:44448へのclient接続が0件である。

release identity、Activity、model catalog、Provider health、JSON、SSEのいずれかが失敗した場合はQueueを fail closedのまま維持する。LARM releaseを既存のtransactional rollbackで戻し、client側の静的 Providerへ暗黙fallbackしない。
