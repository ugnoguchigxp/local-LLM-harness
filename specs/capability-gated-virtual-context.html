高度推論LLM連動型Virtual Context Activation仕様

Qwen 3.8 27Bのように、長い文脈を用いた複雑な推論へ適合すると明示されたLLMが実際にhostされ、 利用可能になっている間だけVirtual Context subsystemを有効化する設計です。対象LLMが存在しない経路では 通常のOpenAI互換Gatewayを使用し、Context Router、KV materialization、prewarmなどの重い処理を 起動しません。

実装結果

Core schema、release certification、host連動activation、20M Source Set、Active View、 source-rebuild、control API、typed client、source provisioning、systemd配備設定を実装した。 quality workerの公開modeはsource-rebuildと認定済みsession-snapshotである。

M3aは容量と同process出力一致を満たしたが、1 byteを反転したraw snapshotをstock llama.cppが HTTP 200でrestoreしたため、raw snapshot直接利用をNo-Goとした。詳細は Qwen3.8 quality KV snapshot M3実測証跡に記録する。これはsnapshot方式全体の構造的No-Goではない。snapshotは再生成可能なローカル実験cacheであり、 悪意ある改ざん、機密性、暗号学的真正性を非目標とする。M3bでchunk CRC32C、atomic commit、strict manifest、source-rebuild fallbackを追加して再試験し、全exit条件を満たしてM3b Goとした。実測は Qwen 3.8 quality CRC32C snapshot M3b Go証跡 に固定する。

再監査のrequirement別結果は Managed Context実装完了トレーサビリティ に記録する。自己申告token数の排除、実chat prompt再tokenize、live identity probe、operation API、 pagination、source byte quotaを追加し、M0–M2の契約差分を閉じた。

決定

  1. model名やparameter数から推論能力を自動推定しません。Operatorがruntimeへ managed-context classを明示し、release単位の適合試験を通した場合だけ対象にします。
  2. Virtual Contextはruntime単位でactivationし、対象runtimeがHOTまたは BUSYで、release identityとContext conformanceが一致している間だけ materialization data planeを有効にします。
  3. 対象runtimeがCOLDならstandbyとします。Context metadataとNVMe snapshotは保持できますが、 prefill、restore、RAM promotion、prewarmを行いません。
  4. 通常LLM、speed専用model、ASR、TTS、embeddingは明示的にdisabledとし、Context subsystemを 経由しません。
  5. Qwen 3.8 Hybrid modelの初期production modeはsource rebuild、exact prefix、session snapshotに 限定します。non-prefix KV blendは別のexperimental capabilityとします。

用語、正本、不変条件

Source Set
principalが参照可能なimmutable sourceの候補集合です。20M tokenはこの集合のtokenized総量上限であり、 一requestのcontext windowでもKV量でもありません。
Context Plan
呼出側が提示する候補、required指定、utility、versionの集合です。まだruntime stateを持ちません。
Active View
一つのAllocationとreleaseへbindした、context window内に収まるcanonical token列です。 LLMが一度にAttentionするのはこの列だけです。
Materialization
Active Viewをsource prefillまたは認定済みsnapshot restoreでruntime stateへ変換する処理です。
Materialized retention target
validなsnapshot entryのtokenCount合計20,000,000 token相当です。 同一viewDigestの完全重複snapshotは一度だけ数え、同時Attention量とは区別します。 stock slot snapshotへsub-prefix dedupは仮定しません。
Context certification
release identityとmodeの組について、安全性と再現性を証明するversioned evidenceです。

次を非交渉の不変条件とします。

  1. runtime lifecycleの正本は既存Observer、配置の正本はAllocation bindingです。
  2. runtime eligibilityの正本はruntime policyとactive Runtime Release certificationの積です。
  3. source本文と選択意味論の正本はSAAA／Source Providerであり、LARMはKnowledgeを推測しません。
  4. token数の正本は対象releaseのtokenizerによるcanonical tokenization結果です。
  5. Active Viewは一つのprincipal、Allocation、runtime、release、slot、lease epochだけに属します。
  6. 20M Source Setから一requestへ入る量は必ずruntimeのinput budget以下です。
  7. cacheは正しさの正本にしません。miss、invalid、No-Go時はimmutable sourceから再構成します。
  8. Context機能がruntimeをload／keep-aliveしてはなりません。対象runtimeがhostされた結果に追随します。

IDは128文字以下のopaque identifier、時刻はUTC RFC 3339、byte数とtoken数は非負整数とします。 永続recordはschema versionを必須にし、unknown fieldを拒否します。

CRC32C snapshot envelope

algorithmはCRC-32C（Castagnoli）へ固定し、snapshotのraw byte列を先頭から64 MiBずつ処理する。 最終chunkだけ短くできる。CRCは各chunkについて独立に初期化し、lowercase 8桁hexでmanifestへ保存する。 chunk配列のindexは0から連続し、各byte数の合計がsnapshotBytesと一致しなければrecord全体を拒否する。 

SnapshotManifestV1 {
  schemaVersion: 1
  algorithm: "crc32c"
  entryId: opaque-id
  compatibilityKey: release-bound-id
  principalScope: principal-id
  snapshotBytes: uint64
  chunkBytes: 67108864
  chunks: [{ index: uint32, bytes: uint32, crc32c: hex8 }, ...]
  state: "committed"
  createdAt: RFC3339
}

保存はsnapshot temporary file、manifest temporary file、両fileのfsync、rename、親directoryの fsyncの順でcommitする。復元はmanifest strict parse、全長照合、全chunk CRC検証、検証前後の device／inode／size／ctime再照合に成功してからslot restoreを呼ぶ。同一boot内の再利用だけ、これらのidentityと manifest revisionを鍵に検証済み状態をcacheする。

Eligibility判定

高度推論LLMであるという運用判断と、KVを安全に扱えるという技術判断を分離します。次の全条件を満たした runtimeだけをeligibleとします。

  1. protocolがopenai.chat-completions.v1である。
  2. runtime catalogでcontext.class: managed-contextが明示されている。
  3. 既定ではllm.reasoning capabilityを持つ。
  4. Active releaseがmodel artifact、tokenizer、chat template、engine buildを一意に固定する。
  5. 宣言されたmaterialization modeについてContext conformance suiteが成功している。
  6. runtime context limitとoutput reserveをtokenizerで強制できる。
  7. principal isolation、byte quota、source rebuild fallbackが構成されている。

Qwenを含むmodel名や27B以上という条件は使用しません。同じmodelでもengine、KV dtype、 MTP、context sizeが違えば別の認定対象です。

Request経路

対象外request

request
  -> model binding
  -> Context Eligibility Gate: disabled
  -> existing ExecutionGate
  -> existing Gateway
  -> runtime

対象外ではContext Registryへ問い合わせず、snapshot storeをopenせず、background timerも起動しません。 判定はmemory上のruntime ID lookup一回に限定します。

対象request

  1. 既存Model Brokerがmodelを解決し、必要ならworkerをloadする。
  2. Allocationとrelease bindingを確定し、activationがACTIVEになるまで待つ。
  3. SAAAがcontext ID、version、relevance、required flagを持つContext Planを提示する。
  4. Schedulerがruntime固有のcontext limitとoutput reserveからActive Viewを決める。
  5. adapterがexact restore、append prefill、source rebuildの順で安全なmodeを選ぶ。
  6. materializationとgenerationを同じexecution reservationとruntime binding内で完了する。
  7. 結果とcache outcomeを記録し、Allocation release後にidle snapshot候補を評価する。

restore後に別requestが同じslotを取得するとstateが混線します。local-nodeの maxConcurrentRequests: 1を維持し、将来複数slotへ広げる場合は view_idとruntime slotを一つのatomic leaseにします。

Active View決定algorithm

inputBudget = min(
  request.maxInputTokens,
  certification.contextLimitTokens
    - policy.outputReserveTokens
    - policy.safetyMarginTokens
)

reject if request.baseInputTokens + requiredTokens > inputBudget
selected = all required items
for item in optional items sorted by (-utility, contextId, version):
  append item only if canonicalized total remains <= inputBudget
viewDigest = sha256(canonicalizationVersion + ordered token digests)
  • 初期値はoutputReserveTokens: 32768、safetyMarginTokens: 4096です。
  • 同点時順序を固定し、同じ入力とreleaseから常に同じviewDigestを得ます。
  • required itemが収まらなければ暗黙truncateせず422 context_budget_exceededです。
  • optional itemのomit理由とtoken数をresponseへ返し、選択の説明可能性を保ちます。
  • source token数が登録値と異なる場合はviewを作らず、descriptorをinvalid化します。

「動的」はgeneration開始前のturn境界、およびtool result後の次generation境界でActive Viewを再選択する 意味です。現行engineの一回のforward／token生成途中にKV blockを差し替えません。 mid-generation fetchが必要になった場合はgenerationを安全に終了し、新しいAllocation-bound viewで再開します。

baseInputTokensは事前planning用の値です。generation直前に認定runtimeのchat templateを実際のmessagesとtool定義へ適用し、全promptをcanonical tokenizerで再計数します。 再計数値がActive View budgetを超える場合は422で拒否するため、過少申告では上限を迂回できません。

起動と停止

起動

  1. ObserverがruntimeをHOTとして公開する。
  2. Activation Controllerがruntime policyとactive release certificationを照合する。
  3. backend adapterがloopback endpoint、slot／cache feature、state formatをprobeする。
  4. tokenizer、template、context limit、KV設定のdigestを検証する。
  5. snapshot indexをopenし、互換性のないentryをinvalidへ遷移する。
  6. 短いContext probeに成功した後だけACTIVEにする。

停止

  1. STOPPING、daemon drain、release切替でDRAININGへ遷移する。
  2. 新しいrestore、prefill、snapshot、prewarmを拒否する。
  3. 実行中requestは既存non-preemptive policyに従い、bounded deadline内で完了させる。
  4. 未完了snapshotをcommitせず、一時fileをorphanとして記録する。
  5. RAM handleとslot reservationを破棄し、NVMe metadataをflushする。
  6. runtimeがCOLDならSTANDBYへ戻る。

Runtime unloadを防ぐためだけにContext subsystemがAllocationを保持し続けることは禁止します。 model lifecycleのownerは既存Controllerのままにします。

Control API案

OpenAI bodyへ独自fieldを必須化しません。SAAAは認証済みcontrol APIでContext Viewを作り、 Chat Completionsへopaqueなview IDをheaderで渡します。raw slot ID、filename、filesystem pathは 外部contractへ出しません。

Resource contract

20M token retentionとdisk quota

Source Setの20M tokenすべてを動的選択の候補にし、q4認定releaseについてはdedup後の有効snapshotを 合計20M token相当保持できることもcapacity targetにします。ただし、一つのrequestで同時Attentionする量は modelのcontext limit以内です。 Qwen 3.8 27Bのfull-attention層だけをq4 KVとして18 KiB／tokenで概算しても、 20,000,000 tokenは約343.32 GiBです。header、alignment、Hybrid recurrent state、一時write、GC余地を加味し、 暫定hard quotaを512 GiBにします。最終値はM3で測ったp99 byte／tokenから算定し、512 GiBで不足する場合は 64 GiB単位で切り上げます。 

retentionBytes = ceil(
  measuredP99SnapshotBytesPerToken
  * materializedRetentionTargetTokens
  * 1.10
)
writeReserveBytes = measuredP99MaxActiveViewSnapshotBytes + 8 GiB
requiredHardQuota = roundUp64GiB(max(
  retentionBytes / cacheHighWatermark,
  retentionBytes + writeReserveBytes
))

Compatibilityとinvalid化

次の値をまとめたdigestをContext compatibility keyとします。一項目でも変わればsnapshotをrestoreせず、 source rebuildへfallbackします。

  • model artifact SHA-256とRuntime Release ID
  • tokenizer、special token、chat templateのdigest
  • engine binary digestまたはbuild commit、state format version
  • K/V dtype、MTP、attention backend、context limit
  • RoPE／YaRN、SWA、Hybrid recurrent checkpoint設定
  • LoRA／adapter digest
  • principal／scope saltとcanonical token prefix digest

Release activation、rollback、worker切替ではkeyを再計算します。旧snapshotは invalidへ遷移し、rollback window中だけquota内で保持できます。

Security

snapshot機能は信頼されたローカルホスト上の実験cacheである。偶発破損、partial write、identity mismatchを検知対象とし、悪意ある同一host管理者、暗号学的改ざん耐性、snapshot単体の機密性は非目標とする。 機密dataを保存する運用はsnapshot機能を無効化するか、host側のdisk暗号化を別途使用する。

  • KV、recurrent state、source referenceはpromptと同じ機密classificationで扱う。
  • snapshot storeはrepository外、mode 0700、service専用ownerとする。
  • forgetはregistry tombstoneとunlinkで実施し、物理secure eraseは保証しない。
  • cache hitをprincipal／scope saltで分離し、cross-consumer timing side channelを抑える。
  • runtimeのslot APIを公開せず、backend adapterだけがloopbackで呼び出す。
  • 外部入力からmodel path、slot、snapshot filename、cache rootを指定させない。
  • Context View credentialは短命かつAllocation、model、principal、releaseへbindする。

M3b測定protocol

  1. release、engine digest、provider config、temperature 0、seed、prompt token列を固定する。
  2. 決定的な多言語token列を8K、64K、229,376 tokenへcanonicalizeする。
  3. source prefillとsave、同process restoreを各5回実施し、runtime restart後も全3長を照合する。
  4. 次のgreedy 128 token、save／restore秒、prefill秒、snapshot byte、peak RAM、disk write量を記録する。
  5. 64 MiBごとのCRC32Cを保存時に計算し、manifestへindex、実byte数、CRCを順序付きで記録する。
  6. truncate、single／multiple bit flip、chunk欠落／並べ替え、manifest不整合、別release、別principal、 stale fenceを注入し、すべてrestore前に拒否されることを確認する。
  7. 検証なしraw restore、boot後初回のCRC32C全走査＋restore、同一boot epochでinode identityを再確認する 検証済みrestoreを交互に各20回測定し、p50／p95、CPU時間、read byteを記録する。日常経路の110% gateとcold経路のprefill比を分離し、400 GiB全体をstartup scanしない。
  8. daemon再起動時はmanifestだけを読み、snapshot本文を全走査しない。初回利用後はdevice、inode、size、ctime、 manifest revision、boot epochを検証済みcacheへ固定する。
  9. evidence JSONと要約HTMLだけをrepositoryへ置き、prompt、snapshot、binary、log本文はcommitしない。

要約

Virtual Contextをdaemon全体の常時機能にはせず、明示認定された高度推論runtimeへ付随する lifecycle-scoped subsystemにします。Qwen 3.8がhostされていない間はstandby、loadとprobe完了後だけ active、unload時は重い処理とRAM stateを解放します。これにより通常providerの単純さを維持しながら、 高度推論LLMにだけ20M候補集合からの動的Active Viewを提供し、q4認定releaseでは 合計20M token相当のsnapshot retentionを目標にします。disk hard quotaは512 GiBですが事前割当は行わず、M3実測式、 90%／80% watermark、256 GiB free floorを正本とします。
