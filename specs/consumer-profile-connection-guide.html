LARM プロファイル選択と接続の共通手順 ContextStillとSAAA

ContextStillとSAAAが、同じLARM Agent Connection APIでプロファイルを選び、返されたProviderへ接続するための共通手順です。標準は6ステップです。即時readyなら待機を省略でき、5回のAPI呼び出しで1回の処理を完了できます。長時間利用では更新と再claimの2操作を追加します。

このPageは2026年10月3日に確認した配備済み実装を根拠とする利用仕様と、Consumerへ適用する共通方針です。Consumerの実装修正・動作確認は未実施です。

ContextStill の ROCmFP4 プロファイル構成

2026年10月3日のリポジトリ設定更新で、公開 selector contextStill は contextstill-background を選択し、 llm・system-one・embedding の3 Providerを提供する。llm は llm-contextstill-ornith 経由で ornith-contextstill runtime を解決する。モデル名は claim 応答の ornith-contextstill を使用する。 この設定更新は配備完了や4並列の実機性能を示す証拠ではない。

Provider 構成 容量と方針

各Queueの1要求は入力と生成の合計32,768 tokenを上限とし、Consumerは送信前にモデルのtokenizerで system prompt・tool schema・履歴を含む入力を数える。出力予約の既定は4,096 tokenなので、 入力は28,672 token以内。catalogのcontextWindowはこの要求上限を表し、backendのKV総量とは区別する。 LARMの設定更新だけでConsumerのtoken検査が実装されるわけではない。

Ornith runtime のメモリ見積もりは44 GBとし、既存256K ROCmFP4経路と同じ保守的な予約値を使う。 4並列のピークと完了ジョブ数／分は未測定。旧Qwen 64K / 128K profileは明示選択用として残り、 contextStill selectorのfallbackには含めない。SAAAとの優先度・排他方針は既存のConnection契約に従う。

2026年10月4日の実機配備調査では、旧モデル名を必須とする起動検査と、会話用Gemmaと ContextStill用Ornithの同時warmによる予約メモリ超過を確認した。起動検査はdefault Agent Profileの 公開LLMからモデルを選ぶ。ContextStill用OrnithはminInstancesを0にして要求時に起動し、 conversation-llm-slotで利用の終わった会話用モデルと入れ替える。 初回の再配備後に3 Providerの実応答と4件の同時処理を確認した。ただし4並列のMTP有効時に 項目の重複や欠落が出たため、ContextStill経路はMTPを無効にする。同じ短い入力でMTP無効時は 4件とも3項目で完了したが、中国語混入が1件あり、日本語品質の課題は残る。 この比較だけでMTPを唯一の原因とは断定しない。最終releaseの実機検証は配備後に記録する。

今回の挙動から分かること

ContextStillの画面にはLocal LLM / coding-defaultが表示され、同時間帯のLARMログはllm-defaultからornith-generalへの実行を記録しています。ContextStill用Qwenの稼働は確認されませんでした。ContextStill用Connectionを使っていない疑いはありますが、画面のタスクIDとLARMのrequest IDを照合していないため、接続作成の欠落、claim結果の未適用、別処理のログ、意図的な既定モデル指定のどれかは未特定です。

LARMはホスト全体を一つのプロファイルへ変更する仕組みではありません。要求したprofileとProvider subsetからConnectionを作成し、そのConnectionに結び付いたProviderを利用します。現在起動中のモデル名だけで、Consumerの選択の成否を判定しません。

正本と適用範囲

モデル・route・runtime・優先度の正本はLARMのcatalogと設定です。Consumerは起動時と再接続時に公開catalogを読み、claimの応答から接続情報を取得します。このPageをContextStillとSAAA共通の利用手順として参照し、アプリごとの独自な接続手順を増やさない方針を提案します。

確認対象は配備release dbbe3237171218d94a9c1f3eeba8aef586288637、APIのcatalog契約agent-connection.v3、Connection操作のURLは/v1/agent-connectionsです。discoveryがv3でもConnection URLを/v3に置き換えません。

SAAAのローカル作業ツリーには未コミット変更があり、プロジェクトの規則に従ってpullと実装調査を保留しました。SAAAが以下の手順を既に満たすとは認定していません。

プロファイルと接続先の選び方

用途別の公開プロファイルとProvider
用途 createのprofile 2026年10月3日の具体Profile Provider
ContextStillの背景処理 contextStill contextstill-background embedding、llm、system-one
SAAAの会話 SAAA saaa-conversation-ornith15 asr、backchannel、embedding、llm、tts
SAAAの会話LLMだけ SAAA 同上 providersにllmだけ指定

profileは大文字小文字を含め公開selectorをそのまま指定します。ContextStillはcontextStill、SAAAはSAAAです。discoveryのprofiles[0].idは具体Profileの確認用で、createのprofileへそのままコピーしません。配備済みcreateは公開selectorを受け取ります。

同じホスト上のConsumerはaudienceにsame-hostを指定します。別端末のConsumerはcatalogにあるsaaa-desktopを使い、その端末から到達できるLARMのLANアドレスへcontrol APIを送ります。別端末で127.0.0.1を使うと別端末自身を指します。clientは利用者識別用の文字列で、権限やプロファイル選択を代替しません。

Provider名とprotocolは毎回catalogから取得します。providersを省略すると選んだProfileの全Providerが対象になるため、用途に必要なsubsetを明示する方針を推奨します。ProfileのservicesはConnectionのprovidersとは別契約です。

標準の6ステップ

接続から解放までの6ステップ
ステップ API 成功条件とConsumerの処理
1 選択を確認 GET /v3/agent-profiles?profile=contextStill requestedProfileと具体Profile、Provider名、protocol、catalogRevisionを確認
2 Connectionを作成 POST /v1/agent-connections 201または202。id、allocationId、bootEpoch、profile、agentProfile、expiresAtを保持
3 readyを待つ GET /v1/agent-connections/{id} statusがreadyかつ必要なProviderがclaimable。pendingとprobingの間は待つ
4 接続情報を取得 POST /v1/agent-connections/{id}/claim 200。ProviderごとのURL・model・credentialを一組として受け取る
5 実処理を送る claimのbaseUrlとprotocolに対応するendpoint claimのmodelと専用Bearerで送信し、成功を確認
6 解放 DELETE /v1/agent-connections/{id} 204。SDKとトークンを破棄

201でもbodyのstatusとProvider状態を確認します。202は受付済みで、利用可能という意味ではありません。GET statusのHTTP 200もreadinessの証明にはならず、bodyを判定します。failed、released、expiredは待機を終了します。

待機は応答のRetry-Afterがあれば尊重し、readyDeadlineとexpiresAtを超えて無制限に繰り返しません。待機間隔は1秒から最大5秒へのbackoffを共通方針として提案します。createはPrefer: wait=Nを受け付けますが、今回の実装は最大3秒の待機なので、ポーリングを省けるとは限りません。

初回のAPI呼び出し数は、discovery 1回、create 1回、status 0回以上、claim 1回、処理1回、release 1回で、合計5回以上です。catalogを有効なrevisionとともに再利用する場合はdiscoveryを省けます。health確認を別に行う場合や複数の実処理を送る場合は、その分だけ増えます。

ContextStillの具体的な要求

以下はHTTP要求のテンプレートです。山括弧の値は応答や実環境の値に置き換えます。control APIの認証は配備の方針に従います。長期control BearerとclaimされたProvider Bearerを混同しません。 

GET /v3/agent-profiles?profile=contextStill

POST /v1/agent-connections
Content-Type: application/json
Idempotency-Key: <この接続作成を識別する一意キー>

{
  "profile": "contextStill",
  "expectedCatalogRevision": "<discoveryのcatalogRevision>",
  "audience": "same-host",
  "client": "contextstill",
  "providers": ["llm"],
  "ttlSeconds": 900,
  "allowFallback": false,
  "deploymentPolicy": "existing-only"
}

expectedCatalogRevisionを使って選択時と作成時のcatalogの不一致を検出します。変更が検出されたらdiscoveryからやり直します。同じcreateの通信再試行は同じIdempotency-Keyとbodyを使い、プロファイルやbodyを変える場合は新しいキーを使います。

existing-onlyは既存の配備済みruntimeを使う方針で、プロセスが既に起動中であることを要求する指定ではありません。LARMが必要に応じて起動します。allow-listedは管理トークンを必要とする別操作なので、通常のConsumer接続には使いません。 

GET /v1/agent-connections/<id>

POST /v1/agent-connections/<id>/claim
Content-Type: application/json

{
  "format": "openai-provider-v1"
}

claimにはIdempotency-Keyを付けません。返されたprovidersからnameがllmのものを取得し、configuration.fields.baseURL、configuration.fields.model、credential.tokenをSDKへ適用します。secretFields.apiKeyの文字列credential.tokenは参照パスであり、APIキーそのものではありません。 

provider = claim.providers.find(name == "llm")
SDK.baseURL = provider.configuration.fields.baseURL
SDK.model = provider.configuration.fields.model
SDK.apiKey = provider.credential.token

POST provider.baseUrl + "/chat/completions"
Authorization: Bearer provider.credential.token
body.model = provider.model

今回のcontextStill discoveryではllmの公開modelはqwen-agent-workerです。実際に使う値はclaim応答から読みます。coding-defaultをハードコードして送る、既存のSDKを使い回して古いmodelやAPIキーを残す、claim後も固定のバックエンドポートへ直接送る、という実装はこの共通手順を満たしません。通常のチャット推論ではallocationヘッダーはProvider tokenから解決され、追加する場合はそのConnectionのallocationIdと一致させます。context viewなど他の契約で必要なヘッダーは別途適用します。

SAAAへ適用する差分

SAAAは同じ6ステップを使い、discoveryとcreateのprofileをSAAAへ変更します。LLMだけの用途はproviders: ["llm"]、会話全体では必要なProviderをまとめて指定します。

claimには混在したProvider descriptorが返り得ます。LLMとbackchannelはChat Completions、ASRはAudio Transcriptions、TTSはAudio Speechを使います。embeddingはlarm.embedding.v1で、OpenAIのembeddings APIと同一とは扱いません。configuration.kindとprotocolを確認して、それぞれ対応するクライアントを構築します。共通claimはformat: "openai-provider-v1"で混在descriptorを返す実装です。

現行SAAAには300秒のforeground idle releaseが設定されています。health確認とrenewだけで会話の利用中とみなされるわけではありません。待機中にConnectionが解放されたら、次の会話で新しいConnectionを作ります。解放がモデル停止につながるかは他のConnectionやruntimeのresident policyによります。

長時間利用と再起動後の復旧

長時間使う場合はPOST /v1/agent-connections/{id}/renewにttlSecondsを送り、その更新操作固有のIdempotency-Keyを付けます。更新後は再claimしてSDKのcredentialを交換します。renewはgenerationを変えるため、古いProvider tokenは使い続けられません。 

POST /v1/agent-connections/<id>/renew
Content-Type: application/json
Idempotency-Key: <この更新操作の一意キー>

{ "ttlSeconds": 900 }

共通方針として、残りTTLが3分の1になる前に更新を開始し、新規送信とtoken交換を直列化します。このタイミングはConsumer側の提案で、LARMの必須値ではありません。更新後にclaimが失敗したら新規処理を止め、readyを確認して再claimします。

LARMの再起動でbootEpochが変わると以前のConnectionとtokenは再利用できません。401、connection_not_found、connection_idle_released、expiredなどを検出したら、古いSDKを破棄してdiscoveryから作り直します。非冪等な生成を通信障害で自動再送する場合は、二重実行がないと確認してからにします。

エラー時の対応
状況 対応
createの400 profileやProvider名、body、必須Idempotency-Keyを確認
401または403 control認証とProvider認証、所有者、scopeを確認。既定モデルへ黙って迂回しない

allowFallback: falseを標準にし、利用者の同意なくcoding-defaultや別profileへ切り替えません。待機や再接続の失敗は画面にも表示し、要求profileと実際のmodelを区別します。

仕様を一元化する実装案

共通Connection管理器にdiscovery、create、待機、claim、renewと再claim、release、再起動復旧をまとめます。アプリ側はprofile、audience、必要なProvider、TTLと用途を渡し、管理器からprotocol別のクライアントを受け取ります。

管理状態は未接続、作成中、準備待ち、claim中、利用可能、更新中、再接続中、終了、失敗とします。利用可能になる前に実処理を送れない構造にし、profile変更時は新しいConnectionを作ってSDKを差し替え、古いConnectionを解放します。

Consumerのtelemetryにはtask ID、要求profile、具体agentProfile、Connection ID、allocationId、bootEpoch、catalogRevision、Provider名、公開model、LARM request IDを記録します。LARMの解決runtimeとbackendは管理側ログで照合します。tokenとAPIキーは記録しません。画面のLocal LLM / coding-defaultだけでは、接続選択の正しさを判定できません。

受け入れ確認

  1. contextStillのdiscoveryとcreate応答が一致し、agentProfileが選んだ具体Profileである。
  2. claimのllm modelとSDKのmodel、tokenの対象Connectionが一致する。
  3. 該当タスクとLARM requestを照合し、要求profileからroute、runtime、backendへの経路が一致する。
  4. ready前に実処理を送らず、失敗時にcoding-defaultへ黙って切り替えない。
  5. renew後に新tokenへ交換し、旧tokenを使い続けない。
  6. LARM再起動、TTL切れ、SAAAのidle releaseから再接続できる。
  7. 終了時にreleaseし、subset指定で不要なProviderを確保しない。

ContextStill側の既定モデル迂回の有無と、SAAAの現在の実装との適合は未確認です。このPageの保存はConsumer修正や実接続試験の完了を意味しません。
