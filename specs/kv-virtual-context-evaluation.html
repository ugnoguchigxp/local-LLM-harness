Provider Harness KV Virtual Context案の適用可能性評価

Provider HarnessへWorking Contextの制御を追加する提案を、現在のLARM、local-node、 Qwen 3.8 27B、llama.cppおよびllama-swapの実装に照らして評価した記録です。 結論は条件付き採用です。Long-term Memoryとの責務分離、有限cache、 token budget、admission、eviction、runtime adapterという原則はLARMへ適用できます。 一方、任意のKV blockを独立部品としてActive Contextへmountする方式と、20M tokenを KVとして一体管理する方式は、現在のruntime contractでは実現できません。

最重要の技術的制約

TransformerのあるtokenのKVは、そのtoken本文だけでなく、それより前のtoken列を処理した結果です。 したがって、ctx:typescriptとctx:postgresを別々にprefillして保存し、 後から任意順序でKVだけを連結しても、同じtextをその順序で通常prefillした状態にはなりません。 位置だけを移動しても、前段layerで既に受けたprefixの影響は除去できません。

vLLMのAutomatic Prefix Cachingも、block tokenだけでなく親prefixのhashをcache keyへ含めます。 これはKV blockがprefix依存であることを明示した設計です。llama.cppの --cache-reuseは既存prompt内の一致chunkをKV shiftで再利用できますが、 arbitrary compositionの意味同一性をLARMのcontractにはしません。

「Context Routerがdigestを検索して対応KVをmountする」は、 「SAAAがsource textを選びcanonical promptを組み立て、LARMが一致prefixのcache hitを使う」へ 置き換えます。cache miss時は通常prefillし、その結果を次回用にmaterializeします。

評価着手時点のLARMとの適合

  • config/local-node/llama-swap.yamlには256Kの qwen-quality／qwen-fastと64Kの qwen-agentがあり、全Qwen workerでK/Vにq4_0を指定しています。
  • Resident qwen-generalも256Kですが、worker swap groupの外にあり、 通常・realtime taskの保護対象です。
  • llama.cpp build 10655には既定8,192 MiBのRAM prompt-state cache、 exact prefix再利用、chunk cache reuse、slot全体のsave／restore APIがあります。
  • 評価着手時点ではslot永続化に必要な--slot-save-pathがlocal-node設定になかった。 LARMの公開APIも/slotsを透過せず、Chat Completions bodyを検証してruntimeへ渡すだけです。
  • LARMはmodel／runtimeのadmission、lease、priority queue、swap、telemetryを既に持ちます。 Context materializationのmemoryとI/O budgetを既存admissionへ統合する土台があります。
  • Chat Completionsのbody上限は既定4 MiBですが、入力token数、retrieved context、 output reserveの配分をLARMはまだ計測・強制していません。
  • ContextStill用のqwen-worker-agentは64Kです。すべてのAgent connectionが 256Kを利用できるという前提にはできず、budgetはruntime profileごとに必要です。

既存のworker構成と資源契約はOn-demand LLM Worker Pool 契約、consumer間の非preemptiveな優先順は動的Provider優先度仕様を正本とします。本設計はこれらを置き換えません。

容量評価

対象GGUFのmetadataは、64のtext layerを 16 × (3 Gated DeltaNet + 1 Gated Attention)として構成し、 Gated Attentionは4 KV heads、head dimension 256です。Full Attention 16層分だけを用いた attention KVの概算は、q4_0で18 KiB/token、q8_0で34 KiB/tokenです。

Qwen 3.8 27B target modelのFull Attention KV概算
tokens q4_0 K+V q8_0 K+V
32K 0.56 GiB 1.06 GiB
64K 1.13 GiB 2.13 GiB
128K 2.25 GiB 4.25 GiB
256K 4.50 GiB 8.50 GiB
1M 18.00 GiB 34.00 GiB
20M 343.32 GiB 648.50 GiB

この表はtarget modelのFull Attention部分だけの下限見積りです。実際のprocessとsnapshotには Gated DeltaNetのrecurrent state、context checkpoint、MTP draft state、token列、allocator、 alignment、file headerが加わります。Residentの独自runtimeはKにq8_0、Vに turbo4を使うため、この表をそのまま適用しません。

local-nodeは128 GiBのうち16 GiBをhost用に予約し、Residentと256K Qwen workerをそれぞれ 約40 GiBとしてadmissionします。提案例の「Warm 1M + Compressed 1M」をRAMへ加えると、 q4_0のattention KVだけで約36 GiBとなり、Residentとworkerの同時運用余力をほぼ使い切ります。 初期RAM cacheはtoken数ではなく4から8 GiB程度のbyte quotaで開始し、実測から増減します。

NVMeには空き容量がありますが、256K slot一つでも数GiBを読み書きします。保存と復元は slotがidleになるまで待ち、runtime処理内で同期I/Oを行うため、容量が足りることはrealtime latencyが 許容できることを意味しません。NVMe tierはbyte quota、I/O rate、同時操作数、save／restore時間の SLOを別に持ちます。

llama.cppのsequence-state fileはmagicとformat versionを検査しますが、現在のfile自体はmodel artifact identityを十分に保持しません。形状が似た別modelや異なるruntime条件へ誤復元すると、 明示的なerrorではなく誤った推論状態になる可能性があります。そのためLARMは上記compatibility keyの 完全一致時だけrestoreし、一項目でも異なればsourceから再prefillします。

sourceはLARM内に複製しても、SAAA内のimmutable rangeを参照しても構いません。ただし、 materializationが失効したときに再生成できる参照とdigestを必須にします。sourceが消えたKVは 「再生成可能なcache」ではないため、pinせず削除対象とします。

動的に必要なContextへAttentionする設計

動的化は可能です。ただし、storage上のAttention tensorをそのまま任意挿入する機能ではなく、 requestごとに必要なsource blockを選び、正しいmodel stateを復元または再計算して Active View epochを作る機能として定義します。modelが実際にAttentionできるのは、 そのepochへmaterializeされた最大context limit内のtokenだけです。

更新単位

現行Chat Completions requestのdecode途中に、外部KVを安全に差し込むことはしません。更新は user turn、tool call、明示checkpoint、watermark到達のいずれかでrequestを区切って行います。 例えばmodelがtool callで追加contextを要求した場合、SAAAがsourceを取得し、tool resultをsuffixとして 次requestへ追加します。既存session prefixを保持したまま追加部分だけprefillできるため、 arbitrary KV fusionを使わずに動的な参照が可能です。

Active Viewを大きく入れ替える場合は、core rules、working digest、選択source、recent turnsを canonical orderで再構成し、新しいepochを作ります。この経路はcache missならprefillが必要ですが、 通常prefillと意味的に同一であり、必ず利用できるfallbackです。

SAAAはsemantic relevanceとrequired指定を渡します。LARMはその値を書き換えず、token budget、 cache availability、restore／prefill cost、priority、deadlineから、どの候補を今回のActive Viewへ materializeできるかを決めます。required contextが収まらない場合は暗黙に落とさず、 context_budget_exceededとして失敗します。

20Mとの関係

20M tokensは全epochから参照できる候補集合です。一つのepochが使うのは最大256K、64K Agent runtimeなら最大64Kです。人気の高いsessionやcanonical bundleはKV化し、それ以外はsource textのまま 保持します。異なるtopicへ移るときは新しいepochへ切り替え、古いepochはRAM、NVMe、削除の順に demotionします。

この方式では「20Mのどこでも次のturnで選択できる」は実現できますが、 「20Mの任意部分をprefillなし、かつ同一decode途中に差し込める」は保証しません。

Active Viewのbudget

16K／32K／48K／128K／32Kという固定配分は初期例に留めます。128KのManaged Contextを常に 埋めると、短いtaskにもprefill costと無関係な情報を追加し、品質とlatencyの両方を悪化させます。 保証するのはManaged Contextの最低量ではなく、出力reserveとcore contextの上限です。 

available_input_tokens =
  runtime_context_limit
  - enforced_output_reserve
  - template_overhead

retrieval_budget =
  available_input_tokens
  - core_system_tokens
  - current_task_tokens
  - required_recent_tokens
  • 256K一般routeと64K Agent routeで別policyを持つ。
  • tokenizerとchat templateが確定した後のtoken数で判定する。
  • Watermarkは絶対値でなくcontext limit比とoutput reserveから導く。
  • retrieval候補はpriorityだけでなく、総token数とprefill／restore costを含めて選ぶ。
  • hard limit超過時に暗黙切捨てせず、選外IDと理由を観測可能にする。

Admissionとeviction

最初のpolicyは意味scoreをLARMで再計算せず、明示priority、pin、TTL、recency、hit count、bytes、 restore costだけを使用します。semantic relevanceはSAAAがrequestごとに提示する選択情報であり、 保存中blobの寿命をLARMが独自解釈する根拠にはしません。

  1. principal／scope単位のRAM byte quotaとNVMe byte quotaを先に適用する。
  2. active requestまたはrestore中のmaterializationはevictしない。
  3. pinはquota免除ではなく、pin用に予約された上限内だけ許可する。
  4. 期限切れ、compatibility不一致、source不在を先に削除する。
  5. 残りをcost-aware LRUでevictし、判断理由をmetricとbounded eventに残す。
  6. 20M token上限とbyte上限は別々に強制し、先に達した方を適用する。

安全性と失敗動作

  • KVは人間可読でなくてもprompt由来の機密dataです。sourceと同じtenant、retention、access classificationを適用し、repositoryやlogへ置きません。
  • NVMe snapshotはmode 0700のrepository外directoryへ置きます。ローカル実験cacheでは暗号化を必須とせず、 64 MiB chunk CRC32C、atomic commit、strict manifestで偶発破損を検知します。機密scopeはsnapshotを 無効化するか、host側disk暗号化を別途使用します。file deleteは物理消去を保証しません。
  • cache keyをprincipal／scope saltで分離し、別consumerのprefix hitをlatencyから推測できないようにします。
  • runtimeの/slotsをLANへ公開せず、LARM backendだけがloopbackで操作します。
  • save／restore中のcrashは一時fileを無効状態として扱い、atomic rename後だけregistryへcommitします。
  • checksum、compatibility、容量、sourceを検証できないsnapshotはfail closedで破棄し、cold prefillへ戻します。
  • cache hitは推論結果の正しさを変えないことを受入条件とし、latency改善だけで採用しません。

推奨導入順

  1. Phase 0: runtime spike。専用workerとrepository外の一時cache rootで、8K、32K、 64K、128K、256Kのslot save／restoreを測定します。snapshot bytes、RAM peak、NVMe write／read、 pause時間、cold prefill比、再起動後restore、決定的出力一致を記録します。
  2. Phase 1: exact-prefix MVP。packages/coreへdescriptor、compatibility、 byte admission、状態機械を追加し、packages/backendsへllama.cpp slot adapterを追加します。 対象はManaged Context bundleとsession snapshotだけです。
  3. Phase 2: token budgetと運用。runtime別Active View budget、cache hit／miss、 saved bytes、restore latency、eviction、invalid materializationを公開し、bounded idle GCを実装します。
  4. Phase 3: 外部KV store比較。対象hardwareとQwen Hybrid modelでvLLM／LMCache等が production要件を満たす場合だけ、新しいruntime adapterとしてCPU／NVMe block offloadを比較します。 LARM自身にtensor compressionを実装しません。
  5. Phase 4: 高度な再利用。non-prefix block reuseは独立researchとし、full prefillとの 品質同等性、model更新耐性、位置変更、Hybrid recurrent stateを検証できるまでproduction contractへ 入れません。

Phase 1受入条件

  1. 同じcanonical token prefixだけがcache hitし、一token差、順序差、scope差はhitしない。
  2. model artifact、tokenizer、template、engine、KV dtype、context parameterの差をrestore前に拒否する。
  3. restore後のdeterministic completionがcold prefillとtoken単位で一致する。
  4. 128Kと256Kでrestore latencyがcold prefillより明確に短く、Resident realtime SLOを悪化させない。
  5. cacheを全削除してもsourceから復旧し、会話・KnowledgeのSource of Truthを失わない。
  6. RAM、NVMe、principal、pinの全quotaを超えず、crash後にorphanを回収する。
  7. worker swap、llama.cpp更新、model release変更で古いsnapshotを自動invalid化する。
  8. cache操作credentialから通常のmodel、別principal、raw filesystem pathへ権限昇格できない。
  9. cache maintenanceとprewarmは高優先request到着時に新しい長時間処理を開始しない。
  10. bun run checkとliveのAgent Connection canaryが既存contractを回帰しない。

初期scopeに含めないもの

  • 独立KV blockの任意順序mount

最終結論

この案は、「20Mの任意アクセス可能なKV Working Context」ではなく、 「最大20M tokenのsource-addressableな候補集合と、その一部に対する有限のprefix／session materialization cache」として定義し直せばLARMへ適用できます。

最初に実装価値があるのは、Managed Contextのcanonical prompt化、runtime別token budget、 exact-prefix hit、session snapshot、compatibility key、byte quota、eviction、CRC32C破損検知、実測です。arbitrary KV mount、progressive compression、semantic routingはそれらの実測後も別のresearch課題として 扱います。この境界なら、LARMのneutral control planeという役割とResident Qwen 3.8 27Bを守りながら、 再prefill削減という提案の実益を段階的に得られます。

対象LLMがhostされている間だけ機能を有効にする詳細は高度推論LLM連動型Virtual Context Activation仕様で定義します。CRC32C snapshotの実装後評価はQwen 3.8 quality CRC32C snapshot M3b Go証跡に記録し、認定範囲をsession continuationへ限定してtechnical Goとしました。
