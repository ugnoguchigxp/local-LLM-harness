視覚解析APIの応答契約・物体検出LAN入口の修正

2026-10-31 JST。詳細分析の説明専用Providerと通常物体検出のhosted serviceを別経路として調査・修正する。API側を対象とし、Eumenes稼働環境の操作・表示確認は対象外。

原因の確定

追跡ID req_c0a39087-5491-47ef-9207-2c5f84ccdf56 と req_284f4ff6-31d8-4ebd-b718-8d4b77e5f645 は、daemon journalでそれぞれ2026-10-31 00:13:45、00:14:46 JSTにruntime lfm3-vl-perceptionへ解決しHTTP 200で終了している。実稼働releaseは95961280a2b4905106755b0e23b0dc93bb51acee。配備中snapshotと同releaseのソースはいずれもdecoderDtypeとvisualTokensを出力しない。

2026-10-29の説明用ランタイム採用時、larm.visual-perception.v1のexecutionにCPU用union分岐を追加し、2項目を欠く応答をLARM内で正常と認めた。Eumenesの必須契約とは異なっていた。配備忘れではなく、公開契約の非互換な拡張と実行metadata実装漏れの組み合わせである。元のdecoderDtypeはマスク生成用pixel decoderの精度であり、言語モデルの量子化形式やlogitsの精度ではない。説明用ランタイムにpixel decoderは存在しない。

通常検出のobject-recognition-hostはloopback gateway 127.0.0.1:18796で稼働していた。LAN addressの同portにはlistenerが存在せず、OCRにだけLAN ingressがあった。保存済みEumenes設定をこちらでは取得していないため、その接続先との一致は未確認。

正式なv1応答スキーマ改訂：2026-10-31

protocolとcontractVersionはlarm.visual-perception.v1、endpointはPOST /v1/vision/perceiveを維持する。CPU分岐の欠落を廃止し、execution.decoderDtypeとexecution.visualTokensを両方必須とする。非搭載decoderにnullを許すのはCPU説明専用分岐だけである。この改訂はdecoderDtypeをstringのみとする利用側に明示的な移行を要する。従来の利用側でそのまま受理できるとは主張しない。公開OpenAPIのVisualPerceptionResponseを機械可読な正本とする。

executionの分岐ごとの意味
項目 Transformers・マスク対応 llama.cpp・CPU説明専用
device / backend / dtype cuda:0 / transformers / bfloat16 cpu / llama.cpp / qad-q4_0
decoderDtype float32。pixel decoderが存在する分岐。 nullを必須とする。pixel decoder非搭載であり、精度不明や計測失敗を意味しない。省略は契約違反。
visualTokens 画像processorのgridとspatial mergeによる実測値。 同一の正規化PNG・query・chat template・オプションをpinned engineの/tokenizeへ渡し、MTMDが返すimageTokensを使用する。正整数必須。省略、null、0、寸法からの推定は禁止。
inputTokens / outputTokens outputTokens必須。 推論usageのprompt_tokens / completion_tokens。tokenizeのpromptTokensとprompt_tokensが一致し、textTokens + imageTokens = promptTokensであることも検証する。

画像tokens取得の失敗、欠落、不整合はHTTP 502 execution_metadata_invalidとし、成功応答に仮の値を入れない。CPU分岐はdescribeだけで、detectionsとmasksは空配列、countは禁止。visualTokensはinputTokens未満とする。マスク対応分岐にnullを許さない。 

{"device":"cpu","backend":"llama.cpp","dtype":"qad-q4_0","decoderDtype":null,"visualTokens":64,"outputTokens":4,"inputTokens":120}

上記数値は構造を示す例であり、実測結果ではない。APIは毎回engineの値を使用する。

通常検出の公開入口

既存OCR ingressを登録service IDを検証する共通実装へ拡張する。installerの--service-id object-recognition-hostで専用unit・config・receiptを作成する。登録済みgatewayからupstreamを解決し、既存OCR設定は変更しない。LANのprivate addressだけで待受し、同LANのsource CIDRだけをfirewallで許可する。

GET /hosting/status、POST /api/analyze、GET /api/jobs/{id}、POST /api/jobs/{id}/cancelを転送する。Authorization以外のowner assertion、cookie、転送headerを渡さず、既存gatewayの共通LARM API token認証を使用する。status参照ではworkerを起動しない。gateway再起動・boot後の復帰はRequires、PartOf、WantedByで維持する。
