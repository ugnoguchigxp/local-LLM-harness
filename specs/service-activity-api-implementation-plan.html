固定判断: activity APIは「LARMを通って現在実行中の利用者workload数」だけを 返します。Providerを確保できるかは判定しません。ContextStillはidle responseを得た後、既存の Agent Connectionを作成し、その時点のresource admissionに従います。

着手時点に確認した実装

  • Profile discovery、Connection create、status poll、semantic readiness、claim、renew、releaseは 実装済みである。
  • Agent Connection createはProfileを既存Allocationへ変換し、COLDなPreferred RuntimeをBackendで 起動する。
  • claimはOpenAI互換のbaseURL、public model、Provider限定の短期Bearer tokenを返す。
  • llm-agent-worker Routeとqwen-worker-agent Runtimeは登録済みで、Resident qwen-generalと同時に動作できる。
  • HTTP LLM・ASR・TTS requestは共通RequestTrackerとExecutionGateを通る。

着手時点ではactivity公開APIとcontextstill-background Profileがありませんでした。着手前のlive GET /v2/agent-profilesはcoding-defaultとdeprecated compatibility aliasだけを 返します。

source実装記録

  • packages/core/src/service-activity.tsへstrict discriminated schema、型、state導出、snapshot生成を追加し、state、count、retry値の矛盾を schema境界で拒否するようにした。
  • apps/daemon/src/app.tsへ認証、no-store、入力拒否を含む GET /v1/activityを追加した。
  • HTTP利用者requestを既存RequestTrackerで集約した。

目的と責務境界

実装すること

  • LARM経由の利用者推論workloadが一件以上あるかを、service全体で集約する。
  • idle、active、drainingを小さなversioned responseとして返す。
  • ContextStillがjob境界でactivityを読み、idleの場合だけProvider取得へ進む。
  • ContextStill用の明示Profileから既存qwen-worker-agentを動的起動し、claimされたProvider 構成を返す。
  • 従来ProviderとSAAAのcoding-default経路を変更しない。

実装しないこと

  • activity GETによるRuntime選択、memory admission、artifact確認、resource予約。
  • Profileごとのavailability判定やcurrentConnectionId query。
  • SAAA process、UI focus、session、heartbeat、callbackの観測。
  • 実行中ContextStill jobのpreemption。
  • 利用開始時のYAML書換えやcatalog hot reload。
  • Provider portへの直接requestをsupported activityとして追跡すること。

activityの定義

activityはservice processやProvider daemonが起動しているかではなく、LARMの公開data planeを通る 利用者workloadが処理中かで決めます。Resident Runtimeが常時HOTでも、requestがなければidleです。

activityへ含める処理と除外する処理
処理 activity 計数期間
HTTP LLM・ASR・TTS 含める Gateway受理からresponse body完了、cancel、errorまで
Agent Connection・Allocationだけが存在 除外 Providerを予約していても推論がなければidle
semantic・health・observer probe 除外 内部正常性確認は利用者workloadではない
activity、profile、control API 除外 制御request自体でactiveにしない

production desired stateでは個別Provider portをloopbackに限定し、通常clientはLARM Gatewayを 使用します。Gatewayを迂回する直接requestはこのcontractの保証外です。移行中hostで直接listenerが 残る場合は、activity APIを排他保証として使用しません。

Service Activity API contract

Request

GET /v1/activity
Accept: application/json

query parameterとrequest bodyは受け付けません。未知queryはHTTP 400 invalid_requestとします。Responseには常にCache-Control: no-storeを付けます。

Idle response

{
  "contractVersion": "larm-service-activity.v1",
  "state": "idle",
  "activeWorkloads": 0,
  "observedAt": "2026-09-05T17:45:00.000Z",
  "validForMs": 1000,
  "retryAfterMs": 0,
  "reservationGuaranteed": false,
  "bootEpoch": "epoch-...",
  "configRevision": "..."
}

Active response

{
  "contractVersion": "larm-service-activity.v1",
  "state": "active",
  "activeWorkloads": 2,
  "observedAt": "2026-09-05T17:45:01.000Z",
  "validForMs": 1000,
  "retryAfterMs": 1000,
  "reservationGuaranteed": false,
  "bootEpoch": "epoch-...",
  "configRevision": "..."
}

State semantics

Activity state
state 条件 ContextStill動作
idle activeWorkloads === 0かつdrain中ではない Connection作成または次jobへ進める
active activeWorkloads > 0 retryAfterMs以降に再確認する
draining daemon shutdown drain中 新規処理を開始せず長いbackoffへ移る

正常なdomain stateはすべてHTTP 200です。schema生成や内部counter取得に失敗した場合だけHTTP 500、 activity機能が構成されていない場合はHTTP 503とします。ContextStillは200以外をfail closedでactive相当に扱います。active、draining、503ではRetry-After: 1を返します。

activeWorkloadsはHTTP利用者request数です。client数、Provider別内訳、model、Runtime、prompt、Connection IDは返しません。

Snapshotと既存admissionの関係

activity responseは取得時点のsnapshotであり、利用権や予約ではありません。idle取得後に別clientが requestを開始するraceは正常です。reservationGuaranteed: falseを恒久contractとします。

  1. ContextStillがjobを持つ間だけGET /v1/activityを呼ぶ。
  2. state: idleならAgent Connectionを作成または既存Connectionを再利用する。
  3. Connection createは既存admissionでmemory、telemetry、swap、capacity、transitionを再判定する。
  4. admission拒否はactivity stateと矛盾せず、ContextStillは待機へ戻る。
  5. job完了後、次jobをdequeueする前にactivityを再確認する。

ContextStill実行中に他workloadが開始した場合、現在のjobは完了させます。次のjobは開始せず、 ContextStillのConnectionを解放してactivityがidleへ戻るまで待ちます。長時間の競合を避けるため、 ContextStill requestには既存のbounded timeoutと生成上限を必須とします。

LARM実装構成

Core contract

  • packages/core/src/service-activity.tsを追加し、response schema、state enum、型、純粋な state導出関数を置く。
  • packages/core/src/index.tsからschemaと型をexportする。
  • packages/core/src/api-contract.tsへoperation ID getServiceActivityとOpenAPI schemaを追加する。
  • fieldはstrictにし、未知field、負数、非整数count、不正日時を拒否する。

Daemon activity source

  • 既存RequestTracker.count()をHTTP利用者workload数として再利用する。semantic probeは proxyGatewayを通らないため、このcountへ入りません。
  • response完了、cancel、Provider failure、shutdownの全経路でcountが0へ戻ることをtestする。

HTTP routeと認証

  • apps/daemon/src/app.tsへGET /v1/activityを追加する。
  • LARM_ALLOW_ANONYMOUS_AGENT_CONNECTIONS=trueの場合だけ、Agent Profileと同じLAN境界で anonymous GETを許可する。それ以外は通常Bearerを必須とする。
  • 活動の内訳、Runtime名、client名、Connection IDをlogへ記録しない。
  • eventのlabelはboundedなstateだけ、countはgaugeまたはevent value、durationはstate別histogramへ記録する。同一stateのpollではeventを反復記録しない。

ContextStill用Provider構成

Profileはdaemon起動時にcatalogへ読み込みます。ContextStill利用開始時にYAMLを変更せず、Connection createがRuntime構成を動的に変えます。既存defaultAgentProfile: coding-defaultは維持し、 次の明示Profileだけを追加します。 

  contextstill-background:
    description: ContextStill background Qwen 3.8 27B provider
    providers:
      - name: llm
        capability: llm.coding
        route: llm-agent-worker
        publicModel: qwen-agent-worker
        readiness: llm-inference
  • 非default Profileなので既存schemaによりexplicit-onlyとなる。
  • claimのbaseUrlからJSONまたはOpenAI互換SSEを要求する。
  • allowFallback: falseによりResident qwen-generalへ迂回しない。
  • deploymentPolicy: existing-onlyによりContextStillからartifact配備を開始しない。
  • workerはConnection中だけAllocationされ、release後は既存idle policyでCOLDへ戻る。

ContextStill実装手順

  1. queueが空の間はactivity APIをpollしない。
  2. queue非空時にGET /v1/activityを最大1 Hz、jitter付きで呼び、strict response validationを行う。
  3. activeまたはdraining、HTTP error、invalid responseでは待機する。
  4. idleかつactiveWorkloads === 0なら、未確立の場合だけ次のConnectionを作る。 
POST /v1/agent-connections
Idempotency-Key: contextstill-<run-id>-<attempt-id>
Content-Type: application/json

{
  "agentProfile": "contextstill-background",
  "explicitAgentProfile": true,
  "audience": "saaa-desktop",
  "client": "contextstill",
  "ttlSeconds": 300,
  "allowFallback": false,
  "deploymentPolicy": "existing-only"
}
  1. 201または202を受理し、readyまでbounded pollしてclaimする。
  2. claimのbaseURL、model、短期tokenをOpenAI互換clientへそのまま渡す。
  3. 一件をconcurrency 1で処理し、JSONまたはSSEの要求形式にかかわらずresponse bodyを最後まで閉じる。
  4. 次jobの前にactivityを再確認する。
  5. activeならConnectionをDELETEして待機する。idleならConnectionをrenewしながら次jobへ進める。
  6. queue空、error、cancel、shutdownでも独立したcleanup signalでConnectionをDELETEする。

TypeScript実装では既存@larm/clientへgetServiceActivity()を追加し、Agent Connection lifecycleは既存methodを再利用します。ContextStillが別言語の場合もOpenAPI生成schemaを 正本とし、独自fieldや固定Provider URLを持ちません。

互換性とsecurity

  • 既存endpoint、Profile、claim、credential、Gateway responseを変更しない。
  • 新Profile追加によりcatalog revisionとProfile配列は変わるが、既存entryのshapeと意味は維持する。
  • 従来Provider adapterは設定と挙動を維持し、新adapterを選んだ場合だけactivity APIを使用する。
  • activity responseはcredential、model、Runtime、他clientのidentityを含まない。
  • responseとerrorにCache-Control: no-storeを付ける。
  • 短期Provider tokenをactivity request、query、logへ含めない。
  • active countを利用者数やtask内容と解釈しない。

必須test

Activity contract

  • 初期値はidle、countは0、responseはstrictでno-store。
  • 一つまたは複数のHTTP Gateway request中はcountが増え、全response完了後に0へ戻る。
  • queued HTTP requestもGateway requestの生存期間としてactiveに含まれる。
  • JSON／SSE request開始で増え、complete、cancel、failure、shutdownで必ず減る。
  • semantic probe、health、activity GETはcountを増やさない。
  • 複数HTTP requestの同時実行は合計値を返す。
  • drain中はcountに関係なくstateがdrainingになる。
  • unknown query、body付きGET、無効credentialを拒否する。

ProviderとContextStill

  • Profile省略時は引き続きcoding-defaultとなる。
  • ContextStill Profileは明示指定なしで409、明示指定ありで受理される。
  • Bindingはllm-agent-worker → qwen-worker-agent、fallback falseとなる。
  • claim値だけでJSONとSSEの両completionを要求どおり完了できる。
  • active response中はConnection createとjob開始を呼ばない。
  • 現在jobの完了後にactiveならConnectionを解放する。
  • 従来Provider fixtureとrequest snapshotが変化しない。

local-node受入条件

  1. workloadなしでactivityがidle、0を返す。
  2. HTTP LLM、ASR、TTSを個別に実行し、それぞれの実行中だけactiveとなる。
  3. SAAAのHTTP SSE request中だけactiveとなる。
  4. 複数data plane同時実行でactiveWorkloadsが期待値と一致する。
  5. idleを読んだContextStillがConnectionを作り、workerをCOLDからHOTへ起動する。
  6. Resident QwenをHOTのまま維持し、ContextStill workerとの二基構成で一件を完了する。
  7. 別workload開始後、ContextStillは現在job完了後に次jobを開始せずConnectionを解放する。
  8. release後にworkerが既定idle TTL内でCOLDへ戻る。
  9. 試験中のfallback、OOM、Provider crash、credential leakが0である。
  10. SAAA HTTP SSE、ASR Service Harness、Agent Connection smokeがすべて成功する。

配備とrollback

  1. LARM側M1からM4を実装し、ContextStill未接続のままrepository testを通す。
  2. daemonをreview済み手順で更新し、activity APIと既存Provider smokeを確認する。
  3. ContextStillを明示opt-inし、短いqueueでcanaryする。
  4. 二基構成時のsystem・accelerator memory headroomと既存workload latencyを採取する。
  5. 十分な反復後にContextStillの継続queueを有効化する。

rollbackはContextStillのProvider kindを従来adapterへ戻し、activity pollを無効化します。LARM側の 新endpointと追加Profileは既存clientから参照されないため残置可能です。catalog rollbackが必要な場合はProfileを除去した旧config revisionへdaemonを戻します。Resident RuntimeとSAAA defaultは全段階で変更しません。

完了定義

LARMが全supported data planeの利用者workloadを漏れなく集計し、ContextStillがidle responseを読んだjob境界だけで既存動的Providerを要求できることを、自動testとlocal-node canaryの両方で確認した時点を完了とします。activity GETだけの成功、Profile公開だけの成功、worker単体推論だけの成功では完了にしません。
