Gemma4マルチセッションへのKittenTTS英語常駐Provider追加

2026-10-12 JSTの利用者指示により、KittenTTS Nano FP32をGemma4の英語TTSとして追加する。 実装・単体HTTP実測済み。本番反映は新規systemd unitの管理者登録と署名付きreleaseの適用後に 検証する。以下は本番適用前の記録であり、常駐追加完了とは区別する。

稼働LARMのv3 catalogはこのGemma構成を返す。反映前releaseは 8a8a2596df40b5fb2fa5b50cc6a853166f617a8c、config revisionは 3d1cecc714cb877ec1e49e4701a0db8d4a90aef097f3e465c18b3649b81095a1。 8080で動いていたOrnithをGemmaの構成不良とは解釈しない。別workloadの実行状態である。

このPCにあるEumenesの参照コードは同じGemma selectorとメインcontext契約を明示する。 音声用途はプロファイル全体を要求し、追加Providerがあっても既存の必須Providerを名前で探す。 ただし通常speakはttsを選ぶため、本追加だけで英語へ自動切替しない。 利用中のEumenes端末の保存設定・声選択・現在Connection IDは取得していない。 コード上の対応と、利用者の端末で現在どの声を選択しているかを区別する。

SAAAのworktreeには既存の未保存変更があるためpullも実装参照も行っていない。 LARMの稼働catalog、LARM設定、Eumenesの参照コードで対象を照合した。

追加構成

  • Gemmaメインは6 Provider。日本語ttsと英語tts-englishを別名・別capabilityで同時に公開する。
  • 英語capabilityはspeech.tts.english、protocolはopenai.audio-speech.v1、公開modelはkitten-tts-nano-0.8-fp32。
  • 英語runtimeはCPU 4スレッド、managed lifecycle、minInstances: 1、メモリ見積1.5 GB。
  • HTTPは127.0.0.1:8088のみ。1 workerでEspeakと推論を直列化。LARMの同時要求1、待ち行列2、待ち期限5秒。
  • Gemma補助64K、ContextStill、既定SAAAのProvider集合は変更しない。Gemmaの画像・音楽selectorは共通メインprofileを使うため追加を共有する。
  • 専用公開model用のtts-english profileも用意し、control認証でモデル一覧・声一覧を取得できる。

ONNX、voices.npz、config.jsonはモデルmanifestに別の固定artifactとして登録し、runtime releaseで 3ファイルをまとめる。revision、サイズ、SHA-256を固定し、Provider起動時にも照合する。 推論エンジンとPython環境は/srv/ai/apps/kittentts-runtime、重みは /srv/ai/models/kittentts/fp32。ソースrepositoryに重み・生成音声を含めない。 追加実行環境の依存はrequirements.lockで固定する。

HTTP契約と声

GET /health、GET /v1/models、GET /v1/audio/voices、 POST /v1/audio/speechを実装。modelは固定、声は既定8種、default_voiceはRosie。 Rosieはfeminine、Hugoはmasculine、languageはen。speedは0.5〜2.0。 出力は24 kHz monoのWAVまたはsigned little-endian PCM16。

数字前処理を常に有効にし、音声ピークが0.98を超えた場合のみ全体gainを下げる。 空文字・日本語混在・未対応声・未知model・未対応format・NaN・4096文字超を拒否する。 request bodyは64 KiB上限で、Content-Lengthなしの分割送信でも上限を適用する。 同時backend要求は429とRetry-Afterを返す。読み上げ本文をアクセスログに記録しない。 pitch／intonation／style指定や音声chunk streamingは実装していない。

公式0.8.1の句読点・略語の文分割は維持する。文字fragmentからの逐次合成や進行中の ONNX呼び出しの中断は追加していない。英語専用を明示することで日本語Providerと区別する。

検証と反映手順

HTTP adapterの8試験が成功。WAV／PCM、声一覧、Rosie／Hugo切替、数字前処理、容量制限、 同時要求拒否と復帰、無効音声拒否、artifact破損拒否を確認した。 実モデルを一時loopback port 18088で起動し、両声ともHTTP 200・24 kHz WAVを生成した。 短文の単発HTTP実測はRosie約0.26秒、Hugo約0.15秒。前処理ありの単発値で、先行5反復の ベンチマーク中央値とは測定条件が異なる。

設定・契約試験はGemmaの追加、既存日本語経路の維持、他profileへの非追加、常駐ポリシー、 公開モデル・Provider数を確認する。全体check、専用Python試験、文書checkを実行する。 本番smokeはGemmaのproviders: ["tts-english"]だけを要求し、LLMを切り替えずに discovery → claim → 声一覧 → Rosie／Hugo生成 → release → credential失効を検証する。

  1. 専用環境と固定重みを準備し、実モデルのHTTP試験を行う。
  2. 既存の作業中変更を混ぜずに独立sourceを作成し、全体check付きの署名release候補を準備する。
  3. 管理者権限でinstall-kittentts-service.shを実行し、新規unitと限定polkit規則を登録する。
  4. 既存の署名release watcherへ候補を提出し、LARM再起動後のcatalog・常駐実体・HTTP smokeを確認する。

新規unit登録は/etc/systemd/systemと/etc/polkit-1/rules.dへの書込を伴う。 このセッションでは非対話sudoの認証が通らず、管理者登録を自動実行できていない。 登録前に本番releaseを提出するとwarm instanceを開始できないため、候補の準備と稼働反映を分ける。 ユーザーの追加指示による反映許可は取得済みであり、追加の採用判断を求めるものではない。
