仮説の評価

a〜dの当否
仮説 判断 根拠
a 無通信60秒の自動解放 今回の原因ではない。 対象はreadyに到達せずidle timerの対象外。08:39:04の明示DELETEで解放。実際の選択profileのidleReleaseは300秒。画像workloadはConnectionではなくMediaVariantManagerが保持し、Control Bearerの要求を特定ConnectionのactiveRequestsへ紐付けない。
b 起動前の受付 接続ready待ちの不足ではない。画像の起動失敗伝播に不具合。 servicesは独立Control API。Connection pendingでも呼べる。画像要求自身がworkerを起動し健康確認後に転送する。今回は健康確認中にworker終了を検知しなかった。
c メモリ・配置 追加llm接続のメモリ待ちは事実。画像停止の直接原因としてのOOMは確認できない。 要求先Gemmaは見積48GB、常駐Ornithは56GB、同じconversation-llm-slot。画像経路は別の実メモリ事前判定を通過して起動した。kernelに該当時間のOOM記録なし。画像nativeは実生成開始前に終了している。
d 10-30最後の成功後の変更 画像API・起動処理のコード変更による回帰は認められない。 成功時release 95961280a2b4と失敗時1bb672dd0530のimage-generations.ts、image-generation-provider.ts、media-variants.ts、runtime-variant.sh、Turbo PythonはSHA-256一致。長い待ちの欠陥は成功時も存在し、起動失敗時に露呈した。

画像native終了の引き金として、直前のStable AudioのTIME_WAITとSO_REUSEADDR / SO_REUSEPORTの不一致が有力。Linuxの実ソケットを使い、推論なしで「音楽相当の終了後にnative相当のbindが失敗する」条件を再現した。ただし当時のerrno・socket一覧・native終了コードは保存されておらず、歴史的な直接原因の確定とは区別する。旧nativeはlisten失敗をログにせず、戻り値も検査せずexit 0へ進める。

画像・音楽サービスの契約

Eumenesが利用するAPIと項目
用途 契約
サービス発見 GET /v3/agent-profilesのトップレベルservices[]からcapability media.image.generate / media.music.generateを選び、url・model・protocolを使う。選択Profileを取得したい場合はprofiles[].services[]も利用できる。Agent Connectionの作成は不要。
ready・資格 services[]にConnection相当のstatus/readinessはない。Connectionのstatus / phaseとproviders[].readiness / claimableは選んだProviderの状態。画像・音楽workerのreadyではない。サービスURLへControl Bearerで送る。Provider credentialやGET connectionのready待ちは不要。
生成中の維持 画像の同期POSTがmedia占有とworkloadを保持する。heartbeat・connection renewは不要。音楽はPOST /v1/music/generationsで202/jobを受け、GET /v1/music/generations/{jobId}のstatusがcompletedになるまで追跡する。音楽job自身が占有を保持する。
Provider推論との違い LLM等のConnection Providerを使う場合はstatus ready、claim後のProvider Bearerを使う。推論中保護はこの経路のactiveRequestsで管理される。renewはexpiresAtを更新するが無通信idle timerのheartbeatとは異なる。画像用に不要なllm接続を作っても画像の保護にはならない。
画像の応答 成功200/status succeeded/artifactまたはartifacts[0]。競合409/media_variant_busy。起動・上流失敗503/image_generation_failed。停止失敗503/worker_stop_failed。生成期限900秒の超過は改修後504/image_generation_timeout。既定の起動健康確認60秒、制御lock待ち10秒、停止は各75秒の上限が別途加わる。60秒が要求全体の上限という意味ではない。
音楽の失敗 同期画像のHTTP statusと同一視しない。POSTの受付拒否と、202後のjob失敗を区別する。GETのjob.status failed/cancelledとerrorを処理する。
