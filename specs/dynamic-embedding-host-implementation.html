LARM 動的Embeddingホスト実装仕様

本仕様は、EmbeddingをLARMの動的workloadとして登録し、Agent Connectionの短期lease、 semantic readiness、claim、renew、releaseへ統合する実装契約を定める。Consumerは固定portや cloud fallbackを保持せず、LARMが返すendpointと短期credentialだけを使用する。

ライフサイクル

claimはGatewayのbase URLとEmbedding endpoint、公開model、完全なsemantic space、 ready、active request数、queue depth、最大queue、retry hint、lease期限を返す。 Consumerは実行開始前にreadyと期限を確認し、処理中は必要に応じてrenewする。release、期限切れ、 daemon boot epoch変更、binding変更のいずれでもtokenを拒否する。

実行契約

requestは1件以上64件以下の非空texts、明示的な type（queryまたはpassage）、 normalize: true、明示的なpriorityだけを受理する。未知field、type省略、 normalize無効、body上限超過はupstreamへ送らず拒否する。

LARMは成功responseをbuffer上限内で読み、JSON media type、件数、入力種別、384次元、 全要素の有限性、各vectorのL2 normを検証してから返す。redirectはfollowしない。 response不一致時はfail closedとし、別model、別dimension、cloud、固定loopbackへのfallbackは行わない。

安全性と観測

  • provider tokenはboot epoch、Connection、Allocation、Provider、capability、Audience、generation、期限へ署名で束縛する。
  • token、署名鍵、完全claim、入力本文、vectorを通常logやLLM inference auditへ保存しない。
  • 非secret eventはrequest ID、Allocation、runtime、protocol、outcome、latencyを記録できる。
  • service activityはEmbedding gateway requestを他のHTTP workloadと同じactive countへ含める。
  • gateway execution gateが同時実行数、queue上限、queue timeout、release時cancelを適用する。
  • semantic readiness cacheは10秒以内とし、host offline、stale binding、invalid responseをreadyとして再利用しない。

配備とrollback

  1. deploy/local-node/scripts/prepare-embedding-runtime.shをoperatorとして実行し、固定source commitからrepository外へRust binaryをbuildする。
  2. LARM artifact APIで固定ONNX/QInt8 snapshotをstageし、6ファイルのsizeとSHA-256を検証する。
  3. multilingual-e5-small-current releaseをactivateする。
  4. unitとpolkit ruleをinstallする。larm-embedding.serviceはboot時disabledのままにする。
  5. LARM releaseを適用し、bun run smoke:embeddingでquery、passage、renew、旧token失効、release後失効を確認する。

rollbackはLARMの前releaseへ戻し、新規Connectionの受付を旧catalogへ戻す。active claimはreleaseまたは boot epoch変更で失効する。Embedding unitは停止・disableできるが、model snapshotの削除はrollbackに含めない。 modelやcredentialをrelease directoryへ置かないため、Gateway rollbackで破壊しない。
