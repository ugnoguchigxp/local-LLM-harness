動的Provider優先度・foreground preemption仕様

SAAA、NightWorker、ContextStillが同じLARMの同一Runtimeまたはswap groupで競合する場合の、 Allocation待機とRuntime実行待機の順序を定義します。SAAA相当のforeground要求は競合する 低優先Allocationをただちに停止してProviderを取得します。それ以外は解放境界で待機中の 最優先要求へ切り替えます。競合しないResident laneとworker laneは従来どおり並行利用できます。

優先度policy

local-nodeの初期優先度
Consumer Profile／公開model 優先度
SAAA SAAA／SAAA-w-Image／SAAA-w-music 4000
通常foreground coding-default 3000
NightWorker nightworker-background／qwen-nightworker 2000
ContextStill contextstill-background／qwen-agent-worker 1000

大きい整数を先に選び、同値は待機開始順のFIFOとします。値域は -1000000から1000000で、初期値の間隔を1000空けるため、 前後や中間へconsumerを追加しても既存値を振り直す必要はありません。

優先度の決定元

通常のOpenAI互換HTTP要求では、request headerやbodyから優先度を受け取りません。 daemonが検証済みAgent ProfileのschedulingPriorityを公開model bindingへ固定し、 Model Brokerの内部Allocationへ渡します。Agent Connectionも選択済みProfileの値を使います。 管理・高度用途の明示Allocation APIだけは、認証済みrequestのpriorityと capacityPolicyを受け取ります。

Allocation状態と切替

  1. 空きがあれば従来どおりpendingまたはreadyへ進みます。
  2. capacityPolicy: waitで同一Runtimeまたはswap groupが使用中なら、 AllocationをwaitingとしてTTL内だけ保持します。
  3. 優先度3000以上のforeground要求が到着した場合、同じRuntimeまたはswap groupを 使用する低優先Allocationをただちにreleasedへ遷移させます。低優先の待機要求も foregroundのadmissionを妨げません。
  4. 解放、失敗、期限切れの境界で待機列を再評価し、優先度降順、同値FIFOでadmissionを再実行します。
  5. 選ばれたRuntimeがswap groupの別memberなら、既存のbackend ensureによりidle memberを停止して 対象memberを起動し、readiness確認後にreadyへ進めます。
  6. foreground Allocationの解放後300秒間は、そのRuntimeを同じswap groupの別Providerへ 切り替えません。同じRuntimeの再利用と同等以上の優先度要求は待たせません。

資源不足、telemetry不明、mutation中など、使用中Allocationの解放だけでは解消しない拒否理由を 無条件に待機へ変換しません。待機Allocationもactive上限、TTL、daemon drainの対象です。

SAAAとContextStillのAgent Connectionは、選択されたRuntime IDやswap groupが異なる場合でも consumer間の排他policyを適用します。SAAA作成時はactiveなContextStill Connectionの低優先 Allocationをforeground_preemptedでreleaseしてcredentialを失効させた後、SAAAの Allocationとreadiness確認へ進みます。

ContextStillへ返す停止理由

foreground preemptionで停止した非streaming Gateway要求はHTTP 409と foreground_preemptedを返します。本文のmessageは request stopped because a higher-priority foreground task requires the providerです。 応答にはRetry-After: 1と X-LARM-Preemption-Reason: higher-priority-foreground-taskを付けます。 Allocation取得・resolveでも同じerrorを保持し、監査event allocation_preemptedのreasonはhigher_priority_foreground_taskです。

Runtime実行待機

同じRuntimeへ複数requestが到着した場合も、実行中requestの完了後に優先度降順、同値FIFOで 次のrequestを開始します。local-nodeのLLM Runtimeは最大16件、120秒まで待機できます。 queue満杯、timeout、cancel、drainは従来どおり失敗として返し、active requestはdrain開始だけでは 中断しません。

互換性と利用方法

  • 従来の明示Allocationは既定のcapacityPolicy: reject、priority: 0です。
  • 通常の既定はcoding-defaultとResident Qwenを維持します。SAAAがQwen 3.8を要求するときはqwen3.8を明示選択します。
  • NightWorkerはqwen-nightworker、ContextStillはqwen-agent-workerを使います。
  • 優先度はQoS順序であり認可境界ではありません。modelとtokenの認可は別に維持します。

受入条件

  1. ContextStill相当のactive AllocationへSAAA要求を追加すると、専用理由を残してただちに停止する。
  2. 優先度3000の通常foreground Allocationがactiveでも、優先度4000のSAAAが専用理由を残して preemptし、待機せず昇格する。
  3. production Profileを使うHTTP E2Eで、SAAA ready・推論・release、ContextStill ready・推論、 SAAA再要求によるContextStill credential失効・worker停止、SAAA ready・推論・releaseを一続きで確認する。
  4. SAAAは低優先のactiveおよびwaiting Allocationを追い越して昇格する。
  5. SAAA解放後300秒は別Providerへ切り替えず、経過後に優先度順で待機Allocationを昇格する。
  6. 同じRuntimeの実行待機でも同じ優先順となり、同値はFIFOになる。
  7. waiting中のcancel、TTL満了、daemon drainでRuntimeを新規起動しない。
  8. HTTP JSON、SSE、ASR、TTS、Connection credential失効の既存contract testが回帰しない。
  9. live daemonのreleaseCommitが新releaseと一致した後、SAAA実機canaryを再実行する。
